# 恢复不只是重载状态：人工暂停后的执行能力重建

谈到可恢复 Agent，最容易把问题理解成“把状态存下来，之后重新加载”。2026-08-13 的这份 Research Object 暴露了一个更窄、但更关键的故障边界：运行体可以找回历史状态，也可以保留待处理的人类确认，却仍然缺少当初由执行流程动态生成的能力。此时系统恢复了“记忆”，却没有恢复一个当前有效的行动资格。

现有证据只覆盖 Google ADK 的一条确认与转交路径，不能推出通用的暂停/恢复语义。但它足以把两个经常混在一起的概念拆开：**持久状态恢复**与**当前可执行能力恢复**。

## 恢复了历史，不等于恢复了行动能力

真正的问题不是“序列化的运行体能不能重新打开”，而是：重新打开以后，在任何动作重新获得执行权之前，系统是否已经根据**当前**拓扑和策略重建了仍然有效的能力。

人工介入流程特别容易暴露这个问题，因为暂停本身就给环境变化留下了时间。暂停开始时，某个 Agent 可能允许把控制权转交给另一个 Agent；等到人完成审批时，目标可能已经消失，路由关系可能已经改变，策略也可能不再允许同样的转交。持久记录可以证明“当时请求过什么”，却不能证明“现在仍然可以做什么”。

因此，一个清晰的恢复契约至少要分别回答两个问题：

- 哪些历史状态已经恢复？
- 哪些执行能力已经依据当前权威完成重建或重新核验？

如果把两者压缩成一个“恢复成功”，真正的安全边界就会被隐藏。

## 缺失的不是确认记录，而是执行能力

同日 Research Object 记录了所选实现中的三个有界事实。

第一，受影响的恢复路径之所以会失败，是因为 `transfer_to_agent` 由流程层动态注入，却没有出现在 `canonical_tools()` 的重建结果中。缺失的不是人的确认记录，而是恢复上下文本来预期拥有的一项可执行能力。

第二，修复会在确认处理之前重新计算当前可用的转交目标，并据此重建转交工具。如果当前没有有效目标，就不会重建这项能力。这个细节很重要：系统不是因为“暂停前曾经有过这个工具”就重放旧的可执行对象，而是根据当前声明重新推导能力。

第三，能力重建与人的批准/拒绝仍然是两个独立门禁。人的同意不能凭空创造能力，能力存在也不能代替人的同意。

这些事实支持一个有限结论：对这条路径而言，正确恢复不仅需要持久状态，也不仅需要记住“还有一个审批待处理”，还需要一个与当前环境一致的能力表面。

**证据与来源边界。** 以上事实依据同日 Research Object：`research/analysis/Q-20260813-01-resume-capability-reconstruction.md`。它记录的是对所选公开实现变更的事实提取与分析，属于公开一手来源基础上的证据，不等于对通用理论的独立验证。

## 把恢复拆成状态恢复与能力准入

更清晰的运行时模型可以写成：

**恢复持久状态 → 重建当前能力 → 比较或重新核验授权 → 处理人的决定 → 授予执行权。**

这不是所有系统都必须照抄的固定顺序。不可变能力可能适合安全序列化，不同 Runtime 也可能采用不同的能力身份模型。真正重要的是把不同责任拆开。

历史状态回答“发生过什么、还有什么待处理”；能力重建回答“这个执行上下文现在具备什么能力”；准入判断回答“现在是否允许使用这些能力”；人的确认回答“人在什么范围内同意了哪个待决动作”。

一旦拆开，原本被单一“恢复状态”掩盖的情形就会变得可见：

- **状态已恢复，能力不存在。** 可以查看历史，但不能安全执行待决动作。
- **能力已重建，人的决定未完成。** 技术上能做，但没有人的授权。
- **人已经批准，但当前能力发生变化。** 系统需要明确处理能力漂移，而不能把旧审批静默扩展成对新能力的授权。
- **状态、能力、授权与人的决定都已重新成立。** 此时恢复后的工作才真正获得执行权。

Research Center 对所选修复的解释是：它为这种职责分离提供了具体证据，但并不能证明所有 Agent 框架都必须采用同一种实现。

## 能力漂移需要明确的受治理不执行结果

最难处理的不是“重建成功”，而是“重建结果与暂停时不一致”。

例如，人在暂停时看到的是“转交给 Agent B”，恢复时 Agent B 已经不再是有效目标。稳健的 Runtime 不应静默替换成 Agent C，不应恢复已经过期的能力，也不应把旧确认扩展成更宽泛的许可。更合适的是产生一个明确、可审计的“不执行”结果，例如：能力不可用、授权已变化、确认已失效，或其他能够说明原因的受治理状态。

这也提示了一条审计边界。一个待决动作至少可以保留：

- 暂停时能力的身份或描述；
- 恢复时重新构建出的当前能力（如存在）；
- 用于重建的当前策略或权威依据；
- 人的决定及其作用范围；
- 最终的执行准入结果。

目的不是堆积元数据，而是确保系统能区分“用户点了同意”和“系统现在仍被允许、并且仍有能力执行同一件事”。

对数字员工而言，这个问题尤其现实。长时间任务意味着暂停不是异常，而是日常状态；人类审批、外部凭据、委派工具、组织拓扑和策略都可能在暂停期间变化。

## 一条转交路径不是通用恢复理论

必须保留证据边界：这里研究的是 Google ADK 的一个 `transfer_to_agent` 确认恢复路径。它没有建立 Exactly-once Execution，没有定义通用 Capability Identity，也没有证明跨进程恢复，更没有给出完整的人机协同恢复规范。

“总是依据当前状态重建”同样存在反方意见。如果某项能力不可变且可以安全序列化，保留原身份可能比重新推导更准确。反过来，如果完全依据当前拓扑重建，也可能得到一个与用户暂停时看到的对象不同的能力。

因此，可迁移的工程结论不是“永远重建”，而是：**明确选择权威来源**——重放、重建、比较，或者拒绝继续执行。

## Pending Confirmation 应绑定哪一时刻的权威？

最终没有解决的问题，是待决确认究竟绑定什么。

它应该绑定暂停时的能力？绑定恢复时重建的能力？还是同时绑定两者，并在发现实质漂移时让原确认失效？

所选实现对一个动态转交能力给出了具体答案：先依据当前目标重建，再处理确认。这足以让更一般的治理问题显形，却不足以替所有系统下结论。

成熟的恢复协议应把这种绑定关系显式化。否则，“恢复”这个词仍然可能同时指“找到了旧状态”“重新有了工具”“人已经同意”或“工作现在获准继续”——而这四件事并不是同一件事。
