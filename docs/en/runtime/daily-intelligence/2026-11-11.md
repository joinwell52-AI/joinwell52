# 2026-11-11 · Agent Research and Competitor Intelligence

## Research analysis

### A1 · O3 / O4 / O5 / O6 / O15 / O18 / O26

Authorization follows execution identity and generation; delegated work need not expose secrets. Evidence supports call-time checks, approval ownership and one-time reveal as distinct mechanisms. Test applicability to CodeFlowMu delegation and credential proxies across employees/organizations. This primarily maps to runtime/adapters and product governance, not automatic FCoP-core additions. Candidate probes: identity switch after approval, removed approval owner and concurrent reveal. Discussion: how do approved pending actions expire after authority changes?

### A2 · O1 / O2 / O8 / O9 / O14 / O17 / O22

Collaborative delivery needs distinct evidence for delivery, acceptance, execution, outcome and recovery. Interrupted records do not prove non-application; transactional receipts strengthen only their protected operations. Test mapping FCoP task/event/artifact semantics to runtime call identities, receipts and unknown outcomes without moving all persistence, scheduling and ownership into the protocol. Candidate probes: lost result after execution, accepted messages without inference, corrupt logs and disconnected steering.

### A3 · O7 / O10 / O11 / O13 / O18 / O20 / O22

Governance must inspect actual boundaries and failure behavior. Default environment inheritance, advisory conflict tags and readOnly declarations provide different assurances from enforcement. Evidence favors preserving original errors, stopping unsafe dispatch and avoiding false success. Experience candidate: bulbasaur digest/conflict checks, pending installation/license/maintenance review; not installed. Discussion: how is refusal preserved when runtime policy reload fails?

### A4 · O12 / O13 / O17 / O21 / O23 / O25

Compare interoperability by layer: MCP Apps/WebMCP concern view tools, ACP client-agent session configuration, A2A inter-agent interfaces; Orca cross-host coordination still has inert pieces. FCoP file/artifact coordination can complement them; substitution is not established. Experience candidates: ACP-registry apps and AG2/MCP Apps, accounting for Node/login, versions, host support and sandbox cost. DSPy 3.5 needs separate migration evaluation rather than classification as a finished digital employee.

### A5 · O16 / O22 / O23 / O25

Independent acceptance checks retained state and faults resembling real deployment. Paperclip staging failures and LangChain outcome guidance reinforce a research method, not universal reliability. Candidate experiment: same-host restart versus changed-process-space redeploy, checking task completion, audit and side effects with held-out cases. Discussion: which different-hostHash owner-death ambiguities remain after K15?

### A6 · O14 / O15 / O16 / O17 / O18 / O19 / O20 / O21 / O24

Radar reassessment: Paperclip offers high learning value and high competitive risk in governed operations/recovery, with staging failures limiting reliability confidence. Orca has medium-high multi-device/chat-API risk while cross-host orchestration is incomplete. Orkas and Agentlas offer medium-high compatibility/upgrade learning and medium delivery risk. Keep Vibe Kanban under low-frequency review of the sunset assessment, without inferring business revival. No verified evidence changes commercial-license assessments this round.
