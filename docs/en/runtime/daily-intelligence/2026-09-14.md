# Agent Research & Competitor Intelligence · 2026-09-14

> Asia/Shanghai · Only meaningful technical or product developments are included.

## Daily conclusion

The strongest convergence today is that **production-grade Agent runtimes are splitting “pre-dispatch judgment” into live resource evidence, Workspace/Run ownership, transport contracts, and recovery boundaries.** A provider still being reachable, a session still being resumable, or a tool name still existing no longer proves that this specific run is safe to execute.

## 1. Yue Zhao / anywhere-agents: parallel dispatch now reads the current quota of the model group before launch

**Status: MERGED (commit 050ee0b)**

Yue Zhao's [`050ee0b`](https://github.com/yzhao062/anywhere-agents/commit/050ee0bd91c5d05c28f6f6b7c196a8d222328a4b) connects Agy's quota meters to `prun` dispatch. Agy meters Gemini separately from Claude/GPT-OSS. Previously a fan-out did not read those meters before launch; in a real seven-unit batch on 2026-09-11, the Claude group's five-hour bucket emptied mid-batch and four units failed in a row.

The dispatcher now reads the snapshot maintained by `agent-quota.py` before each dispatch. It judges a group by its tightest bucket; if Claude/GPT is empty while Gemini is available, it falls back to the Gemini default. If Gemini is empty, it exits explicitly instead of escalating unasked into the scarcer group. The fallback is recorded as `MODEL-FALLBACK`, and the state ledger records the model that actually ran. The change also handles snapshot TTL, expired reset times, stale refreshes, non-finite fractions, and a forced refresh after a failed run.

**Why it matters:** resource routing is moving from “wait for the provider to reject the call, then fallback” to **pre-dispatch live-capacity admission**. It also preserves `unknown != empty`: unreadable or stale evidence does not become a false deny.

**CodeFlowMu/FCoP relevance:** a multi-model team can treat models as role resources instead of pretending that every model is equivalent. A useful auditable chain is `Role → Candidate Models → Live Capacity/Cost → Selected Model → Fallback Receipt`, while high-value EVAL/gatekeeper roles can retain stronger models.

**Interaction value: very high.** Suggested question: *Would you persist the quota snapshot identity and age into each dispatch receipt so later evaluation can prove which live resource evidence selected the model?*

## 2. OpenAI Codex: Agents Overview can create and bind a new Managed Worktree Session directly

**Status: MERGED (PR #45276)**

PR [#45276](https://github.com/openai/codex/pull/45276) adds managed-worktree creation to the Agents Overview. Codex can create a new worktree from the project's default branch and immediately start a **blank Session** bound to that checkout. It does not automatically send a first turn and does not interrupt existing agents.

The boundary details are more important than the shortcut itself. The default branch comes from cached remote `HEAD`, with `main/master` fallback and no fetch; source-checkout edits and the selected subdirectory are preserved; the selected approval reviewer carries into the new session. While the worktree is being created, conflicting actions are paused. A clean unclaimed worktree is removed if ownership never transfers, while a checkout that must be retained is reported explicitly when session startup fails. Pending creation state is also cleared on reconnect.

**Why it matters:** Codex's Agent overview is becoming a **Workspace + Session lifecycle control surface**, not only a list of conversations.

**CodeFlowMu/FCoP relevance:** for role rooms and Branch TASK work, `Workspace Creation → Session Binding → Approval Context → Ownership/Cleanup` should form one transaction, while conversation history, workspace identity, and inherited authority remain distinct facts.

**Interaction value: high.** Suggested question: *Will managed-worktree creation eventually emit a durable lineage receipt binding source revision, new checkout identity, thread ID, and inherited approval context?*

## 3. AG2: the MCP Server's HTTP transport is becoming an operator-owned product contract instead of an upstream default

**Status: DRAFT / OPEN (PR #3252)**

Draft PR [#3252](https://github.com/ag2ai/ag2/pull/3252) exposes a significant MCP runtime boundary. AG2 creates the streamable-HTTP session manager itself, but historically exposed only `stateless` and `json_response`; most security and lifecycle behavior silently followed the defaults of the installed `mcp` package.

The proposed `TransportConfig` explicitly owns MCP session idle timeout, maximum sessions, request-body size, transport security, SSE retry interval, and event store. It also adds optional RFC 8707 token-resource validation so a bearer token minted for another service can be rejected. An event store makes reconnect-and-replay of missed events reachable for served agents.

The PR notes that served agents previously had no operator-accessible DNS-rebinding protection, while `mcp` 2.2.0 changed session timeout and cap defaults inside the same 2.x dependency range. Two deployments that appear to run the same AG2 version can therefore have materially different runtime behavior because of an upstream patch/minor dependency resolution.

**Why it matters:** **Dependency Default ≠ Product Contract.** Long-running Agent timeout, session caps, resumability, Host/Origin policy, and token audience/resource rules should be fixed and observable by the product that depends on them.

**CodeFlowMu/FCoP relevance:** Host admission should not stop at “MCP connects.” It should validate the effective transport contract: session lifetime, request limits, host/origin policy, event replay, and token audience/resource binding.

**Interaction value: very high.** Suggested question: *Would you expose a transport-contract digest in server metadata so clients can bind resumability and security assumptions to the exact runtime configuration they connected to?*

## 4. Paperclip: clean-machine onboarding now separates API-key users from local-CLI subscription users

**Status: MERGED (PR #13372)**

PR [#13372](https://github.com/paperclipai/paperclip/pull/13372) came from a real nightly release-gate failure. A clean Docker install became stuck at “Connect a model”: the API key had already been live-validated by the provider, but managed adoption still required a local Claude CLI hello probe. A clean machine has no provider CLI, so the user could not hire the first agent.

The merged behavior is more precise. An `api_key` binding is live-verified again against the provider endpoint at adoption and no longer requires the CLI hello path; subscription adoption keeps the strict hello probe. Paperclip also added an HTTPS provider mock to the release smoke harness. It serves only `GET /v1/models` and returns 404 elsewhere, allowing CI to prove that the packaged product can finish onboarding when the provider accepts the credential without storing a real paid credential in CI.

**Why it matters:** this is a substantive installation/delivery maturity improvement. A shippable Digital Employee product cannot treat “provider credential is valid” and “the matching local CLI is installed” as the same admission condition.

**CodeFlowMu/FCoP relevance:** Host/provider admission should split `Credential Validity`, `Required Local Runtime`, and `Selected Execution Lane` into separate facts. Each lane should verify only the dependencies it actually needs.

**Learning: very high | Competitive risk: very high | Radar: keep Paperclip at the highest priority; onboarding maturity increases.**

**Interaction value: high.** Suggested question: *Will onboarding publish the selected execution-lane identity so later runs can prove whether they were admitted through API-key direct execution or a local subscription CLI?*

## 5. Paperclip: an @mention heartbeat Run can incorrectly become another Agent's Issue execution lock

**Status: OPEN / NOT SAFE TO MERGE YET (PR #13374)**

PR [#13374](https://github.com/paperclipai/paperclip/pull/13374) documents a classic multi-agent ownership bug. An Issue belongs to Agent B. A comment @mentions Agent A, so A starts a heartbeat run whose `contextSnapshot.issueId` points at that same Issue. If B's assignee wake arrives while A's run is active, legacy logic can adopt A's run as the Issue's active execution lock, writing A's `runId` into `executionRunId` and blocking B for roughly 30 minutes.

The primary proposed fix is correct in direction: a legacy run can be adopted only if `legacyRun.agentId === issue.assigneeAgentId`, and the database update predicate carries the same condition to close a concurrent-reassignment race.

However, the PR **is not yet safe to treat as a completed fix**. Review has identified that the added ten-minute stale-lock sweep can clear lock fields without running deferred-wake promotion, potentially stranding later work indefinitely. Focused regression tests for the ownership/race and crash-recovery paths are also missing. This is therefore strong incident evidence and an important ownership design signal, not a released capability.

**Why it matters:** `context points to issue` does not mean `run owns issue`. Comment/watch/mention relationships are observation links, not execution authority.

**CodeFlowMu/FCoP relevance:** multi-role TASK/REPORT/notification flows should distinguish `Referenced Object`, `Responsible Role`, `Execution Owner`, and `Wake Recipient`. Lock adoption must be owner-bound rather than inferred from a related object ID.

**Learning: very high | Competitive risk: high | Radar: increase attention to Paperclip cross-agent ownership and deferred-wake recovery.**

## 6. Superset: the formal weekly product update combines parent/subagent topology, more agents, mobile review, Host updates, recurring Automation, and monetization

**Status: MERGED / FORMAL WEEKLY CHANGELOG (PR #7507)**

Superset's merged [2026-09-13 weekly changelog](https://github.com/superset-sh/superset/pull/7507), reviewed by the team, moves several changes into the formal product surface at once:

- Claude Code and Codex subagents now appear **nested under their parent Agent** in the workspace row, and each subagent can be opened to follow its transcript and completion state.
- Muse Code and Devin CLI join the built-in agent catalog with session resume and token history.
- Published Pages can be read and commented on from iOS.
- Standalone CLI Host versions are visible, compatibility can gate workspaces, and owners can update Hosts from the app.
- A pinned-workspace Automation can continue its existing Agent Session instead of creating a new one for every occurrence.
- **Automations are now a Pro feature**: create/run/enable require Pro, while read/pause/delete remain available on Free.
- Web billing now supports upgrading/cancelling Pro, and the iOS paywall links to it.

The official install material still describes macOS as supported, Linux x64 AppImage as experimental, and Windows as unavailable.

**Why it matters:** Superset has moved beyond a multi-coding-agent desktop shell toward **Agent catalog + parent/subagent topology + Host lifecycle + mobile review + recurring automation + subscription monetization**.

**CodeFlowMu relevance:** this is increasingly close to the Digital Employee Workstation product shape. CodeFlowMu can still differentiate through explicit Role/Responsibility, FCoP durable facts, independent EVAL, and stricter authorization/recovery boundaries. Commercially, Superset has now made Automation itself a paid value driver rather than monetizing only model usage.

**Learning: very high | Competitive risk: very high | Radar: promote Superset from priority second ring to the main radar.**

**Interaction value: very high.** Suggested question: *Now that subagents are first-class in the UI, will their parentage also become a durable execution/audit identity rather than only a presentation hierarchy?*

## 7. OpenAI Agents SDK Python: after `clear_session()`, stale Response/Compaction chain identities can still leak back into the future

**Status: OPEN (PR #5000)**

PR [#5000](https://github.com/openai/openai-agents-python/pull/5000) fixes `OpenAIResponsesCompactionSession.clear_session`. The underlying history was deleted, but `_response_id` and `_last_unstored_response_id` remained. A later `run_compaction` could therefore reuse an old response ID that pointed at the cleared conversation, reconnecting a future compaction to state that the user expected to be gone.

The proposed fix makes `clear_session` invalidate `_response_id`, `_deferred_response_id`, and `_last_unstored_response_id`, including the failed-acknowledgement path, matching the stronger reset semantics already used after deletion with `pop_item`.

**Why it matters:** deleting visible history is not a complete reset if continuation, deferred, or response-chain pointers can still reconnect future operations to the old world.

**CodeFlowMu/FCoP relevance:** Reset / Archive / Forget / Revocation should create an explicit **generation barrier**. Old checkpoints, provider continuations, pending retries, and approval references must fail if they belong to a previous generation.

**Interaction value: high.** Suggested question: *Would it be safer to model session clear as a monotonic generation change so every continuation pointer carries the generation it belongs to and fails structurally after reset?*

## Cross-project convergence

> **Production-grade Agents are moving from “preserving state” to preserving state with identity, freshness, ownership, and resource evidence.**

Yue Zhao moves live quota evidence in front of dispatch; Codex binds Worktree and Session explicitly; AG2 aims to freeze MCP transport security and lifecycle semantics; Paperclip separates credential lanes and exposes a cross-agent execution-ownership bug; Agents SDK shows that reset must sever continuation chains.

A useful CodeFlowMu/FCoP model is:

**Work/Run Identity → Workspace Identity → Responsible Owner → Live Capability/Capacity Evidence → Transport/Provider Contract → Call-time Admission → Effect → Settlement / Generation Barrier**.
