## 1. Yue Zhao / GRADE: dependency-graph bug fixed and a structural claim withdrawn

**Status: MERGED / RESEARCH CLAIM CORRECTED**

Yue Zhao personally submitted the correction in [commit a9a87a1](https://github.com/yzhao062/grade/commit/a9a87a13866e6410f83664bf8a59642fb36aac8e). A mapping named `last_on_id` used `setdefault`, which preserved the **first producer** for an identifier even though downstream logic assumed the latest producer. The correction changed a large fraction of dependency edges and spans; together with an earlier hash-order fix, the relevant transfer and within-corpus cells became stable across multiple `PYTHONHASHSEED` values.

More importantly, Zhao withdrew the earlier claim that the dependency layer outperformed run size as a predictor of failure. The old control used only a linear size baseline; stronger nonlinear size baselines and null/chain controls showed that the structural model no longer supported a unique superiority claim. Execution-layer fault-localization findings were stated to remain unaffected.

**Why it matters:** a graph feature being structurally richer does not prove that it carries independent information.

**CodeFlowMu/FCoP relevance:** any future EVAL claim about dependency, audit, or recovery graphs should include nonlinear size baselines plus null, chain, and matched-source controls.

**Interaction value: very high.** Suggested question: *Would you make nonlinear size baselines and null/chain graph controls mandatory release gates for future GRADE structural claims rather than post-hoc diagnostics?*

## 2. Paperclip: the human origin of a shared Digital Employee becomes an operation-time contract

**Status: #13005 MERGED; #13000 DRAFT; #13002 DRAFT**

PR [#13005](https://github.com/paperclipai/paperclip/pull/13005) has been merged. Paperclip no longer derives GitHub identity simply from task ownership or a long-lived provider token. It persists an **ordered execution identity context** so new human instructions, steering, queued continuations, retries, delegations, approvals, routines, and server restarts retain the real originating person. When `git`, `gh`, or the GitHub gateway actually executes, an operation-time broker resolves credentials for the responsible person behind the currently accepted instruction; personal tokens do not live in the long-lived provider process.

Two follow-up drafts extend the same direction:

- [#13000](https://github.com/paperclipai/paperclip/pull/13000): private Slack task control with explicit human mapping, persist-before-ACK semantics, at-most-once mutation fencing, and `uncertain` rather than automatic replay when outcome is ambiguous.
- [#13002](https://github.com/paperclipai/paperclip/pull/13002): durable sandbox work folders split into task / agent / user / project / repos scopes, with checkpointing and object storage as the durable layer.

**Why it matters:** Employee Identity, Human Principal, Task Owner, Credential Scope, and Conversation Continuity are now separate runtime facts.

**CodeFlowMu/FCoP relevance:** a long-running Digital Employee should record who the employee is, who issued the current instruction, and whose credential/workspace scope the effect used as separate identities.

**Learning: very high | Competitive risk: very high | Radar: keep at the highest priority and add operation-time principal as a dedicated dimension.**

**Interaction value: very high.** Suggested question: *Will responsible-person identity, Slack attribution, and user-scoped work-folder binding converge on one durable authority envelope so every side effect proves both who instructed it and whose credential/workspace scope it used?*

## 3. OpenAI Codex: Human Verification reaches Secure Enclave + biometric signing

**Status: MERGED / MERGED**

PR [#43624](https://github.com/openai/codex/pull/43624) implements macOS human verification using a P-256 Secure Enclave key stored through the Data Protection Keychain. The private-key access-control policy requires biometric authentication, each challenge signature uses a fresh `LAContext`, and credential creation/reuse/deletion/signing is serialized with a cancellable cross-process file lock.

PR [#43524](https://github.com/openai/codex/pull/43524) tightens the authority boundary: an arbitrary user-configured MCP server cannot impersonate the official Apps MCP surface and request human verification. The capability is projected only to Host-owned Apps MCP, and local identity uses a workspace-scoped opaque ChatGPT account user ID with workspace/account consistency checks.

**Why it matters:** approval is moving from “the user clicked allow” to hardware-protected, human-presence, challenge-specific cryptographic proof.

**CodeFlowMu/FCoP relevance:** ADMIN approval can eventually have multiple assurance levels—UI confirmation, authenticated approval, and device-bound biometric proof—but a strong proof should still commit to effect digest, principal, workspace/company, authority epoch, nonce, and expiry.

**Interaction value: very high.** Suggested question: *Will the signed verification challenge commit to the normalized effect, workspace principal, and authority epoch so biometric proof is specific to one consequential action rather than merely proving user presence?*

## 4. Kazuhiro Sera / OpenAI Agents JS: two fixes ask the same question—who owns this state?

**Status: MERGED / MERGED**

Kazuhiro Sera personally submitted PR [#1841](https://github.com/openai/openai-agents-js/pull/1841) and [#1842](https://github.com/openai/openai-agents-js/pull/1842), both merged.

- #1841 fixes deferred-tool discovery attribution after multi-agent handoff. A same-named tool on Agent B must not inherit Agent A’s earlier discovery merely because the history contains a match; persisted attribution is restored only when the logical Agent identity is unambiguous.
- #1842 fixes concurrent session compaction. If another writer appends after a Run reads a snapshot, the old snapshot no longer has authority to replace the whole session. The Runner carries an ephemeral ownership receipt, and expired ownership causes automatic replacement to be abandoned.

**Why it matters:** history existing does not mean I own it; a same-named capability does not mean it belongs to me; reading a snapshot once does not grant future overwrite authority.

**CodeFlowMu/FCoP relevance:** any whole-state replacement in Branch/REPORT convergence should require a still-valid ownership generation; otherwise the system should append or reread.

**Interaction value: high.** Suggested question: *Do you see session-compaction ownership and tool-discovery attribution converging on a general Agent/run generation primitive instead of subsystem-specific receipts?*

## 5. Superset: Host upgrades become backup → restart → verify → rollback

**Status: OPEN**

PR [#7270](https://github.com/superset-sh/superset/pull/7270) makes Host build/version/install-source visible in Desktop settings, device selection, and workspace compatibility gates. For supported standalone CLI Hosts, the Owner can trigger an upgrade from the Desktop. The updater locks the install directory, keeps a backup, restarts on the **same port**, verifies the successor version, and rolls back on failure.

A real desktop click test upgraded a standalone Host from 1.26.0 to 1.27.0 in roughly eight seconds, but production relay/auth, active-terminal reconnect, and the full incompatible-workspace gate were not yet fully end-to-end validated; interrupted upgrades could also leave an install lock.

**Why it matters:** a Digital Employee workstation upgrade is a Host lifecycle transaction, not merely binary replacement.

**CodeFlowMu/FCoP relevance:** the Windows product path should include **Host Version → Compatibility → Upgrade Admission → Backup → Binary Replace → Restart → Successor Verification → Rollback → Session Reconnect**.

**Learning: very high | Competitive risk: high | Radar: keep as a priority second-ring competitor; promote if production relay and active-terminal reconnect are verified.**

**Interaction value: very high.** Suggested question: *Before replacing a live standalone host, do you plan to drain/fence active agent leases and then prove ownership transition to the verified successor binary?*

## 6. Orca: a corrupted record being unsafe to replay does not justify deleting the evidence

**Status: DRAFT**

Draft PR [#19399](https://github.com/stablyai/orca/pull/19399) changes journal repair semantics. The previous logic could delete an unreadable row and the suffix after it, even though provider transcripts cannot reconstruct Orca’s own submission receipts.

The proposal introduces **sealed recovery generations**: original bytes from the old epoch remain preserved and sealed, while only the verified readable prefix is published into a new epoch. SQLite triggers prevent sealed history and recovery metadata from being modified or deleted. Unknown future database/row versions become read-only rather than guessed, migrated, or repaired.

The key principle is:

> **Evidence Recoverable ≠ Evidence Safe to Replay.**

Evidence after a corruption boundary may remain available for audit without regaining execution authority.

**Why it matters:** evidence retention and replay authorization are distinct capabilities.

**CodeFlowMu/FCoP relevance:** for damaged REPORTs, runtime event logs, EVAL evidence, or authorization receipts: seal old evidence unchanged → recover only the deterministic prefix into a new generation → preserve uncertain suffixes as evidence only, never as execution authority.

**Learning: very high | Competitive risk: medium-high | Radar: raise Orca’s Recovery / Auditability weight, but the feature remains draft.**

**Interaction value: very high.** Suggested question: *Do you expect sealed journal generations to become the general evidence-retention primitive for rewind/fork/recovery so superseded evidence remains immutable without ever regaining replay authority?*

## Cross-project convergence

> **“State” is being decomposed into who owns it, who authorized it, whether it may overwrite, whether it may replay, and whether it may exist only as retained evidence.**

A useful CodeFlowMu/FCoP model is:

**Principal Identity → Ownership Generation → Authorization/Verification → Effect Authority → Durable Evidence → Replay Eligibility**.

The last term matters: **a fact that can be recovered does not automatically have the right to execute again.**
