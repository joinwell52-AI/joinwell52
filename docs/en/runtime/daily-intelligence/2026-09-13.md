## Daily conclusion

The strongest signal today is not “more agents,” but a sharper decomposition of **continuity contracts in long-running execution**. A provider session may continue while the current task objective, human interrupt, credential lease, client origin, workspace capability, and tool identity each require separate proof. An unbroken session does not imply that an old objective, old authority, old notification audience, or old tool interpretation remains valid.

## 1. Yue Zhao / anywhere-agents: a real fan-out audit exposes “exit 0 but business failure”

**Status: COMMITTED / FIXED**

Yue Zhao personally recorded an audit of **152 real Agy dispatches** in [commit 3c94f45](https://github.com/yzhao062/anywhere-agents/commit/3c94f459fa942727bbbf0a51ad1967d235096bc7). The most important defect was a false-success boundary: Agy can exit with process code **0** when quota-limited even though its terminal event is `ERROR`, and that event may still contain the model’s opening narration. The old dispatcher used the exit code and response, so four units in one fan-out published opening narration as their deliverable without a `FALLBACK` marker. The Gemini reviewer path carried the same risk.

The dispatcher now treats the terminal event’s `status` as the provider outcome: anything other than `SUCCESS` fails the run. If a worker already wrote its own result, that artifact is preserved, but the run still exits non-zero and the partial response is retained as evidence. Two other real defects were fixed at the same time: Windows long paths could break staged-snapshot export, and `read(65536)` could leave a live tail at zero bytes until a full 64 KiB block arrived, misleading stall monitors.

A follow-up by Zhao in [commit 0d2221e](https://github.com/yzhao062/anywhere-agents/commit/0d2221e0089106e72d69d1cf79bee279ccf25a4e) also corrected the documented model-routing intent: the cost reduction comes from removing Codex from large `prun` fan-out, while the `/vet` gatekeeper keeps the flagship GPT-6 Astra. In other words, cheaper models scale the worker fleet; the strongest model remains where gate quality has the highest value.

**Why it matters:** Process Exit, Worker Artifact, Provider Event Status, and Gate Verdict are distinct facts. `exit 0` must not own the business-completion decision, and a preserved partial artifact does not automatically become an acceptable result.

**CodeFlowMu/FCoP relevance:** a useful contract is `Process Outcome → Provider Outcome → Work Result → Verification Verdict`, with model quality assigned by role rather than assuming all agents are interchangeable.

**Interaction value: very high.** Suggested question: *Would you record process exit, provider terminal status, artifact provenance, and verifier verdict together in each dispatch receipt so no single layer can masquerade as final completion?*

## 2. AG2 / AG-UI: human-in-the-loop becomes “end one exchange, hold the original turn,” explicitly avoiding replay

**Status: DRAFT / OPEN**

AG2 Draft PR [#3248](https://github.com/ag2ai/ag2/pull/3248) adds real mid-run human input over AG-UI. When a tool calls `context.input()`, the current exchange finishes normally with `RUN_FINISHED` + an `interrupt`, while the original Python turn remains suspended. The client later submits `resume` with the **same thread and a new run id**.

The central design choice is that **continuation is not replay**. The suspended Python function retains its current instruction pointer, locals, and any side effects already performed. Reconstructing from message history would re-enter the tool from the top and could repeat those effects, so the PR holds the coroutine in the serving process instead.

Resume also requires a per-interrupt `proof` echoed by the client. It is a capability token, not a digital signature; bad proof, expired interrupts, and non-outstanding interrupts get machine-readable error codes. Tool approval uses the same path. The limitations are explicit: sticky routing is required; a server restart loses held turns; held coroutines cannot be serialized into a shared backend; and only one question may be outstanding per turn today.

**Why it matters:** this is a clean distinction between `Thread Continuity`, `Run Continuity`, and `Turn Replay`.

**CodeFlowMu/FCoP relevance:** human approval should be a distinct durable object. If the executing turn itself remains in memory, its lease and restart boundary must be explicit. Restart-safe continuation needs a durable continuation design rather than pretending replay is equivalent.

**Interaction value: very high.** Suggested question: *Could interrupts/continuations become durable objects so sticky routing is an optimization rather than a correctness requirement?*

## 3. Paperclip: a real Credential Lease fix lands while another recovery bug shows that the correct session can still execute the wrong objective

**Status: #13347 MERGED; #13345 DRAFT / OPEN**

Paperclip PR [#13347](https://github.com/paperclipai/paperclip/pull/13347) has merged. A real hosted subscription login could save successfully and pass its environment check, yet the first task then failed with `AI connection busy`. The cause was a session advisory lock remaining on a transaction-pooled PostgreSQL backend. The credential grant lock is now held inside **one database transaction**, with rollback on cleanup or failed acquisition and idle timeout disabled while a long provider execution owns the lease. Real Claude and OpenAI subscription sign-ins, environment checks, task executions, and immediate repeat executions were exercised on staging, with transaction-scoped locks observed during execution and absent after completion.

The immediately adjacent Draft PR [#13345](https://github.com/paperclipai/paperclip/pull/13345) found a different continuity failure. During upgrade acceptance, legacy Codex **resumed the original provider conversation correctly**, but the invocation prompt omitted the user’s edited task description and selected an old human comment as the objective. The system therefore ran an old script inside the correct saved session. The proposed fix delivers the current task brief on fresh and resumed runs, prefers an edited brief over already-delivered historical comments, and preserves the current objective only on later resumes when the brief remains unchanged. CI and final staging acceptance are still pending, so this must not be described as released behavior.

**Why it matters:** Credential Lease must match the true execution lifetime, and correct Session Identity still does not prove correct Objective Revision.

**CodeFlowMu/FCoP relevance:** recovery should bind at least **Provider Session + Current Task Revision + Principal/Credential Lease + Authority Epoch**. “The session resumed” is not proof that task semantics resumed correctly.

**Learning: very high | Competitive risk: very high | Radar: keep Paperclip as a first-line runtime competitor.**

**Interaction value: very high.** Suggested question: *Will current task revision / objective digest become part of the provider-session resume receipt, so a stale comment can never regain authority under a newer task revision?*

## 4. Superset: the Lock Screen Agent fleet moves from foreground polling toward APNs push, but real iPhone delivery is still unverified

**Status: OPEN / NOT MERGED**

Superset PR [#7491](https://github.com/superset-sh/superset/pull/7491) reopens work from #7482 after that version was merged and then reverted by #7489. It directly attacks the limitation noted yesterday: Live Activity was driven by the phone polling each host every five seconds in the foreground, so the Lock Screen card froze shortly after the phone was locked. The new design has the Host report derived agent-state transitions (`working / review / permission / failed / gone`), the API persist terminal state and ActivityKit tokens, and APNs perform `start / update / end` rewrites for the Lock Screen card.

The design also separates push urgency: ordinary working transitions use APNs priority 5, while human-interest states such as review, permission, and failure use priority 10. Mobile retains push tokens and push-to-start tokens, and each row carries an epoch `since` so the widget can keep elapsed time current without another server push. API testing with a fake APNs HTTP/2 server, ES256 provider JWT verification, and iOS simulator builds have passed.

The boundary remains important: **real Apple-to-real-iPhone delivery has not been verified**; it needs production APNs secrets and a native build. The PR is still open, so this is not a released capability.

**Why it matters:** the phone is moving from “open the app to inspect agents” toward a genuine background supervision surface.

**CodeFlowMu/FCoP relevance:** mobile is most valuable for state, review, permission, evidence, and control—not as a miniature PC interface. Future typed approvals should bind Human Principal, target run/effect, and state version.

**Learning: very high | Competitive risk: very high | Radar: Superset remains a main-radar candidate; promote only after merge and real APNs/iPhone validation.**

**Interaction value: high.** Suggested question: *Will permission/review states on Live Activity carry a verifiable run/effect identity so a future Lock Screen approval can become a formal receipt rather than a UI hint?*

## 5. Orca: a shared remote server begins isolating focus, notifications, and push by the client that originated each run

**Status: DRAFT / OPEN**

Orca Draft PR [#20402](https://github.com/stablyai/orca/pull/20402) addresses a classic multi-client failure: when two clients share one remote Orca server, work started by client A can switch client B’s workspace or make B receive agent notifications that do not belong to it.

The proposal carries existing host/paired-device provenance forward as **run origin** through terminal creation, child CLI commands, native sessions, persistence, and daemon/SSH reattachment. CLI activation is addressed only to the originating client, while notification display, unread state, live delivery, replay, and push are filtered by origin. Unknown origins stay in the background, and reconnect does not replay activation.

The project reports a real background Electron server plus two independently paired web clients passing a 4/4 E2E flow. Physical Windows/Linux, live SSH, and actual `orca serve` bootstrap remain untested; the PR also stays draft pending final visual evidence.

**Why it matters:** shared Workspace must not imply shared Audience, and task attribution should not be inferred from the workspace creator. Navigation, notifications, and push need their own **Run Origin / Audience Scope**.

**CodeFlowMu/FCoP relevance:** after multi-host / room support, formal messages and UI focus should bind to the initiating principal/run rather than falling back to host-wide ambient broadcast.

**Learning: very high | Competitive risk: medium-high | Radar: increase Orca’s multi-client isolation and remote-control weight.**

**Interaction value: high.** Suggested question: *Do you expect Run Origin to become an authorization/audit principal as well, rather than remaining only a navigation and notification-routing field?*

## 6. Fusion: an MCP tool can exist but have the “wrong name,” causing an entire agent session to spin without progress

**Status: OPEN / NOT MERGED**

Fusion PR [#3597](https://github.com/Runfusion/Fusion/pull/3597) fixes an ACP + MCP tool-name mismatch. Fusion planning prompts refer to bare logical names such as `fn_task_prompt_write`, while an ACP client may expose the same MCP schema to the model as `mcp__fusion_custom_tools__fn_task_prompt_write`.

In real planning runs, agents interpreted the naming mismatch as a missing capability and spent whole sessions searching CLI commands, REST routes, source code, and the filesystem for substitutes. `PROMPT.md`, task steps, and the task branch did not advance. The proposed fix injects a bare-name ↔ namespaced-name mapping only when the custom-tool bridge is actually attached and the referenced `fn_*` tool is really registered; the bundled Claude, Grok, and OMP runtimes receive the same bridge-aware guidance in their vendored ACP adapters.

**Why it matters:** Capability Presence, Protocol Exposure Name, and Prompt Vocabulary are distinct facts. Drift in any one can be misdiagnosed by the model as “tool unavailable.”

**CodeFlowMu/FCoP relevance:** Host capability probes should verify not only tool counts/names, but that the **model-visible schema identity** maps stably to the logical tool identity used by the business contract.

**Learning: high | Competitive risk: medium | Radar: raise Fusion’s MCP/Host compatibility monitoring weight.**

**Interaction value: high.** Suggested question: *Would a machine-readable logical-tool-id / exposed-schema-name manifest be safer than prompt text mapping, so Host admission can validate the mapping directly?*

## 7. OpenHands: a Docker conversation must not expose Host Workspace controls; live runtime capability begins driving the UI boundary

**Status: DRAFT / OPEN**

OpenHands Draft PR [#17387](https://github.com/OpenHands/OpenHands/pull/17387) repairs a Canvas runtime boundary. A Docker backend cannot attach a user-selected host folder, yet the old Canvas still exposed **Open Workspace**, and some File/Git/Terminal/VS Code service calls lost their conversation scope.

The proposed fix consumes SDK typed runtime clients and Server-advertised capabilities: an isolated runtime rejects host-project selection, hides unsupported host-workspace controls, and carries conversation identity into file, Git, terminal, and VS Code operations. A real Chromium probe also found and removed a raw, unscoped bash WebSocket in favor of the existing SDK `BashClient`; a disposable Docker conversation was verified to keep its fixture file, Git branch, and Terminal viewer conversation-scoped.

The PR depends on an unreleased TypeScript client version and therefore remains draft. The live deployment used for validation exposes no editor, so no real VS Code launch is claimed.

**Why it matters:** a visible UI control is itself a capability claim. If the Host/Runtime does not own a workspace authority, the UI must not imply that it does.

**CodeFlowMu/FCoP relevance:** after Host admission, `DetectedHostFacts` should project one shared capability contract into UI, Worker, and Tool routing instead of letting each layer infer capabilities independently.

**Interaction value: high.** Suggested question: *Will runtime capability snapshot/version be persisted with conversation identity so a resumed UI can prove it is not using stale Host capability?*

## Cross-project convergence

The common pattern today is:

> **Continuity is not a boolean. Session, Task, Human Interrupt, Credential, Client Origin, Workspace, and Tool Schema each have their own continuity contract.**

A useful long-running object chain for CodeFlowMu/FCoP is:

**Run/Thread Identity → Current Work Revision → Principal/Credential Lease → Host Capability Snapshot → Human/Client Origin → Logical Tool Identity → Effect / Result → Verification / Replay Eligibility**

A change in any one of those should not inherit authority merely because the underlying provider session still exists.
