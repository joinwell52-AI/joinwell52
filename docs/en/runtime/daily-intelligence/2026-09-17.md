## Daily conclusion

The strongest common signal today is that **user intent must be translated into an actually effective runtime contract, and that contract must participate in connection, cache, retry, recovery, and credential identity.** A UI that says read-only, Manual, approved, revoked, or “retry the same operation” is not enough if the underlying connection, provider, or source of authority carries a different contract.

## 1. Yue Zhao / anywhere-agents: no-op persistence was evicting the evidence needed for recovery

**Status: MERGED (commit `ce6457a`)**

Yue Zhao fixed a failure mode observed in a real multi-consumer environment. Bootstrap runs at every session start; a 27-consumer loop can therefore run it 27 times in one afternoon. The old merge path republished `settings.json` and backed up the previous file even when the resulting bytes were identical. On 2026-09-15, 27 consumers produced **198 backups, all byte-identical to the live settings.json**, filling a bounded history with no-op copies and evicting genuinely useful recovery history.

The merge now compares the canonical bytes under the existing lock and returns without publishing or backing up when nothing changed. First installs, real changes, and different byte shapes still publish and retain recovery material. The Bash/Windows bootstrap paths and release smoke were aligned; multiple `/vet` rounds caught and fixed BOM, concurrent-overwrite, and false-success issues in the repair itself.

**Why it matters:** more recovery records are not automatically better. If no-op facts share a bounded history with real state changes, churn can actively destroy recoverability.

**CodeFlowMu/FCoP relevance:** configuration, rules, Host profiles, and authorization facts should use **semantic/no-op dedupe plus real-change retention**. A scheduler or bootstrap should not manufacture new business facts simply because it runs again.

**Interaction value: high.** Suggested question: *Would you move backup retention from “number of file copies” toward distinct content/revision generations, so recovery history is counted by real state transitions rather than session starts?*

Source: [anywhere-agents commit ce6457a](https://github.com/yzhao062/anywhere-agents/commit/ce6457a830dead5e05c3a17f685f7ff32575ce20)

## 2. OpenAI Codex: MCP read-only becomes connection identity instead of a model hint

**Status: MERGED (PR #46042)**

Codex merged read-only MCP policy support. When enabled, both `tools/list` and `tools/call` carry `openai/readOnly=true`, overriding a caller-supplied `false`; more importantly, the policy is included in **MCP connection identity**. Read-only connections do not reuse unrestricted connections and do not consume or populate shared Apps or persistent tool-catalog caches, because a writable catalog cached earlier could otherwise bypass filtered discovery.

Tests cover legacy/modern protocol modes, session recovery, unrestricted-connection isolation, and shared Apps catalog isolation.

**Why it matters:** filtering only the visible tool list while sharing an unrestricted connection or cache is not an authority boundary.

**CodeFlowMu/FCoP relevance:** MCP/Host connection pools and tool catalogs should be partitioned by **Authority Scope**. ReadOnly / Write / Approval-required belongs in connection and cache identity, not just in a prompt.

**Interaction value: very high.** Suggested question: *Will normalized MCP effect scope / read-only policy also be recorded in connection and tool-call receipts so resume or cache reuse can prove the authority scope that actually applied?*

Source: [openai/codex PR #46042](https://github.com/openai/codex/pull/46042)

## 3. Paperclip: approval or answer during an active run becomes a durable fact before delivery is decided

**Status: MERGED (PR #13539)**

Paperclip now projects confirmation, checkbox-confirmation, and question responses submitted during an active run into its existing message queue. A click immediately persists an **immutable typed response** with the exact approval revision and selected answers, but it no longer implicitly steers the currently executing Agent. The default path queues continuation behind the active run; the user may explicitly choose **Steer** for a compatible native turn or **Interrupt** when a fresh session is required. If the provider is blocked on the original question request, the answer may still resolve that request directly.

Acknowledgement consumes the receipt so retries cannot duplicate delivery; process-stop, environment-cleanup, ownership, and recovery gates still apply. Final CI was green and the PR is merged.

**Why it matters:** when a human decision happens and when an Agent consumes it are different facts. A UI click should not be treated as an implicit mutation of a turn already in flight.

**CodeFlowMu/FCoP relevance:** ADMIN/EVAL/QA approvals, answers, and corrections should be modeled as **Decision Receipt → Delivery/Continuation Policy**. This keeps decisions durable across queues, restarts, and provider changes without accidentally applying them to a later generation of work.

**Learning: very high | Competitive risk: very high | Radar: Paperclip remains highest priority.**

**Interaction value: very high.** Suggested question: *Will the typed interaction receipt eventually bind target run, task revision, or effect generation, so a delayed approval cannot regain authority over a later plan?*

Source: [Paperclip PR #13539](https://github.com/paperclipai/paperclip/pull/13539)

## 4. Paperclip: recovery exposes that an error code is not a failure cause; credential revocation must modify the authority source, not a projection

**Status: OPEN / NOT MERGED (PR #13549, #13529)**

PR #13549 includes strong production evidence: on one calendar day **320 terminal runs** failed with a subscription/session-limit message, all with `errorCode=acpx_turn_failed`; **186 had a non-null `retryOfRunId`, while 0 carried a quota retry reason**. Recovery only scanned a few error codes, so provider messages that explicitly said “session limit / resets at …” fell through as ordinary continuation failures and launched more runs inside the same exhausted window. The proposed fix treats `acpx_turn_failed` as eligible for quota classification only when quota semantics are actually present and waits until the provider reset time. It remains unmerged.

A separate OPEN PR #13529 fixes credential revocation. `company_secret_bindings` is only a projection derived from an Agent's `adapterConfig`. Deleting the binding row alone would appear successful, but the next config write would recreate it and the Secret could still project into runtime. The proposal therefore removes the secret reference from the **authoritative adapterConfig**, records a versioned config revision, lets the binding projection converge, and emits a `secret_access_events outcome=revoked` record.

**Why it matters:** both defects are the same category: **derived fields and phase error codes are not substitutes for their semantic source of truth.** `acpx_turn_failed` is a phase outcome, not a failure cause; a binding row is a projection, not credential authority.

**CodeFlowMu/FCoP relevance:** Recovery should consume typed causes rather than treating transport/error codes as business verdicts; revocation must modify the **source of authority** and then let UI/projections/caches converge.

**Learning: very high | Competitive risk: high | Radar: increase Paperclip Recovery Cause and Credential Revocation weight.**

**Interaction value: high.** Suggested question: *Could provider failure cause and config/secret authority generation become stable typed facts, so Recovery and revocation no longer infer authority from text or derived rows?*

Sources: [Paperclip PR #13549](https://github.com/paperclipai/paperclip/pull/13549) · [Paperclip PR #13529](https://github.com/paperclipai/paperclip/pull/13529)

## 5. Superset: Slack is becoming a remote Agent operations surface with the human's own credentials

**Status: #7585 MERGED; #7589 OPEN / NOT MERGED**

Superset merged #7585: the Slack Agent can use **the linked user's own connected Linear/GitHub plugins**. Credentials are decrypted per call inside the API server and used through a credential proxy, never handed to the model. A curated allowlist is exposed today—11 Linear and 12 GitHub tools—with reads plus bounded mutations such as creating issues/comments or opening PRs, while deletes, merges, and bulk writes are excluded. The allowlist is enforced at both discovery and execution. Plugin calls share the run deadline/AbortSignal; users without a connection get a Connect button. The PR explicitly says it was not live-tested with authenticated Linear/GitHub connections, so this is a merged implementation, not a claim that every remote provider path has production E2E proof.

Follow-up #7589 remains OPEN: when Slack launches an Agent, the plan is for the originating thread to receive one completion reply after the first turn, backed by `slack_agent_launches` and QStash polling from 30 seconds to 5 minutes for up to 24 hours. A conditional `completed_at` claim provides at-most-once completion posting. PermissionRequest is treated as waiting, but this capability is not merged yet.

**Why it matters:** Slack is moving from a trigger surface toward **Remote Command + Per-human Plugin Effect + Long-running Completion Callback**.

**CodeFlowMu/FCoP relevance:** IM/mobile remote control should bind `Human Principal → Run → Tool Credential Scope → Effect Receipt → Completion/Approval Notification`, rather than acting as a smaller chat window.

**Learning: very high | Competitive risk: very high | Radar: Superset remains in the primary radar; raise IM Remote / Human Credential / Completion Callback weight.**

**Interaction value: very high.** Suggested question: *Will Slack instruction principal and per-user plugin credential projection be bound into every real tool/effect receipt, especially when the same thread is handed between different people?*

Sources: [Superset PR #7585](https://github.com/superset-sh/superset/pull/7585) · [Superset PR #7589](https://github.com/superset-sh/superset/pull/7589)

## 6. Orca: a lost mobile response must not launch a second Agent

**Status: OPEN / NOT MERGED (PR #21106)**

Orca found that `agent.launch` could not be retried safely. Existing-workspace launches had no idempotency; create-worktree only had a 60-second in-memory cache that was not caller-partitioned and disappeared on restart. A normal mobile retry after a lost response could therefore create two Agents or two Workspaces for one tap.

The proposal adds an optional `operationId`, with a Host-computed fingerprint over the parsed intent, and runs **admission before mutable live preconditions are resolved**. The core is a durable atomic claim: `pending → unknown` is a conditional state transition, and only one winner reaches the real launch. The complete successful result is persisted; `unknown` is terminal and refuses automatic re-execution, fallback, or a new ID. Replay across a Host restart returns the recorded answer.

There is also an important compatibility rule: the Host advertises `agent.launch.replay.v1`. An older Host would silently drop an unknown `operationId` field and still launch, so a Client may only regard retries as safe after it has observed the Host capability.

**Why it matters:** “I sent an idempotency key” does not prove the receiver understands an idempotency contract. Retry safety is itself a negotiated capability.

**CodeFlowMu/FCoP relevance:** Schedule, mobile, IM, PWA, and Host mutations should use **Effect Operation Identity + Host Capability Proof**. An unknown outcome stays Unknown; a lost response cannot be rewritten into failure and replay authority.

**Learning: very high | Competitive risk: medium-high | Radar: raise Orca Mobile / Idempotency / Effect Identity weight.**

**Interaction value: very high.** Suggested question: *Will operationId become the common durable effect identity for schedule/mobile/remote launch surfaces, with caller principal separated from the current bearer-token fallback?*

Source: [Orca PR #21106](https://github.com/stablyai/orca/pull/21106)

## 7. Orca: the UI could say Manual while Codex actually ran with approvals bypassed

**Status: OPEN / NOT MERGED (PR #20977)**

Orca's Agent Permissions toggle originally passed the selected posture to Codex `app-server` as a CLI flag. But `app-server` reads policy from typed `thread/start` / `thread/resume` fields. As a result, a user could choose **Manual** in the UI while `~/.codex/config.toml` contained `approval_policy="never"`; a new Codex chat could still run with approvals bypassed even though Settings said Manual.

The proposal makes Manual explicitly send `approvalPolicy=on-request` and `sandbox=workspace-write`, while Yolo sends `never / danger-full-access`. The posture is re-derived from current Settings on every structured-session acquisition instead of being latched into an old session record. The author measured the typed fields against Codex 0.153.4; the PR remains unmerged.

**Why it matters:** across UI, config, and provider, only the provider-effective policy is the final execution fact. A permission toggle that is not translated into the protocol field the provider actually reads is a false control surface.

**CodeFlowMu/FCoP relevance:** Host admission should verify not just whether a Tool exists, but whether **Permission Projection is actually accepted and effective in the Host/Provider**. An active binding or UI toggle must not become its own source of truth.

**Learning: very high | Competitive risk: medium-high | Radar: increase Orca Host compatibility / permission-projection weight.**

**Interaction value: very high.** Suggested question: *Could provider-reported effective approval/sandbox policy be written into the Run receipt, so the UI renders verified effective posture rather than intended posture?*

Source: [Orca PR #20977](https://github.com/stablyai/orca/pull/20977)

## Cross-project convergence

Today's developments converge on one principle:

> **Control Intent becomes Authority only after it crosses the authoritative execution boundary and is verified as effective.**

A useful CodeFlowMu/FCoP chain is:

**Human/Control Intent → Authority Source & Revision → Connection / Provider Effective Policy → Operation Identity → Effect → Durable Settlement / Replay Eligibility**.

Three engineering rules are especially clear today:

1. **Read-only/permission scope belongs in connection and cache identity**, not only in UI or prompts.
2. **Revocation must change the authoritative source**; deleting a derived projection is not revocation.
3. **Retry safety requires capability negotiation**; a Client sending an idempotency key is not enough when an older Host does not understand it.
