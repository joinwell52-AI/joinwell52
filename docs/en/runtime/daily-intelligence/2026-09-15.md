## Daily conclusion

The strongest convergence today is that **execution authority is shrinking from “the Agent/session is still alive” to a much narrower proof: did the user authorize this expansion, which Run owns the work, whose credential is in use, which sandbox package identity is executing, and is there positive evidence that permits retry after failure?**

Production-grade runtimes therefore need to model **Intent, Run Identity, Principal, Host/Package Identity, and Effect Outcome** separately. An old instance of any one of those cannot stand in for the others.

## 1. Yue Zhao / anywhere-agents: unrequested fan-out becomes an explicit governance violation, while prun becomes Agy-only

**Status: COMMITTED**

Yue Zhao made two directly related governance changes in `anywhere-agents`:

- [e26fafb](https://github.com/yzhao062/anywhere-agents/commit/e26fafb43962abe6fb3cd0aa12940988b66d8131): `prun` no longer uses Sonnet/Claude subagents and no longer falls back to Workflow agents. Every unit is dispatched only to Agy. The change follows real usage on 2026-09-13 where Sonnet units and descendants became the largest identifiable contributor to draining a Claude five-hour window, and one unit spawned ten nested agents of its own.
- [28acaaf](https://github.com/yzhao062/anywhere-agents/commit/28acaafe81e620c05f11df3a1b46e551da85b244): documents another real incident in which a user merely asked a session to inspect a repository, but the session autonomously launched four Sonnet prun units, one of which spawned ten nested agents, plus a 14-agent Opus Workflow. The routing rule now says parallel fan-out must be proposed to the user first, with the user choosing prun or Workflow; a previously chosen route may continue only within its agreed scope.

Notably, the “do not fan out without user authorization” rule is intentionally kept as a semantic instruction rather than a deterministic hook. Whether authorization was already granted depends on conversational context; a mechanical hook could block parallelism the user explicitly approved.

**Why it matters:** subagent count is not merely a performance parameter. It expands cost, authority surface, side-effect count, and audit complexity. Allowing an Agent to decide on its own to launch dozens of workers is itself an authority expansion.

**CodeFlowMu/FCoP relevance:** this aligns closely with CodeFlowMu’s role boundaries. A PM may organize work, but formal team expansion, broad fan-out, and cross-host execution should have an explicit authorization source; internal helper agents should not become formal collaborators simply because the model thinks parallelism is faster.

**Interaction value: very high.** Suggested question: *Would you bind evidence that the user authorized fan-out to every worker’s parent/run identity in the dispatch ledger, so later audit can distinguish user-authorized parallelism from autonomous authority expansion?*

## 2. OpenAI Agents Python: Realtime approval has a real fail-open path; proposed fix makes it strict fail-closed

**Status: OPEN · PR #5029**

PR [#5029](https://github.com/openai/openai-agents-python/pull/5029) found that Realtime sessions call the shared `needs_approval` evaluator with `strict=False`. An invalid setting such as `needs_approval="always"` is therefore interpreted as `False`, allowing the tool to run **without the approval the configuration appeared to request**. The core runner already raises `UserError` for the same invalid input.

The proposed fix makes Realtime use the same strict behavior as the core runner: invalid approval configuration raises before any tool invocation instead of silently degrading to “approval not required.” The PR is not merged yet.

**Why it matters:** an approval-policy schema/configuration error must never be interpreted as permission. This is a textbook governance fail-open.

**CodeFlowMu/FCoP relevance:** `approval_required`, authorization boundaries, Host admission, and EVAL gates should all follow the same rule: **Invalid / Unknown / Unparseable policy = No Authority**.

**Interaction value: high.** Suggested question: *Would you include the approval-policy parsing outcome and policy revision in the tool-call receipt, so audit can prove which validated policy governed the invocation?*

## 3. OpenAI Codex: Windows Sandbox now binds execution to a registered Package Identity rather than copied helpers or PATH

**Status: MERGED · #45542 / #45550**

Two merged Windows Sandbox changes form a coherent identity chain:

- PR [#45542](https://github.com/openai/codex/pull/45542) adds service-managed `registered_core` provisioning. Managed sandbox accounts receive registered app packages and runner aliases, while callers are authenticated against the service package family and installed version. Runtime ownership/readiness is published only after package registration and AppData metadata grants succeed; legacy setup or a different owner cannot replace the registered sandbox accounts.
- PR [#45550](https://github.com/openai/codex/pull/45550) makes the sandbox actually launch registered runners through service-recorded execution aliases. Before commands are sent, the service validates ownership, OS package identity, and the staged runner image, with no fallback to copied helpers or PATH lookup. Package context is preserved for sandbox descendants so they can launch executables from the protected package directory.

**Why it matters:** “which binary is executing inside the sandbox?” moves from a path convention to a verifiable software-package identity. That matters especially on Windows, where installer updates, services, sandbox accounts, and executables can drift independently if identity is inferred from filesystem location alone.

**CodeFlowMu/FCoP relevance:** Host admission can continue toward `Host Product Identity → Installed Package Identity → Service Owner → Sandbox Runtime Identity → Executable Alias`, rather than treating an “official version PASS” as sufficient proof.

**Interaction value: very high.** Suggested question: *Will registered package identity eventually be included in every sandbox execution receipt, so a resumed Run can prove which installation generation and service owner actually executed it?*

## 4. Superset: Cloud Workspaces can now commit, push, and open PRs as the current human GitHub principal

**Status: MERGED into `sandbox-v2`; not yet evidence of production rollout**

PR [#7555](https://github.com/superset-sh/superset/pull/7555) adds a personal GitHub connection. Each user can store an encrypted user-to-server token; refresh is protected by a per-user advisory lock because refresh tokens rotate and concurrent refreshes could invalidate one another.

For a Cloud Workspace whose creator has connected GitHub:

- GitHub firewall policy uses that human’s token instead of the organization App token;
- commit author/committer identity uses that person’s GitHub no-reply identity;
- `gh` and pull requests execute as that person;
- workspace creation rejects repositories the person cannot access before clone begins;
- an unattended workspace asks the API every 30 minutes, using the workspace host secret, to re-apply credential policy — **the workspace itself never receives the token**.

The team live-tested real Vercel-box commit/push/PR attribution. The 30-minute timer, token refresh after expiry, and disconnect revocation have not yet been live-verified, and the PR merged into `sandbox-v2`, not a production branch, so this must not be described as a shipped production capability.

**Why it matters:** Digital Employee Identity and Human Principal are being separated further. A long-lived Cloud Agent may persist, while each GitHub effect still needs a defensible answer to “which human was represented?”

**CodeFlowMu/FCoP relevance:** this converges strongly with Paperclip’s operation-time principal work. If multiple ADMINs or team members can drive the same long-lived Digital Employee, CodeFlowMu should distinguish `Employee → Current Instruction Principal → Credential Scope → Effect Attribution`.

**Learning: very high | Competitive risk: very high | Radar: Superset remains in the primary radar; add human action attribution and unattended credential refresh as explicit dimensions.**

**Interaction value: very high.** Suggested question: *Will the personal GitHub principal be bound to a specific Run/instruction generation rather than only to workspace creator identity, so different humans can safely drive the same long-lived workspace over time?*

## 5. Paperclip: Pause was misread by Recovery as “budget exhausted,” turning dozens of healthy tasks into permanent Blocked state

**Status: OPEN · PR #13443**

PR [#13443](https://github.com/paperclipai/paperclip/pull/13443) documents a representative recovery failure. When an operator deliberately sets a Company to `paused`, `budgets.getInvocationBlock` returns an invocation block. The stranded-recovery sweep interpreted every block as “over budget,” changed healthy assigned issues to `blocked`, and attached a recovery action.

Observed scale: one sweep moved **28 issues** to blocked; **36** were affected across the full pause window, including four watchdog issues only six seconds old. Worse, resuming the company does not reopen these issues because a blocked issue has no dispatch queue, monitor, or real blocker, leaving manual repair as the only path.

The proposed fix makes the block carry an explicit `cause=company_paused | budget_exhausted`. Recovery skips a paused company instead of escalating it, and tests cover a pause that begins in the middle of a sweep. The PR is still open.

**Why it matters:** “stop work” and “work failed” are different business facts. Recovery that collapses pause, budget, permission, transport, and crash into one Blocked state can itself create unrecoverable work.

**CodeFlowMu/FCoP relevance:** `Pause/Stop` should be an independent, reversible authorization state, not a lifecycle failure. The track/recovery layer should not reinterpret an ADMIN pause decision into a business terminal state.

**Learning: very high | Competitive risk: very high | Radar: Paperclip remains first-line; typed recovery causes and reversible controls deserve dedicated tracking.**

**Interaction value: high.** Suggested question: *Will invocation-block cause become a stable typed control fact, with Recovery explicitly forbidden from materializing operator pause as a business terminal state?*

## 6. Orca: restart reconciliation stops inferring “not delivered” from absence, while canonical Run Identity is being rebuilt around Orca-owned IDs

**Status: OPEN · #20723; OPEN stacked series · #20717/#20718**

PR [#20723](https://github.com/stablyai/orca/pull/20723) fixes a real duplicate-dispatch hazard. After a connection dies before provider acknowledgement, Orca tries to infer whether the message arrived from transcript history. The old history window was **empty by construction**, so comparable unsettled submissions were classified as `rejected/not_delivered`. `rejected` permits client-message-id rotation, so Retry could send a prompt again even after the provider had already acted on it.

The proposed fix removes this second-hand non-delivery inference. A positive match can settle `accepted`; without positive evidence the state remains `unknown`. `rejected` is reserved for first-hand provider refusal or proof that a frame never reached the child. Previously persisted recovered rejections also no longer automatically gain rotate/retry authority.

At the same time, #20717 and #20718 are building a deeper identity model. Canonical status rows are keyed by an **Orca-minted `runId`**, while a provider session ID becomes an alias set. This follows a measured case where two concurrent `claude --resume <same-id>` processes shared one provider session ID yet were both live Runs and could write divergent branches. Child work receives host-minted `childWorkId` and retains an `unverifiable` state. Only structured/native-chat sessions with trustworthy full scope are routed into canonical ownership for now; PTY/relay evidence remains on a legacy adapter where execution-host/WSL/workspace scope cannot be proven, rather than fabricating scope.

**Why it matters:** this simultaneously establishes two principles: `absence ≠ negative evidence`, and `Provider Session ID ≠ Run Identity`.

**CodeFlowMu/FCoP relevance:** `Agent/Role Identity`, `Run Identity`, `Provider Session Alias`, `Child Work Identity`, and `Delivery Settlement` should be distinct facts; recovery should never substitute one for another.

**Learning: very high | Competitive risk: medium-high | Radar: raise Orca’s identity / recovery / multi-host weight again.**

**Interaction value: very high.** Suggested question: *Will canonical runId become the shared foreign key for delivery receipts, child work, workspace/host scope, and replay eligibility?*

## 7. CrewAI: a runtime exception can invoke the same Tool twice inside one attempt, creating a real duplicate-side-effect window

**Status: OPEN · one candidate fix for Issue #7449 is PR #7458**

PR [#7458](https://github.com/crewAIInc/crewAI/pull/7458) found that the `try/except` intended only to protect argument-schema filtering in `ToolUsage._use/_ause` also wrapped `tool.invoke()/ainvoke()`. If the Tool itself raises a runtime exception, that exception is mistaken for argument-filter failure and the system calls the same Tool **again inside the same outer attempt**, this time with unfiltered arguments.

This means a failing Tool may execute twice per attempt. A sibling candidate PR for the same issue notes that with the default `_max_parsing_attempts=3`, a persistently failing Tool can therefore be invoked up to six times. For payments, database writes, messaging, or other non-idempotent effects, that is direct duplicate-effect exposure.

The proposed fix keeps only schema extraction/filtering inside the `try/except`, so each outer attempt performs exactly one real invocation. Multiple candidate PRs currently target the same issue, so the bug must not yet be described as fixed on main.

**Why it matters:** a hidden second invocation can exist underneath the high-level retry policy. Counting `attempt_count` alone is insufficient to audit real side effects.

**CodeFlowMu/FCoP relevance:** Tool execution receipts should identify each real invocation rather than only the Agent attempt. If an effect lacks an idempotency key, any implicit re-entry inside one attempt should be treated as a serious governance defect.

**Interaction value: high.** Suggested question: *Will CrewAI assign a stable invocation/effect ID to each actual tool call, so outer retries and real effect counts can be audited independently?*

## Cross-project convergence

Today’s changes suggest a more precise runtime model:

> **“Still in the same job” is no longer proof of authority. User authorization, Run identity, provider session, human principal, sandbox package, pause cause, and tool effect each need their own identity.**

For CodeFlowMu/FCoP, a useful chain is:

**User Intent / Fan-out Authorization → Role & Run Identity → Human Principal / Credential Scope → Host & Package Identity → Call-time Admission → Effect Invocation Identity → Evidence-driven Settlement / Replay Eligibility**.

Three conclusions are especially worth turning into durable engineering rules:

1. **Without positive evidence, preserve Unknown; do not infer failure from absence.**
2. **Pause/Stop is a reversible control decision, not business failure.**
3. **One Agent attempt and one real Tool effect are not the same counting unit.**
