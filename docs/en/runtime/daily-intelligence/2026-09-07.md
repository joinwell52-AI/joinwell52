# Agent Research & Competitor Intelligence · 2026-09-07

> Asia/Shanghai · Only meaningful technical or product developments are included.

## Daily conclusion

The strongest convergence today is that **Agent runtimes are moving their final safety checks closer to the real side-effect boundary, while capability declarations, execution ownership, and action semantics are becoming explicit, verifiable contracts.**

## 1. OpenAI Codex: single-writer sessions, managed Windows process control, and human verification

**Status: MERGED / MERGED / MERGED (capability still gated)**

- PR [#43253](https://github.com/openai/codex/pull/43253) introduces a clear **single-writer lease / multi-reader observation** model for conversation resume. A second instance no longer steals write ownership and instead receives a read-only snapshot until the active writer is released.
- PR [#43308](https://github.com/openai/codex/pull/43308) moves managed Windows app-server shutdown to a local control socket and binds the shutdown request to the server PID before entering the existing drain flow.
- PR [#43289](https://github.com/openai/codex/pull/43289) adds protocol handling for MCP `openai/userVerification`, with explicit capability negotiation plus proof-size, format, cancellation, and capacity limits. The capability was not yet fully activated in the product at this point.

**Why it matters:** conversation ownership, process control, and human verification are becoming capability-gated, identity-bound runtime objects rather than loose state.

**CodeFlowMu/FCoP relevance:** a runtime should distinguish **Writer Lease / Observer Access / Host Process Identity / Human Verification Receipt** rather than collapsing them into `Running`.

**Interaction value: high.** Suggested question: *Will user-verification proofs eventually be bound to the active writer/authority epoch so a proof obtained under one owner cannot survive a writer handoff?*

## 2. OpenAI Agents SDK: tool names are not effect contracts

**Status: OPEN / OPEN**

- PR [#4893](https://github.com/openai/openai-agents-python/pull/4893) identifies that `*** Add File:` may overwrite an existing destination while still reporting `Created`. The proposed fix requires create-only semantics to prove non-existence first.
- PR [#4894](https://github.com/openai/openai-agents-python/pull/4894) identifies delimiter injection in S3 mount option construction, where one input field may expand into additional mount capabilities.

**Why it matters:** `create` must not silently mean upsert, and one configuration field must not become a second hidden capability.

**CodeFlowMu/FCoP relevance:** authorization should reason over **normalized effect semantics**, not tool labels.

**Interaction value: high.** Suggested question: *Would you expose normalized effect classes so authorization can distinguish create-only, overwrite, and mount-policy mutation without reverse-engineering arguments?*

## 3. AG2: MCP Apps introduce tools callable by an app but invisible to the model

**Status: OPEN**

PR [#3235](https://github.com/ag2ai/ag2/pull/3235) adds MCP Apps support to the AG2 Agent Server, including UI resources, `structuredContent`, extension negotiation, and app sandbox policies such as CSP and permissions.

The key design is `visibility=["app"]`: a tool may be invoked by a button in the MCP App while remaining hidden from the model.

**Why it matters:** MCP now has at least two distinct invocation paths: `Model → Tool` and `Human → App UI → Tool`.

**CodeFlowMu/FCoP relevance:** approval, execute, retry, and revoke buttons in a Digital Employee console should be treated as formal invocation principals, not as UI shortcuts around the protocol.

**Interaction value: very high.** Suggested question: *For app-only tools, do you plan to expose distinct invocation-principal / user-gesture provenance so audit can distinguish model-selected calls from human UI actions?*

## 4. Paperclip: pre-start admission, plugin capability escalation, and recovery failures

**Status: OPEN / OPEN / OPEN**

- PR [#12949](https://github.com/paperclipai/paperclip/pull/12949) introduces a **pre-start admission hook** after run claim but before adapter/native runner/provider startup. In enforce mode, stale or missing telemetry fails closed, and a veto guarantees zero provider calls.
- PR [#12928](https://github.com/paperclipai/paperclip/pull/12928) moves new plugin capabilities into `upgrade_pending` until an operator explicitly approves the expanded grant, while also detecting manifest drift.
- PR [#12946](https://github.com/paperclipai/paperclip/pull/12946) addresses production issues including stale Running state after lease release, continuation retries bypassing caps, API aborts reported as success, and evidence errors in cross-issue guards.

**Why it matters:** Paperclip is converging on `Declared Capability → Approved Grant → Pre-start Admission → Run Ownership → Provider Effect → Recovery Classification`.

**CodeFlowMu/FCoP relevance:** this overlaps directly with Host admission, call-time authorization, and recovery governance.

**Learning: very high | Competitive risk: very high | Radar: keep as a first-line runtime competitor.**

**Interaction value: very high.** Suggested question: *Will pre-start admission be bound to an authority epoch/effect receipt so a queued run cannot execute after telemetry or capability grants materially change?*

## 5. GitHub MCP Server: exact patching rejects fuzzy writes

**Status: DRAFT**

Draft PR [#3232](https://github.com/github/github-mcp-server/pull/3232) proposes `apply_file_patch` after an incident where a large full-file replacement was truncated upstream. The new operation requires exact `expected_head_sha` and `expected_blob_sha`, exact match counts for `old_text`, rejects fuzzy matching and unsafe patch shapes, and updates branches with `force=false` so concurrent changes fail instead of being overwritten.

**Why it matters:** a write now carries explicit effect preconditions: the branch and blob must still be exactly what the caller expected.

**CodeFlowMu/FCoP relevance:** strongly aligned with linearizability, idempotency, atomic updates, and effect preconditions.

**Interaction value: high.** Suggested question: *Would you return a durable effect receipt containing expected head/blob and resulting commit/blob so the precondition-to-effect transition is directly auditable?*

## 6. Orca: Unknown can converge only through positive evidence

**Status: MERGED / OPEN / OPEN**

- PR [#19140](https://github.com/stablyai/orca/pull/19140) allows a durable message state to advance from `unknown` to `accepted` when a later provider echo proves delivery, without issuing a second dispatch.
- PR [#19149](https://github.com/stablyai/orca/pull/19149) adds process creation-time evidence to Windows PID ancestry checks so PID reuse is not mistaken for process identity.
- PR [#19155](https://github.com/stablyai/orca/pull/19155) allows a native session lease to be released when provider-root death is positively proven and no known-live descendants remain, while preserving uncertainty about descendant cleanup; lease expiry itself does not prove death.

**Why it matters:** Unknown may be settled later, but timeout, lease expiry, or a PID value alone cannot become evidence of success, delivery, or death.

**CodeFlowMu/FCoP relevance:** recovery should use evidence-driven settlement rather than binary timeout-derived inference.

**Learning: very high | Competitive risk: medium-high | Radar: increase Orca’s long-running / Windows / recovery weight.**

**Interaction value: high.** Suggested question: *Do you plan to converge delivery and process/lease evidence onto one general transition model where `unknown → accepted/dead` requires a named positive observation?*

## Cross-project convergence

> **A safe Agent runtime does not check once and trust forever. It repeatedly re-proves, closer to the side-effect boundary, that the object is still the same object, the capability is still the same grant, the owner still owns execution, and the preconditions still hold.**

A useful CodeFlowMu/FCoP execution chain is:

**Capability Grant → Admission Decision → Effect Preconditions → Call-time Authority → Effect Receipt → Evidence-driven Settlement**.
