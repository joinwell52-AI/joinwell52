# Agent Research & Competitor Intelligence · 2026-09-09

> Only meaningful new developments are recorded. Primary sources are preferred: maintainers, official engineering posts, GitHub PRs/issues/releases, and original project documentation.

## Daily takeaway

The strongest shared direction today is that **Agent runtimes are moving the final safety check closer to the real side-effect boundary, while capability declarations, execution ownership, effect semantics, and recovery evidence are becoming explicit contracts.**

For CodeFlowMu/FCoP, the execution chain increasingly looks like:

**Capability Grant → Admission Decision → Effect Preconditions → Call-time Authority → Effect Receipt → Evidence-driven Settlement**.

## 1. OpenAI Codex — single-writer conversations and identity-bound process control

PR #43253 makes a conversation single-writer: if an active writer already owns the conversation, another resume becomes a read-only history view instead of competing for write authority. PR #43308 moves Windows managed app-server shutdown onto a local control socket and requires the Server PID to match before drain begins. PR #43289 adds MCP `openai/userVerification` protocol handling behind an explicit client capability gate.

**Why it matters:** `Running` is not enough to describe authority. Production runtimes need distinct Writer Lease, Observer Access, Host Process Identity, and Human Verification Receipt concepts.

**Interaction angle:** *Will user-verification proofs eventually be bound to the active writer/authority epoch, so a proof obtained by one conversation owner cannot survive a writer handoff?*

Sources: [#43253](https://github.com/openai/codex/pull/43253) · [#43308](https://github.com/openai/codex/pull/43308) · [#43289](https://github.com/openai/codex/pull/43289)

## 2. OpenAI Agents SDK — tool names are not effect contracts

PR #4893 reports that `apply_patch` Add File may overwrite an existing destination while still reporting `Created`; the proposed fix makes create-only semantics require proof that the destination does not exist. PR #4894 reports delimiter injection into sandbox S3 Files mount options, where one argument value can expand into an extra mount capability.

**Why it matters:** authorization cannot rely on tool names alone. It needs normalized effect classes such as create-only, overwrite, or mount-policy mutation.

**Status:** both PRs are OPEN and are not yet released behavior.

Sources: [#4893](https://github.com/openai/openai-agents-python/pull/4893) · [#4894](https://github.com/openai/openai-agents-python/pull/4894)

## 3. AG2 — MCP Apps introduce an app-only invocation principal

PR #3235 is adding MCP Apps support. UI documents are resources bound to tools, and UI metadata is only delivered when the client declares rendering support. The important design point is `visibility=["app"]`: an MCP App can invoke a tool that the model never sees.

**Why it matters:** the system now has at least two invocation paths—Model → Tool and Human → App UI → Tool. App-only tools need their own principal, user-gesture provenance, and authorization evidence.

**Status:** OPEN.

Source: [AG2 #3235](https://github.com/ag2ai/ag2/pull/3235)

## 4. Paperclip — pre-start admission and plugin capability escalation

Paperclip remains one of the highest-priority competitors. PR #12949 introduces a pre-start admission hook after a run is claimed but before adapter/native runner/provider side effects begin; enforcement fails closed on missing, stale, or invalid telemetry. PR #12928 treats plugin upgrades that add capabilities as `upgrade_pending` instead of silently extending the existing grant. PR #12946 records real production problems involving lease release, runaway continuation, false success classification, and incorrect cross-issue evidence.

**Why it matters:** Paperclip is converging on a full runtime governance chain: Declared Capability → Approved Grant → Pre-start Admission → Run Ownership → Provider Effect → Recovery Classification.

**Competitor view:** learning value very high; risk very high; continue treating Paperclip as a first-tier runtime control-plane competitor.

**Status:** these PRs are still OPEN.

Sources: [#12949](https://github.com/paperclipai/paperclip/pull/12949) · [#12928](https://github.com/paperclipai/paperclip/pull/12928) · [#12946](https://github.com/paperclipai/paperclip/pull/12946)

## 5. GitHub MCP Server — exact patching requires proof of preconditions

Draft PR #3232 adds `apply_file_patch`, requiring exact `expected_head_sha` and `expected_blob_sha`; patch matches must be exact, fuzzy matching and guessing are rejected, and branch updates use `force=false` so concurrent changes fail rather than overwrite newer facts.

**Why it matters:** file writes become preconditioned effects: “I expect branch X and blob Y; only if both remain true may I produce Z.” This maps directly to concurrency linearization, idempotency, and effect preconditions in FCoP 4.0.

**Status:** DRAFT.

Source: [GitHub MCP Server #3232](https://github.com/github/github-mcp-server/pull/3232)

## 6. Orca — unknown state converges only through positive evidence

Merged PR #19140 lets a previously `unknown` message-delivery record advance to `accepted` when a late provider echo proves the original submission arrived, without dispatching a second message. Open PR #19149 combines PID and creation-time ordering to avoid Windows PID-reuse ancestry errors. Open PR #19155 explicitly says lease expiry cannot prove an owner died; lease release requires positive root-death evidence and descendant-state evidence.

**Why it matters:** unknown may converge through positive evidence, but timeout, lease expiry, and “process not observed” cannot manufacture facts.

**Competitor view:** Orca's long-running, Windows, and recovery weight should keep increasing.

Sources: [#19140](https://github.com/stablyai/orca/pull/19140) · [#19149](https://github.com/stablyai/orca/pull/19149) · [#19155](https://github.com/stablyai/orca/pull/19155)

## Cross-project judgment

> **A safe Agent system is not one that checks once and trusts forever. It repeatedly proves, closer and closer to the side-effect boundary, that the object is still the same object, the capability is still the granted capability, the owner is still the owner, and the effect preconditions still hold.**

For CodeFlowMu/FCoP, six distinct stages should remain visible:

1. **Capability Grant**
2. **Admission Decision**
3. **Effect Preconditions**
4. **Call-time Authority**
5. **Effect Receipt**
6. **Evidence-driven Settlement**

A settlement must be allowed to remain **unknown** until named evidence moves it to a confirmed state; retry, timeout, or absence of evidence must not silently rewrite it as failure.
