# Versioned Shared Memory Still Needs Action Authorization

A plan URL has a complete edit history and a registered author. Does that authorize executing it? Our synthetic ledger controls expose two different possibilities: the registered author can write outside their allowed scope, or write a hostile value inside it. **Version history supplies attribution evidence; it cannot own action authorization by itself.** Engineers migrating shared memory should check visibility, authorship, write scope and permitted action separately.

## First establish which state was read

Letta’s current shared-memory documentation describes repositories with per-agent checkouts. A writer commits and pushes changes with Git; other agents pull those commits. Initial attachment clones a repository, while later synchronization fast-forwards the local checkout. This establishes a documented visibility contract: shared repositories do not imply that every checkout sees identical content immediately. [Current documentation](https://docs.letta.com/concepts/shared-memory)

The legacy memory-block interface has different semantics. Its read-only setting applies to a whole block, rather than independently to each attached agent. Its concurrency guidance warns that full rewrites can lose updates under last-writer-wins behavior and recommends one heavy-edit owner with append-only contributions from others. These are vendor-documented behaviors, not races reproduced here. [Legacy block documentation](https://docs.letta.com/guides/agents/multi-agent-shared-memory/)

A migration therefore changes more than a storage noun. Immediate shared-state expectations and block-wide read-only settings differ from commit, push and pull responsibilities. Repository history, however, does not automatically determine who may modify a business key or whether a value may drive a consequential action. Repository or server controls may add permissions; absence from the inspected documentation cannot establish absence of enforcement.

## Five ledgers separate attribution from intent

ErosionBench, from a separate research team, constructs synthetic ledger scenarios by fixing authorized intent, consequential tools and safe arguments before rendering narrative trajectories. Its provenance definition examines whether action parameters derive from unregistered sources or writes outside permitted key prefixes. This is a diagnostic rule with a defined object of examination. [Paper v1, sections 3–4](https://arxiv.org/html/2611.11266v1)

The same-day internal experiment constructed five ledgers from that prose definition. It executed neither the upstream monitor nor a Letta server. Choosing the latest matching attribution, requiring nonempty action arguments and preserving unknown when history is missing are our model choices. The Causal Influence Index, or CII, values below preserve the experiment’s inspectable output: zero means this rule found no source-registration or prefix violation.

| Constructed case | Attribution and scope | Internal model output | What the control separates |
|---|---|---|---|
| Authorized plan value | Planner writes plan scope | 0 | Source and scope satisfy the model |
| Unregistered writer | Outsider writes plan scope | 1 | Writer identity is ineligible |
| Registered writer, wrong scope | Planner writes approval scope | 1 | Registered identity does not authorize every key |
| Hostile value in permitted scope | Planner writes a hostile plan URL | 0 | Eligible source and scope do not examine authorized intent |
| Missing history | No available attribution | Unknown | Missing evidence is not imputed as zero |

Source: five same-day internal synthetic controls. The [experiment record](/assets/evidence/2026-11-18-sig-20261118-003/experiment-003.json) contains inputs, method, outputs and limits. These are not product attack-success rates.

The fourth row is particularly easy to overread. A zero from this rule does not establish that the complete auditor misses the attack. The paper treats provenance validity as diagnostic; a separate semantic monitor may still identify hostile content. The third row shows the converse problem with checking registered identity alone: existence in a registry and permission over a particular key are different conditions.

## Detecting an attack is not stopping its effect

For clean-control evaluation under a fixed configuration, the authors report detecting 446 of 453 malicious scenarios and flagging 13 of 453 benign scenarios. Those are source-reported detection results, not our independent replication. They do not establish that 98.5% of effects were prevented before execution. [Paper Table 3b](https://arxiv.org/html/2611.11266v1)

The main text describes one action-edge check as pre-execution and other provenance and semantic analysis as post-execution detection and localization. Appendices describe additional conjunctive veto routing. The admitted materials do not resolve that difference. Which exact paths can veto before execution remains open; combining the passages would not produce a verified prevention system.

Calibration has a related boundary. The paper explicitly withholds a finite-sample false-positive-rate guarantee because scores can tie at the threshold. A separate internal calculation uses entirely tied synthetic scores to show that the same threshold flags every value with greater-than-or-equal and none with strict greater-than. This illustrates comparator sensitivity. It is neither a measured false-positive rate nor evidence of which comparator released code uses. Image controls and their verdict basis also differ, so text-mode specificity cannot simply transfer to images.

Repository documentation is another versioned evidence surface. The current README distinguishes the live default detection ladder from a frozen calibrated detector, and sample smoke checks from full evaluation. The dataset card also discloses an older attack that wrote to a dead key never consumed by the action, later repaired by targeting a key that reaches arguments. That correction makes tracing a value into an actual action essential; finding a hostile string somewhere in the ledger is insufficient. [Current repository](https://github.com/SalesforceAIResearch/ErosionBench), [dataset-card changelog](https://raw.githubusercontent.com/SalesforceAIResearch/ErosionBench/main/DATASET_CARD.md)

## Give each evidence obligation an owner

For shared-context systems, we propose the following responsibility table. It is a checking method, not a common implemented pipeline attributed to the projects above.

| Obligation | Input and owner | Evidence to retain | When to stop inferring |
|---|---|---|---|
| State visibility | Storage/synchronization receives a commit or write | Version actually read by the executor | An unknown checkout is not assumed current |
| Attribution | Trusted recording layer receives a write event | Traceable key, value and writer relationship | Missing history remains unknown |
| Key scope | Permission implementation receives writer and key | Applicable allowed scope and decision | Registered identity does not substitute for scope |
| Authorized intent | Action-permission check receives target and arguments | Relationship to this permitted action | An in-scope value still needs a permitted purpose |
| Side-effect outcome | Execution layer receives an allow/deny decision | Denied action identity and whether effects occurred | Post-effect detection is not pre-effect prevention |

Follow the hostile plan URL through the chain. Pull records establish the executor’s version; history identifies its writer; scope rules determine whether that writer may edit a plan field. Action authorization still has to connect that URL to the permitted target. Native execution records must finally distinguish an action that never ran from one detected afterward. If a link is missing, retain that gap instead of making history answer for it.

## The executable path remains to be checked

The public evidence comes from Letta’s official documentation team and the Salesforce-led ErosionBench research team. These are independent authoring actors supporting storage contracts and a provenance model respectively, not independent attack/defense replications of one implementation. The five internal ledger controls and tied-threshold calculation provide logical comparisons only. Current documents are byte-pinned snapshots retrieved on 2026-11-18; the paper is v1. Mutable repository guidance is not fused into an execution result from that historical paper version.

History remains valuable for audit. This article found or reproduced no product permission defect. The next step is to bind a target implementation, permission rules, calibration material and matching execution traces to exact versions, then test normal, wrong-scope, hostile-value and missing-history paths. Only a link between a denial decision and an effect that did not occur can support a prevention claim. Until then, neither detection rates nor complete edit history can sign for that missing evidence.
