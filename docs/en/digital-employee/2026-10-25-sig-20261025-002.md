# What did review equality compare? A bounded proposal-set experiment

Changing a retraction target left equality unchanged; changing the text produced a mismatch. This control in our internal experiment raises a precise question: does agreement after review cover the whole edit object, or only part of it?

We executed a ten-line comparison block from the retrieved source and observed that it compares sets of three-field projections. The bounded conclusion is that equality of selected fields is not identity of the complete edit object. The probe did not perform an edit or establish a path that bypasses a protected target.

## The object shrinks before comparison

The case concerns prompt evolution in quant-agent. Its paper describes restricted editable targets and a requirement to apply a saved, reviewed reflection. These are mechanisms described by the project's public materials, rather than an exhaustive account of safeguards in a current deployment.[1][2]

The extracted block maps staged and saved proposals into sets. Each element retains only agent name, operation and learning text. Other fields, including the retraction target hash, are absent from the tuple. Set construction also collapses duplicate elements and discards input order. This expression illustrates the representation, rather than the complete editor:

```python
{(agent_name, operation, learning_text) for proposal in proposals}
```

Equality therefore starts as equality in this reduced representation. Reading it as complete-object identity requires additional premises: omitted fields cannot change the authorized object, and multiplicity and order cannot change relevant semantics. Set equality alone does not establish those premises.[2]

## Five probes, including a change the check detects

The same-day Analysis stage executed the literal comparison block with synthetic proposals. It retained an identical-input control and a changed-text control. The local environment used Python 3.13.15 on 2026-10-25; expected comparison results were encoded in the probe script before execution.[3]

- Identical proposals produced no mismatch.
- Changed learning text produced a mismatch: the check was not simply returning equality for every input.
- A changed retraction target hash produced no mismatch.
- Duplicating one proposal into two identical proposals produced no mismatch.
- Reversing two distinct proposals produced no mismatch.

The final three results are not three confirmed execution failures. The first follows from a field omitted by projection; the other two follow from set semantics. Together they bound the promise made by this comparison. The complete model's input rejection, any separate canonical-file binding and the effect on actual edits were not executed.[3]

## Object identity, adoption and benefit are separate questions

The comparison can be useful for the content it actually compares. If another constraint makes a retraction target unique, or a later path independently binds the object, this check may serve a supporting role. We did not run those paths and cannot declare the whole review mechanism ineffective.

The existence of other checks also cannot stand in for examining complete-object binding. An inspectable review contract should state its fields, treatment of duplicates and order, and the object ultimately consumed by the edit entry point. Object identity, admissibility, behavioral adoption and outcome benefit need separate checks.

The paper's replay results illustrate why those questions cannot be exchanged. The authors report the prescribed form in 5/20 selected Q3 trigger outputs versus 0/20 at baseline. This measures adoption on selected inputs, rather than improved return. We did not reproduce that replay or use the set experiment to explain trading performance.[1, section 5.4 and Table 9]

## Version and execution boundaries still unresolved

The retrieved model fragment has a 200-character ceiling; the paper describes 300 in a later cycle. Editor and model fragments came from different cached snapshots. They cannot be assembled into a build established as equivalent to the paper deployment. Likewise, the README's ten-invariant description versus twelve in the appendix and editor declaration is not evidence that the source lacks two invariants.[1][2]

No prompt files, complete model validators or saved-reflection entry points were exercised. Whether duplicates or ordering affect real execution remains untested. The next discriminating check would pin one immutable commit and trace the reviewed object into the final edit entry point, including any independent binding. Until then, the conclusion concerns the representation's boundary.
