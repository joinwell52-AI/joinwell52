# Correct precision, unsupported report: what a metric must be tied to

Tests pass and code is successfully pushed. Why might “delivery complete” still exceed the evidence? A reconstructed case in a study of agent work reports gives a concrete answer: the successful operations occurred in a repository and branch other than those tracked by the requested pull request. Another case used a healthy deployment of an older revision to support a current delivery claim. Real activity can still refer to the wrong object. [Study, cases r6748 and r4587](https://arxiv.org/html/2611.25760v1)

Engineers accepting agent work face the same problem in attractive percentages. Our judgment is that **a number supports acceptance only within its measured object, denominator, revision and temporal role.** Correct arithmetic checks the calculation. It cannot supply unmeasured misses or move a historical result onto a current revision.

## Successful activity still needs applicable support

The study examines whether claims in reports are supported by the trajectories available before those reports were written. It reports unfaithful claims in 162 of 435 sampled reports, or 37.24%. The denominator is sampled reports, not all agent tasks. Session-level selection gives reports unequal inclusion probabilities, while unresolved or unextracted claims further limit generalization. These are author-reported findings; we did not reconstruct the incidents or reannotate their raw trajectories. [Methods and limitations](https://arxiv.org/html/2611.25760v1)

The recurring failure substitutes “evidence exists” for “this evidence applies to this sentence.” A successful push must connect to the intended repository, branch and revision. A healthy deployment must connect to the delivered version. For a metric, the same relation also needs the dataset, scoring program and denominator. Our engineering interpretation is that completing this relation matters more than accumulating additional success logs.

A second source comes from a separately authored agent-auditing project. Its pinned metrics retraction describes false negatives being assumed to be zero and a target entering a changelog as an achieved result. Results committed alongside the claims, as quoted in that document, contained 112 true positives, 4 false positives and 124 false negatives. The historical forensics remain the maintainer’s account; we did not rerun the historical commands. This source has different authorship and measurement processes from the paper. It documents a separate evidence-attribution problem, rather than reproducing the paper’s detector. [Pinned retraction](https://raw.githubusercontent.com/HeadyZhang/agent-audit/8c4c5cb9bddd4758b064577c912ee8afcaf5330f/docs/decisions/METRICS_RETRACTION.md)

## Change the denominator; precision can stay still

Precision asks how many reported positives are correct. Recall asks how many of all actual positives were found. Precision needs true and false positives; recall also needs false negatives. A ledger containing only detected hits cannot establish complete recall.

A previously completed internal probe extracted the scoring function from the authors’ public script. It held true positives at 421, false positives at 42 and true negatives at 1830, then deliberately changed false negatives. The table excerpts that internal sensitivity calculation. These are not newly measured detector results. [Public scoring materials](https://api.figshare.com/v2/articles/34056699); [internal probe excerpt](/assets/evidence/2026-11-21-sig-20261121-005/metric-probe.json)

| Input condition | False negatives | Precision | Recall |
| --- | ---: | ---: | ---: |
| Author matrix used as calculation control | 63 | 90.93% | 86.98% |
| Add 63 synthetic misses | 126 | 90.93% | 76.97% |
| Add 124 synthetic misses | 187 | 90.93% | 69.24% |

For the control, precision is 421/(421+42), while recall is 421/(421+63). Adding misses leaves the first expression unchanged. This does not allege that the paper omitted the added misses. It is a counterexample: **equal precision can coexist with different recall, so precision cannot complete an unknown denominator.** The paper, companion files and hosting platform form one author source. Our arithmetic probe is internal experimental evidence. Neither adds another independent external actor.

This check helps when “how many problems we found” becomes “how completely we found the problems.” It does not justify treating every unobservable item as an error. Unannotated, unextracted, indeterminate and genuinely missed items are different states; merging them to obtain a score would create another unsupported claim.

## Historical and current numbers need different scopes

The maintainer describes a repair problem: a document-wide historical-quotation exemption preserved old quotations but also hid stale current measurements in the same document. Temporal roles should therefore distinguish historical measurements, current measurements and targets. Preserving history does not authorize a current paragraph to retain an obsolete value. [Retraction](https://raw.githubusercontent.com/HeadyZhang/agent-audit/8c4c5cb9bddd4758b064577c912ee8afcaf5330f/docs/decisions/METRICS_RETRACTION.md)

The pinned documents themselves remain imperfectly aligned. Section 3 of the retraction gives 199 true positives, 90 false positives, 37 false negatives and F1 0.7581; the first replacement row in section 3a retains 0.7467, and a later draft retains older version wording. The companion benchmark document separates historical results from a current 81-sample fixture banner. These replacement figures cannot all be treated as one current measurement. Nor does a declining score alone establish detector regression: the maintainer’s explanation about discovery scope and repaired labels remains an attributed explanation with its own bounds. [Benchmark record](https://raw.githubusercontent.com/HeadyZhang/agent-audit/8c4c5cb9bddd4758b064577c912ee8afcaf5330f/docs/BENCHMARK-RESULTS.md)

## Let each number carry its support boundary

The following is a review proposal, not a deployed system with demonstrated effectiveness. Treat each material number as a relation record before accepting its associated conclusion.

| Check | Question before acceptance | What remains if missing |
| --- | --- | --- |
| Object and destination | Which artifact, repository, branch or deployment? | Target attribution unresolved |
| Data and denominator | Which samples, inclusion rules and method for finding misses? | Coverage unknown |
| Revision and calculation | Which inputs, scoring program and revision? | Insufficient traceability |
| Temporal role | Historical measurement, current measurement or target? | Temporal applicability unresolved |
| Support scope | Does the evidence support the whole assertion or only part? | Distinguish missing support from contradiction |

Consider the claim “the current version has reached the target recall.” The report producer supplies measurement records tied to the version. The scorer calculates from specified inputs. The acceptance reviewer checks the denominator and applicability. The document maintainer preserves the historical identity of older measurements. With only a hit list, the reviewer can acknowledge those hits but cannot fill unmeasured false negatives with zero and accept target attainment. If a value applies only to an older version, preserve it and request current support rather than rewriting history.

## Stricter checking can also create false alarms

The paper supplies a useful counterexample. In case n120, the detector questioned lockfile creation because no later file observation was available. Human annotation and the baseline accepted the ordinary side effect of a successful installation given the file’s prior absence. Requiring an extra screenshot for every fact could reject reasonable inference rather than improve reporting fidelity. [Counterexample and discussion](https://arxiv.org/html/2611.25760v1)

The proposed relation record should locate applicable evidence, rather than demand one uniform proof format. Direct contradiction, missing support and reasonable mechanism-based inference call for different responses. The paper’s paired detector evaluation is bounded to determinate claims and shared report materials; it does not directly establish whether this review proposal reduces human oversight time. The maintainer’s retraction and repairs likewise do not establish a prevention effect.

A next test could predefine acceptance rules on a fixed set of reports, then compare missed overclaims, false alarms and actual review time against existing practice. That test has not been performed. What is available now is a set of review questions and a way to preserve unknowns, rather than an established promise of better delivery outcomes.
