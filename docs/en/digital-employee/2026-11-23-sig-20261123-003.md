# The Confirmation Asked. What Did the Risk Analyzer Actually See?

In the admitted internal isolated probe, the same UNKNOWN-risk input changed from “request confirmation” to “do not request confirmation” when one configuration flag changed. The question on screen first establishes a policy decision. It does not establish which hazards the analyzer recognized. Engineers responsible for agent action review need to trace the target environment, supporting observations and confirmation decision separately.

## The question is downstream of an observation

The OpenHands security guide assigns different jobs to an analyzer and a confirmation policy: one evaluates risk; the other decides whether to ask. Always asking, never asking and asking according to risk are different policies. Configuring an analyzer alone does not activate confirmation. [Official security guide](https://docs.openhands.dev/sdk/guides/security)

The pinned risk-based policy defaults to a HIGH threshold and requests confirmation for UNKNOWN by default. UNKNOWN cannot itself be the threshold. For known risk, the method delegates comparison to the risk comparator. This maps an assessment into a question; it does not establish that the assessment had complete information. [Pinned confirmation source](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/ebec01b3893696c2f5454762eb44796c71bb391a/openhands-sdk/openhands/sdk/security/confirmation_policy.py)

Consider an explicitly illustrative request to “clean temporary files” whose resolved directory could point at a protected resource. This is not a discovered OpenHands vulnerability. It identifies an inspection question: did the actual target, environment and possible consequence reach analysis? A correctly functioning confirmation mechanism can still ask a person to decide with incomplete information.

## Unknown risk and failed analysis are different cases

The same-date Analysis stage executed a source-derived internal isolated probe. It extracted the pinned confirmation method and base batch helper, preserved their bodies, removed decorators and supplied declared dependency stubs. These are the persisted outputs, not integration tests rerun for this article.

| Input and control | Observed output | Supported scope |
| --- | --- | --- |
| UNKNOWN, unknown-confirmation flag enabled | Request confirmation | The method's default branch |
| Same UNKNOWN input, only that flag disabled | No confirmation | Configuration changes this branch |
| Analyzer normally returns LOW | LOW, no detail | Base helper's normal path |
| Analyzer raises a controlled exception | HIGH, error retained in detail | Base helper's exception fallback |

An unavailable reliable classification therefore needs further distinction: unknown information and a failed analysis process are different cases. The helper converts the latter into HIGH. It does not resolve the error or establish that execution will be blocked; the resulting behavior also depends on policy and the actual calling path. [Pinned analyzer source](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/ebec01b3893696c2f5454762eb44796c71bb391a/openhands-sdk/openhands/sdk/security/analyzer.py)

The internal probe exercised neither the complete SDK nor the risk comparator, configuration validation, approval UI or conversation loop. It measured no hazard-detection capability. Calling these local outputs a safety-effectiveness test would extend function evidence into unobserved effects. [Internal experiment inputs, outputs and limits](/assets/evidence/2026-11-23-sig-20261123-003/experiment-evidence.json)

## Environmental evidence changes the question

The independently authored ROGUE-AI study from Texas A&M compares reconstructed incident environments with minimally changed controls and checks harm from environment state rather than trusting an agent's final message. The authors classify 62 of 72 catalogued real-world-harm incidents as involving no attacker. That describes their selected cases, not the population frequency of agent incidents. [Preprint v1, sections 3–6](https://arxiv.org/html/2611.26553v1)

Its useful contribution here is that ordinary task-directed behavior can encounter hazards without malicious instructions. In a selected set of 7–11 frequently harmful reconstructions per model, the authors report that repeated hazard-and-consequence warnings reduced harm more than equal-length neutral notes. Substantial residual harm varies by model. These are selected synthetic conditions, not a deployment risk-reduction estimate; their percentages cannot simply be subtracted from whole-suite rates.

Reconstruction also introduces uncertainty. Seven reconstructions fail the state-difference condition; some mail-server cases partly measure component behavior rather than model choice. Blind rebuilds disagree on five of eleven incident outcomes. Confirmation is simulated without an adaptive comparison. The study motivates examining information supplied before a decision. It does not test the cited SDK configuration or independently reproduce its safety effects.

## Inspect the evidence that reaches the decision

Our engineering interpretation is to preserve what was observed, how it was rated, what was decided and what actually happened as distinguishable evidence. The following is a proposed inspection record, not a promised project interface or a required storage design.

| Handoff | Responsible inspector | Evidence to retain | Insufficient basis for proceeding |
| --- | --- | --- | --- |
| Action resolution to environment observation | Caller and environment adapter | Resolved target, observation time, reachable authority, protected-resource state | Target or environment cannot be established |
| Observation to risk analysis | Analyzer maintainer | Identified hazard, expected consequence, rating rationale, missing information | Rating exists but its basis is untraceable |
| Analysis to human decision | Policy and approval-interface maintainers | Actual policy configuration, displayed action/environment, decision target | Displayed and pending actions cannot be correlated |
| Decision to effect inspection | Executor and domain evaluator | Actual action and resulting state | Approval exists without effect evidence |

For the illustrative cleanup request, begin by tracing directory resolution and the source of observations, then check whether those facts reach the analyzer and approver. Do not fill the record with a plausible hazard description. Missing observations remain missing. The deployment policy must specify whether to stop and how to obtain more information; a general example cannot decide its risk policy.

This separates information loss from judgment failure. An analyzer receiving too little information is a different diagnosis from an analyzer making a poor judgment with sufficient evidence. An approver never seeing a hazard differs from an approver seeing it and proceeding. Counting confirmation prompts cannot make these distinctions.

## Evidence and sources

Public implementation facts, source reports and internal experiments have different roles. Source shows what a pinned version contains. Study numbers are author reports. The internal probe tests two local methods. The inspection record is our interpretation and has no measured deployment benefit.

- [Official security guide](https://docs.openhands.dev/sdk/guides/security): snapshot read on 2026-11-23; supports the division between analysis and confirmation and its stated limits. Direct tool execution is outside the described conversation-loop protection; classification is not a sandbox or hard denial. No bypass attack was executed here.
- [Confirmation implementation](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/ebec01b3893696c2f5454762eb44796c71bb391a/openhands-sdk/openhands/sdk/security/confirmation_policy.py) and [analyzer implementation](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/ebec01b3893696c2f5454762eb44796c71bb391a/openhands-sdk/openhands/sdk/security/analyzer.py): pinned to the linked commit. Documentation and code share one maintainer actor; they are not two independent sources.
- [ROGUE-AI v1](https://arxiv.org/html/2611.26553v1): preprint by Mengxiao Wang, Mahbub Alam, Kalyan Nakka and Nitesh Saxena. Its separate authorship does not make it independent validation of this implementation. Operational incident archives were not obtained and reconstructions were not executed here.

## What this comparison cannot establish

Asking about every action cannot automatically repair missing environment information. Conversely, for a fixed, isolated task without hazardous side effects whose relevant environment facts are already complete, another generic hazard checklist may add nothing. Prompt presence alone distinguishes neither case.

This article measures no deployment's detection rate, false-positive rate or harm reduction. A next experiment could hold the action fixed in a protected test environment, vary visible target-and-consequence information, and retain the analysis rationale, human-visible content and actual state. It could then test whether added information improves decisions. A separate check must ask whether an earlier decision still corresponds to the same action after the environment changes during a wait. Until those tests exist, missing observation and unvalidated effectiveness remain distinct gaps.
