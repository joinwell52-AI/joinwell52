# A Request Reached Policy. What Intervention Actually Happened?

A tool request reaches a policy checkpoint. What has that established? It does not yet establish that every intervention declared there ran as intended. Platform and security engineers integrating agent policy need two separately reviewable records: which paths reached policy, and what policy actually did to the proposed action.

Comparing a proxy gateway with an in-process action hook makes the distinction concrete. The first asks which interactions mediation can see. The second also asks what intervention meaning survives into execution. These mechanisms can complement each other, while requiring different evidence.

## Routing and action hooks expose different objects

Salesforce's MuleSoft architecture guide describes gateway policies for tools, resources and caller attributes. Its MCP attribute-based access control applies to tools and resources exposed by an MCP server. Its A2A Agent Card policy rewrites the card URL so traffic passes through the governed proxy. Routing is therefore part of the described governance mechanism. [Architecture guide](https://architect.salesforce.com/docs/architect/fundamentals/guide/mulesoft-architecting-agentic-enterprise).

These are the vendor's architectural statements, not our measurements of a deployed network. A documented proxy route does not itself establish coverage of arbitrary local actions.

AgentSpec places a different boundary inside agent execution. Its paper describes intervention before an action, after an observation and at task completion. Static inspection of the pinned real executor shows validation and enforcement before tool action execution. The paper's mechanism and a checked source path must not be combined into a claim of observed execution on every path. [Paper, Section 4](https://arxiv.org/html/2503.18666v3); [pinned executor](https://github.com/haoyuwang99/AgentSpec/blob/e6fa3902e2cfb9681f454b355691b771f70543f8/src/controlled_agent_excector.py), retaining the repository's filename spelling.

| Dimension | Proxy gateway sample | Action-hook sample |
| --- | --- | --- |
| Observed object | Proxied protocol interactions | Instrumented actions, observations and completion events |
| First evidence obligation | Relevant traffic traverses the configured proxy | Relevant actions traverse the inspected hook |
| Further obligation | Actual policy effects under the target configuration | How declared intervention becomes the actual action |

This is our comparison of the two sources, not a product ranking. Consider an illustrative agent that can write files through a remote tool and can also launch a local process. No such bypass was observed here. The example simply asks an acceptance reviewer to identify mediation for both paths instead of treating a log from one as a complete inventory.

## Two callbacks arrive; one value remains

Same-day Analysis executed an internal, isolated method probe at commit `e6fa3902e2cfb9681f454b355691b771f70543f8`. It extracted original methods, removed third-party type annotations while leaving method bodies unchanged, and called them with synthetic contexts. The environment was Python 3.12.9 on Windows, without model or network calls. This article reuses that verified execution; Production performed no additional experiment.

The interpreter's `enterEnforcement` callback reads context text into one member value. The following body excerpt comes from the [pinned source](https://github.com/haoyuwang99/AgentSpec/blob/e6fa3902e2cfb9681f454b355691b771f70543f8/src/interpreter.py#L105-L109):

```python
if self.check:
    self.enforce = ctx.getText()
else:
    self.enforce = "none"
```

The internal probe returned these values. They are retained strings, not executions of the tool effects those strings might select.

| Check | Supplied callback order | Value after each call | Retained value |
| --- | --- | --- | --- |
| True | skip | skip | skip |
| True | skip → stop | skip → stop | stop |
| True | stop → skip | stop → skip | skip |
| False | skip → stop | none → none | none |

Source: [internal method-probe record](/assets/evidence/2026-11-25-sig-20261125-002/method-probe.json). The observation is narrow: the tested callback assigns later text to the same slot, and reversing the supplied order changes the retained value. It rebuts the assumption that entering this method repeatedly necessarily accumulates every intervention.

It does not establish that parsing a real rule produces those callback sequences. The grammar permits multiple enforcement clauses, but this probe did not execute raw rule parsing, rule integration or the complete executor. The harness supplied callback order. Reporting this as “the system drops multiple rules” would conflate clauses with rules and method behavior with end-to-end execution.

## Returning an action does not establish replacement execution

The same internal probe examined two invocation helpers. `InvokeAction.apply` returned the continue marker and the original action object, preserving object identity. Another interpreter helper returned the same fixed traffic-light dictionary for two distinct synthetic requests. The inspected mapping also did not connect the invocation name to that class. [Enforcement implementation](https://github.com/haoyuwang99/AgentSpec/blob/e6fa3902e2cfb9681f454b355691b771f70543f8/src/enforcement.py); [internal record](/assets/evidence/2026-11-25-sig-20261125-002/method-probe.json).

Those observations do not demonstrate a replacement tool invocation. A class name, a returned dictionary and a reachable call chain are different evidence objects. Accepting a replacement action still requires a trace from real rule parsing through the intended implementation to the expected effect at an actual tool.

This is not an established deployment vulnerability. The helpers may represent an unfinished path, and users may rely on other interventions. We did not install the full dependency tree or run real tools, and we do not transfer observations about a virtual executor to the real executor.

## Keep two acceptance records

Our recommendation is to maintain a path-coverage inventory separately from intervention input/output controls. This is a proposed test design, not a unified acceptance feature demonstrated in either sample.

| Record | Minimum contents | Evidence available here |
| --- | --- | --- |
| Path coverage | Effect-capable entry point, actual route or hook, configuration version, mediated and unmediated controls | Documentation and static source observations; no deployment inventory |
| Intervention semantics | Pinned version, original action, declared order, intended composition rule, returned action and actual tool effect | Isolated callback/helper outputs; no real parse or tool-effect trace |

A file-write request can serve as a continuous illustrative fixture. First inventory the protocol-tool and local-process entry points and identify their policy boundaries. For a path known to reach its boundary, test a single intervention, reversed clause order and a false condition separately. If replacement is declared, also inspect the actual tool's parameters and effect. This procedure is a recommendation; it was not executed in this study.

In this proposed responsibility chain, platform maintainers supply entry points and configuration for coverage review; policy authors supply the composition contract and expected output; integrators supply parsing, action and effect records; acceptance reviewers check that both evidence sets refer to the same request. An omitted entry point, unspecified contract or uncheckable effect should suspend that acceptance decision and return the missing evidence, rather than produce a pass.

Do not assume multiple interventions must accumulate. Establish whether the contract requires sequential composition, priority or last-value selection before defining expected output. A discrepancy becomes actionable only against an explicit expected rule. Preserve parse or execution failures and the point reached; absence of an effect must not silently become a successful-policy-block result.

## Evidence and sources

A source-reported statement establishes what its authors describe. A source observation establishes what a pinned file contains. Internal experimental evidence establishes only the tested method behavior under synthetic inputs. None is an independent reproduction or a safety certification.

- [Architecting the Agentic Enterprise with MuleSoft](https://architect.salesforce.com/docs/architect/fundamentals/guide/mulesoft-architecting-agentic-enterprise): official Salesforce architecture documentation supporting the proxy-policy and routing claims. The same-day reading snapshot did not provide an explicit update date.
- [AgentSpec paper, version 3](https://arxiv.org/html/2503.18666v3): the AgentSpec research team's July 31, 2025 version, supporting the hook mechanism and stated limitations. This is a prior-art comparison, not today's release news. Its benchmarks are not new measurements here and do not substitute for local integration acceptance.
- [Pinned implementation](https://github.com/haoyuwang99/AgentSpec/tree/e6fa3902e2cfb9681f454b355691b771f70543f8): implementation evidence from the same research team, grouped with the paper as one actor.
- [Method-probe record](/assets/evidence/2026-11-25-sig-20261125-002/method-probe.json): scope, source excerpts, inputs, actual outputs and limitations of the same-day internal experiment. We reuse completed evidence without rerunning the full framework.

Salesforce and AgentSpec are independent authors supporting different sides of the comparison; they do not validate each other. A paper, its repository and its hosting addresses are not additional independent actors. Publication, citation and review status do not establish theoretical validity; implementation success does not establish general validity.

## Questions for a real parser and real effects

One plausible alternative is that maintainers intend last-value priority. Another is that real parsing does not generate the multiple-callback sequence supplied to the same listener by this probe. Specification and integration evidence are needed to distinguish these explanations; a local assignment cannot exclude them.

The method-level finding therefore does not apply to long-horizon trajectory safety, absence of bypass across all entry points or production reliability. The paper itself distinguishes discrete enforcement from trajectory-based safety analysis.

The most discriminating next test would pass a real rule through a pinned parser and record its composition contract, callback sequence, final action and actual tool effect. A separate deployment inventory would check routing. Only when both evidence chains refer to the same target execution path can a reviewer determine what policy accomplished for that request.
