# Access to a Service Does Not Approve This Operation

Imagine an agent that can reach a restricted service, finds an approval record for the same actor, and checks rules before acting. A platform reviewer still has to ask: was this request approved, or an entire class of work? Comparing the objects bound by three mechanisms produces a practical review matrix. Resource access, operation approval and event predicates answer different questions; evidence at one layer cannot supply another layer’s missing decision.

## Three mechanisms recognize different objects

The captured Model Context Protocol (MCP) authorization specification requires target-resource identifiers in authorization and token requests, along with server-side audience validation. This concerns whether a token is used at its intended resource. It does not define the complete approval lifecycle of each business operation. These are normative requirements, not observations that a deployment complies. [Authorization specification](https://modelcontextprotocol.io/specification/latest/basic/authorization)

SIDJUA supplies a different kind of evidence: implementation of pre-action approval lookup. The inspected pipeline orders forbidden checks, approval, budget, classification and policy. A block or pause short-circuits processing; passing approval can still lead to a later refusal. This is an observation about a pinned path, without an endpoint inventory or bypass test. [Pipeline source](https://raw.githubusercontent.com/GoetzKohlberg/sidjua/747b5bb125c8cc94e7cb99a581dc63bedb2c9bb2/src/pipeline/index.ts)

AgentSpec puts predicates at event checkpoints, with responses including stopping, user inspection, predefined actions and self-examination. Its binding object is a condition observable at that checkpoint. That is neither a token audience nor automatic human consent to a particular operation. [Paper, sections 3.2–4](https://arxiv.org/html/2503.18666v3)

| Layer | Object directly examined | What that evidence leaves unanswered |
| --- | --- | --- |
| Resource authorization | Token target and audience | Whether this operation’s parameters were approved |
| Approval lookup | A row selected by actual query predicates | Whether it concerns this operation, and whether the final effect is allowed |
| Event rules | Conditions at a specified checkpoint | Uninstrumented paths, unexpressed conditions and complete long-horizon trajectories |

This is a table of evidentiary responsibilities, not a security ranking. A specification, implementation and paper mechanism operate at different levels. Their common governance vocabulary does not make their guarantees interchangeable.

## Storing request identity does not make it a lookup predicate

Consider an illustrative request: an actor obtains approval for target A and quantity one, then submits target B and quantity one thousand. A contract for one concrete operation requires examining which fields remain equal. A contract intentionally authorizing a class of work over time instead requires a clearly communicated and recorded scope. Broad reuse is not automatically a vulnerability.

At the pinned commit, the approval lookup selects the latest row by actor, rule, record status and creation time. Request ID, serialized action and division can be stored without participating in the query’s comparisons. A comment describing request-ID matching cannot replace executable predicates. Recent local research has already examined this behavior; it serves here as a diagnostic of layering, not a new discovery. [Approval source](https://raw.githubusercontent.com/GoetzKohlberg/sidjua/747b5bb125c8cc94e7cb99a581dc63bedb2c9bb2/src/pipeline/approval.ts)

The same-run Analysis stage executed nine internal isolated probes. The original function ran through TypeScript erasure against real in-memory SQLite with synthetic requests and rows. A row with different request ID, action and division was selected. Different-actor, different-rule, expired and excluded-status controls were not selected. Pending and denied rows could also be selected across request differences; malformed metadata left the row selected with null metadata. This establishes lookup scope, not permission to perform the operation. The whole application, resume entry points, caller invariants and real effects were not exercised.

[Complete internal probe cases and results](/assets/evidence/2026-11-26-sig-20261126-001/experiment-evidence.json)

The useful audit compares stored fields with decision fields. These probes neither demonstrate a reachable production authorization bypass nor establish a victim incident. Correct resource tokens cannot add a missing comparison to this query; a stricter query cannot replace audience validation either.

## A rule language still depends on what its rules can see

Rules can add operation constraints when their trigger placement and predicates cover the risk. AgentSpec’s authors report 87.26% code-risk enforcement for automatically generated rules and discuss overfitting to enumerated sensitive files. Generated rules perform worse than manual rules in that evaluation. This is author-reported evidence, not locally replicated performance or independent security validation of the approval implementation. [Paper, section 5.3](https://arxiv.org/html/2503.18666v3)

The paper also explicitly limits discrete-checkpoint enforcement: it lacks trajectory-based safety analysis. Correctly checking a visible condition cannot establish arbitrary long-horizon safety. Our interpretation is that a policy language cannot conjure operation identity absent from the data available at its checkpoint. Whether it can fill the gap depends on actual fields, predicates and execution paths. [Paper, section 6.3](https://arxiv.org/html/2503.18666v3)

The three source actors are independently authored and support their own specification, implementation and method. None of these materials reproduces both other systems. Public code, publication and citation add no experiments that were never performed.

## Follow one approval through its responsibilities

For a high-risk write requiring specific human consent, the following is a proposed review method. It is not a lifecycle already implemented jointly by the three sources.

| Stage and responsible actor | Input and output to retain | Stop or ask again when |
| --- | --- | --- |
| Client and resource service | Resource target, token and audience-check result | Target or audience differs |
| Trusted request constructor | Actor, target, canonical parameters and preconditions | Identity or parameter origin is unclear |
| Approver and approval store | Explicit scope, expiry and applicability conditions | Scope is exceeded, time expires or preconditions change |
| Execution entry point | Correspondence between current request and valid approval | Correspondence cannot be established |
| Execution and recovery layers | Consumption record, outcome and retry identity | Retry, repeated consumption and renewed consent cannot be distinguished |

Define single-operation versus scope authorization first. Then change request ID, target, parameters, state and time individually, observing the actual entry point. Separately inspect one-time consumption, replay resistance, revocation races and process, container or operating-system enforcement. An application rule does not establish all these capabilities.

## What these materials cannot decide

A low-risk read-only service may reasonably need only a resource-scoped token. Per-operation human approval is not universally appropriate. Another alternative explanation is intentional workflow-level approval, or caller invariants constraining request reuse. An isolated lookup cannot exclude either possibility.

This assessment uses the same-date captured specification page, paper version and pinned code. The specification’s latest URL moves; the retained extraction hash bounds the observation. Approval source is pinned to commit 747b5bb125c8cc94e7cb99a581dc63bedb2c9bb2. No deployed token audit, concurrent-revocation test, all-entry refusal test, host-isolation test or full lifecycle test was performed.

The next step is to establish the maintainer’s intended scope, then exercise real request and resume entry points with old approvals against changed parameters and with revocation racing execution. Those observations are needed to move from lookup-level to operation-level judgment. The current deliverable is a layered review method, not whole-system security certification.
