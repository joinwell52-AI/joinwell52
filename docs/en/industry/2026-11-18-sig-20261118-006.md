# Why Did the String “False” Earn Completion Credit?

A value that says “not found” can earn different progress depending on its type. In our isolated probe, one documented function awarded a record-read milestone for the string `"false"`, while boolean `false` remained partial. The consequential moment is the conversion from tool output to evidence: **truthiness cannot substitute for a type contract**. Adapter authors can use this example to locate who guarantees a field’s type and who must reject malformed values.

## One conversion changes what the field means

The current MedHarnessBench runner documentation includes a read-result resolver. Its `resolve_read` function extracts `found` from an event, converts it with Python’s truth-value operation, and uses that result to decide whether to add the `record_read` milestone. This expression is an exact field-level excerpt from the [runner documentation](https://raw.githubusercontent.com/Tomry1114/Awesome-Agent-Harness-for-Healthcare/main/runner/README.md):

```python
found = bool((event.get("result") or {}).get("found"))
```

The expression asks whether a value is truthy; it does not first establish that the value is a boolean. A nonempty string remains truthy even when its spelling means false. Integer one behaves similarly. These questions become equivalent at this interface only if a producer has already guaranteed the input type. That guarantee is an interface precondition, not something established by a function name or successful parsing.

The paper usefully separates model proposals, effects produced by the environment, and evaluation judgments. Yet that high-level separation does not supply every conversion point’s preconditions. Conversely, one helper example cannot establish that the process evaluation defined in [v1, section 3.2](https://arxiv.org/html/2610.15714v1) fails as a whole.

## Eight inputs answer an example-level question

The same-day Analysis stage already ran an internal experiment. It extracted the unchanged function from the admitted documentation using Python’s abstract syntax tree and supplied eight constructed results. It imported no upstream runner and called no model or healthcare environment. The middle column below records its actual outputs. The final column is our proposed strict-boolean control policy, **not extracted upstream code**.

| Field value | Documented function output | Our proposed strict-boolean control |
|---|---|---|
| Boolean `true` | Success; adds record-read | Success |
| Boolean `false` | Partial; adds nothing | Partial |
| `null` | Partial; adds nothing | Invalid type |
| String `"false"` | Success; adds record-read | Invalid type |
| String `"true"` | Success; adds record-read | Invalid type |
| Integer `0` | Partial; adds nothing | Invalid type |
| Integer `1` | Success; adds record-read | Invalid type |
| Empty list `[]` | Partial; adds nothing | Invalid type |

Source: the same-day internal isolated experiment. See the [experiment record](/assets/evidence/2026-11-18-sig-20261118-006/experiment-006.json) and [inspectable experiment program](/assets/evidence/2026-11-18-sig-20261118-006/resolver-probe.zip) for method, inputs and outputs. Eight inputs are neither eight clinical tasks nor eight complete benchmark runs.

The result falsifies a narrow hypothesis: this example adds progress only for boolean true. It does not establish that non-boolean values survive the native producer, adapter dispatch and final aggregation. If a producer’s serialization contract enforces booleans, the string may never reach this function. In that setting the probe concerns defensive robustness, rather than a reachable failure.

## A strict judge contract owns a different interface

The current chi-Bench judge documentation explicitly requires JSON booleans and does not interpret a string false as a passing boolean. It also checks exact rubric identities, evidence references and output completeness. Missing, timed-out or incomplete required judgments invalidate a measurement; a numeric zero used for transport is a placeholder, not automatically an agent’s zero score. These are documented requirements in the [judge contract](https://raw.githubusercontent.com/actava-ai/chi-bench/main/docs/judge.md).

The materials have separate authoring teams, but neither independently replicates the other system. One interface converts tool events into progress; the other admits judge output as a valid measurement. Their comparison identifies where responsibility sits. It does not rank benchmark reliability or establish that every chi tool-result interface enforces the same types.

For a reader’s own adapter, the following chain makes the responsibility question actionable:

| Stage | Owner and input | Required output | Stop condition |
|---|---|---|---|
| Produce a tool result | Tool implementation supplies raw fields | Explicit, versioned field types | Record unknown when the type contract is absent |
| Admit and parse | Adapter receives the raw value | Separate legitimate values, business negatives and invalid measurements | Handle wrong types or missing fields under a declared policy |
| Add progress | Aggregator consumes admitted results | A milestone traceable to the original result | Do not equate nonempty, parseable or truthy with business success |
| Form an evaluation | Evaluator receives required evidence | A valid result or an explicit invalidity reason | Do not turn a missing required judgment into a valid failure |

This is our proposed checking method, not a claim that both projects implement one common pipeline. Follow the string false through it: if the producer cannot establish a boolean-only output, the adapter needs an explicit responsibility to reject or mark the value invalid. The aggregator can then consume a result with known identity and meaning. The actual call chain determines where a repair belongs.

## The missing evidence is the native path

The public facts here are definitions in each project’s own materials. They are primary-source facts, not independent execution evidence. The internal probe supports the extracted function’s behavior only. Our interpretation concerns assigning type responsibility across producers and consumers; we observed no clinical impact, distorted overall success rate or native-path vulnerability. Reading retrieved and byte-pinned the document snapshots on 2026-11-18. Mutable branches are not presented as fixed commits used by historical paper runs.

The next check is the native producer schema, followed by a single-call evidence trail through admission, parsing and aggregation. Test whether malformed types are reachable. If upstream consistently rejects them, the conclusion should remain at example-level robustness. If they enter aggregation, their effect on milestones and final outcomes still needs measurement. **Distinguishing boolean false from an invalid measurement starts the investigation; establishing that an entire system does so requires another layer of evidence.**
