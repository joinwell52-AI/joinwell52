# The Review Request Returned. Did Its Notification Settings Return Too?

An application resumes a task awaiting human review. Its request identifier survives. Does that mean the reviewer will keep receiving notifications? This is an integration acceptance scenario, not a reported outage: one interface re-emits pending requests, while another requires notification destinations to be supplied again. Request restoration, response correlation and notification configuration deserve separate acceptance checks. The practical output is an ownership table for platform engineers deciding what “resumed successfully” actually covers.

## Two documents describe different recovery boundaries

The [Microsoft Agent Framework human-in-the-loop documentation](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop) describes external responses correlated with request identifiers and routed to the executor that originated the request. Its example builds a response mapping keyed by request ID. Pending requests enter checkpoint state and are emitted again after restoration. A caller can also supply responses in the same call that resumes a checkpoint.

That contract addresses where waiting continues and where the response goes. The [checkpoint guide](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints) describes saved executor state, pending messages, requests and responses, and shared state. In-memory storage does not provide persistence across process restarts; file and database stores serve different durability uses. A reconstructed workflow must retain its topology—the execution nodes and their connections—and executor identities. Custom executors must save and restore their own state.

These are documented requirements, not deployed behavior measured in this study. Finding the original request does not establish that the person answering it is still authorized.

The [CrewAI human-in-the-loop guide](https://docs.crewai.com/en/learn/human-in-the-loop) describes a different surface: an Enterprise webhook carries execution ID, task ID and task output; execution pauses for human input; a resume caller provides feedback and an approval field. Crucially, the guide requires the task, step and crew notification URLs used at kickoff to be supplied again at resume. These notification settings are not automatically carried forward.

Retaining execution and task identifiers therefore cannot supply the caller's missing notification configuration. This requirement belongs to the guide's Enterprise webhook path. It should not be attributed to the local human-feedback decorator, nor stretched into a claim that Enterprise retains no state at all.

The documents neither contradict each other nor support a reliability ranking. Microsoft explains restoration of pending requests and their return to external interaction. CrewAI highlights configuration that a resume caller must provide for continued notifications. The comparison makes distinct responsibilities visible beneath the broad label of human participation.

## What seven local checks actually examined

Same-day Analysis executed two kinds of internal checks. One extracted the event collector from the Microsoft documentation, replacing the framework stream with synthetic asynchronous events while leaving the function unchanged. Human input remained the example's Ellipsis placeholder. The other used an analyst-written checker for notification fields explicitly required by the CrewAI guide. It made no Enterprise service request.

| Input | Observed output | Evidentiary limit |
| --- | --- | --- |
| No request events | No response mapping | Covers only the empty-input branch |
| Two distinct request IDs | Two mapping entries | The example distinguishes these keys |
| Repeated occurrence of one request ID | One mapping entry | Key coalescing is not replay resistance |
| One ID with changed content | Still one mapping entry | The mapping does not adjudicate content conflicts |
| Complete documented resume payload | No notification field missing | Checks presence only |
| Retained execution/task IDs, all notification URLs removed | Three notification fields missing | Identifiers do not restore configuration |
| Only step notification URL removed | One notification field missing | The checker locates that omission |

The [local-check evidence](/assets/evidence/2026-11-20-sig-20261120-002/probe-evidence.json) preserves inputs, outputs, environment, the source fragment and limitations. These counts comprise four collector checks and three payload checks. Two repeated-ID cases have identical actual inputs, so seven recorded cases do not mean seven distinct branches, much less seven real restart tests. They remain internal evidence; independent vendor authorship does not turn our checks into third-party reproduction.

A small example makes the mapping boundary tangible. One request ID first carries a “below” hint and later an “above” hint. The dictionary still has one slot. This does not show a real framework collision or an overwritten approval: the example's answer is still a placeholder. It shows why an integration cannot delegate the relationship between occurrence identity, content version and external response to a dictionary assignment.

## Assign acceptance ownership for one waiting task

The following table is a proposed integration acceptance aid, not a common protocol claimed to exist in both products. Follow one task whose output awaits human review across a pause and restoration. Identify the input and owner at each boundary, then ask each boundary for its own inspectable output.

| Boundary and input | Proposed owner | Output to retain | Separate condition to examine |
| --- | --- | --- | --- |
| Task state at pause | Application and storage component | Locatable checkpoint and pending request | Cross-restart storage and complete custom state |
| Checkpoint entering restoration | Workflow construction and resume entry point | Reappearing request under compatible topology and identities | Handling of incompatible structure or identity |
| Request event entering external integration | Event consumer | Request occurrence linked to review content | Whether re-emission denotes the same occurrence; how content changes are recognized |
| Resume call continuing notifications | Caller and notification integration | Required settings plus actual send/receive records | Required URLs supplied again; actual reception |
| Response entering task continuation | Response routing and application authorization | Response ownership, current authority and corresponding action | Expiry, duplication, reassignment and changed actions |

The synthesis connects what is retained with who must act next. A request record tells restoration which response is awaited; configuration tells the integration where to send a notification; a reception record establishes whether it arrived. The final row raises a separate authority question. Records in the preceding rows do not make that row pass automatically.

For an application using the documented Enterprise webhook path, a concrete next test would create matched, separately paused task instances on a pinned deployment and retain their respective execution/task IDs. Resume one with complete notification configuration and the other with omitted settings. Record service responses and actual sends and receptions. For a Microsoft integration, pin the package revision and persistent store, restart the process, and reconcile re-emitted requests with the external consumer's records. Each test answers its own integration question. They should not be merged into a product contest. Neither test was performed here.

## Explicit configuration can be a reasonable design

Re-emitting a pending request can be the correct way for an external consumer to rebuild its waiting state. Coalescing repeated instances of one request ID may also be intentional. Neither observation establishes duplicate notification side effects or their prevention.

Likewise, supplying notification destinations explicitly at resume could allow callers to change them. That is a plausible alternative explanation, not a vendor-confirmed design motive. It is enough to prevent us from calling an explicit configuration requirement a defect merely because it exists.

The table is also unnecessary in full for local synchronous review with no cross-process restoration and no external notifications. Conversely, claims of reliable delivery after restart or rejection of replayed approvals need real deployment, duplicate-response and changed-authority experiments. The guide's descriptions of reviewer assignment, permissions, escalation and service-level management remain vendor claims here; their implementations were not examined and cannot fill these gaps.

## Which external record should the next acceptance test produce?

The evidence supports separate acceptance entries for restoration, correlation and notification configuration. It does not establish reliable post-restart delivery or approval security for either product. The most useful next record joins the same request across a real process restart, an actual reception receipt and the resulting response handling. If the reviewer was reassigned or the proposed action changed, examine what happens to the old response as well. Those records would let an evaluator ask who still approves which occurrence of an action, rather than merely whether a task identifier survived.
