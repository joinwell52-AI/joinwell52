# Before a Lesson Enters the Skill Library, Bind It to the Program That Was Tested

A repair report contains a sound proposal and its source program clears the development threshold. Should the library accept the entire edit? The available research separates three judgments: the program can perform a task, a proposal deserves retention, and the edited text actually expresses that proposal. For maintainers of shared skill libraries, the useful question is whose measurements support which new text. The cases below turn that question into concrete checks.

## The two studies accept different objects

A skill library carries strategies and experience into later tasks. Admitting a lesson therefore extends its influence beyond the attempt that produced it. Before comparing admission mechanisms, identify what each decision accepts.

RegHarness distinguishes within-run step commitment from between-run skill refinement. Its authors describe a step entering committed code after error-free execution, verifier success and an auditor’s commit proposal. Between-run refinements use default-off switches, off-state equivalence checks and leakage inspection; the authors choose which changes to enable. The library stays frozen within a trial. That is author-gated refinement, not an automatic evidence-based comparison of every lesson against its predecessor. [Sections 3.1–3.6 and Appendices A–C](https://arxiv.org/html/2611.33739v1)

Skeptic sets a different contract for admitting knowledge. In its LIBERO robot-manipulation setting, a source program must succeed on at least eight of fifteen development seeds, and a fresh verifier must judge a proposed repair sound. Seeds specify development trial conditions; the score is not a guarantee across future tasks. The paper uses a separate threshold of fourteen out of twenty-five for Robosuite, a robot simulation environment. Eight out of fifteen is not a universal threshold. [Section 3.3 and Appendices F–G](https://arxiv.org/html/2611.33560v1)

| Object being accepted | Decider and evidence | What the admitted material supports |
| --- | --- | --- |
| A RegHarness code step | Verifier and auditor assess execution and propose commitment | Author-described step conditions; replay reruns code rather than restoring an identical physical state |
| A RegHarness between-run refinement | Authors choose after switch, equivalence and leakage checks | Author-described refinement selection, rather than automatic per-proposal admission |
| A Skeptic skill lesson | A service outside editable programs checks development performance and verification | Author-described and source-observed program eligibility; correspondence of every edit still needs separate examination |

The papers have different authors and institutions and supply two independent sources for this contract comparison. They do not reproduce each other’s effectiveness. This synthesis compares decision objects, evidence and responsibility; it does not rank scores from different experiments. Each capability in the table remains attributed to its source.

## Keep the score attached to the same program

At revision `bf0e78d2e2ce308d9d678e0bbb1196b5b3ad4ebb`, Skeptic’s public admission script hashes the selected `fix_code.py`, then collects finished runs whose saved program has that same hash. For each development seed it retains the result with the greatest run name and recounts coverage and passes. It does not simply trust “8/15” in the verification report. “Latest” here means the script’s run-name ordering, not a causal-order or cross-host clock guarantee. [Run collection and eligibility functions](https://raw.githubusercontent.com/lmsdss/Skeptic/bf0e78d2e2ce308d9d678e0bbb1196b5b3ad4ebb/skeptic/gate/promote.py)

This equivalent, shortened sketch shows the program-score relationship in that fixed source. It omits report checks and is not a callable interface:

```text
selected_hash = hash(selected_program)
matching_runs = finished_runs_with_program_hash(selected_hash)
latest_results = greatest_run_name_for_each_development_seed(matching_runs)
program_eligible = every_seed_is_covered(latest_results)
                   and count_successes(latest_results) >= 8
```

For a small example, change one line of the selected program while leaving a report that says “8/15.” Reusing the old score would attach measurements to the wrong content. The script instead looks for runs of the changed program. If all saved copies contain the old version, coverage for the new one is zero. Hash binding identifies whose score this is; it does not establish program safety or proposal truth.

## Eight fixtures exercise the admission functions

The same-date Analysis stage already executed eight internal cases. It extracted three unchanged function bodies from the pinned source—`sha_file`, `program_runs` and `check`—and let them read synthetic filesystem directories. The environment was Windows with Python 3.12.9. Fixture outcomes were preset; no robot program, model, simulator or sensor pipeline ran. This article reuses completed results rather than presenting another robot experiment. [Case results and provenance](/assets/evidence/2026-11-27-sig-20261127-002/skill-evidence.json), [public synthetic fixture corpus](/assets/evidence/2026-11-27-sig-20261127-002/fixture-corpus.json)

Unless a row changes it, the reference input has one matching program, all fifteen seeds covered, eight passes and one proposal judged sound.

| Fixture change | Actual eligibility | What the case examines |
| --- | --- | --- |
| Positive control | Eligible | The disclosed conditions can pass on this synthetic input |
| Seven rather than eight passes | Ineligible | The threshold uses recounted results |
| Only fourteen seed records | Ineligible | Eight passes do not replace complete coverage |
| Overall report refuted, one sound proposal retained | Eligible | Whole-report and individual-proposal judgments differ |
| Overall report void, one sound proposal retained | Ineligible | A void report cannot supply the required judgment |
| No sound proposal | Ineligible | A passing program does not replace proposal assessment |
| Selected program changed, old runs retained | Ineligible, zero coverage | Old measurements do not follow changed content |
| A later failing run added for a previously passing seed | Ineligible, recounted as 7/15 | Selection cannot retain only an older successful result |

All eight actual outcomes matched their preset expectations. “8/8 matched” describes this function-fixture collection, not a task success rate or complete service-path coverage. A transparent text corpus retains the original archive’s 384 member files for these eight admission cases, preserving their bytes and per-file integrity information. The results file records source hashes, revision, extracted functions, inputs and outputs so the experiment record can be distinguished from our interpretation.

## Why a refuted report can still carry a sound proposal

The script permits an overall verdict of `verified` or `refuted`, excludes `void`, and requires at least one proposal with disposition `sound`. This is not an explanation invented to excuse an anomalous pass. Its introductory comment explicitly says that requiring an overall verified verdict would let one defective entry sink an otherwise sound attempt, while only sound proposals may be promoted. [Pinned source description and checks](https://raw.githubusercontent.com/lmsdss/Skeptic/bf0e78d2e2ce308d9d678e0bbb1196b5b3ad4ebb/skeptic/gate/promote.py)

The refuted-with-sound case is therefore an important positive control. Summarizing the contract as “only verified reports may enter the library” would erase its intended partial-acceptance semantics.

The next question concerns what is actually written. Does every edited passage correspond to that sound proposal? The inspected eligibility function checks attempt-level conditions. Later source processing rechecks evidence, rejects a stale library hash and lints staged content, but the admitted path does not visibly establish a semantic mapping from each edit to its sound proposal. The coordinator’s instructions carry the restriction to retain only sound proposals. This is an assurance boundary to examine, not a reproduced incident of incorrect admission. The coordinator may follow those instructions correctly. The eight fixtures did not execute the downstream library-writing process or test that correspondence.

Our interpretation for shared-library maintenance is to account separately for **program eligibility, proposal judgment and edit correspondence**. They can contribute to one admission decision without substituting for each other. The presence of a report is not evidence that all three hold.

## Aim the next check at the admitted text

Start with one proposed lesson and inspect four things in order: the selected program’s content hash; complete development-seed coverage and the chosen run for each seed; each proposal’s disposition and source; and the correspondence between final edits and those proposals. The first three have different levels of support in the source observations and fixtures above. The fourth is a proposed additional acceptance check, not an already verified capability.

A discriminating follow-up integration experiment would hold the passing program and sound proposal constant while changing only the staged text. One version would faithfully express the proposal; the other would mix in an unsupported conclusion. The real admission service’s handling of those versions remains untested. We do not predict whether it would reject or accept them.

The non-applicability boundaries are concrete. A conversation-ending orchestrator is not admitting reusable knowledge. Eight out of fifteen is a policy for one development setting, not a safety threshold. Matching hashes establish content identity without supplying missing observations. In a counterexample reported by Skeptic’s authors, a task with 12/15 development successes was still closed on a mistaken impossibility judgment, with no knob-angle measurement available. Program scores do not automatically repair task closure. RegHarness also reports false commits, replay aborts and governance-induced failures. We have not reproduced either full study and infer no general efficacy guarantee. [Skeptic Appendices C, E and H](https://arxiv.org/html/2611.33560v1), [RegHarness Sections 4.4–4.7 and appendices](https://arxiv.org/html/2611.33739v1)

## Evidence and sources

This article separates author-reported claims, source observations, internal experiments and interpretation. Author claims describe their methods and reported scope; source observations concern a pinned file; the internal fixtures exercise limited functions; per-edit acceptance is a proposed next check. Two independent author teams are not independent replications of one another, and public availability does not increase a claim’s evidentiary strength by itself.

- Shengming Liu et al., *RegHarness: Regulating What Code-as-Policy Agents Keep from Steps to Skills*, author preprint, November 2026, v1. [Paper and supplement](https://arxiv.org/html/2611.33739v1). Supports the described step-commit and author-enabled refinement contracts. Implementation code and raw trial-log reproduction were not available in the admitted material.
- Wenfang Sun et al., *Skeptic: Grounding Failure Diagnosis for Robot Skill Discovery*, author preprint, November 2026, v1. [Paper and supplement](https://arxiv.org/html/2611.33560v1). Supports the reported program-performance and proposal-judgment contract and counterexamples. A fresh verifier is a separate execution role, not an independent research institution.
- Skeptic project, [admission script](https://raw.githubusercontent.com/lmsdss/Skeptic/bf0e78d2e2ce308d9d678e0bbb1196b5b3ad4ebb/skeptic/gate/promote.py) at `bf0e78d2e2ce308d9d678e0bbb1196b5b3ad4ebb`. This belongs to the same author source as the preceding paper. The inspected code is not asserted to be the exact revision behind every paper measurement.
- Research Center, internal source-function experiment, 2026-11-27: [eight cases, environment and mapping](/assets/evidence/2026-11-27-sig-20261127-002/skill-evidence.json), [synthetic input corpus](/assets/evidence/2026-11-27-sig-20261127-002/fixture-corpus.json). Supports bounded program-evidence checks, not real robot gains, proposal truth, per-edit semantic binding or full-service security.
