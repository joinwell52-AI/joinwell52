# An approval record stores the action. Does acceptance compare it?

An approval row stores both a request identifier and the action itself. Does that guarantee that a resumed action is the one approved? The decisive question is what acceptance compares. In our internal isolated probe, holding agent identity and workflow constant while changing the request ID, target or parameters still produced an approval-stage pass.

The result offers a concrete inspection method: separate “the record contains this field” from “the decision constrains this field.” It does not yet establish that the complete system can execute the changed action. Resume tokens, callers and other policy stages may prevent it.

## Stored actions and actual selection predicates

The inspected SIDJUA implementation stores structured action content and request metadata. At the pinned revision, however, the approval lookup selects by agent, workflow, record status and time window, without comparing the request ID or action payload in that query. A comment mentions request-metadata matching and a compatibility fallback; the corresponding comparison and fallback branch are absent from the inspected implementation. This is an observation of specified source, rather than a repository-wide security audit. [Approval source](https://github.com/GoetzKohlberg/sidjua/blob/747b5bb125c8cc94e7cb99a581dc63bedb2c9bb2/src/pipeline/approval.ts)

Action type, target and optional parameters belong to the action descriptor; request ID is a separate field. An unchanged request ID is therefore insufficient by itself to establish an unchanged payload. Conversely, storing a complete payload does not automatically constrain a decision whose predicate never compares it. [Request types](https://github.com/GoetzKohlberg/sidjua/blob/747b5bb125c8cc94e7cb99a581dc63bedb2c9bb2/src/types/pipeline.ts)

## Changing three fields independently

The same-day Analysis stage executed an isolated approval stage derived from pinned source. The environment was Node.js v24.19.0 and real in-memory SQLite, with a fixture-only schema. Imports and type annotations were removed while retaining function logic and SQL. The matcher was an exact-equality stub, logging was a no-op and the condition-parser branch was unused.

With the same agent and an exactly matching workflow, the experiment inserted one live approved row, then varied one input field at a time. The following is internal experimental evidence, rather than a new full-resume test. [Complete experiment record](/assets/evidence/2026-11-08-sig-20261108-002/approval-probe.json)

| Change from original request | Approval-stage result | Directly supported observation |
| --- | --- | --- |
| None | PASS | Baseline can match a live approval |
| Request ID only | PASS | This stage does not distinguish the original request ID |
| Target only | PASS | This stage does not distinguish the original target |
| Parameters only | PASS | This stage does not distinguish the original parameters |
| Agent only | PAUSE | The agent predicate distinguishes this fixture |
| Denied row | BLOCK | The denial control blocks |
| Expired row | PAUSE | The time-window control pauses |

The first three perturbations turn a static query observation into controlled stage-level behavior. Agent, denial and expiry controls also show that the fixture does not indiscriminately pass every input. Those controls do not cover concurrent approvals, denial precedence or full production-schema constraints. They establish neither overall reliability nor overall failure of the approval system.

## Resume-token checks are a different boundary

The inspected resume code computes an HMAC over request ID and approval ID, verifies it and re-evaluates the supplied request through the policy pipeline. Target and parameters are absent from the signed content. This does not mean the experiment bypassed the signature: it never executed token generation, token validation or the complete resume path, and performed no file deletion or external effect. [Resume source](https://github.com/GoetzKohlberg/sidjua/blob/747b5bb125c8cc94e7cb99a581dc63bedb2c9bb2/src/pipeline/resume.ts)

A changed request ID passing the isolated approval stage does not establish that it passes resume-token validation. Whether changed targets or parameters can even reach that stage depends on caller preservation of the originally approved object. The complete pipeline also includes other governance stages that may reject the action. Unexpected errors return BLOCK, but audit persistence is best effort: a blocked result alone does not guarantee a durable audit row. [Pipeline source](https://github.com/GoetzKohlberg/sidjua/blob/747b5bb125c8cc94e7cb99a581dc63bedb2c9bb2/src/pipeline/index.ts)

The strongest alternative explanation is therefore a caller invariant. If callers strictly preserve approved payloads, the absence of a repeated comparison in this stage may not create an exploitable substitution path. The available experiment does not test that premise.

## A human reply is a different object from action approval

The inspected ChatDev human-node path provides a useful but limited comparison. It requests input for a node, description and context, then forwards the returned content downstream. Its prompt service locks the request channel, adds optional session metadata and records interaction. This is a content-interaction path, rather than the same object as a persisted approval decision and signed continuation. [Human node](https://github.com/OpenBMB/ChatDev/blob/464a681ba7bda869db97a50c5fa707c9a0fb57a0/runtime/node/executor/human_executor.py), [prompt service](https://github.com/OpenBMB/ChatDev/blob/464a681ba7bda869db97a50c5fa707c9a0fb57a0/utils/human_prompt.py)

This is not a security ranking. A prompt-service file that does not establish reviewer authentication does not establish its absence across the product. The comparison asks engineers to define whether human input is content, advice or permission for an immutable action before choosing what to verify.

## Carry the same perturbation to the final effect

Our interpretation supports using a one-field change as a test carried across the responsibility chain, rather than stopping at an approval log or signature. The following is a proposed verification chain. Except for the explicitly executed stage probe, the entries remain untested.

| Location | Input and responsibility to examine | When to stop or obtain a new decision | Present evidence |
| --- | --- | --- | --- |
| Caller | Submit the approved object with aligned identity, target and parameters | Approved payload cannot be established | Not executed |
| Resume entry | Check token relationship to request and approval | Invalid token or mismatched ownership | Source read; not executed |
| Approval stage | Select an effective decision using match predicates | Missing approval pauses; denial blocks | Internal isolated probe executed |
| Other policies | Re-evaluate incoming action under current permissions and policy | Current policy does not permit the action | Pipeline read; no integration test |
| Effect executor | Consume the approved action and record actual effects | Effect differs from permission, duplicate consumption or conflicting precondition | Not executed |

This is not a claim that either product implements every listed control. It locates missing evidence and avoids substituting interaction logs for authority, a valid signature for complete payload binding, or stage acceptance for an effect that actually occurred.

## Evidence and sources

Direct implementation sources come from two maintainers at fixed revisions: SIDJUA `747b5bb125c8cc94e7cb99a581dc63bedb2c9bb2` and ChatDev `464a681ba7bda869db97a50c5fa707c9a0fb57a0`, linked above. These are public implementation evidence. The [2026-11-08 isolated-stage record](/assets/evidence/2026-11-08-sig-20261108-002/approval-probe.json) is internal experimental evidence containing environment, source hash, inputs, results and stub scope. No third party independently reproduced the stage finding, and no independent security assessment of the full system is supplied. The cover depicts only the local binding relationship, without an external effect.

## What remains undecided

The experiment did not execute the repository's actual database schema, condition parser, crypto helpers, concurrent decisions, process restart or final effects. It did not inspect a complete call graph. It therefore cannot support a security advisory, demonstrated exploit or product-defect verdict.

The next questions are concrete. Does every caller preserve the original approved payload? Does a changed precondition invalidate an earlier decision? Can an approval be consumed only once, and how do network retries differ from renewed approval? Who resolves conflicting decisions, revocation, expiry and policy revisions after restart? Do host permissions supply a boundary beyond application rejection? Mapping those questions to actual calls, records and effects is the work needed to advance from a stage boundary to a system-level judgment.
