# The Chat Stopped. Which Evidence Accepts the Task?

One message says “unfinished”; another says “DONE.” In the same-date Analysis stage's internal isolated probe, they trigger a round limit and a termination-message condition respectively, yet return the same handler result. If a caller records that result as task success, an exhausted budget can become apparent acceptance. Multi-agent orchestration engineers need to retain the stopping reason and separately request the artifact and its acceptance evidence.

## One return value, two stopping reasons

The AG2 classic GroupChat guide describes manager selection, context broadcast, round limits and message markers that end a conversation. These organize interaction. A terminating marker does not automatically establish that a deliverable meets its requirements. [Classic guide](https://docs.ag2.ai/latest/docs/user-guide/advanced-concepts/groupchat/groupchat/)

Analysis pinned classic v0.9.10 at commit `ac380f5c7962ad875f77c4f8310e3c1167bceeb7`. The internal probe extracted the manager's `run_chat` body unchanged and isolated dependencies with inert manager, group, message and event stubs. Both controls use a one-round limit; only the message and termination predicate change.

| Input and condition | Actual stopping event | Return | Domain success checked? |
| --- | --- | --- | --- |
| “unfinished,” predicate false | Maximum rounds (1) reached | Same handler tuple | No |
| “DONE,” predicate true | Manager termination-message condition met | Same handler tuple | No |

Both branches actually return the following. It is a message-handler result, not an independently computed task score:

```python
(True, None)
```

This is not an experiment showing that the framework scores failure as success. The mistake occurs when a consumer expands handler semantics into acceptance semantics. Static source also distinguishes no eligible speaker and no generated reply; this probe executes only the two branches above. [Classic source](https://raw.githubusercontent.com/ag2ai/ag2/v0.9.10/autogen/agentchat/groupchat.py); [internal inputs, outputs and limits](/assets/evidence/2026-11-23-sig-20261123-004/experiment-evidence.json)

## A verification label is not an outcome

MAST, the Multi-Agent Systems Failure Taxonomy study, comes from a separate research team. Its third version reports 1,642 traces from seven frameworks and distinguishes premature termination, missing or incomplete verification, and incorrect verification. These labels help describe behavior, but are not interchangeable with final task failure. Verification-related labels also occur in successful runs. [Paper v3, sections 3–4 and appendix J](https://arxiv.org/html/2503.13657v3)

Its appendix cases make the problem more concrete than “check once more.” One omits verification of a fish-price assumption; another correctly calculates spending but answers how much money remains; an editor claims a change that a later test finds absent. These concern premises, delivery objectives and actual artifacts, not one shared stopping-condition defect.

Three records therefore need distinct meanings: why the conversation ended, who performed which verification, and which requirements the delivered artifact met. A positive verifier answer records a process event. A verifier inspecting the wrong artifact or checking the wrong question can still accept incorrectly. Conversely, a successful answer does not establish complete verification.

## Adding a verifier is a conditional intervention

The paper's MathChat experiment is a useful counterpoint to an automatic prescription. On 200 sampled GSM-Plus exercises with six repetitions, the reported GPT-4 topology intervention reaches 85.50 versus 84.75 at baseline, with Wilcoxon p=0.4; prompt refinement reaches 89.75. For GPT-4o, the topology comparison is 88.83 versus 84.25, with reported p=0.03. [Appendix H.1, table 5 and appendix L](https://arxiv.org/html/2503.13657v3)

The small GPT-4 increase is not significant in that reported comparison. The GPT-4o result does not generalize to every model, task or verifier. Other appendix analyses favor topology interventions by failure-label breakdown; label distributions and final correctness remain different metrics.

This does not dismiss a dedicated verifier. It separates responsibility from measured benefit. Giving only a verifier the terminating marker can change who may end the conversation. Whether it improves task quality still depends on what the verifier receives, how it judges and how outcomes are measured.

## Give acceptance its own evidence handoff

Consider an explicitly illustrative task to modify a calculation function. The following is a proposed handoff, not a tested new feature or a description of existing AG2 interfaces.

| Stage | Responsible actor and input | Evidence delivered | Insufficient for acceptance |
| --- | --- | --- | --- |
| Requirements enter execution | Task owner supplies expected behavior and checkable conditions | Artifact version corresponding to the requirements | Ambiguous or substituted objective |
| Conversation exits | Orchestration manager handles messages and budget | Stop reason, final message, artifact location | Only a boolean handler result |
| Artifact enters checking | Domain evaluator reads that version and requirements | Tests actually executed, outputs, unchecked requirements | Only the editor's completion claim |
| Checks enter acceptance | Accountable actor evaluates the results | Explicit accept, reject or defer decision for requirements | Tested and delivered versions cannot be correlated |

If the budget expires before an artifact is ready, retain the stopping fact and defer domain acceptance. If the artifact already meets its requirements, a separate domain check may accept it even after a budget stop. “Separate” here means an acceptance responsibility distinct from a handler return; it does not turn our internal experiment into third-party validation.

A useful first inspection is to find the code mapping the chat return into application task state. Does it also request the stop reason, artifact version and domain-check results? The delivery requirements determine the tests needed. A message keyword cannot replace test output or decide whether missing checks are acceptable.

## Keep the version boundary visible

Classic implementation findings remain classic findings. Current main has changed architecture; an old function probe is not a complete assessment of the current product. A selected documentation URL containing “latest” cannot erase that difference. Speaker constraints describe particular orchestration paths; this article does not treat them as a universal authorization guarantee.

For a simple deterministic application with a complete built-in domain check, termination may intentionally bind acceptance. The useful question remains what that binding actually executes, rather than mechanically adding another role. For open-ended work, sufficient evidence and responsibility for omissions remain domain decisions. A next deployment check should trace a budget stop and a normal termination, correlate the delivered version and actual tests, and inspect the caller's state mapping before concluding that acceptance has its own responsible owner.
