# Deployment, Channel, Action: What Each Approval Actually Decides

A file-reading task has been approved, but its symbolic link points somewhere else by the time it runs. Does the earlier check still authorize this call? Approval to deploy an agent cannot answer that question on its own. Deployment approval, channel arbitration and action confirmation decide different things. An audit becomes more useful when it records who checks what, when they intervene and which paths they exclude.

## The same word conceals different decisions

This is a comparison of documented responsibilities, not a security ranking. ServiceNow's approvals documentation describes assets or servers requiring approval before becoming available when the relevant feature is activated. That answers whether a capability may be offered. It does not automatically answer whether a particular caller may perform a particular action on a particular target. An available but inactive feature is also not observed enforcement. [Deployment approvals documentation](https://www.servicenow.com/docs/r/intelligent-experiences/ai-control-tower/explore-approvals.html)

AG2's network documentation separates arbitration before a channel decision from listeners that observe afterward. Arbitration can intervene before the transition; a listener can record what happened. The existence of a record does not establish prior authorization. These are documented architectural responsibilities, not a transport-authentication audit performed here. [Network overview](https://docs.ag2.ai/docs/user-guide/network/overview/)

OpenHands describes an analyzer assigning action risk and a confirmation policy deciding whether to ask the user. Its security guide explicitly excludes direct tool execution from the analyzer and confirmation policy in the conversation loop. That is a documented coverage boundary; we did not execute a bypass attack. [Security guide](https://docs.openhands.dev/sdk/guides/security.md)

| Documented check | Decision object and intervention time | Question the evidence does not settle |
| --- | --- | --- |
| Deployment approval | Before an asset or server becomes available, with the feature activated | Whether this caller, target and parameter set are authorized |
| Channel arbitration | Before a channel-transition decision | Whether origin identity is authenticated and every tool entrance is covered |
| Listener observation | After a transition | Whether that transition was permitted or blocked beforehand |
| Action confirmation | After risk classification and before execution in the covered conversation loop | What happens on direct calls, recovery entrances and the approval lifecycle |

The product descriptions are source-reported claims from their respective teams. Separately authored descriptions support comparison of objects and timing; they do not constitute mutual replication of one implementation. An unanswered question is not evidence that a product lacks the corresponding control.

## How far a passing confirmation function takes us

The pinned confirmation predicate has a narrow responsibility. Unknown risk follows a separate confirmation switch. Known risk delegates to the risk comparator with the configured threshold. The threshold itself cannot be unknown. This function decides whether confirmation is needed; it is not a credential system or evidence that all entrances reach it. [Pinned source](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/141423921fdaeb08cd5f53464a69e860da70b66f/openhands-sdk/openhands/sdk/security/confirmation_policy.py)

Same-day Analysis derived function bodies from this source and ran six isolated checks using an unknown-risk sentinel and a known-risk comparator test double. The following reproduces those existing observations; Production ran no new experiment.

| Input or control | Internal observation |
| --- | --- |
| Unknown risk, confirmation enabled | Confirmation required |
| Unknown risk, confirmation disabled | Confirmation not required |
| Known-risk double, comparator returns true | True returned; threshold passed unchanged |
| Known-risk double, comparator returns false | False returned; threshold passed unchanged |
| Unknown value supplied as threshold | Error rejecting an unknown threshold |
| Known object supplied as threshold | Object returned unchanged |

These are internal experimental observations, not third-party validation. They did not execute the real risk enum's equality semantics, configuration-model integration or the complete conversation chain. An upstream comment says equality with the threshold requires confirmation; that comment is not a measurement of the real enum in this probe. Current documentation and pinned code are also different revision nodes, so they cannot be combined into one end-to-end pass report.

The useful result is a responsibility limit. We have internal observations of the switch and comparator delegation. We do not have evidence that every tool call reaches the predicate. Acceptance therefore needs a separate entrance-coverage question rather than a promotion of a function-level pass into a complete authority guarantee.

## Inside the allowed directory can still mean the wrong object

The independently authored four-framework study by Lazer, Aryal, Gupta and Bertino separates changed symbolic links from path containment. The authors report that tested configurations followed a changed link after earlier path validation, while protected configurations could block traversal using canonical checks or a sandbox. Both results can hold: a resource can be inside an allowed directory without remaining the object previously approved. [Authorization study, section 3.2](https://arxiv.org/html/2611.21259v1)

The opening file-read is an audit example adapted from that scenario, not a newly observed production incident. Following it produces different questions. Deployment approval establishes availability; arbitration concerns task movement; confirmation identifies risks requiring a decision; current resource resolution determines which file is actually touched. Our interpretation is that earlier permission cannot substitute for evidence about the current target. This does not require four components in every system. It requires an acceptance claim that matches the actual responsibility.

The study also distinguishes unauthorized tool invocation, host effects and final information disclosure. A request reaching an execution interface and then being stopped is different from a request never reaching that interface. Compressing both into one safe/unsafe label hides the boundary needing repair. [Study scope and results](https://arxiv.org/html/2611.21259v1)

Those outcomes remain author-reported; we did not reproduce attack success rates. The study uses a shared model and specified versions and configurations. Enterprise identity and access management, credential authentication and external policy engines were not comprehensively evaluated. Its Microsoft AutoGen sample must not be equated with the current AG2 network documentation.

## Audit one real call instead of checking feature boxes

The following is a research recommendation, not a unified mechanism established in any sample. Select an actual call, such as reading a reviewed file, and request evidence from the responsible party at each stage.

| Stage | Input, responsibility and output | Reason to pause acceptance |
| --- | --- | --- |
| Offer a capability | Deployment administrator receives asset configuration and defines availability | Activation conditions or exclusions are unclear |
| Transfer a task | Application or arbiter receives caller identity and task, then permits a request to proceed | Only a name or retrospective log exists, without an authority basis |
| Obtain confirmation | Policy and approver receive the concrete action and produce a traceable decision | Approval is unbound to target, parameters or necessary prior state |
| Execute | Executor receives the request and current resource, producing an effect and record | The actual entrance skips checks or changed-resource handling is unknown |
| Retry or recover | Recovery receives the prior decision and current state, then continues or requests approval | Network retry, replay and a newly approvable action cannot be distinguished |

For high-risk operations, separately establish expiry, one-time consumption, invalidation after state changes, and the process or container restrictions backing application checks. Mark missing evidence as unverified. A successful record at another stage cannot fill the gap.

A counterexample matters: synchronous local confirmation may suffice for a limited single-user threat model. There is no need to add components simply to match the table. Align the threat model, real entrances and acceptance claim. Missing evidence calls for investigation, not an assertion that the product has no control.

## Evidence still needed

This work did not install the complete SDK or test direct-tool bypass, approval expiry, one-time consumption, replay, recovery revocation or host isolation. The four external teams are independent authors, but they did not cross-replicate one authorization implementation. The six internal checks support only local branch behavior.

The next verification should pin one real path and version, then compare state changes, retries and renewed approval for the same target. Record separately whether the request entered the tool, whether the host changed and whether information escaped. That is a proposed test, not a completed one. The useful final question is whether the object bound to the decision is still the same object when the effect occurs.

Official documentation supports attributed descriptions; pinned code supports a locally inspectable implementation; internal probes support bounded observations. Comparing decision objects and timing is our interpretation. Publication, citation and the existence of code do not establish general validity.
