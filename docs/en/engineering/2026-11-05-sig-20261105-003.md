# A resumed answer needs a slot, not just a task

The first question has already received “yes.” A second question is now waiting. If both are addressed only by the task's identity, retrying the first answer risks making an old response look like an answer to the new question. The retained LangGraph change contains a regression for that stale-answer case. It also retains a compatibility path that accepts an older identifier. Reading those two facts together is more useful than declaring that all old answers are now rejected. [1]

The mechanism has three separate jobs: identify the pending answer slot, preserve selected saved-state compatibility, and restart replay at the correct response index. Our same-day internal helper probe exercises narrow pieces of these jobs. It does not establish full runtime correctness, action authorization or exactly-once external effects.

## The task identifies too much; the answer slot narrows the question

At commit `6ea1751a93bda2b57bbf38dea494c461c34e13df`, the added identifier helper uses the task namespace unchanged when no answers have been stored. For a later question it appends a separator and the count of stored answers before hashing. The retained regression changes the expectation for successive question identifiers from equal to different, while preserving the first bare-namespace identity. These are observations of the changed source and test definition, not observations of a passing full suite. [1]

This choice gives the answer a more specific address than the task alone. It does not simply number source-code call sites. The patch's parallel-call regression uses the order in which questions are raised by a task; the count of existing answers is the selected boundary. A question's place in replay therefore still matters.

Our internal experiment extracted the added helper and replaced the unavailable hash dependency with a recorder of its input. For the illustrative namespace `ask:task-example`, answer counts zero, one and two produced the distinct inputs below. These are **hash preimages, not genuine interrupt hashes**. [3]

```text
ask:task-example
ask:task-example|1
ask:task-example|2
```

The observation supports unchanged first-slot input and separated later-slot inputs. It says nothing about actual hash outputs, storage behavior or simultaneous submissions. The upstream stale-answer regression expects an old identifier to be rejected as not pending, with the current pending identifier included in the error. We did not execute that full enforcement path. [1; 3]

## Compatibility is a scoped lookup, not a universal rejection rule

The inspected resume-mapping branch first looks for the current slot's identifier. If it is absent, the branch also checks the first identifier as a legacy fallback. The internal extracted-branch experiment starts with one stored “yes” and observes these cases: [1; 3]

| Mapping supplied to the isolated branch | Observed stored answers afterward |
|---|---|
| Current slot maps to “no” | “yes”, “no” |
| Only legacy first identifier maps to “legacy” | “yes”, “legacy” |
| Current maps to “current”, legacy maps to “legacy” | “yes”, “current” |
| Only an unknown identifier maps to “x” | “yes” |

The current mapping takes precedence, while an unknown key adds no response in this branch. The legacy case is a concrete counterexample to the claim that the identifier change rejects every old first identifier in every state. It does not contradict the separate strict-resume regression: the isolated lookup and the complete enforcement path are different evidence objects.

Our interpretation is that a migration review must identify which saved states can enter the fallback and which outer checks constrain them. A helper-level success cannot establish full migration safety. Conversely, removing a fallback solely because a newer identifier looks stronger could break a deliberately supported saved-state path. This study does not prescribe such a change.

## A correct address can still be read from the wrong position

Official interrupt documentation states that resuming restarts the node from its beginning, with stored responses matched by index. This creates a different failure opportunity: replay can have the right answer list but start reading it from an already advanced cursor. [2]

The retained retry helper replaces the interrupt counter while preserving stored responses. In our internal substituted-dependency probe, a counter that has already advanced returns index one without reset. After the extracted reset helper, the next index is zero and the stored answer remains “yes.” Configuration, scratchpad and counter dependencies were substitutes. Neither synchronous nor asynchronous runtime retry behavior was executed locally. [1; 3]

The architectural distinction is important. Slot-specific addressing decides which new answer belongs to a pending question. Cursor reset decides where replay begins consuming previously stored answers. One can be correct while the other is wrong. The official requirement to preserve interrupt order remains relevant; new identifiers do not make arbitrary reordering safe. [2]

## What these mechanisms leave to the application

For an approval-sensitive application, an answer's correct address is only one input to an authorization decision. The inspected change does not establish binding to immutable action parameters, the approver's authority, expiry, credential scope or external-effect deduplication. These are missing guarantees in this evidence scope, not a claim that every surrounding application lacks them.

The responsibility boundary can be stated concretely. The caller supplies a response and identifier; the inspected lookup contributes a selected stored answer; replay consumes stored responses in order. An application authorizing an action still needs evidence for the action being approved and the authority under which it may run. A retry that successfully recovers “yes” cannot reconstruct that missing authorization evidence.

Official documentation also warns that a node can commit an effect and fail before completing; a retry can then repeat the effect. Merely placing an operation after a question does not establish exactly-once execution. Our study performed no external action and measured no deduplication behavior. [2]

The remaining tests therefore concern complete paths: stale and current submissions through the outer enforcement layer, supported legacy saved states, concurrent submissions across actual checkpoint backends, and a separately specified application authorization lifecycle. The current probe used a hash-input recorder and substitute containers; it is internal mechanism evidence, not an independent replication or a security audit. A changed regression definition and a published commit make intent inspectable, but do not establish general validity or an observed passing suite.
