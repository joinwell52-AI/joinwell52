# A stored rule can disappear before the model sees it

The store still contains all three history records, including a rule. The next retrieval returns only the latest assistant reply. In one case from our internal function experiment, nothing was deleted from storage, yet the rule was absent from the returned context. A successful persistence check would miss the distinction.

For engineers maintaining agent memory and context compaction, the useful question is which transformation carries a constraint into the next call. Isolated probes of two frameworks' pinned source support a bounded answer: constraint delivery requires checking structural protection along the concrete path. Persistence, role labels and parameter names are insufficient evidence. Throughout this experiment, “delivery” means presence of the rule string in a tested function's output messages, before any real model request or action execution.

## Where the experiment draws its boundary

The research was completed on October 28, 2026. CAMEL's history retrieval and context creation were pinned to commit `64b9a613d1c3f4606be64aa6b66ebca437e50cda`; CrewAI's summary function was pinned to `76784a02f9a7342866d80400ffe067d1b3a28843`. These revisions identify the inspected source. They do not identify when a defect was introduced or establish the state of a live deployment. The [history source](https://github.com/camel-ai/camel/blob/64b9a613d1c3f4606be64aa6b66ebca437e50cda/camel/memories/blocks/chat_history_block.py) and [summary source](https://github.com/crewAIInc/crewAI/blob/76784a02f9a7342866d80400ffe067d1b3a28843/lib/crewai/src/crewai/llms/context_window.py) support the implementation descriptions.

The harness extracted method bodies through the abstract syntax tree and retained their implementation. Explicit adapters replaced framework records, storage and counting, while summary dependencies were controlled doubles. This is source-derived function testing, not an installation and reproduction of either complete framework. The internal record contains 36 role/position/window combinations, one empty-history control, six context-creator cases and six controlled-summary cases: 49 constructed cases in total. That count describes coverage. It is neither a collection of production incidents nor a denominator for a violation rate.

History tests compared storage before and after retrieval and checked whether an exact rule sentinel appeared in returned messages. Summary tests supplied outputs that either retained or omitted that sentinel, asking whether the surrounding structure depended on summary content. No real summarizing model was called, no external action was performed, and semantic equivalence after rewriting was not evaluated.

## History protection depends on position as well as role

The tested retrieval method protects the initial consecutive `system` and `developer` prefix, then applies a recency window to the remaining messages. “Initial” matters: a later record carrying the same role does not automatically acquire prefix protection. This is a mechanism for selecting returned records, not evidence that records were deleted from storage. The distinction is visible in the [pinned retrieval implementation](https://github.com/camel-ai/camel/blob/64b9a613d1c3f4606be64aa6b66ebca437e50cda/camel/memories/blocks/chat_history_block.py).

The following internal observations use a window of 1 and three stored records per case. Positions are zero-based. At position 1, an ordinary message precedes the rule, so it is outside the protected prefix. User messages supply ordinary input; the latest reply is an assistant message.

| Rule role and position | Sentinel in output? | Storage changed? |
|---|---|---|
| System, position 0 | Yes | No |
| System, position 1 | No | No |
| Developer, position 0 | Yes | No |
| Developer, position 1 | No | No |
| User, position 0 or 1 | No | No |

Source: the Research Center's same-date internal history cases. These are isolated-function observations without independent reproduction.

The later-system case makes the failed inference concrete: storage retained three records, while the output contained only the latest assistant reply. Initial system and developer rules survived the same window. No-window and negative-window controls retained the records; a zero window retained only the protected prefix. Together these outcomes reject both blanket claims: that all rules disappear as history grows, and that a role label alone establishes protection.

## A score-and-budget interface need not prune here

A tempting explanation is that a low-scoring old rule is subsequently evicted to meet a token budget. That is not what this pinned `ScoreBasedContextCreator` does: it no longer filters retrieved records by score or `token_limit`. The [implementation](https://github.com/camel-ai/camel/blob/64b9a613d1c3f4606be64aa6b66ebca437e50cda/camel/memories/context_creators/score_based.py), rather than the class name, is the relevant evidence.

Our internal uncached-path probes supplied three messages, changed the limit among 1, 10 and 10000, and reversed score ordering. All six cases returned all three messages. A deliberately artificial counter assigned 100 units per message and therefore returned 300 each time. It is a ruler for examining pruning conditions, not a real-model tokenizer or evidence of a live request overflowing.

This negative result narrows the diagnosis. The experiment cannot attribute an omission to score-based eviction in this creator. Another component might enforce the budget in a real deployment; identifying it requires following that call path. Nor can the existence of a downstream creator be treated as evidence that it will restore a rule already excluded by retrieval.

## Summarization changes content rather than selecting records

The other path rewrites working messages into a summary. The tested function separates explicit system messages for retention and passes the rest into summarization. That structural split is visible in the [summary implementation](https://github.com/crewAIInc/crewAI/blob/76784a02f9a7342866d80400ffe067d1b3a28843/lib/crewai/src/crewai/llms/context_window.py); it is not a promise of verbatim preservation for every role.

For each policy role, our internal test used one summary double that retained the sentinel and another that omitted it.

| Input rule role | After the retaining summary double | After the omitting summary double |
|---|---|---|
| System | Sentinel present; original system object retained | Sentinel present; original system object retained |
| Developer | Sentinel present in summary | Sentinel absent from output |
| User | Sentinel present in summary | Sentinel absent from output |

Source: the six same-date internal summary cases. Test doubles supplied these summaries; a real model did not generate them.

The system record did not depend on a faithful summary for retention. Developer and user rules did depend on what the summary said. The retaining control also matters: “summaries always erase rules” is unsupported. The observed distinction is structural dependence, not a measured frequency of omission by a summarizing model. Developer messages might also be normalized before reaching this function. Those paths were not audited, so these cases do not establish a framework-wide developer-channel vulnerability.

## Split “still there” into four checks

A history window changes output by selecting records; summarization changes it by rewriting content. The comparable dimension is constraint presence after transformation, not framework security. Our interpretation is that an investigation should record four distinct facts:

1. Is the rule still stored?
2. After selection, assembly and summarization, does it reach the context actually sent?
3. Which actor may modify, replace or override it?
4. Do the model and execution layer ultimately follow it?

These function probes cover local mechanisms within the first two checks. Finding a sentinel in output does not answer the last two. A practical next inspection would retain rule identity, role, position and output observations at each relevant transformation, then align them with the real request and action result. This is a proposed checking method derived from the evidence, not an implemented and validated general governance solution.

## What remains to trace in a real call

A sentinel's presence establishes only that this string crossed the tested transformation. Semantic equivalence, legitimate override, modification authority, model compliance and execution enforcement remain unmeasured. Cached counting and multimodal paths are outside the experiment. No prior paper's benchmark was reproduced, and none of its violation rates are attributed to these frameworks.

The next deployment-level questions are concrete: who determines message role and position, who can change an authoritative rule, and which component enforces the context budget after the creator? A model-and-action experiment must then ask a separate question: when a rule is actually delivered, can a noncompliant action still occur? Evidence for delivery cannot close the enforcement question.
