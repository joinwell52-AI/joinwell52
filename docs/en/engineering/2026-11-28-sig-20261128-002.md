# When similar issuer URLs are different identities

Two issuer addresses differ only by a trailing slash. A helper calls them equal; strict string comparison does not. The isolated experiment examined here observed that difference, without demonstrating a real login bypass. Client implementers first need to decide whether they are comparing a normalizable address or an identity the protocol requires to match literally, then connect their tests to the actual callback entry point.

## Three valid pairs, two equality relations

OAuth clients use issuer identifiers to distinguish authorization sources. The examined MCP authorization snapshot, labelled 2026-07-28, says that callback validation must not apply scheme or host case folding, default-port elision, trailing-slash or percent-encoding normalization before comparing decoded issuer strings. [Authorization response validation](https://modelcontextprotocol.io/specification/latest/basic/authorization)

The shared issuer helper in the admitted Gemini CLI PR #30454 head diff instead normalizes origins and trims path trailing slashes. An internal experiment in the completed Analysis extracted the original functions from that diff and found these valid HTTPS pairs equal under the helper but unequal under strict comparison.

| Difference between the pair | Helper | Strict decoded-string equality |
|---|---|---|
| Uppercase versus lowercase hostname | Equal | Unequal |
| Explicit versus omitted default port | Equal | Unequal |
| Present versus absent trailing path slash | Equal | Unequal |

Every cell is an internal function-probe observation, not third-party security validation. The [internal isolated-experiment record](/assets/evidence/2026-11-28-sig-20261128-002/experiment-evidence.json) retains exact inputs, all 11 outputs and controls. The distinction concerns equality; it does not equate same origin, trusted issuer and safe login.

## Where extraction and execution stopped

The probe binds PR head commit `c7e8d01912b897f6e1dc7c2a2765831f72b231e0`. Two original functions were extracted from the admitted diff. Conversion removed only export keywords and TypeScript annotations, preserving the function bodies. Analysis executed them in a local JavaScript environment with the standard URL parser, without network authorization or a simulated remote service. [Pinned helper source](https://github.com/google-gemini/gemini-cli/blob/c7e8d01912b897f6e1dc7c2a2765831f72b231e0/packages%2Fcore%2Fsrc%2Fmcp%2Foauth-utils.ts)

Of the 11 cases, identical valid addresses provide a positive control. Tenant paths, queries, fragments, userinfo and encoding differences probe the boundaries. The tested userinfo pair was rejected; the tested path, query, fragment and percent-encoding differences were not collapsed. The normalization results do not mean the helper treats every different string as equal.

Two deliberately invalid-input probes add another boundary: identical non-URL strings return equal, and relative strings differing by a trailing slash can also compare equal. A standalone equality helper is therefore not a complete URL validator. This does not establish that such strings can reach a production callback; preceding guards may exclude them. Literal equality is not a complete protocol validator either.

## Endpoint validation cannot replace identity comparison

The examined patch also rechecks endpoints after discovery, displays authorization and token origins during consent, and binds refresh destinations. Its manual cross-origin exception requires no discovery and explicit configuration of the required authorization URL, token URL and client ID. These are separate patch branches. Inspecting test text does not execute the full consent flow. [PR and diff](https://github.com/google-gemini/gemini-cli/pull/30454)

Those checks ask where credentials will go. Callback issuer comparison asks whether the returned identity matches the expected one. Resource-audience binding asks whether a token was issued for this resource service. The specification permits resource and authorization servers to be separate; the patch's endpoint-origin checks cannot be restated as a protocol requirement that both services share an origin.

Our interpretation is that reusing a URL-processing helper requires checking the equality contract at each call site. Normalization may be intentional for discovery metadata, while callback identity comparison may need to retain string differences. Separately maintained specification and implementation artifacts support the two sides of this comparison; neither independently reproduces the patch's security effectiveness.

## The next evidence has to come from a real callback

The next investigation needs complete pinned callback code and preceding validation. It should send the three valid address pairs through the actual path starting with the decoded issuer parameter. It should also check the mismatch rule for error responses, keeping displayed errors or downstream actions distinct from helper outputs. These are requests for subsequent research, not tests run here.

If the real path calls a different strict comparator, or preceding guards reject a form, the helper result cannot simply be generalized. If it uses this normalizing helper, the reached branch and consequences still need recording before drawing conformance or security conclusions. Both explanations require call-path evidence.

The supported finding is a comparison-contract difference for three valid address pairs. No full repository suite, OAuth network request, callback server, dynamic client registration, token refresh or exploit was executed. The helper already existed in callback code and was moved into shared utilities by this patch. The result therefore does not establish that this patch newly introduced the equivalences or a vulnerability.
