# A Past Approval, a Dedicated Predecessor, or a Fresh Question?

The same action enters inspection a second time, and the system asks again whether to perform it. Was an approval lost, or was each invocation supposed to ask? The completed internal source probe observed a fresh question without performing an external operation. Before judging that result, a platform or security engineer needs to identify the approval's lifetime: a fact somewhere in history, a predecessor available to one target, or a decision about the current invocation. The contract table below helps select the right second-occurrence test.

Our judgment is that **historical approval presence, predecessor consumption and synchronous current-action inspection specify different approval lifetimes. A retry guarantee must name the occurrence consumed and the evidence supporting that boundary.** This is a comparison of mechanisms, not a security ranking.

## Existing in history is different from being available once

Kyvvu's public manifest repository gives the contracts separate names. A historical approval rule requires a completed gate whose output decision passes, optionally restricted by kind, somewhere in task history. A dedicated-predecessor rule is separately documented as one predecessor consumed per target. The first asks whether approval exists in the past. The second introduces an allocation between predecessor and target. Calling both human approval does not make them the same single-use contract. [Repository rule definitions](https://github.com/Kyvvu/manifests/blob/main/README.md)

The captured high-risk policies use the historical rule with human kind. Read trace fixtures describe a passed human gate before a resource action and blocking when a gate is absent. These are source artifacts that were read, not engine tests executed in this run. They do not exercise a second target attempting to consume the same approval. [High-risk policy](https://github.com/Kyvvu/manifests/blob/main/manifests/compliance/eu-ai-act-high-risk.yaml)

Ordering has more than one granularity too. A financial policy requires a gate predecessor without an intervening model step before a resource POST. An external-content compound policy requires a gate directly before a high-impact step and counts attempts in its history query. These constrain order or adjacency. The disclosed conditions do not themselves show durable consumption bound to specific arguments, resource identity and a unique external effect. [Financial policy](https://github.com/Kyvvu/manifests/blob/main/manifests/compliance/financial-services-dora-mifid.yaml), [external-content policy](https://github.com/Kyvvu/manifests/blob/main/manifests/security/owasp-agentic-default.yaml)

Consider an illustrative sequence, not a deployed incident: one approval in history followed by two resource writes. Looking up history, demanding immediate adjacency and allocating one predecessor to one target ask different questions. Allowing the first write does not establish the second write's outcome. The actual selected rule and its consumption implementation still matter.

## Inspecting the current action does not create a durable credential

AgentSpec comes from a different author team. Its pinned human-inspection handler displays the current action, returns CONTINUE with that same action after an affirmative answer, and returns SKIP after refusal. The executor applies rules before performing the unwrapped action. This is a synchronous inspection path for the current in-memory action. [Pinned handler](https://github.com/haoyuwang99/AgentSpec/blob/e6fa3902e2cfb9681f454b355691b771f70543f8/src/enforcement.py), [executor](https://github.com/haoyuwang99/AgentSpec/blob/e6fa3902e2cfb9681f454b355691b771f70543f8/src/controlled_agent_excector.py)

The completed same-date internal experiment extracted the relevant classes from pinned source and exercised eight isolated cases with Action and Enforcement doubles. Invoking the same inspection handler twice prompted twice and returned CONTINUE twice. Refusal returned SKIP, while the separate Stop handler returned STOP. Invalid input, empty input and end-of-input cases also retain their observations. All eight cases matched their respective expectations; that is not eight full-system security tests. [Internal experiment record](/assets/evidence/2026-11-22-sig-20261122-002/approval-probe-results.json)

Two distinctions matter. SKIP suppresses the current action rather than establishing that all subsequent work stops. README wording that refusal halts therefore needs narrowing to the actual implementation path. Also, returning the same object is not an immutable approval snapshot. The post-return mutation case shows reference aliasing with the mutable double; it did not reproduce a concurrent deployment mutation or attack. [Documentation and implementation comparison](https://github.com/haoyuwang99/AgentSpec/blob/e6fa3902e2cfb9681f454b355691b771f70543f8/README.md)

The isolated experiment did not execute the full interpreter, framework dependencies, models, tools, external effects, concurrency or restart, nor the Kyvvu engine. No durable approval identifier, consumption ledger or restart protocol was displayed in the inspected path. That supports an unestablished guarantee, not a claim that the entire product lacks every such capability.

## Put the second occurrence into the contract table

The following is our interpretation of the captured materials and internal probe. Each row keeps its evidence form beside its unanswered question so documentation, visible code and execution are not collapsed into one capability label.

| Mechanism and sample | What the current evidence supports | Which occurrence to examine next |
| --- | --- | --- |
| Historical approval: manifest rule | Documentation and read artifacts require a qualifying approval in history; no engine run here | How does the selected rule decide for a second target with the same approval history? |
| Ordering or adjacency: financial and external-content policies | Read conditions exclude intervening steps or demand adjacency; no durable-consumption execution evidence | What happens after one intervening step or one additional attempt? |
| Dedicated predecessor: rule definitions | Documentation states one predecessor consumed per target; captured shipped manifests did not use this rule | How does a second target reserve or consume it? Does a blocked attempt spend it? |
| Current-action inspection: pinned handler | Visible code and internal isolated invocations show fresh prompts; refusal skips the current action | Does re-entering the call prompt again? Full-executor retry behavior remains untested |

The first three rows derive from the linked Kyvvu definitions and policies; the fourth derives from pinned AgentSpec source and the internal experiment. No row establishes replay resistance after restart, atomic concurrent consumption or exactly-once external effects.

The practical action is specific. The integrator identifies the actual rule, adapter and entrance. The evaluator records the approval object, lifetime, consumption unit and evidence form, then chooses a second occurrence matching that contract. If an integration promises dedicated consumption but supplies only evidence of a passed approval in history, acceptance of that consumption guarantee should pause. Stronger wording cannot supply the missing evidence. For per-call inspection, however, another question is not itself a contract violation.

## Two counterexamples to an easy verdict

A synchronous local interaction may intentionally ask every time and offer no reusable cross-process credential. Within that scope, another prompt is the policy, not evidence of lost approval. Conversely, an unseen engine might implement documented dedicated-predecessor consumption. Missing engine evidence is not evidence that the mechanism is ineffective.

Adapter context matters as well. Generic engine documentation says critical violations block while other levels ordinarily warn; a Claude Code integration manifest separately maps high severity to ask. Saying that a severity always blocks would generalize a conditional mapping. The public manifest repository is a generated mirror of a private platform, and a public merge alone does not establish shipment. [Authoring guide](https://github.com/Kyvvu/manifests/blob/main/docs/authoring-guide.md)

There is consequently no uniform “call it twice” shortcut to approval safety. History lookup, adjacency, dedicated consumption and synchronous inspection need different expected results. Without defining those expectations first, another prompt, a refusal and an allow decision can each be interpreted to fit a preferred verdict.

## Evidence and sources

The two external author groups supply primary evidence for their own disclosed contracts. Their authorship is independent; neither reproduced or certified the other. “Documented” refers to a public contract, “visible implementation” to the bounded pinned source, “internal experiment” to local isolated execution, and “our interpretation” to this synthesis. Citation is not endorsement, publication or a public repository is not validation, and internal implementation success is not general validity.

The research cutoff is the completed same-date object. The captured Kyvvu tree is `d7062e2de2b42144219f387106d81e44b1aa204f`; the AgentSpec commit is `e6fa3902e2cfb9681f454b355691b771f70543f8`. Mutable main-branch links locate the materials; judgments use the captured versions. Production did not refresh the research. [Internal results and version boundaries](/assets/evidence/2026-11-22-sig-20261122-002/approval-probe-results.json)

The next step is not to require every mechanism to issue the same credential. It is to obtain the missing occurrence for the chosen contract: real engine traces for a second target and a blocked attempt under dedicated consumption, or full-executor retry traces for per-call inspection. Cross-process promises additionally need restart, concurrency and actual-effect evidence. Until that evidence exists, which approval survives which retry remains an unaccepted guarantee.
