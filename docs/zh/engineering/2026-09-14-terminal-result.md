# 开场白为什么成了交付结果？

模型说“我来检查一下”，程序随后正常退出。自动调度器拿到一段非空文字，便把它放进结果文件。直到人工复查，才发现这不是完成报告，只是任务尚未开始时的开场白。

问题不在于模型说得像不像答案。供应商已经报告了错误，只是调度器采用了另一层更容易读取的信号：进程退出码为 0。

我们受到 anywhere-agents 一次修复的启发，用它的原始调度脚本和测试 CLI 做了五组前后对照。三种错误场景在旧版都无法满足验收断言，修复后全部通过；另外两组正常与兼容场景保持通过。这个实验说明，“正常退出”究竟可以替我们回答多大的问题。

## 错误事件里，也可能有一段像样的文字

anywhere-agents 是把不同编码 Agent 接到并行工作与评审流程中的工具集。Yue Zhao 在[这次修复](https://github.com/yzhao062/anywhere-agents/commit/3c94f459fa942727bbbf0a51ad1967d235096bc7)中处理了一个具体错位：Agy 遇到额度限制时，进程可能返回 0，而最终事件的状态为 `ERROR`，同时仍带着模型开场文字。

作者报告了真实批次中的错误发布。我们没有重新审计那 152 次历史 dispatch，也没有重跑真实 Agy 配额耗尽；本轮验证的是调度器怎样解释这样的输入。

实验使用固定提交的原始 Python 脚本，真实启动调度器子进程、读取流式事件并写入临时结果文件。供应商 CLI 由上游测试夹具模拟，因此我们能保持“进程退出 0”不变，只改变终态与产物是否已经存在。对照使用该修复的父提交，测试文件始终来自修复版本。

| 输入场景 | 旧版是否满足验收 | 修复后是否满足验收 |
| --- | --- | --- |
| 退出 0，终态 ERROR，附开场文字 | 否 | 是：失败并标记 FALLBACK |
| ERROR，但 Worker 已写结果文件 | 否 | 是：保留文件，执行仍失败 |
| ERROR 后又来一条不含状态的结果事件 | 否 | 是：保留先前错误判断 |
| 明确 SUCCESS，附结果文字 | 是 | 是 |
| 没有状态字段，附结果文字 | 是 | 是：保留旧版本兼容行为 |

这里的“通过”是测试断言成立，不是失败任务被批准为成功。前三行恰恰要求调度器正确承认失败。

## 文件可以留下，完成资格不能跟着留下

第二行最值得注意。一次运行后半段失败，并不意味着前半段生成的文件毫无价值。删除它会丢失证据；保留它却又不能等于整项任务通过。

修复选择保留 Worker 已写的结果，同时以非零退出状态报告执行失败。产物和执行结论从此可以表达两个同时成立的事实：“有材料可检查”，以及“本轮没有成功完成”。独立验收还要进一步检查材料是否满足用户目标，这一步也不能由文件存在代替。

第三行则处理事件流中的信息退化。最后到达的事件不一定包含最完整的信息；一个后来省略状态字段的事件，不应把之前明确的 ERROR 擦掉。原解析函数分别保留最近提供的状态、错误和非空文本。它解决的是这种缺字段覆盖，不代表我们已经证明所有事件乱序、重放或供应商协议变体都安全。

同样，不能把规则概括为“非 SUCCESS 一律失败”。当前实现对缺失或空白状态保留兼容通过，明确错误与没有判断依据仍是不同情况。未来记录这类结果时，值得让后续验收看见它是兼容路径，而不是把它写成供应商明确确认的成功。

## 第二天，问题向调度之前移动了一步

紧接着的[额度路由提交](https://github.com/yzhao062/anywhere-agents/commit/050ee0bd91c5d05c28f6f6b7c196a8d222328a4b)把模型组额度快照接到调度前。Claude/GPT 组已空时，可以转向 Gemini；Gemini 已空时，不擅自反向升级到较稀缺的模型组。降级选择会留下实际模型与 FALLBACK 说明。

我们另跑了七项上游额度策略单元测试：最紧额度桶、非有限数值、刷新失败的旧快照、重置时间、未报告模型组、模型名分组和关闭门禁，均通过。另有四项默认值、脚本存在、标识和终态辅助检查通过。这些用例使用临时缓存与替身，不是实时可用量或节省成本的测量。

其中一个细节限制了结论：另一个模型组没有出现在快照中时，代码把它视为未知，仍允许尝试。未知没有被包装成“确实可用”，也没有被一概当成“已经耗尽”。因此准入决定也需要保留证据的性质；调度前允许出发，不能替代调度后的完成判定。

## 我们自己的工程检查要落在哪里

在 CodeFlowMu/FCoP 的开发评审中，这组实验适合转成四个检查问题：进程如何结束，供应商如何结束，产物由谁生成，独立验收得出什么结论。先映射已有记录，再决定是否缺字段，不能因为画出了四层就立即新增四套账本。本轮没有审计或确认 CodeFlowMu 存在同一缺陷。

继续交流的问题也可以很具体：当旧供应商省略终态、系统按兼容策略允许结果继续流转时，后续验收能否区分“明确成功”和“缺失终态但允许尝试”？这是本轮实验引出的待验证问题，而不是已发现的新漏洞。
