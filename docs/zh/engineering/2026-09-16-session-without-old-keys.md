# 会话恢复了，旧密钥也该留下吗？

保存一段 AI 会话，是为了明天还能接着做。文件里有历史、设置、会话标识，都不奇怪。

如果启动程序时用过的密钥也一起保存了呢？

它明天可能已经不再适用，却仍躺在那份会话文件里。更容易误判的是：恢复时程序明明换用了新密钥，旧文件也未必已经干净。

我们用真实临时文件做了一个小实验。**“恢复用了新值”和“磁盘不再留着旧值”，确实是两个不同结果。**

## 一个值得拆开的保存动作

这个问题来自 electrumnz 提交的 [Paperclip #13498](https://github.com/paperclipai/paperclip/pull/13498)。Paperclip 是用于组织 AI 助手工作的开源应用。这份尚未合入的提案指出：启动助手时使用的环境变量，会随会话设置写入记录；其中可能含有当前运行绑定的凭证。

上游还讨论了同一操作系统账号下多个助手席位的读取风险。那是来源报告的部署条件，我们没有在真实多席位环境中复现。

我们关注它，是因为长期任务常常把“可恢复”理解成“尽量多保存”。但对话内容、文件成果与启动凭证的有效期并不相同。研究问题因此可以收窄：恢复会话，是否必须从旧记录恢复当时的环境变量？

候选实现给出的做法是，写盘前移除启动环境；恢复时从当前运行重新注入。它还提出关闭相关 shell 快照的改动，本文没有把那条路径算作已验证。

## 用假凭证，检查真的文件

我们直接执行候选的会话存储包装器，把底层存储接到临时 JSON 文件。测试只使用明确的合成字符串，不读取任何真实密钥。

先设一个旧值，再用另一个当前值恢复；同时检查原始会话对象、磁盘字节与加载后的对象。对照结果如下：

| 操作 | 磁盘是否仍含旧合成值 | 恢复时是否使用当前值 |
| --- | --- | --- |
| 不经保存过滤，直接写原记录 | 是 | 是，恢复仍经过候选包装器 |
| 经候选包装器保存新记录 | **否** | 是 |
| 读取一份已有旧记录，不再保存 | **是** | 是 |
| 读取旧记录后，再经候选包装器保存 | **否** | 是 |

四个场景都保留了对话历史，也没有把传给保存函数的原对象改掉。最后一点很实用：运行中的会话仍可能需要原环境；去掉磁盘里的环境，不该顺手破坏内存中的当前运行。

## 为什么旧记录读过了，旧值还在？

因为“读取并返回一个新对象”，本来就不等于“重写原文件”。

候选加载函数把当前运行的环境放进返回对象，所以恢复者可以看到新值。但它没有在读取期间调用保存函数。我们直接检查磁盘字节，旧值仍然存在；随后明确再保存一次，它才从受测位置消失。

这不是说候选修复无效。它成功阻止了新保存记录继续携带启动环境，也让恢复采用当前环境。实验揭示的是升级时的另一项责任：已有记录是否需要清理，清理何时发生，哪些备份仍可能保留旧副本？

只看“下一轮能正常启动”，回答不了这些问题。

我们还做了第五个边界场景：故意把同一个合成值塞进一个无关的调试字段。候选移除了指定的启动环境字段，但没有删除那个任意字段里的值。这说明它是针对已知结构的过滤，不是扫描整个对象的通用清洗器。这个字段是我们人为构造的，不能据此宣称生产程序存在另一条泄露路径。

## 新写入、旧副本与凭证失效，要分别回答

这项研究带来的启发，不是“会话都不能落盘”。该保存的对话历史仍然保存，而一次运行使用的权限材料，应有自己的有效期与处理方式。

开发者可以把升级检查拆成三问：新写入是否还带旧环境？既有记录是否被处理？需要失效的旧凭证是否已经失效？第三问涉及凭证管理，本实验并未执行轮换或吊销。

对普通使用者，更容易理解的需求是：更换账号或连接配置以后，软件不仅要告诉我“现在能用了”，还要说明是否仍保留旧连接材料，以及哪些历史内容会继续保存。

下一步值得与维护者交流的是：清理旧会话记录是由本提案处理，还是明确交给独立迁移？只有把这个责任说清，才能避免把“恢复成功”误当成“旧副本已经处理完”。
