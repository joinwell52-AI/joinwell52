# 超时必须终结它所拥有的生命周期

一个命令显示“已超时”，调用者却仍然不返回，这并不矛盾。直接子进程可能已经退出，但它创建的后代仍持有输出管道；清理代码为了收集完整输出继续等待，于是超时只终结了一个进程标识，没有终结这次调用拥有的生命周期。

Google ADK Python（智能体开发工具包）的一项已合并变更展示了具体的本地主机方案。命令在新的 POSIX（可移植操作系统接口）会话与进程组中启动，整个生命周期只有一个受保护的输出读取任务。超时和调用者取消走同一清理路径：先发送终止信号，等待一个有界宽限期；仍未结束时发送强制结束信号，再等待第二个有界宽限期；输出读取仍卡住时，放弃等待并返回。

核心判断是：**有界执行应沿生命周期所有权，而不是只沿直接进程身份。终态证据必须准确说明所拥有的进程域发生了什么，不能把有界清理扩大成“所有后代和外部效果都已消失”。**

## 从直接进程扩展到调用所有权

一次工具调用可以把工作委派给多个后代。若运行体只拥有最初返回的进程标识，委派就会成为责任断点：父进程结束后，后代仍可运行、占用资源或保持管道打开。

进程组比直接进程更接近真实责任范围。它把同一次调用创建的本地进程域放在一个可统一发信号的边界内。测试覆盖的后台心跳后代，在超时和取消两条路径后都会停止，这说明边界关闭了已展示的逃逸。

但“进程组”仍不是抽象意义上的完整进程树。后代可以创建新会话并逃离原组；远程任务、容器和外部服务也不受本地组信号约束。因此，可迁移的原则是显式所有权域，而不是把某个主机机制误写成通用答案。

## 清理也必须有截止时间

只给主要命令设置超时不够。若清理阶段无限等待管道、锁或温和退出，用户看到的截止时间就不真实。清理本身需要自己的上界和升级策略。

一个受保护的输出读取任务很重要，因为超时时重新启动第二次读取会制造两个消费者，产生丢失、重复或竞态。共享同一个读取所有者，再让超时与取消复用清理路径，可以让两种终止原因遵守相同资源责任。

先温和终止、后强制结束，给进程短暂释放资源的机会；第二次等待仍失败时放弃输出，则明确选择了生命周期有界性优先于取证完整性。这不是无损方案，而是可说明的工程取舍。

## 取消不能抛弃拥有的工作

调用者取消常被实现为立即抛出异常。如果父协程在清理前退出，子进程就变成无主资源。更可靠的顺序是：先执行有界清理，再传播取消信号。这样，控制流可以被取消，生命周期责任却不会被静默丢弃。

有意长期运行的服务属于例外，但需要显式移交所有权。移交回执应指出谁接管、凭什么授权、如何终止；没有移交证据的脱离进程，应被视为泄漏或不确定残余，而不是合法服务。

## 终态应报告真正证明的事实

一个有用的超时回执可以分别记录：直接进程是否退出、所拥有进程组是否终止、是否升级到强制结束、输出是否被放弃，以及是否存在逃离所有权域的资源不确定性。

这种分层语言避免两种错误。第一种是把“命令已超时”误报为“所有工作都已停止”；第二种是因为无法证明任意后代都消失，就否定所拥有进程组已完成有界清理的事实。

## 适用边界

证据来自一个已合并实现及其维护者测试，并只在支持进程组信号的平台上建立保证。它不覆盖 Windows（视窗操作系统）作业对象、容器、远程作业、守护进程移交或分布式外部效果回滚。强制结束后的输出也可能不完整。

因此，跨平台设计应寻找等价的所有权抽象：本地主机可以是进程组，其他环境可以是作业对象、容器标识或远程租约。机制可以变化，责任不应变化：**截止时间必须约束调用真正拥有的工作，完成回执也只能声称已被证据覆盖的边界。**

**一手证据：** [Google ADK Python 已合并提交 fa321f1b](https://github.com/google/adk-python/commit/fa321f1b49f7bd961b58ad19fd8b8e6fa285b918)。该实现支持有界的本地进程组清理结论，不证明任意进程树或外部效果均已终止。
