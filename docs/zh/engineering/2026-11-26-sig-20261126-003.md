# 回执丢失后，操作仍然没有定论

订单提交后连接断开，本地只剩一条待决记录。此时再发一次，可能重复下单；直接清掉记录，又可能失去追踪已发生效果的责任。这是一个示意故障场景。本文的判断是：超时没有裁定远程结果，即使取回格式正确的记录，也要先检查它属于哪次操作，再决定如何恢复。读者可以据此写出一张保留、再验证与终态清理的处置表。

## 本地提交与远程效果之间的缝隙

PIEQ（来源隔离的认知仲裁研究）区分两种情形：去重记录与受保护效果共用原子边界，以及真正发生在远端的操作。前一种设计可在同一边界内联动裁决；后一种如果没有共同事务，网络确认丢失后，调用方不能只凭本地超时判定远端未执行。论文要求保留未知状态并对账，不能把本地去重直接升级成远程恰好一次效果。[论文第 5.2 节](https://arxiv.org/html/2611.32032v1)

固定实现进一步显示，控制器仅在验证到经过隔离的无效果结果时释放风险敞口，否则保留未知状态。这里的观察不包含内存台账的崩溃持久性证明。[控制器源码](https://raw.githubusercontent.com/openkedge/openkedge/80836b200ec56d8d4ef845cf86c0c2873314b287/research/pieq/pieq/hardened.py)

这个边界问题并不意味着“永远不重试”。如果目标系统提供经验证的原生幂等合同，某些重复请求可以安全合并；关键是合同是否覆盖同一操作、持续多长时间，以及失败边界是什么。本轮没有测试这类目标保证，所以不能据此宣布某个远端调用可以安全重发。

## 取回订单，还要确认是同一笔

独立作者团队的 Vibe-Trading（智能体交易研究系统）提供了具体对账路径。论文区分研究证据与下单授权，并区分已接受、已拒绝和未决订单；所查实现会在提交前保存面向 Alpaca（券商接口）的操作意图。论文与其仓库属于同一个作者主体，不因材料形式不同而增加来源数量。[论文](https://arxiv.org/html/2611.24845v1)

固定版本的恢复函数按原客户端订单编号查询外部结果，不重新提交订单。后续校验要求结果具有券商订单编号，并比较客户端编号、标的、方向、订单类型与有效期，再比较数量、名义金额与限价；时间必须带时区，成交量不能为负，状态必须属于已知集合。它检查的是恢复证据与待决请求的一致性，不能单独认证提供者说的是真话。[订单恢复源码](https://raw.githubusercontent.com/HKUDS/Vibe-Trading/2134f408b1cd715c74fa8c5021f4402d50b00ea8/agent/src/live/sdk_order_gate.py)

待决记录模块还把请求、客户端编号、券商编号、阶段与持仓归因连接起来，但该模块支持的是上述券商路径。不能把这份证据写成全部连接器已经具有相同恢复能力。[待决记录源码](https://raw.githubusercontent.com/HKUDS/Vibe-Trading/2134f408b1cd715c74fa8c5021f4402d50b00ea8/agent/src/live/pending_action.py)

这里的独立性是作者独立：前者团队给出原子边界和保留责任的研究，后者团队给出具体订单实现。它们能支持机制比较，不构成相互复现实验，更不能推出实盘可靠性或投资收益。

## “已成交、成交量零”为什么仍能通过一层检查

同次研究分析已运行两组内部隔离探针：十七个记录校验用例、五个恢复用例。方法从固定源码提取原函数，用合成请求、券商应答和外部边界替身运行；计数、持久审计、待决迁移和清理只记录调用意图，没有实现真实存储。这里消费的是已完成的实验，Production（文章生产阶段）没有重新实验。

记录校验拒绝身份或数量不符、无时区时间、未知状态与不合法数字；数值十与十点零零视为相等。一个刻意构造的反例是：状态写“已成交”，成交量却为零。记录校验仍返回规范化结果；随后恢复函数识别状态与成交量矛盾，走停止分支。因此，单看前一函数“接受”就宣布系统放行，会读错层次。

| 合成输入 | 被观察的层 | 本轮实际结果 |
| --- | --- | --- |
| 客户端编号或数量不符 | 记录校验 | 不形成可用恢复记录 |
| 查询抛错，或取回身份不符 | 恢复函数 | 返回未决拒绝，不重提订单 |
| 身份一致、仍在工作中的订单 | 恢复函数 | 请求计数与策略再验证 |
| 身份一致、明确拒绝的零成交订单 | 恢复函数 | 请求清理待决记录 |
| “已成交”且成交量为零 | 先校验、后恢复 | 前层接受，后层停止 |

[内部探针的完整用例与结果](/assets/evidence/2026-11-26-sig-20261126-003/experiment-evidence.json)

这正是分层解释的价值：格式和字段一致性负责筛出可解释材料，恢复策略负责决定材料意味着什么。本轮五个恢复分支没有调用重新下单，但这不证明所有上游入口都不会重发，也不证明替身记录的清理已在真实磁盘持久化。

## 让待决责任跟着证据走

下面是一份供远程写操作使用的建议责任表，不是对所有交易系统已有行为的描述。它把“等待”“拒绝使用错误证据”“停止处理矛盾”分开，避免用一个失败标签覆盖所有后续动作。

| 责任主体与输入 | 应保留的产物 | 处置边界 |
| --- | --- | --- |
| 提交方构造操作意图 | 可关联到具体操作的身份与请求 | 尚未发送，与已发未确认分开 |
| 恢复方面对超时 | 原待决记录与查询尝试 | 读取失败保留未决，不能宣称未执行 |
| 证据校验方接收外部记录 | 一致性检查与规范化记录 | 身份不符不应用到当前操作 |
| 恢复策略接收工作中状态 | 责任归属与再验证要求 | 仍在工作中，不等于重新获准写入 |
| 清理方接收确切终态 | 对应操作的终态与清理结果 | 清理失败仍需保留恢复责任 |

在这一路径中，“明确拒绝”与“工作中”产生不同处置；部分成交又涉及持仓归因，不能沿用零成交清理。审查时应把待决记录、每日计数、审计与外部订单的持久性逐项列出。代码中存在清理调用，不代表它与券商效果原子完成。

## 下一次故障注入应回答什么

本轮结果限定于固定版本：具体恢复实现来自提交 2134f408b1cd715c74fa8c5021f4402d50b00ea8，原子边界比较来自提交 80836b200ec56d8d4ef845cf86c0c2873314b287 与论文第一版。前者是较晚的实现证据，不等同于论文评测时冻结的代码。完整券商服务、文件锁持久性、审计失败、部分成交归因与多客户端竞争均未在这些探针中复现。

PIEQ 论文中的物理测试仍是作者报告。其共享宿主内核和每秒一次的观察方式，不能排除更短时间窗的双主状态；原生集群保护也不能归功于逻辑推理本身。论文发表或源码开放，只确立材料来源，不补足独立验证。[原子边界与物理测试说明](https://arxiv.org/html/2611.32032v1)

下一步可在有授权的测试环境中注入：外部记录格式正确但过期、审计落盘失败、清理中断、部分成交后重启，以及另一个客户端同时操作。还应验证目标原生幂等合同。若这些问题没有答案，合理结果可能仍是保留待决并人工对账。超时后的恢复价值，首先在于没有丢掉责任，而不是更快地宣布完成。
