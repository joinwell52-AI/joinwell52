# 因果标签之后：一次归因模块探针能说明什么

两端判据都失败，再放入一个非空字符串，就足以得到“框架导致失败”的输出吗？在本次固定模块的合成调用中，可以。更值得注意的是：候选连接的两个端点都不存在于失败集合时，因果标签仍然激活，而已追踪失败数量为零。这一组合把标签名称与证据状态之间的距离具体暴露出来。

本文只报告归因模块的局部契约：候选机制链的程序化激活与完成因果核验是两种证据状态。它不报告完整基准复现，不估计真实运行的错误归因率，也不推断调用方一定没有预校验。

## 两个失败还没有构成因果链

TraceTrial（框架与智能体双维度评估基准）把任务侧表现与框架侧判据分开，并区分测量装置是否可用。这个区分有价值：任务结果错误不自动说明框架损坏，框架判据为零也不能单独证明它导致了任务失败。论文对传播链提出额外核验要求，包括确认端点、识别中间信息失真、支持事件顺序，以及检查竞争解释。[论文第一版，第 3.5 节、表 5 及附录中的传播链说明](https://arxiv.org/pdf/2610.32285v1)

证据的权威来源也因问题而异。环境状态支持实际效果，模型实际收到的原生记录支持它接触的信息；提供方记录只能支持已捕获的结构化声明。整理后的连续序号是展示顺序，不会凭空创造因果顺序。本文据此把“有候选连接”与“连接已经得到证据核验”分开。[论文，第 3 节](https://arxiv.org/pdf/2610.32285v1)

## 固定版本上的局部实验

同日分析阶段使用读取时固定的归因源码提交（见下文固定版本链接），对原始独立模块执行了 12 组合成判据调用。环境为 Python（程序解释器）3.12.9 和 Windows（操作系统）。写作阶段复用已完成结果，没有运行新实验。

这不是原生轨迹回放：没有执行基准任务，没有读取真实档案、私有判定标准、语义裁判或调用方。完整合成输入、输出、源码哈希及环境见[内部探针记录](/assets/evidence/2026-11-13-sig-20261113-007/article-evidence.json)。下表列出全部 12 组调用；“框架导致”等中文是原始输出标签的对应含义，不是本文对真实因果关系的判定。

| 合成条件 | 模块输出的标签含义 | 已追踪失败数 |
|---|---|---:|
| 两层失败，没有连接 | 智能体导致 | 0 |
| 两层失败，链为空串 | 智能体导致 | 0 |
| 两层失败，链只有空白 | 智能体导致 | 0 |
| 两层失败，链为单字符占位串 | 框架导致 | 1 |
| 两层失败，框架连接端点不存在 | 框架导致 | 1 |
| 两层失败，两个连接端点都不存在 | 框架导致 | 0 |
| 两层均通过 | 干净运行 | 0 |
| 仅框架层失败 | 框架缺陷被吸收 | 0 |
| 仅智能体层失败 | 智能体导致 | 0 |
| 测量装置失败，仍提供非空链 | 因装置失败而无法判定 | 0 |
| 框架层没有可测量判据 | 因未测量而无法判定 | 0 |
| 智能体绕过指定观测通道 | 智能体导致 | 0 |

预设断言均通过。重要的负对照是空串、空白、测量装置失败和未测量条件：模块并非给任何输入都附上框架因果标签。最后一项也按代码的操作规则处理了被绕过的观测条件，不能直接读成框架自身的内在缺陷。

核心占位输入可以简写如下；这段仅摘示已执行输入，不是另一次实验：

```text
failed harness criteria: H1
failed agent criteria: A1
candidate link: H1 -> A1
chain: "x"
output attribution: harness_caused
```

当连接两端都改为失败集合之外的标识时，输出仍为同一个因果标签，但追踪数量变为零。代码计算追踪数量时检查智能体端点是否位于失败集合；进入联合失败的因果标签分支则只需要仍有被接受的连接。两者的接受条件并不相同。[固定版本归因模块](https://raw.githubusercontent.com/TraceLite-AI/TraceTrial-Bench/98a381307184fa4212db3466b21b4c92a031940b/tracetrial_bench/attribution.py)

## 激活与核验是两种契约

属性 `is_substantiated`（是否具有实质支撑的属性）在这个模块中检查的是去除首尾空白后，链文本是否非空。这个名字容易让读者联想到“已有实证支撑”，但函数本身没有完成论文描述的端点、失真、顺序与竞争解释审阅。内部探针展示的是该程序谓词的接受范围。

因此，模块输出的 `harness_caused`（框架导致标签）应被理解为候选机制链被激活的状态，不能自动升级成“因果核验完成”。论文自己的操作解释也保留了这个区别。局部源码的命名和可执行条件需要一起阅读，不能只相信其中较强的一面。[论文传播链规则](https://arxiv.org/pdf/2610.32285v1)；[原始模块实现](https://raw.githubusercontent.com/TraceLite-AI/TraceTrial-Bench/98a381307184fa4212db3466b21b4c92a031940b/tracetrial_bench/attribution.py)

这个区别也约束了基准数字的解释。论文报告 95 个任务、9 个模型组和4种框架构成 3,420 个选定实验单元，每个单元保留一次执行，包含替代运行。在 1,700 个双侧未达标运行中，842 个激活了至少一个候选链接，即条件比例 49.5%。这些是来源报告的档案计数，不是本次复跑结果；49.5% 不是因果判断准确率，也不是已经核验的传播率。必需证据选择器没有匹配而得到零分，仍不能单独证明被测系统存在缺陷。[论文，第 4—5 节](https://arxiv.org/pdf/2610.32285v1)

## 调用方的预校验可能改变解释

最有力的替代解释是：这个模块可能有意只接收已核验连接。若调用方已经确认端点和机制链，模块不重复检查未必错误。本次没有审计调用方，也没有检查真实档案中传入的连接，所以合成畸形输入并不建立已经发生的生产故障。

版本绑定也是边界。读取时的源码提交不等于论文实验冻结版本。论文使用的清单名称与当前仓库说明不同；当前清单中的文档摘要也不同于已读取的第一版论文文件，且清单指向的是另一文件名。因此，字节身份尚未建立；摘要差异本身不能证明任务成员已经变化。本文没有核算最终评分档案，也没有重跑基准。[固定版本任务清单](https://raw.githubusercontent.com/TraceLite-AI/TraceTrial-Bench/98a381307184fa4212db3466b21b4c92a031940b/Task/final.manifest)

这些边界不是对论文造假的暗示。论文要求更强的人工审阅，与局部模块采用较窄的输入契约可以同时成立。

## 保留证据状态，而不只保留标签

由本次观察支持的接口设计判断是：分别保存判据失败、候选链接、端点核验、中间失真与顺序审阅的状态，并说明由哪一层承担核验。如果只有一个强因果名称，下游读者容易把尚待审阅的候选解释当成已完成判断。缺失证据应保留为缺失，而不是被字段名称遮蔽。

对实际效果与交互要求也应采用同样的区分。论文的配对案例中，正确的最终值可以与重复执行了仅允许一次的动作同时出现；任务产物正确与交互合规因此需要不同依据。MAST（多智能体系统失败分类研究）所描述的未完成验证、错误验证与过早终止，可以作为定位问题的比较词汇，但它没有独立复现本次模块或验证同一条传播链。[配对案例，论文附录最后部分](https://arxiv.org/pdf/2610.32285v1)；[失败分类研究，第三版](https://arxiv.org/html/2503.13657v3)

## 真实运行中仍需建立什么证据

本次能够回答模块接受了什么输入，不能回答真实候选链有多少通过了端点、信息失真、事件顺序与竞争解释审阅。下一步需要把选定运行、任务版本、原生轨迹、判定提示和最终评分绑定到同一个实验版本，再检验候选链如何进入归因模块。

在这项证据出现之前，最稳妥的读法是保留两种状态：程序已经激活了一个解释，因果证据是否足够仍待核验。
