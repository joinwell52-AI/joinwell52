# 部署许可、通道仲裁与动作确认，各自在批准什么

一次文件读取任务已经获准，执行前符号链接却指向了另一个文件：旧检查还能代表这次调用的权限吗？这不是仅靠“智能体已经批准上线”就能回答的问题。部署许可、通道仲裁与动作确认检查的对象不同。把它们逐项写成“谁在什么时候检查什么、哪条路径除外”，比把三个功能勾选为已启用更有用。

## 同样叫批准，决定的却不是同一件事

下面比较的是已读材料中的责任范围，不是产品安全排名。ServiceNow（企业服务管理平台）的批准文档描述：相应功能启用后，资产或服务器需获批准才能成为可用对象。这个决定回答“能否提供使用”，并不自动回答“某个调用者能否对这个目标执行这组参数”。未启用的能力也不能算作已观察到的防护。[部署批准文档](https://www.servicenow.com/docs/r/intelligent-experiences/ai-control-tower/explore-approvals.html)

AG2（多智能体框架）的网络文档把通道决定前的仲裁与决定后的监听分开。前者能够在转换之前参与判断；后者适合观察已经发生的转换。监听记录能说明发生了什么，却不能单凭“有记录”推出操作之前已经获得授权。文档描述的是架构责任，本轮没有审计其传输身份认证。[网络架构文档](https://docs.ag2.ai/docs/user-guide/network/overview/)

OpenHands（软件开发智能体项目）的安全指南描述由风险分析器给动作评级，再由确认策略决定是否询问用户。它还明确指出，直接调用工具的接口会绕过对话循环中的分析器和确认策略。这是文档声明的覆盖边界；本轮没有执行绕过攻击。[安全指南](https://docs.openhands.dev/sdk/guides/security.md)

| 材料中的检查 | 决定对象与介入时点 | 证据还没有回答的问题 |
| --- | --- | --- |
| 部署批准 | 配置启用后，资产或服务器成为可用对象之前 | 当前调用的目标、参数与调用者权限是否匹配 |
| 通道仲裁 | 通道转换决定之前 | 发起身份是否真实、工具是否覆盖全部入口 |
| 事后监听 | 转换发生之后 | 这一次转换是否曾被事前阻止或放行 |
| 动作确认 | 受覆盖的对话循环中，风险判定之后、动作执行之前 | 直接调用、恢复入口以及批准生命周期如何处理 |

表中前三类材料来自各项目自己的官方说明，属于来源陈述。不同团队对各自范围的说明足以支持对象与时点的比较，不能相互充当同一系统的独立复现。“尚未回答”也不表示产品没有相应能力。

## 一个确认函数通过检查，能支持多大结论

固定源码中的确认谓词很具体：风险未知时读取单独的确认开关；风险已知时把阈值交给风险比较方法；配置阈值不能是未知值。这个函数判断是否需要确认，不是凭据系统，也不负责说明所有调用入口是否经过它。[固定源码](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/141423921fdaeb08cd5f53464a69e860da70b66f/openhands-sdk/openhands/sdk/security/confirmation_policy.py)

同日分析阶段的内部实验从这份源码派生函数体，使用未知风险哨兵和已知风险比较替身，执行了六项隔离检查。下表只复述已经取得的结果，制作阶段没有新运行实验。

| 输入或对照 | 内部观察 |
| --- | --- |
| 未知风险，确认开关开启 | 返回需要确认 |
| 未知风险，确认开关关闭 | 返回无需确认 |
| 已知风险替身，比较方法返回真 | 返回真，阈值原样传入 |
| 已知风险替身，比较方法返回假 | 返回假，阈值原样传入 |
| 把未知值作为阈值 | 抛出阈值不可为未知的错误 |
| 把已知对象作为阈值 | 原样返回该对象 |

这是内部实验依据，不是第三方验证。真实风险枚举的阈值相等语义、配置模型的集成行为和完整对话执行链均未在这些检查中运行。源码注释说明阈值相等时也需确认，但注释不是本次对真实枚举的测量。当前安全指南与固定提交又是不同版本节点，不能合并成同一版本的端到端通过报告。

这组结果的价值在于限定责任：开关和比较委派的分支行为有内部观察支持；“所有工具调用都经过这个函数”没有。因此，验收应继续问入口覆盖，而不是把函数通过升级为完整授权保证。

## 目标仍在目录内，也可能不是先前批准的目标

独立作者团队（Lazer、Aryal、Gupta 与 Bertino）的四框架研究，把符号链接变化与路径包含检查放在不同实验中。作者报告，在旧路径验证之后改变链接，受测配置仍会跟随新目标；另一些受保护配置能用路径规范化检查或沙箱阻止路径穿越。这两个结果可以同时成立：资源位于允许目录中，不代表它还是先前核准的那个对象。[四框架授权研究，第 3.2 节](https://arxiv.org/html/2611.21259v1)

开头的文件读取是依据这一研究场景改写的审查例子，不是本文新发现的线上事故。沿着它追问会得到不同答案：部署批准说明工具可用；通道仲裁说明任务怎样流转；动作确认说明哪类风险需要询问；当前资源解析则决定实际触及哪个文件。我们的解释是，前面的许可不能替代后面针对当前目标的证据。这不要求每个系统使用四个组件，而要求验收结论准确对应真实责任。

研究还区分了未经授权的工具调用、宿主副作用与最终信息泄露。请求抵达执行接口但被后续防护阻断，与请求从未抵达接口，是不同结果。把它们压成一个“安全/不安全”的标签，会遮住真正需要修补的责任边界。[研究范围及结果说明](https://arxiv.org/html/2611.21259v1)

这些都是作者报告，本文未复现其攻击成功率。研究使用共同模型和特定版本配置；企业身份与访问管理、凭据认证以及外部策略引擎并未得到全面评估。论文中的微软多智能体框架样本也不能等同于当前网络文档中的项目。

## 用一条真实调用替代功能勾选

下面是研究建议的验收方法，不是任何样本已经实现的统一机制。选择一条实际调用，例如“读取审核后的文件”，逐阶段向负责方索取证据：

| 阶段 | 输入、责任与输出 | 应暂停验收的条件 |
| --- | --- | --- |
| 提供能力 | 部署管理者接收资产配置，输出可用范围 | 启用条件或排除范围不清楚 |
| 传递任务 | 应用或仲裁者接收调用身份与任务，输出获准流转的请求 | 只有名字或事后日志，无法解释授权依据 |
| 请求确认 | 策略与批准者接收具体动作，输出可追溯的决定 | 批准没有绑定目标、参数或必要前置状态 |
| 执行调用 | 执行方接收请求与当前资源，输出效果及记录 | 实际入口不经过检查，或资源变化后的处理不明 |
| 重试或恢复 | 恢复方接收原决定与当前状态，输出继续或重新申请 | 无法区分网络重试、重放与需要重新批准的动作 |

对于高风险操作，还要分别查明批准何时过期、是否只能消费一次、状态变化是否使旧批准失效，以及应用检查之外有哪些进程或容器权限限制。没有记录就把该项列为未验证；不要因为另一个阶段有成功记录而补成通过。

反例同样重要：有限单用户场景里的同步确认可能已经足够，不必为了对齐表格增加整套组件。只需让威胁模型、实际入口和验收结论保持一致。缺证据是继续核查的理由，不是断言产品缺失能力的理由。

## 仍需补齐的证据

本轮没有安装完整软件开发工具包，没有进行直接工具绕过、批准过期、一次性消费、重放、恢复路径撤权或宿主隔离测试。四个外部团队是独立作者，但并没有交叉复现同一个授权实现。内部六项检查只能支撑局部分支行为。

下一步应先固定一条真实路径及版本，再对同一目标执行状态变化、重试与重新批准的对照，并分别记录请求是否进入工具、宿主是否产生效果、信息是否外泄。这是待执行的验证方案。真正值得追问的不是“批准功能有没有”，而是“这次决定绑定的对象，在产生效果时还是同一个吗”。
