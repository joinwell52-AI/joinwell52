# 检查已经报错，AI 为什么还记住了那句答案？

AI 写出了一段答案，负责检查它的服务却断了。界面告诉你“出错了”。

你接着问下一句，心里大概会默认：刚才那段没有完成检查的内容，不会被当成正式历史继续使用。**但在我们的对照实验里，旧逻辑一边报错，一边把答案存了下来；下一轮，模型真的收到了它。**

问题不在于 AI 忘记了什么，而在于它记住了一句还没有通过检查的话。

## 错误提示，只说明了眼前这一轮

这个问题由 jbeckwith-oai 在 [OpenAI Agents JS #1938](https://github.com/openai/openai-agents-js/pull/1938) 中提出并修复。这个程序库帮助开发者把模型、工具和多轮对话接在一起。它的输出检查可以判断答案是否应被拦下；检查本身也可能因为服务故障而异常退出。

我们研究长期运行的 AI 助手，对这类变化感兴趣，是因为错误常常被理解成“一次回答没成功”。如果未经检查的答案已经进入会话历史，影响却可能延续到以后。仅测试“本轮有没有抛错”，就漏掉了更重要的一问：下一轮究竟看到了什么？

上游把明确拦截与检查异常区分开来。旧实现已经会处理“检查说不行”；这次修复补上的是“检查没能完成”。

## 把下一轮也跑起来，才看得见差别

我们固定源码版本，让一个测试模型输出同一句标记文本，再控制检查程序分别通过、拒绝、抛错，或让一项检查通过而另一项抛错。随后真正调用下一轮运行入口，检查模型收到的历史。

模型服务由脚本替代，运行入口和会话处理使用真实 SDK 代码。我们同时覆盖流式与非流式运行，以及内置内存会话与只支持追加的会话。每种检查结果都有四个组合，两个版本共记录三十二条观察。

| 检查结果 | 旧判断：答案进入下一轮 | 修复后：答案进入下一轮 |
| --- | --- | --- |
| 全部通过 | 4/4 | 4/4 |
| 明确拒绝 | 0/4 | 0/4 |
| 检查抛出异常 | **4/4** | **0/4** |
| 一项通过，另一项抛错 | **4/4** | **0/4** |

这不是线上事故发生率。每个分母 4 都是我们明确安排的“运行方式 × 存储方式”四种组合。

正常答案没有被一刀切地删除。三十二条观察中，先前已保存的回答和本次用户问题都保留了。我们还运行了上游对应测试文件，七十一项通过；它覆盖了工具输出等更多情况，不能与这三十二条自编观察相加成一个可靠性分数。

## 一项检查通过，不能替另一项补答案

更容易忽略的是表格最后一行。一段回答可能要接受几项不同检查：一项已经说可以，另一项却没能给出结论。

实验里，部分通过没有改变修复后的处理：这份最终答案仍不进入正式会话历史。这并不表示答案已被证明有错，只表示它还没有取得本次所需的检查结果。

由此得到的启发很具体：**保存“模型曾经说过什么”与让它成为下一轮的工作记忆，是两种用途。** 调试记录可以帮助定位故障；被自动送回模型的历史，则会影响下一步推理。系统需要知道自己正在做哪一种保存。

同样，检查全部通过也不等于答案在现实世界一定正确。它只说明受配置的这批检查完成了，并允许它进入当前规定的后续路径。

## 如果稍后补验，应该补哪一句？

这次修复不负责延后重新检查，因此还有一个自然的追问：检查服务恢复后，能否补验刚才的答案？如果答案已被重生成或编辑，补回来的结论又该归给哪一个版本？

我们的实验没有验证补验流程。它提示下一步应检查“答案内容、检查版本、会话轮次”的绑定，而不只看一个迟到的通过标记。

开发者可以照着本实验做一个小检查：让验证器主动抛错，再开下一轮，读取实际传给模型的历史。普通使用者则可以留意一种体验：刚刚提示失败的答案，是否又被后续回答当作“我们已经确认过”的前提？这样的反馈能提供新线索，但仍需要记录和复现。
