# 动作已经成功，为什么又执行了一次？

恢复执行结束后，操作状态重新变成 `succeeded`，本地效果记录却已经有两条。

这不是并发请求，也不是重复点击。第一次动作其实已经成功并写入一条效果记录；只是成功收尾时的审计追加失败，把它重新归类成了 `failed`。恢复审计路径、退出原进程，再由新进程继续这项已批准操作，第二条记录出现了。

这次研究要回答的不是“重试有没有用”，而是一个更窄的问题：**失败发生在动作之后，Runtime 还有什么依据允许重做动作？** 本文的核心命题是：**执行状态、效果事实和重试资格是三个不同概念。`failed` 不是“动作没有发生”的证据，因此不能直接推出 retry eligible。**

CodeFlowMu 是我们开发和维护的本地多 Agent 协作系统：多个角色 Agent 围绕工程任务工作，由本地运行时管理会话、工具执行、人工审批和结果记录。我们既是系统的开发者，也是本次实验的研究者；关注的是操作实际做了什么，以及出错后该如何恢复，而不是模型回答得好不好。

这值得研究，因为恢复操作的人面对一个 `failed`，需要决定是重做动作、只补记录，还是先停下来核对效果。把记录失败当成动作失败，可能再次执行已经完成的操作；一律禁止恢复，又会阻断本可安全继续的工作。研究的价值，是为这个决定提供依据，而不是再增加一种错误提示。下面用动作前后的故障落点和三类执行器作对照，判断哪些路径值得修复、哪些保护应当保留。

V2.1.2 已补强 `write_task` 的提交幂等、普通事件消费者投影和技能调用会话绑定。但提交身份去重与受控操作收尾是不同路径：前一种问题是“成功结果没有被调用方收到”；本次问题则是“Runtime 已观察到动作成功，却被后续记录故障重新分类为失败”。前者主要考验幂等重放，后者首先考验重试资格的判定。一个入口具备幂等，不意味着所有执行器都获得了同样的保护。

## 1. 为什么审计功能会引出重试问题

研究线索来自 [UniEmployee](https://github.com/zj-unicom-ai/UniEmployee)。这是由 `zj-unicom-ai` 组织维护的企业数字员工平台，把岗位、业务流程、技能、知识库和工具组合起来，面向客服、销售、HR 等工作场景。管理员会修改这些配置，因此平台需要记录谁改了什么，便于出问题后追查。

它的管理端审计实现把审计失败与业务响应分开处理，并包含“审计失败不向外抛出”的测试。这不是普遍正确的答案：有的操作必须在审计不可用时停止，有的旁路日志则不应推翻业务结果。但它提出了值得回到自家代码验证的问题——审计异常究竟会改变哪一层状态？[UniEmployee #17](https://github.com/zj-unicom-ai/UniEmployee/pull/17)

我们因此检查 CodeFlowMu 的审批服务 `OperationApprovalService`，而没有先提出一个“统一事务框架”。研究固定在 main 提交 `f0f42f01`，并用 V2.1.2 发布工作树 `919c3b48` 对照；相关服务源码与标签 `cb8869a3` 相同。固定版本和文件摘要收录于[来源清单](evidence/provenance.json)。

服务将操作记录写入 JSON，再向审计 JSONL 追加事件。单个 JSON 采用临时文件替换，不等于 JSON、审计文件、外部动作共同处在一个原子事务里。真正的问题，要由异常落在哪一步来决定。

## 2. 四个落点，不能统称“执行失败”

探针使用真实产品服务，执行器只向隔离目录追加合成标记，不推送 Git、不创建远端 Issue。故障注入方法是保留原审计文件，在原路径建立目录，使真实追加调用抛出 `EISDIR`。它测试审计目的地异常，不模拟掉电或磁盘写满。

| 探针 | 故障位置 | 调用方看到的结果 | 盘上操作状态 | 已发生效果 |
|---|---|---|---|---:|
| P0 | 正常完成后再次执行 | `APPROVAL_ALREADY_CONSUMED` | succeeded | 1 |
| P1 | 审批记录写好，审批审计追加失败 | 错误 | approved | 0 |
| P2 | executing 已写好，开始审计追加失败 | 错误 | executing | 0 |
| P3 | 效果完成，成功收尾审计追加失败 | 错误 | failed | 1 |

这四个结果在两个基线上一致。P0 是必要的反例：正常完成后的单次消费保护有效，不能因为 P3 存在，就写成“审批系统任意重放”。[双基线捕获数据](evidence/fixtures/historical-probes.json)

P1 说明“返回错误”不等于审批未保存；P2 说明“executing”不等于动作已发生；P3 更危险：动作已发生，却被归入可能继续执行的失败状态。

![透明单轴通道中，两枚钴蓝效果晶核被中央琥珀收尾断点隔开](/assets/figures/2026-08-31-audit-failure-retry-p3-cutaway.png)

*图 1：P3 的视觉化关系。第一枚效果证据已经存在；收尾记录发生断点后，恢复可能产生第二枚效果。图不替代 P0–P3 的实验数据。来源：RCR-20260831 E-A0/E-A1 脱敏捕获数据。*

故障观察也曾踩到一个坑：服务的 `get()` 会追加查看审计。用它观察坏掉的审计路径，会再次抛错。最终探针只读原始 JSON 观察状态，执行过程仍走真实服务。这个调整保留在实验记录中，不能把观察工具的失败混成第二个业务故障。

## 3. 一次收尾异常怎样变成第二次效果

源码与故障现场能拼出同一条因果链：

1. ADMIN 已批准操作；服务保存 executing，并写开始审计。
2. 执行器完成本地效果，返回成功证据。
3. 服务先保存 succeeded，再追加完成审计。
4. 追加失败落入与执行器错误共用的 `catch`，状态随后被改为 failed。
5. 故障后的记录仍保留首次成功证据；失败审计追加也因同一路径异常而抛错。
6. 审计恢复后，恢复入口读取这项仍带有效批准、但已被写成 `failed` 的操作；它没有先把首次效果证据作为“不得重做”的条件，而是接受恢复并再次调用执行器。

因此，问题不是错误信息“不够友好”，而是错误分类改变了后续动作资格。**收尾失败被折叠成执行失败，恢复入口又把它当作可重试依据。**

这条解释能直接对上自己的落盘数据。非幂等对照在故障返回时，操作记录的 `status` 与 `execution_status` 都是 `failed`，但同一记录的 `evidence` 仍保留 `kind=local-marker、observed_count=1`；独立效果快照也已有 `E1`。恢复后，效果快照不是把 `E1` 多读一遍，而是出现 `E1`、`E2` 两个不同标记，并且二者的 `operation_key` 相同。标识均为实验合成值，原样收录在[分阶段捕获数据](evidence/fixtures/restart.json)。操作状态、执行器回传证据和独立效果文件因此形成了可核对的矛盾：**状态说失败，第一次效果却已经存在；恢复随后又产生了新效果。**

为了排除“只在同一个服务对象里成立”，补充实验把首次故障和恢复分成两个 Node 进程，并经过真实 `ControlledExecutorRegistry` 的请求重算与执行分派。注册的是合成本地适配器，不是生产 Git 适配器。

| 执行器对照 | 故障后效果数 | 新进程恢复后效果数 | 累计执行器调用数 | 恢复结果 |
|---|---:|---:|---:|---|
| 无去重，相同请求摘要 | 1 | 2 | 2 | succeeded |
| 按稳定操作键去重，相同摘要 | 1 | 1 | 2 | succeeded |
| 重算请求后摘要变化 | 1 | 1 | 1 | `APPROVAL_STALE` |

三组对照在[第二轮运行](evidence/fixtures/repeatability.json)中得到相同结果。这里的“换进程”是保存故障现场后正常退出，再新建进程；不是强杀进程实验。[分阶段快照与计数](evidence/fixtures/restart.json)

两轮分别保留现场，不以第二轮覆盖第一轮。对照中保持相同故障位置，改变的是执行器去重能力或恢复时的请求摘要；所以数据支持“哪一层能挡住第二次效果”的机制判断，不支持线上重复执行的发生率。两轮重复不是两种独立故障，更不能将不同用例加总为产品可靠性得分。

表中最重要的不是第一行，而是三行的区别：通用恢复层允许再次调用，并不意味着每个业务执行器必然重复产生效果。执行器自身去重能保护效果；请求重算发现变化，也能阻断恢复。反过来，没有这两层保护时，单靠 failed 状态并不安全。

三组对照给出的不是“failed 以后总要重试”，而是一条更小、也更可执行的恢复原则：**`failed ≠ effect_absent ≠ retry_allowed`。** `failed` 只能说明某条控制路径没有正常完成，不能证明外部动作没有发生。重试资格必须由请求身份、效果证据和执行器去重能力共同决定，不能由一个终态字段推导。

因此，恢复至少有三种不同去向：请求身份仍有效且效果明确不存在时，才可以重新执行；效果已经存在，或执行器能以稳定操作键识别首次结果时，应做结果或审计的 reconciliation（核对并补齐），不重复动作；效果是否发生无法确认、执行器又不能安全去重时，不应自动重试，而应停在待核对状态。这是从本组受控实验导出的设计建议，不是本版本已经交付的自动恢复策略。

## 4. 为什么不能照搬一个“审计失败策略”

[Paperclip](https://github.com/paperclipai/paperclip) 则是开源的多 Agent 团队管理平台：它接入不同的 Agent，管理任务、组织角色、预算和审批，而不是训练一个新模型。团队持续工作时，运维需要暂停接收新任务，同时等待在途工作结束；其 task-drain（暂停接单、等待在途工作结束）变更就来自这个需求。

这项变更提供了另一种对照：task-drain 的持久化审计写入被事务化；审计失败时，进程内状态只在没有后续并发变更的条件下回滚，代码用 generation counter 防止陈旧恢复覆盖新状态。活动事件则放到事务提交之后发布，发布失败只记录异常，不再把已经提交的 drain 结果重新表现为 HTTP 500。这是对不同失败阶段的区分。[Paperclip #12485](https://github.com/paperclipai/paperclip/pull/12485)

但它操作的是可恢复的进程内 drain 状态，不能据此推导“已经发出的 Issue、邮件或支付都能随审计失败回滚”。外部动作不受本地数据库事务统一控制时，重试必须有额外证据。

对本次已复现窗口，合理的工程方向是先冻结三条小合同：

- 执行器异常、结果保存异常、审计追加异常分别分类；不要让后两者自动抹掉已观察到的效果。
- 恢复先判断效果是否发生、能否查询或去重，再决定补审计、补结果、重新执行，还是停在待核对。
- 错误回执明确动作结果与重试资格，调用者不靠自然语言或一个 failed 值猜测。

这是由实验支持的修复候选，不是本轮已交付的新能力。也不需要因此改写所有写工具，或重新实现 V2.1.2 已有的 `write_task` 回执协议。

## 5. 读者可以怎样复核

[配套证据包](/zh/research/evidence/2026-08-31-runtime-continuity)提供捕获数据、分时快照、检查器和产品探针。进入证据包运行：

```text
node check.mjs
```

公开层可检查三组重试对照及两基线 P0/P3 的内部一致性；取得对应产品源码后，才能用 `reproduce-product.mts` 重新执行服务实验。这两个复核层次不能混称为“人人可重跑全部产品”。

本研究还复跑了审批、会话合同、恢复互斥、技能记录四组既有测试，[共 28 项通过](/assets/evidence/2026-08-31-runtime-continuity/fixtures/existing-tests.log)。它们是既有保护的对照，不抵消新故障探针；P3 断言通过，恰好表示问题被复现。本轮没有完整 HTTP、真实远端效果、断电测试或独立 QA，适用范围停在受控服务与合成执行器。

如果要把这种检查应用到自己的 Runtime，先在“动作前、动作后、结果落盘后、审计提交时”分点注入故障，再换进程重试，逐项核对效果次数。恢复系统真正需要回答的不是“上一次是不是 failed”，而是“上一次到底有没有产生效果，以及这一次重新调用是否仍然安全”。只验证最后一个状态变绿，很容易漏掉本文开头的现象：**第二次终于成功了，但第一次其实已经做成了。**
