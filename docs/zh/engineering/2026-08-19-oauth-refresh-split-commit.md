# OAuth 刷新成功后，持久化失败不是普通失败

授权服务器已经返回新的访问令牌和刷新令牌，客户端却在保存时遇到“磁盘已满”。这时认证流程到底成功了，还是失败了？

如果只允许一个布尔答案，系统很容易丢失最重要的事实：远端权威状态可能已经推进，本地持久状态却没有同步推进。把这种情况归类为普通刷新失败，随后自动跳转到重新授权，不仅描述错误，还可能掩盖在令牌轮换策略下难以恢复的凭据断点。

2026-08-19 合并的一项 MCP TypeScript SDK 变更修正了这个故障边界。变更前，`refreshAuthorization` 与 `provider.saveTokens` 处于同一个 `catch` 路径，部分异常会继续进入新的授权请求。变更后，只有远端刷新调用留在受保护的刷新块中；远端成功后再调用 `saveTokens`，其拒绝会直接向调用方传播。回归测试先取得新令牌，再让保存操作以“磁盘已满”失败，要求认证流程传播同一个持久化错误，并确认没有调用重定向授权。

这组证据支持一个有界的可靠性判断：**当远端签发与本地持久化是两个操作时，OAuth 刷新就是分段提交工作流。远端成功后的本地失败属于部分成功，必须保持可见。**

## 两个操作成功在不同的权威面

远端刷新交换改变的是授权服务器所认可的凭据状态。本地保存改变的是客户端在进程重启、崩溃或下一次请求后还能否恢复这些凭据。

两者按顺序发生，却不共享原子提交。远端调用返回成功时，服务器一侧已经完成了它承诺的操作；本地存储随后失败，不能把刚才的远端成功“变回未发生”。如果服务器采用刷新令牌轮换，旧令牌甚至可能不再可用。

因此，这个状态不是简单的“认证失败”，而是两个提交点不一致：远端已提交，本地未持久提交。可靠恢复必须从这个状态事实开始。

## `catch` 边界本身就是可靠性模型

异常处理常被视为代码清理，但这里的 `catch` 范围决定了系统能否区分哪一侧已经成功。

把远端交换和本地保存放在同一异常分支时，`saveTokens` 的失败可能被刷新错误处理逻辑接管。系统随后看到的只是“刷新阶段出了问题”，而不是“已取得新凭据但未能持久化”。如果再自动进入重新授权，原始部分状态就被新的流程覆盖。

同日变更通过移动一行故障边界保留了语义：刷新请求的失败继续走刷新恢复逻辑，保存失败则以保存失败的身份传播。回归测试证明，在已测试路径中，持久化错误不会再静默变成重定向。

这并非只是更准确的错误文字。它保留了恢复决策所需的证据分类。

## 保持可见是恢复前提，不是恢复本身

传播持久化错误能让调用方知道远端交换已经成功、本地耐久性没有建立。调用方于是可以根据部署策略选择有界重试、切换安全存储、停止服务并告警操作员，或进入显式协调流程。

但可见性本身没有解决部分状态。当前变更没有提供自动重试，也没有定义包含新凭据的标准恢复对象。若存储提供方可能发生部分写入，调用方仍需知道写入是原子替换、仅被接收，还是已经耐久落盘。

更强的接口可以让令牌提供方声明：

- 是否支持原子替换；
- 成功返回是否代表耐久确认；
- 失败后重试是否安全；
- 是否可能出现部分写入；
- 恢复流程需要哪些非敏感状态证据。

这些能力不能从一个通用 `saveTokens` 方法名中自动推断。

## 错误传播不等于事务性

现有证据来自一个已合并 SDK 变更及其仓库测试，不是独立 OAuth 可靠性基准。服务器侧后果还取决于具体授权服务器策略；刷新令牌轮换并非所有实现都采用。

该变更没有跨授权服务器与本地存储建立分布式事务，不能回滚服务器侧签发，也没有保证“仅一次”保存。即使本地提供方能做到原子替换，远端与本地两个系统之间仍不存在共同提交。

因此，准确结论是：故障被正确分类并保持可见，安全恢复因此有了必要证据；但回滚、重试、协调和操作处置仍需要独立设计。

接下来的问题应成为接口合同，而不是运维猜测：SDK 是否应暴露结构化的部分成功错误，记录远端签发已完成而本地耐久性失败？令牌提供方如何机器可读地声明原子性、耐久确认和安全重试能力？无界面部署如何及时告警操作员，避免下一次启动才发现持久凭据没有更新？只有把“哪一侧已经提交”作为一等事实，恢复逻辑才不会从错误的失败模型出发。

**一手证据：** [MCP TypeScript SDK 合并提交 3924de99](https://github.com/modelcontextprotocol/typescript-sdk/commit/3924de99df834302d89f5997a1b64ca268282284)。代码与仓库测试属于公开一手证据，不构成分布式事务性、回滚或通用令牌轮换行为的独立验证。
