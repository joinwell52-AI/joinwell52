# Agent 核心研究与竞品动态 · 2026-09-07

> Asia/Shanghai · 仅收录达到 meaningful new developments 阈值的公开技术与产品变化。

## 当日结论

本日最强的共振是：**Agent Runtime 正把“最后一次安全检查”不断推近真实副作用边界，同时把能力声明、执行所有权和操作语义从模糊标签变成可验证合同。**

## 1. OpenAI Codex：单写者会话、Windows 受管进程控制与 Human Verification

**状态：MERGED / MERGED / MERGED（能力仍受 gate）**

Codex 连续收紧三条执行控制边界：

- PR [#43253](https://github.com/openai/codex/pull/43253)：当已有实例持有 conversation active writer 时，新 resume 不再抢写，而是降级为 read-only history snapshot；原 writer 关闭后才允许显式重试。这形成了清晰的 **single-writer lease / multi-reader observation** 模型。
- PR [#43308](https://github.com/openai/codex/pull/43308)：Windows managed app-server 的 shutdown 改为本地 control socket `/daemon/shutdown`，请求必须绑定并匹配 Server PID；先 ACK，再进入 drain，PID 不匹配或非 managed launch 会拒绝。
- PR [#43289](https://github.com/openai/codex/pull/43289)：加入 MCP `openai/userVerification` 协议处理，只有 client 明确声明 capability 才接受；proof 有格式、大小、取消和容量限制。当前 Codex 仍未全面激活这一能力。

**为什么重要：** Conversation ownership、Process control、Human verification 都在从“当前状态”变成 capability-gated、identity-bound 的控制对象。

**与 CodeFlowMu/FCoP 的关系：** Runtime 状态不能只写 `Running`，还需要区分 **Writer Lease / Observer Access / Host Process Identity / Human Verification Receipt**。

**值得互动：高。** 技术切入：*Will user-verification proofs eventually be bound to the active writer/authority epoch, so a proof obtained by one conversation owner cannot survive a writer handoff?*

## 2. OpenAI Agents SDK：工具名字并不是副作用合同

**状态：OPEN / OPEN**

两个新问题都说明，仅凭 tool name 无法推断真实 effect：

- PR [#4893](https://github.com/openai/openai-agents-python/pull/4893)：`apply_patch` 的 `*** Add File:` 在目标文件已存在时可能静默覆盖，并仍向模型报告 `Created`。候选修复要求 create 必须证明 destination 不存在，否则明确拒绝。
- PR [#4894](https://github.com/openai/openai-agents-python/pull/4894)：sandbox S3 mount 通过逗号拼接 mount options，某些字段值可借 delimiter 注入额外 mount option。候选修复要求在进入 `mount -o` 的 key/value 上拒绝这种语法层能力扩张。

**为什么重要：** `create` 不能实际是 upsert；一个配置字段也不能偷偷展开成第二种 capability。

**与 CodeFlowMu/FCoP 的关系：** 授权判断应该基于 **normalized effect semantics**，而不是基于工具名或 UI 标签。

**值得互动：高。** 技术切入：*Would you expose normalized effect classes from sandbox tools, so authorization can distinguish create-only, overwrite and mount-policy mutation without reverse-engineering arguments?*

## 3. AG2：MCP Apps 引入“App 可调用、模型不可见”的工具主体

**状态：OPEN**

PR [#3235](https://github.com/ag2ai/ag2/pull/3235) 为 AG2 Agent Server 加入 MCP Apps (`io.modelcontextprotocol/ui`) 支持。UI document 作为 Resource 与 Tool 绑定，支持 `structuredContent`、SEP-2133 extension negotiation，以及 AppResource 的 CSP / permissions / domain 等 sandbox policy。

最值得关注的是 `visibility=["app"]`：某些工具可由 MCP App 中的按钮调用，但不会暴露给模型。

**为什么重要：** MCP 的执行主体从单一的 `Model → Tool` 扩展为至少两条路径：`Model → Tool` 与 `Human → App UI → Tool`。

**与 CodeFlowMu/FCoP 的关系：** 数字员工面板里的批准、执行、重试、撤回按钮，都应被视为正式 invocation principal，而不是 UI 绕过协议直接改状态。

**值得互动：非常高。** 技术切入：*For app-only tools, do you plan to expose distinct invocation-principal / user-gesture provenance so audit can distinguish model-selected calls from human UI actions?*

## 4. Paperclip：Pre-start Admission、插件能力升级与恢复事故

**状态：OPEN / OPEN / OPEN**

Paperclip 本日继续逼近治理 Runtime：

- PR [#12949](https://github.com/paperclipai/paperclip/pull/12949)：增加 provider 副作用之前的 **pre-start admission hook**。Run 已 claim、但 adapter/native runner/provider 尚未启动时，Host 可基于 issue、run、wake、provider、model、capacity snapshot 做最后裁决；Enforce 模式下 telemetry 缺失、过期或无效会 fail closed，veto 后保证零 provider call。
- PR [#12928](https://github.com/paperclipai/paperclip/pull/12928)：处理 Plugin capability escalation。升级新增 capability 不再自动扩大 grant，而进入 `upgrade_pending`，需要 operator 明确批准；同时增加 manifest drift 检测。
- PR [#12946](https://github.com/paperclipai/paperclip/pull/12946)：汇总并修复环境 lease 释放后 Agent 永远 Running、continuation retry cap 被错误码交替绕过、API abort 却 exit 0、cross-issue guard 使用错误证据等真实运行问题。

**为什么重要：** Paperclip 正形成 `Declared Capability → Approved Grant → Pre-start Admission → Run Ownership → Provider Effect → Recovery Classification` 的治理链。

**与 CodeFlowMu/FCoP 的关系：** 与 Host 准入、call-time authorization、恢复治理直接重合。

**学习：非常高｜竞争风险：很高｜雷达判断：维持一线 Runtime 竞品。**

**值得互动：非常高。** 技术切入：*Will pre-start admission be bound to an authority epoch/effect receipt so a queued run cannot execute after telemetry or capability grants materially change?*

## 5. GitHub MCP Server：精确补丁工具拒绝 fuzzy write

**状态：DRAFT**

Draft PR [#3232](https://github.com/github/github-mcp-server/pull/3232) 新增 `apply_file_patch`。背景是一份约 303 KB changelog 的修改中，完整 replacement 在上游被截断，错误 commit 虽被拦截，但恢复需要借助本地 Git client。

新工具要求同时提供 exact `expected_head_sha` 与 exact `expected_blob_sha`，且 `old_text` 必须精确出现预期次数；禁止 fuzzy matching、offset guessing、no-op、symlink、非 UTF-8 和过大 patch。最终 branch update 使用 `force=false`，并发变更会 non-fast-forward 失败，而不是覆盖别人的新事实。

**为什么重要：** 写操作开始携带明确的 effect preconditions：只有“我预期的 Branch 和 File 仍然成立”时才允许执行。

**与 CodeFlowMu/FCoP 的关系：** 与并发线性化、幂等、原子更新、effect precondition 高度一致。

**值得互动：高。** 技术切入：*Would you return a durable effect receipt containing expected head/blob and resulting commit/blob, making the precondition-to-effect transition directly auditable?*

## 6. Orca：Unknown 只能被正证据收敛，不能被 timeout 猜成事实

**状态：MERGED / OPEN / OPEN**

- PR [#19140](https://github.com/stablyai/orca/pull/19140) 已合入：Structured Claude Chat 的一条 submission 若先被标记为 `unknown`，但后续 provider echo 能证明该消息实际已接受，则 durable journal 会由 `unknown → accepted`，且**不产生第二次 dispatch**。
- PR [#19149](https://github.com/stablyai/orca/pull/19149)：处理 Windows PID reuse，新增 PID creation-time ordering 作为 ancestry evidence；证据不足仍保持 `unverifiable`。
- PR [#19155](https://github.com/stablyai/orca/pull/19155)：provider root 已正证明死亡且无 known-live descendant 时，可释放 native session lease，同时保留 uncertain descendant-cleanup evidence；**lease expiry 本身不能证明 owner 已死**。

**为什么重要：** Unknown 可以被后续正证据收敛，但 timeout、lease expiry、PID 数值都不能自行升级成事实。

**与 CodeFlowMu/FCoP 的关系：** Recovery 与 lifecycle state 应采用 evidence-driven settlement，而不是 `if timeout then dead` 的二态推断。

**学习：非常高｜竞争风险：中高｜雷达判断：提高 Orca 的 long-running / Windows / recovery 权重。**

**值得互动：高。** 技术切入：*Do you plan to converge delivery and process/lease evidence onto one general transition model where `unknown → accepted/dead` requires a named positive observation?*

## 跨项目共振

本日可以归纳成一条非常强的原则：

> **真正安全的 Agent 不是“先判断一次，然后长期相信”，而是在距离副作用越来越近的地方不断重新证明：对象还是那个对象、能力还是那份能力、Owner 还是那个 Owner、前置事实还成立。**

对 CodeFlowMu/FCoP，建议把执行链继续明确为：

**Capability Grant → Admission Decision → Effect Preconditions → Call-time Authority → Effect Receipt → Evidence-driven Settlement**。

其中任何一环都不应由“上一次检查通过”自动替代下一环。
