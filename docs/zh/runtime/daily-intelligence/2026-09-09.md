# Agent 核心研究与竞品动态 · 2026-09-09

> 仅记录 meaningful new developments。来源优先采用本人、官方项目、GitHub PR/Issue/Release 与一手工程资料；不以 star 数、营销转发或无技术增量的小版本凑数。

## 今日结论

本轮最强的共同趋势是：**Agent Runtime 正把最后一次安全检查不断推近真实副作用边界，同时把能力声明、执行所有权、操作语义和恢复事实拆成可验证合同。** 对 CodeFlowMu/FCoP 来说，执行链更适合明确为：

**Capability Grant → Admission Decision → Effect Preconditions → Call-time Authority → Effect Receipt → Evidence-driven Settlement**。

## 1. OpenAI Codex：单写者会话、PID 绑定的进程控制与真人验证能力边界

Codex 正在把 Conversation ownership、Process control 与 Human verification 做成独立控制面。PR #43253 规定同一 conversation 只允许一个 active writer；新的 resume 在 writer 已存在时降级为只读历史视图，不再抢写。PR #43308 则让 Windows managed app-server 的 shutdown 通过本地 control socket 请求，并要求 PID 匹配后才进入 drain；错误 PID 或非受管启动会拒绝。PR #43289 新增 MCP `openai/userVerification` 协议处理，但 capability 仍受 Host 控制，未声明支持的 client 不能使用。

**为什么重要：** `Running` 不足以表示执行权。生产级 Runtime 需要区分 Writer Lease、Observer Access、Host Process Identity 和 Human Verification Receipt。

**互动切入：** *Will user-verification proofs eventually be bound to the active writer/authority epoch, so a proof obtained by one conversation owner cannot survive a writer handoff?*

来源：
- [Codex PR #43253](https://github.com/openai/codex/pull/43253)
- [Codex PR #43308](https://github.com/openai/codex/pull/43308)
- [Codex PR #43289](https://github.com/openai/codex/pull/43289)

## 2. OpenAI Agents SDK：工具名称不能代替真实 effect semantics

两个新安全问题都说明工具表面语义可能比真实副作用更窄。PR #4893 指出 `apply_patch` 的 `*** Add File:` 在目标已存在时可能静默覆盖，却仍向模型报告 Created；拟议修复要求 create-only 行为必须证明目标不存在。PR #4894 则发现 sandbox S3 Files mount 的逗号拼接参数可被输入值注入额外 mount option；拟议修复是在进入 `mount -o` 之前拒绝 delimiter injection。

**为什么重要：** Authorization 不能只看 tool name。真正需要进入授权合同的是 normalized effect class，例如 create-only、overwrite、mount-policy mutation。

**状态：** 两条 PR 均仍 OPEN，尚不能视为正式发布能力。

**互动切入：** *Would you consider exposing normalized effect classes from sandbox tools, so an authorization layer can distinguish create-only, overwrite, mount-policy mutation and other effects without reverse-engineering tool arguments?*

来源：
- [Agents SDK PR #4893](https://github.com/openai/openai-agents-python/pull/4893)
- [Agents SDK PR #4894](https://github.com/openai/openai-agents-python/pull/4894)

## 3. AG2：MCP Apps 引入“App 可调用、模型不可见”的工具主体

PR #3235 正在加入 MCP Apps (`io.modelcontextprotocol/ui`) 支持。UI document 作为 Resource 与 Tool 绑定；只有 client 明确声明可渲染 MCP App 时才下发 UI binding。更值得关注的是 `visibility=["app"]`：这类 Tool 可以由 App UI 按钮调用，但不暴露给模型。

**为什么重要：** 执行主体不再只有 Model → Tool，还出现 Human → App UI → Tool。App-only tool 需要自己的 principal、user gesture 和 authorization evidence，不能因为“模型看不到”就默认更可信。

**状态：** OPEN，尚未合入。

**互动切入：** *For `visibility=['app']` tools, do you plan to expose a distinct invocation principal/user-gesture provenance so audit can distinguish model-selected calls from human UI actions?*

来源：
- [AG2 PR #3235](https://github.com/ag2ai/ag2/pull/3235)

## 4. Paperclip：pre-start admission、插件能力升级与恢复分类继续逼近治理 Runtime

Paperclip 仍是本轮最高竞争优先级之一。PR #12949 正在增加 provider 副作用发生前的 pre-start admission hook：Run 已 claim，但 adapter/native runner/provider 尚未启动时，Host 可依据 issue、run、wake、provider、model 和 capacity snapshot 做最后裁决；Enforce 模式遇到缺失、过期或无效 telemetry 时 fail closed。PR #12928 则处理 Plugin capability escalation：升级新增 capability 不再自动成为既有 grant，而进入 `upgrade_pending`，等待 operator 明确审批。PR #12946 记录真实部署中的 lease、无限 continuation、错误 success classification 和 cross-issue guard 证据问题。

**为什么重要：** Paperclip 正形成完整链条：Declared Capability → Approved Grant → Pre-start Admission → Run Ownership → Provider Effect → Recovery Classification。

**竞品判断：** 学习价值非常高；竞争风险很高；继续按一线 Runtime 控制面竞品观察。

**状态：** 上述 PR 当前仍 OPEN，不能提前算作正式发布能力。

**互动切入：** *Will pre-start admission eventually bind the resulting decision to an authority epoch/effect receipt, so a queued run cannot pass admission and then execute after its telemetry or capability grant has materially changed?*

- [Paperclip PR #12949](https://github.com/paperclipai/paperclip/pull/12949)

## 5. GitHub MCP Server：精确补丁写入开始要求“前置事实证明”

Draft PR #3232 新增 `apply_file_patch`，要求调用方同时提供 exact `expected_head_sha` 和 exact `expected_blob_sha`；`old_text` 必须精确出现预期次数，禁止 fuzzy matching、offset guessing、空匹配、no-op、symlink、非 UTF-8 和过大 patch，branch 更新也使用 `force=false`，并发变化会以 non-fast-forward 失败。

**为什么重要：** 写文件不再只是“执行一个命令”，而是明确声明：我预计 Branch 仍是 X、File 仍是 Y，只有两项前置事实都成立才允许产生 Z。对 FCoP 4.0 的并发线性化、幂等和 effect precondition 很有参考价值。

**状态：** DRAFT，尚未合入。

**互动切入：** *Would you consider returning a durable effect receipt containing expected head/blob and resulting commit/blob, making the exact precondition-to-effect transition directly auditable by agent runtimes?*

来源：
- [GitHub MCP Server PR #3232](https://github.com/github/github-mcp-server/pull/3232)

## 6. Orca：Unknown 由后续正证据收敛，PID 与 lease 不再被当作死亡事实

已合入的 PR #19140 修复 Structured Claude Chat 的 delivery journal：消息初始可能被标成 `unknown`，但 provider 后续 echo 到达后，会根据原 `clientMessageId` 将同一 durable submission 推进为 `accepted`，不会产生第二次 dispatch。两个仍 OPEN 的后续 PR 则继续收紧 Windows Runtime：#19149 将 PID 与 creation-time ordering 一起作为 process ancestry evidence，避免 PID reuse 把无关进程误判为 descendant；#19155 明确 lease expiry 不能证明 owner 已死，只有 provider root 的正死亡证据和已知 descendant 状态才能驱动 lease release。

**为什么重要：** Unknown 可以被正证据收敛，但 timeout、lease expiry 和“没看到进程”不能自行升级成事实。

**竞品判断：** Orca 的 long-running、Windows 与 recovery 权重继续上调。

**互动切入：** *Do you plan to converge message-delivery identity and process/lease evidence onto one general evidence-transition model, where `unknown → accepted/dead` requires a named positive observation rather than timeout-derived inference?*

来源：
- [Orca PR #19140](https://github.com/stablyai/orca/pull/19140)
- [Orca PR #19149](https://github.com/stablyai/orca/pull/19149)
- [Orca PR #19155](https://github.com/stablyai/orca/pull/19155)

## 跨项目判断

今天的共同方向可以压缩成一句话：

> **真正安全的 Agent 不是“先判断一次，然后长期相信”，而是在距离副作用越来越近的地方不断重新证明：对象还是那个对象、能力还是那份能力、Owner 还是那个 Owner、前置事实还成立。**

这进一步支持 CodeFlowMu/FCoP 将执行链拆成六个不可互换的阶段：

1. **Capability Grant** — 当前主体被授予什么能力；
2. **Admission Decision** — 本轮任务是否允许进入执行；
3. **Effect Preconditions** — 真实副作用前的事实前提是否仍成立；
4. **Call-time Authority** — 到真正执行时权限是否仍有效；
5. **Effect Receipt** — 实际做了什么、依据什么；
6. **Evidence-driven Settlement** — 成功、失败或 unknown 只能由明确证据收敛。
