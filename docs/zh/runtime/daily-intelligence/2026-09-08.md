## 当日结论

## 1. Yue Zhao（赵岳）/ GRADE：修复依赖图构造缺陷，并主动撤回一项核心结构性结论

**状态：MERGED / RESEARCH CLAIM CORRECTED**

赵岳本人提交了 GRADE 修正：[commit a9a87a1](https://github.com/yzhao062/grade/commit/a9a87a13866e6410f83664bf8a59642fb36aac8e)。核心问题是一个名为 `last_on_id` 的映射实际通过 `setdefault` 保存 identifier 的**第一个 producer**，而下游逻辑却假设取得的是最近 producer。修正后，大量依赖边和 dependency span 发生变化；此前另一处 hash-order 缺陷也被一并纠正，修复后 transfer / within-corpus cells 在多组 `PYTHONHASHSEED` 下保持一致。

更重要的是，赵岳明确撤回“dependency layer 比 run size 更能预测失败”的原表述：旧基准只是线性 size baseline，不能排除依赖特征仅编码了 run size 的非线性函数。新的 nonlinear size baseline 与 null/chain controls 表明，原 structural superiority claim 不再成立；Execution-layer 的 fault localization 结论不受该修正影响。

**为什么重要：** Graph feature 看起来更复杂，不等于它提供了独立信息。研究结论必须用足够强的 null / nonlinear baseline 做对照。

**与 CodeFlowMu/FCoP 的关系：** 未来若 EVAL 要证明 dependency graph、audit graph、recovery graph 的独立价值，应同时加入 nonlinear size baseline、null graph、chain graph 与 matched-source control。

**值得互动：非常高。** 技术切入：*Would you make nonlinear size baselines and null/chain graph controls mandatory release gates for future GRADE structural claims, rather than post-hoc diagnostics?*

## 2. Paperclip：共享数字员工的真人来源身份进入 operation-time contract

**状态：#13005 MERGED；#13000 DRAFT；#13002 DRAFT**

Paperclip PR [#13005](https://github.com/paperclipai/paperclip/pull/13005) 已合入。系统不再根据 task owner 或长驻 provider token 决定 GitHub 身份，而是持久保存**有序 execution identity context**：新的真人指令、steering、queued continuation、retry、delegation、approval、routine 与 Server restart 都保留真正的 originating person。真正执行 `git` / `gh` / GitHub gateway 时，才由 operation-time broker 为当前 accepted instruction 的 responsible person 解析凭证；个人 token 不进入长期 provider process。

真实双账户验收还验证了：A 指令 → B steering → queued A continuation 可以在同一 conversation 中运行，实际 commit/push 身份分别正确；delegated subtask 跨 Server restart 后仍保留原 responsible person。

同日两条后续方向也很强：

- Draft [#13000](https://github.com/paperclipai/paperclip/pull/13000)：private Slack task control，只允许显式映射的真人私聊；消息先持久化再 ACK，mutation 使用 at-most-once fence，结果不确定进入 `uncertain` 而不自动 replay。
- Draft [#13002](https://github.com/paperclipai/paperclip/pull/13002)：durable sandbox work folders，将 task / agent / user / project / repos 分域，周期 checkpoint + final save，让 object storage 而非 sandbox disk 成为耐久层。

**为什么重要：** Employee Identity、Human Principal、Task Owner、Credential Scope、Conversation Continuity 被正式拆开。

**与 CodeFlowMu/FCoP 的关系：** 数字员工长期运行时，应将“谁是这个员工”“谁发出当前指令”“当前动作使用谁的 credential/workspace scope”作为不同事实。

**学习：非常高｜竞争风险：很高｜雷达判断：维持最高优先级，并新增 operation-time principal 专项维度。**

**值得互动：非常高。** 技术切入：*Will responsible-person identity, Slack attribution and user-scoped work-folder binding converge on one durable authority envelope, so every side effect proves both who instructed it and whose credential/workspace scope it used?*

## 3. OpenAI Codex：Human Verification 进入 Secure Enclave + 生物识别签名

**状态：MERGED / MERGED**

PR [#43624](https://github.com/openai/codex/pull/43624) 已合入 macOS Human Verification：使用 P-256 Secure Enclave key，并通过 Data Protection Keychain 保存；私钥 access-control policy 强制 biometric authentication，每次 challenge signature 创建新的 `LAContext`。credential 创建/复用/删除/签名还通过 cancellable file lock 做跨进程序列化。

此前合入的 [#43524](https://github.com/openai/codex/pull/43524) 又明确限制：普通用户配置的 MCP Server 即使伪装成官方 Apps MCP 的同名 server，也不能请求真人验证。`userVerification` capability 只投射给 Host-owned Apps MCP；local identity 还使用 workspace-scoped opaque ChatGPT account user ID，并要求 token workspace 与当前选中 account 一致。

**为什么重要：** Approval 正从“用户点了允许”升级为硬件保护、真人在场、针对 challenge 的密码学证明。

**与 CodeFlowMu/FCoP 的关系：** ADMIN 高风险批准可以分级：普通 UI confirmation、authenticated human approval、device-bound biometric proof；最终 proof 还应绑定 effect digest、principal、workspace/company、authority epoch、nonce/expiry。

**值得互动：非常高。** 技术切入：*Will the signed verification challenge commit to the normalized effect, workspace principal and authority epoch, so biometric proof is specific to one consequential action rather than merely proving user presence?*

## 4. Kazuhiro Sera（seratch）/ OpenAI Agents JS：两次修复都在回答“谁拥有这份状态？”

**状态：MERGED / MERGED**

Kazuhiro Sera 本人提交的 PR [#1841](https://github.com/openai/openai-agents-js/pull/1841) 与 [#1842](https://github.com/openai/openai-agents-js/pull/1842) 均已合入。

- #1841 修复 Multi-Agent handoff 后的 deferred-tool discovery attribution。同名 tool 不能因为历史中曾被 Agent A 搜索，就让 Agent B 误以为自己也已完成 discovery；只有 logical Agent identity 可唯一判定时才恢复归属，歧义则重新搜索。
- #1842 修复 session compaction 并发覆盖：Run 读到历史准备 compaction 期间，如果同一 session 已被其他 writer append，旧 snapshot 不再有资格做整体 replacement。Runner 持有 ephemeral ownership receipt；receipt 过期时放弃自动 replacement。

**为什么重要：** 历史存在不代表我拥有它；同名能力不代表它属于我；曾经读取 snapshot 也不代表现在仍有覆盖权。

**与 CodeFlowMu/FCoP 的关系：** Branch/REPORT/并发收敛中，任何“整体替换事实”的操作都应该持有仍有效的 ownership generation；无法证明时只能 append 或重新读取。

**值得互动：高。** 技术切入：*Do you see session-compaction ownership and tool-discovery attribution converging on a general Agent/run generation primitive instead of subsystem-specific receipts?*

## 5. Superset：Host 升级开始产品化为 backup → restart → verify → rollback

**状态：OPEN**

PR [#7270](https://github.com/superset-sh/superset/pull/7270) 让 Host 报告 build/version/install source，并在 Desktop 的 Settings、device picker、workspace compatibility gate 中展示版本状态。对支持的 standalone CLI Host，Owner 可以直接从 Desktop 触发升级；Updater 先锁安装目录、保存 backup，在**同一个 port**重启并验证 successor 的目标版本，失败则自动 rollback。

团队已做真实 Desktop click 验证：standalone Host 1.26.0 → 1.27.0 约 8 秒。但 production relay/auth、active terminal reconnect、完整 incompatible-workspace gate 仍未真正 E2E；中断升级也可能留下 install lock。

**为什么重要：** 数字员工工作站的升级不能只解决“替换二进制”，而必须有完整 Host lifecycle transaction。

**与 CodeFlowMu/FCoP 的关系：** 对 CodeFlowMu Windows 产品版，升级链应至少包括 **Host Version → Compatibility → Upgrade Admission → Backup → Binary Replace → Restart → Successor Verification → Rollback → Session Reconnect**。

**学习：非常高｜竞争风险：高｜雷达判断：保持重点第二圈；若 production relay + active terminal reconnect 真正验证，可升主雷达。**

**值得互动：非常高。** 技术切入：*Before replacing a live standalone host, do you plan to drain/fence active agent leases and then prove ownership transition to the verified successor binary?*

## 6. Orca：损坏记录不能 replay，不等于可以删除证据

**状态：DRAFT**

Draft PR [#19399](https://github.com/stablyai/orca/pull/19399) 修改 journal repair 语义。旧逻辑遇到无法读取的一行，会删除该行和后面整个 suffix；但 provider transcript 无法重构 Orca 自己的 submission receipt，因此这种“修复”可能永久销毁审计证据。

新方案采用 **sealed recovery generations**：旧 epoch 的原始字节全部保留并 seal，只把已确认可读的 prefix 发布到新 epoch；SQLite trigger 禁止修改/删除 sealed history 与 recovery metadata。未来无法理解数据库/row version 时，也只读，不猜、不迁移、不修。

最关键的原则是：

> **Evidence Recoverable ≠ Evidence Safe to Replay。**

损坏点之后即使存在看起来合法的 receipt，也只能保留 evidence qualification，不能自动取得 replay authority。

**为什么重要：** 恢复系统必须区分“保留证据”与“允许重放”。

**与 CodeFlowMu/FCoP 的关系：** 对损坏 REPORT、Runtime event log、EVAL evidence、authorization receipt，应坚持：旧证据封存不改 → 新 generation 恢复可确定部分 → 不确定 suffix 只保留证据资格，不获得执行资格。

**学习：非常高｜竞争风险：中高｜雷达判断：提高 Orca Recovery / Auditability 权重，但此项仍为 draft。**

**值得互动：非常高。** 技术切入：*Do you expect sealed journal generations to become the general evidence-retention primitive for rewind/fork/recovery, so superseded evidence remains immutable without ever regaining replay authority?*

## 跨项目共振

本日最强的共振不是 Session/Resume，而是更底层的一句话：

> **“状态”正在被拆成：谁拥有、谁授权、能不能覆盖、能不能重放、能不能只作为证据保存。**

对 CodeFlowMu/FCoP，可以进一步收敛为：

**Principal Identity → Ownership Generation → Authorization/Verification → Effect Authority → Durable Evidence → Replay Eligibility**。

其中最后一个 `Replay Eligibility` 很关键：**能恢复出来的事实，不一定拥有再次执行的权力。**
