# Agent 核心研究与竞品动态 · 2026-09-13

> Asia/Shanghai · 仅收录达到 meaningful new developments 阈值的公开技术与产品变化。

## 当日结论

今天最强的共同信号不是“更多 Agent”，而是 **长期执行中的连续性正在被拆成不同合同：Provider Session 可以继续，但当前任务目标、Human Interrupt、Credential Lease、Client Origin、Workspace Capability 与 Tool Identity 都必须分别证明。** 一个 Session 没断，不等于旧目标、旧权限、旧通知范围和旧工具解释还能继续使用。

## 1. Yue Zhao（赵岳）/ anywhere-agents：真实 fan-out 审计暴露“exit 0 但业务失败”的错误完成语义

**状态：COMMITTED / FIXED**

赵岳本人在 [commit 3c94f45](https://github.com/yzhao062/anywhere-agents/commit/3c94f459fa942727bbbf0a51ad1967d235096bc7) 记录了对 **152 次真实 Agy dispatch** 的审计，发现三个生产问题。其中最重要的是：Agy 在 quota limit 时会以进程 **exit code 0** 退出，但最终事件实际是 `ERROR`，而事件里仍可能带有模型的开场 narration。旧 dispatcher 只看进程退出码和 response，导致一次 fan-out 中四个 unit 把开场白当成正式结果发布，且没有 `FALLBACK` 标记；Gemini reviewer 路径也存在同类风险。

修复后，dispatcher 以最终事件的 `status` 作为业务结果：非 `SUCCESS` 即失败；若 Worker 已经写出自己的结果，则保留该文件，但 Run 仍以非零退出结束，同时保存 partial response 作为证据。另两个真实问题分别是 Windows 长路径导致 staged snapshot 导出失败，以及 `read(65536)` 让实时 tail 长时间停在 0 字节、影响 stall monitor。

同一仓库随后又由赵岳本人在 [commit 0d2221e](https://github.com/yzhao062/anywhere-agents/commit/0d2221e0089106e72d69d1cf79bee279ccf25a4e) 修正文档中的模型岗位意图：成本下降来自把 Codex 移出 `prun` 大规模 fan-out，而 `/vet` gatekeeper 恰恰保留旗舰 GPT-6 Astra；也就是说，**便宜模型用于规模化 Worker，最强模型保留给高价值 Gate**。

**为什么重要：** Process Exit、Worker Artifact、Backend Event Status、Gate Verdict 是四种不同事实。`exit 0` 不应该拥有“业务完成”的裁决权；反过来，保留下来的 partial artifact 也不自动等于可接受结果。

**与 CodeFlowMu/FCoP 的关系：** 这非常适合固化成 `Process Outcome → Provider Outcome → Work Result → Verification Verdict` 四层分离；同时支持“模型差异天然存在”的岗位化治理：fan-out 与 EVAL/gatekeeper 不必使用同一档模型。

**值得互动：非常高。** 技术切入：*是否考虑让每个 dispatch receipt 同时记录 process exit、provider terminal status、artifact provenance 与 verifier verdict，避免任何一层被误当成最终完成？*

## 2. AG2 / AG-UI：Human-in-the-loop 改成“中断一次 Exchange、保持原 Turn”，明确拒绝重放副作用

**状态：DRAFT / OPEN**

AG2 Draft PR [#3248](https://github.com/ag2ai/ag2/pull/3248) 给 AG-UI 增加了真正的 mid-run human input。一个 tool 在执行中调用 `context.input()` 时，当前 exchange 以 `RUN_FINISHED` + `interrupt` 正常结束，但 Python 中的原 Turn 被挂起；客户端随后使用**同一 thread、全新的 run id**提交 `resume`。

这里最重要的设计是：**continuation 不是 replay。** 被挂起的是 Python function 内部正在执行的位置、locals 和已经发生的副作用；如果只靠 message history 重新进入 tool，就可能把前半段副作用再做一次。因此 PR 选择在 serving process 中保持 coroutine，而不是从头重跑。

Resume 还要求客户端回传 per-interrupt `proof`。这是 capability token，不是数字签名；错误 proof、过期、非 outstanding interrupt 都有机器可读错误码。Tool approval 也复用同一路径。作者同时明确写出限制：需要 sticky routing；Server restart 会丢掉 held turn；held coroutine 不可序列化到共享 backend；当前一条 Turn 只允许一个 outstanding question。

**为什么重要：** 这是非常清楚的 `Thread Continuity ≠ Run Continuity ≠ Turn Replay` 设计。

**与 CodeFlowMu/FCoP 的关系：** Human Approval 最好成为独立 durable object；原执行若必须保留内存态，就应明确其 lease 和 restart 限制。如果要跨重启恢复，必须设计可持久化 continuation，而不是假装 replay 等价。

**值得互动：非常高。** 技术切入：*下一步是否会把 interrupt/continuation 外部化为 durable object，使 sticky routing 只是优化，而不是 correctness requirement？*

## 3. Paperclip：一边修复真实 Credential Lease，一边发现“恢复了正确 Session 却执行了旧任务目标”

**状态：#13347 MERGED；#13345 DRAFT / OPEN**

Paperclip PR [#13347](https://github.com/paperclipai/paperclip/pull/13347) 已合入。真实 hosted subscription login 保存成功且 environment check 通过后，第一项任务仍可能报 `AI connection busy`。根因是 session advisory lock 留在 transaction-pooled PostgreSQL backend 上。现在 credential grant lock 被绑定到**一个数据库 transaction**，cleanup 或获取失败时 rollback；长 provider execution 期间还显式避免 idle timeout。真实 Claude/OpenAI subscription 登录、环境检查、任务执行和立即重复执行均完成 staging 验证，并观察到运行期间 transaction-scoped lock 存在、结束后消失。

紧接着的 Draft PR [#13345](https://github.com/paperclipai/paperclip/pull/13345) 又发现另一种 continuity 错误：升级验收中，legacy Codex **成功恢复了原 provider conversation**，但 invocation prompt 没带用户刚刚修改过的 task description，反而把历史 comment 当成当前 objective，于是在正确 Session 中执行旧脚本。候选修复要求 fresh/resumed run 都携带当前 task brief；edited brief 优先于已交付的历史 comment；之后未变化的 resume 才保持当前 objective。当前 CI 仍在运行，最终 staging acceptance 尚未完成，所以不能写成已发布能力。

**为什么重要：** Paperclip 同一天分别证明了两件事：Credential Lease 必须绑定真实执行寿命；Session Identity 正确也不代表 Objective Revision 正确。

**与 CodeFlowMu/FCoP 的关系：** 恢复合同应至少绑定 **Provider Session + Current Task Revision + Principal/Credential Lease + Authority Epoch**。不能把“Session 找回来了”当作“任务语义也找回来了”。

**学习：非常高｜竞争风险：很高｜雷达判断：继续保持一线 Runtime 竞品。**

**值得互动：非常高。** 技术切入：*是否会把 current task revision / objective digest 与 provider-session resume receipt 绑定，从结构上禁止旧 comment 在新任务版本中重新成为 authority？*

## 4. Superset：Lock Screen Agent Fleet 从“前台轮询”迈向 APNs Push，但真实 iPhone 投递仍未验证

**状态：OPEN / NOT MERGED**

Superset PR [#7491](https://github.com/superset-sh/superset/pull/7491) 是前一版 #7482 被合入后又由 #7489 revert 的重新提交。它直接解决我们昨天指出的限制：此前 Live Activity 只有手机前台每 5 秒轮询 Host，锁屏后约两分钟就冻结；新方案由 Host 上报 derived Agent state transition（working / review / permission / failed / gone），API 持久化最新 terminal state 与 ActivityKit token，并通过 APNs 对 Lock Screen 卡片执行 `start / update / end`。

设计里还区分推送优先级：普通 working transition 用 priority 5，review/permission/failed 等人类需要关心的状态用 priority 10。Mobile 保存 push token / push-to-start token，卡片行改存 epoch `since`，由 Widget 自己持续计算 elapsed time。API + fake APNs HTTP/2、ES256 provider JWT、iOS simulator build 都已验证。

必须保留边界：**真实 Apple → 真实 iPhone 投递尚未验证**，需要生产 APNs secrets 和 native build；PR 当前仍 OPEN，不能写成正式发布能力。

**为什么重要：** 手机端正在从“打开 App 看 Agent”变成真正的 background supervision surface。

**与 CodeFlowMu/FCoP 的关系：** 移动端最值得做的仍是状态、Review、Permission、证据与控制，而不是缩小 PC UI。未来 typed approval 若接入这里，应绑定 Human Principal、target run/effect 与状态版本。

**学习：非常高｜竞争风险：很高｜雷达判断：Superset 继续作为主雷达候选；待合入并完成真实 APNs/iPhone 验证后再正式升级。**

**值得互动：高。** 技术切入：*Live Activity 上的 permission/review 状态未来是否会带可验证的 run/effect identity，从而让锁屏审批成为正式 receipt 而不是 UI hint？*

## 5. Orca：共享 Remote Server 开始按“谁发起这个 Run”隔离焦点、通知和 Push

**状态：DRAFT / OPEN**

Orca Draft PR [#20402](https://github.com/stablyai/orca/pull/20402) 处理一个典型 multi-client 问题：两个客户端共享同一台远程 Orca Server 时，客户端 A 启动的工作可能切换客户端 B 的 workspace，或让 B 收到与自己无关的 Agent 通知。

候选修复把现有 host/paired-device provenance 继续传递为 **run origin**，并贯穿 terminal creation、child CLI、native session、持久化、daemon/SSH reattach；CLI activation 只发给 originating client，notification display / unread / live delivery / replay / push 也按 origin 过滤。未知 origin 保持 background，不因 reconnect 重放 activation。

项目报告了真实后台 Electron server + 两个独立 paired web client 的 4/4 E2E；但 physical Windows/Linux、live SSH 与真实 `orca serve` bootstrap 尚未覆盖，且 PR 因缺少最终视觉证据仍保持 Draft。

**为什么重要：** Workspace 共享不应推导出 Audience 共享；任务归属也不应由 workspace creator 代替。通知、聚焦、Push 都需要独立的 **Run Origin / Audience Scope**。

**与 CodeFlowMu/FCoP 的关系：** 多 Host/多房间后，正式消息和 UI focus 应绑定发起者与 Run，不应该有 host-wide ambient broadcast 默认值。

**学习：非常高｜竞争风险：中高｜雷达判断：继续提高 Orca 的 multi-client isolation / remote-control 权重。**

**值得互动：高。** 技术切入：*Run origin 是否会进一步成为 authorization/audit principal，而不仅用于 navigation 与 notification routing？*

## 6. Fusion：MCP 工具“明明存在但名字不同”，足以让整个 Agent Session 空转

**状态：OPEN / NOT MERGED**

Fusion PR [#3597](https://github.com/Runfusion/Fusion/pull/3597) 修复 ACP + MCP 的 tool-name mismatch。Fusion 的 planning prompt 使用裸工具名，如 `fn_task_prompt_write`；但 ACP client 通过 MCP 暴露时，模型实际看到的 schema 名可能是 `mcp__fusion_custom_tools__fn_task_prompt_write`。

真实 planning runs 中，Agent 因此把“名称不匹配”理解成“能力不存在”，整个 Session 花在搜索 CLI、REST route、源码和 filesystem substitute 上，最终 `PROMPT.md`、task steps 和 task branch 都没有进展。候选修复只有在 custom-tool bridge 确实 attach 且对应 `fn_*` 真正注册后，才向 outgoing prompt 注入 bare-name ↔ namespaced-name 映射；Claude / Grok / OMP 的 vendored ACP adapter 也各自补上相同机制。

**为什么重要：** Capability Presence、Protocol Exposure Name、Prompt Vocabulary 是三层不同事实。任何一层漂移，都可能被上层模型错误归因为“工具缺失”。

**与 CodeFlowMu/FCoP 的关系：** Host capability probe 不应只问“工具数量/名字”，还要验证 **模型实际可见 schema identity** 与业务合同使用的 logical tool identity 能否稳定映射。

**学习：高｜竞争风险：中｜雷达判断：提高 Fusion 的 MCP/Host compatibility 观察权重。**

**值得互动：高。** 技术切入：*是否考虑用机器可读的 logical-tool-id / exposed-schema-name manifest 替代 prompt 文本映射，让 Host 准入直接验证映射完整性？*

## 7. OpenHands：Docker Conversation 不应暴露 Host Workspace 控件，Runtime Capability 开始真正驱动 UI

**状态：DRAFT / OPEN**

OpenHands Draft PR [#17387](https://github.com/OpenHands/OpenHands/pull/17387) 修复 Canvas 的 runtime boundary。Docker backend 本身不能 attach 用户选择的 host folder，但旧 Canvas 仍会暴露 **Open Workspace**，而部分 File/Git/Terminal/VS Code service call 还会丢失 conversation scope。

候选修复改用 SDK typed runtime clients 与 Server 广告的 capability：isolated runtime 会拒绝 host project selection、隐藏不支持的 host workspace controls，并把 conversation identity 传入 files、Git、terminal 和 VS Code 调用。真实 Chromium probe 还发现并移除了一个 raw、unscoped bash WebSocket，改为现有 SDK `BashClient`；测试确认 disposable Docker conversation 的 fixture file、Git branch 和 Terminal viewer 都保持 conversation-scoped。

当前依赖尚未发布的 TypeScript client 版本，所以 PR 保持 Draft；真实部署没有 editor，不能声称 VS Code launch 已验证。

**为什么重要：** UI 可见按钮本身就是 capability statement。如果 Host/Runtime 不支持某种 workspace authority，UI 也不能继续假装它可用。

**与 CodeFlowMu/FCoP 的关系：** Host 准入后的 `DetectedHostFacts` 最终应该向 UI、Worker 与 Tool routing 投射同一份 capability contract，而不是每一层自行猜测。

**值得互动：高。** 技术切入：*是否会把 runtime capability snapshot/version 与 conversation identity 一起持久化，使恢复后的 UI 能证明自己没有使用旧 Host capability？*

## 跨项目共振

今天可以把共同趋势概括成：

> **连续性不是一个布尔值。Session、Task、Human Interrupt、Credential、Client Origin、Workspace 与 Tool Schema 都有各自的连续性。**

更适合 CodeFlowMu/FCoP 的长期对象链是：

**Run/Thread Identity → Current Work Revision → Principal/Credential Lease → Host Capability Snapshot → Human/Client Origin → Logical Tool Identity → Effect / Result → Verification / Replay Eligibility**

其中任何一项变化，都不能因为 Provider Session 仍然存在，就默认继承上一轮的 authority。
