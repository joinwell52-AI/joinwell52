# Agent 核心研究与竞品动态 · 2026-11-09

本轮最重要的研究结论：数字员工的价值正在从“并行调用多个 Agent”走向“主管可响应、后台任务可持续、授权可追溯、完成有证据”。Deep Agents 的异步参考实现值得优先体验；Paperclip 原生 Runner 正式交付值得跟踪；Paradev 扩大云端到宿主权限、Palmier 转向自动批准，需要单独审视企业治理适配度。

本报告按实际执行日期 **2026-11-09（Asia/Shanghai）** 归档，补查上次成功监测之后的空档，不倒填11月6–8日空日报。执行起点为09:21:57（UTC 01:21:57）；多数完整提交查询的上次基线为11月5日05:43:53 UTC，各来源以本地成功记录为准。除另注外，条目时间采用原始来源的 UTC 日期。Orkas #193 是执行期间后续核验到的新增，已单独标明。既有事项的 OPEN→MERGED 或主干→发行只计状态推进，不冒充全新机制。

## 第二层：研究分析

### A1 主管可触达与后台持续履职，开始有可比较的实现

依据：O4、O6、O20、O29、O30、O31

证据支持：Deep Agents 将任务线程、持久任务登记、改向/取消和审批中通知分开；Cursor、Claude、Orca 分别补充对话、后台工具及移动控制入口。它们覆盖不同层次，不能由此宣称行业已有统一数字员工协议。待验证：CodeFlowMu 是否可借鉴“主管保持响应、任务有独立身份、完成唤醒主管”的组合，需要与现有 Runtime 对照。优先体验 async-deep-agents，核查通知 wiring、版本差异、License、worker 容量和任务清理；再体验 Orca 弱网控制。代价是独立线程/worker、事件排序、通知去重、取消后副作用和历史保留。这一组主要映射 Runtime 与产品层；互动主题为任务登记在压缩后是否仍权威、审批期间结果如何排队。

### A2 授权要沿恢复、宿主和凭据继续成立，不能只在起点检查

依据：O2、O3、O5、O6、O8、O18、O19、O22、O25

证据支持：Codex 区分项目信任/写权限并处理授权落盘顺序；ADK 暴露参数表示变化对审批的影响；Paradev 增加 owner 云工作区到宿主的明确通道；Palmier 则主动减少审批。不能把这些相反方向都归为治理成熟。待验证：企业员工的委派、恢复和跨宿主调用是否能持续核验主体、范围与撤销，属于 CodeFlowMu Runtime/适配层及企业产品策略问题，不自动成为 FCoP 字段。实验候选为权限模式恢复、撤权后跨宿主请求、非法只读配置和 Enum 审批对照。收益是减少隐式授权，代价是策略版本、身份凭据、恢复兼容与人工阻塞。Paradev/Palmier 风险关注上调，Paperclip 交付成熟度与治理适配度分别评估。

### A3 恢复与完成必须有终态证据，“安静”不能冒充成功

依据：O8、O9、O10、O13、O14、O17、O21、O23、O26、O28、O31

证据支持：strict_resume、旧 owner 结算限制、挂起工具等待、最后一条 JSON-RPC 冲刷、非零退出、空评分拒绝、压缩失败 error 和 ACK/模型消费差异，都在划清状态边界。多个项目出现相近修正，只支持这些机制的跨项目共振，不能证明任何一方已实现完整 exactly-once。待验证：任务执行、结果验收、用户汇报、网站发布应可分别判断成功/失败/未知；本地适用性仍需实验。候选为断流末记录、空测试结果、审批暂停时重启与重复输入；收益是可恢复且可追责，代价是持久状态、因果 ID、幂等键和补偿流程。交付证据可与 FCoP 契约比较，具体资源锁、排程和收尾归 Runtime。

### A4 治理证据从轨迹扩展到岗位声明、技能版本和独立签名

依据：O1、O7、O9、O16、O24、O27

证据支持：ARC/Ponder/Tracekit 的目录条目覆盖执行前声明、复核过程与外部签名三种不同职责；Paperclip 固定 run 的技能版本，Langfuse 将读取/下载纳入受限审计，StaffDeck 报告提示 SOP 要求与工具输出可能断裂。待验证：岗位→SOP→工具能力→产物→独立验收能否形成可追溯链，不以增加日志数量替代。优先源码复核 ARC/Ponder/Tracekit，核查原仓库许可、维护及信任假设后再决定体验；本轮目录的许可摘要不等于完整采用审查。候选实验比较静态声明通过但运行越权、签名完整但执行绕路、最终成果达标但过程缺证三类反例。维护 schema、外部签名隔离及隐私保留均有成本。

### A5 协议与开源应用要比较语义层次和可运行边界

依据：O3、O7、O10、O11、O12、O15、O18、O20、O22、O28、O30、O32

### A6 授权要保存人类意图，并把拒绝交接到可执行的人类入口

### A7 恢复和并发控制要显式区分已证明、未知与接受的风险

依据：O33、O35、O38、O40、O41、O42、O44、O45、O52、O53

已有证据支持：Paperclip仅在未交付且runner已死时回滚，Beads保留取消期间重复历史的窄边界，Orca交接则主动放宽停止证明；这些不是同一种“恢复增强”。完整会话、导出、turn终结、后台进程存活、消息失败与会话暂停也有不同契约。待验证推断：CodeFlowMu可研究按对象分离task/turn/session/worker/job状态，并为unknown、策略放行和风险接受保留证据；不据上游问题认定本地同缺陷。实验候选为硬杀authority轮换窗口、取消中的并发delete、旧Agent幸存后交接、并发字段写和cap事件重放。收益是可解释恢复与一致验收，成本是状态持久化、fence、日志和可用性取舍；FCoP比较聚焦状态/事件/证据语义，锁和进程控制仍属Runtime。
