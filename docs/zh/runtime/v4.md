# Research Runtime Center V4

## 一句话定义

Research Runtime Center V4 是数字研究员的运营中心：三条研究情报管线共同为三个栏目发现选题，上午推进研究，下午生产完整报告，晚上完成 GitHub 与网站发版。

## 研究情报系统

“从哪里找”和“研究什么”是两个不同维度。

### 三条来源情报管线

```text
Skill 01-P — AI 平台变更情报发现
Skill 01-G — GitHub 工程情报发现
Skill 01-R — 论文与研究成果情报发现
```

三条管线共同形成统一信号池，完成跨来源去重后，再由 Skill 02 进行三栏研究筛选。

### AI 平台一级观察范围

每日固定检查：

- OpenAI / ChatGPT / Codex；
- Anthropic / Claude / Claude Code；
- Google / Gemini；
- Cursor；
- GitHub Copilot；
- Microsoft Copilot Platform。

检查对象包括官方 Release Notes、文档、论坛或社区、官方 GitHub、状态页、企业控制、权限和产品边界。需要登录的渠道必须记录为受限，不能冒充“已检查无更新”。

### GitHub 工程雷达

GitHub 不做不可能的全量扫描，而是采用：

```text
70% 固定组织与仓库 Watchlist
20% 固定主题 × 变化类型查询
10% 有边界的新项目探索
```

扫描 Release、Tag、已合并 PR、高价值 Issue、Discussion、安全公告和架构、测试、Benchmark 等关键文件的增量变化。

### 论文与研究成果雷达

观察论文、预印本、技术报告、Benchmark、数据集、System Card、Model Card、标准以及关联代码与评估工具。摘要或厂商宣传不能单独形成工程结论。

[查看研究情报系统 V1.0](/zh/runtime/research-intelligence)

## 三个栏目

每日 10:00 的 Research Runtime Queue 必须分别对以下栏目作出决定：

1. **数字员工**：岗位、职责、工作流、运行、治理、恢复、交付与评估；
2. **行业架构**：主要 AI 平台的产品、Workspace、Agent 运行模式、控制平面、权限、连接器、企业控制与产品边界；
3. **开源工程**：开源运行时、协议、SDK、工具、基准、恢复、测试与可观测性工程。

每个栏目必须显示：

- 今日选题，或“未选题”；
- 选题原因或未选题原因；
- 主要来源；
- 优先级与生命周期；
- 下一步。

## 每日班次

| 时间 | 班次 | 工作成果 |
|---|---|---|
| 09:00 | Research Runtime Engine | 严格推进一个受治理生命周期转换。 |
| 10:00 | Research Runtime Queue | 执行三条情报管线、跨来源去重、候选评分与三栏选题计划。 |
| 11:00 | Research Runtime Knowledge | 合格研究笔记的知识准入与架构候选。 |
| 15:00 | **Research Runtime Production** | 完成中英文报告、配图、引用与出版编辑，形成 Publication Candidate。 |
| 20:00 | Research Runtime Publication | 发布完整候选、更新索引和网站、提交并验证 GitHub。 |

周一 12:00 另有架构评审；周日 20:30 生成每周综合；周三 10:00 运行学术研究。

## 10:00 情报发现与选题班次

Queue 完成的标准不再是“搜索到了一条新闻”，而是：

- 三条情报管线均有覆盖结果；
- 所有到期来源已检查、明确受限或记录失败原因；
- 同一变化在平台、GitHub 和论文来源中完成去重；
- 每个入选对象只有一个主栏目；
- 三个栏目均作出“已选题”或“未选题”决定；
- 情报运行记录与三栏计划中的选题 ID 一致。

## 15:00 生产班次

下午班次执行已有 Research Skills：

```text
Skill 05 — Research Writing
→ Skill 06 — Visualization
→ Skill 07 — Evidence & Citation
→ Skill 08 — Publication Editing
```

输出不是半成品草稿，而是完整的 **Publication Candidate（出版候选）**：

- 中文 Markdown 完整；
- 英文 Markdown 完整；
- 元数据与栏目归属正确；
- 配图完成，或明确说明不需要配图；
- 证据与引用完成校验；
- 出版编辑完成；
- 尚未进入公共文章目录。

## 20:00 发版班次

20:00 只负责发布，不重新研究或写作：

```text
Publication Candidate
→ 中英文公共文章
→ Metadata / Index / Website
→ GitHub Commit
→ Commit Verify
→ Release
```

候选未通过发版门禁时，应退回 Production 或更早的研究阶段。

## 四类权威运行产物

```text
research/runtime/YYYY/MM/YYYY-MM-DD-runtime.md
```

记录每个班次的状态、输入、工作成果、输出、下一步和 GitHub 证据。

```text
research/intelligence/runs/YYYY/MM/YYYY-MM-DD-intelligence.json
```

记录三条情报管线的覆盖、失败、信号、候选与三栏筛选决定。

```text
research/runtime/plans/YYYY/MM/YYYY-MM-DD-plan.json
```

记录三个栏目的每日选题决定，并必须与情报运行记录一致。

```text
research/runtime/candidates/YYYY/MM/YYYY-MM-DD-candidates.json
```

记录 15:00 形成的完整出版候选，供 20:00 发版使用。

## 完成率

只有 `Completed` 计入完成率：

```text
完成率 = 已完成任务数 ÷ 当日计划任务数
```

`Waiting`、`Running` 尚未完成；`Skipped`、`Blocked`、`Failed` 虽已终止，也不算完成。

## 最高原则

> 三条情报管线共同服务三个研究栏目。

> 已检查但没有重要变化，与没有检查，是两个不同事实。

> 每个定时任务都必须汇报实际工作成果，而不是只汇报“执行完成”。

> 下午生产完整报告，晚上只负责正式发版。

> 没有 Runtime Record 和 Commit Verify 的发布，不属于正式运行结果。
