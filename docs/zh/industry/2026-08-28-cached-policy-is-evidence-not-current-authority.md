# 缓存策略是证据，不是当前权限

企业系统常把缓存命中当作“状态仍然有效”。对于界面配置和性能数据，这种简化通常只影响新鲜程度；但当配置决定工具能否执行、插件能否变更或安全限制能否绕过时，旧数据继续可读与旧权限继续有效是两件完全不同的事。

GitHub Copilot CLI（命令行代码助手）1.0.81 的官方变更说明提供了一个有界案例。启用强制远程设置刷新后，一小时内的缓存快速路径和文档所述的二十四小时旧数据回退都不能替代新的受管策略。在最新策略尚未成功取得期间，一组被点名的能力进入限制状态。

核心判断是：**当治理合同明确要求当前远程权限时，旧策略可以保留为可追溯的存储证据，但必须失去授权行为的资格。无法确认新鲜权限，应表现为显式、有限、可恢复的限制状态，而不是悄悄回到最后一次允许结果。**

## 缓存仍可保留，但权限可以失效

缓存至少包含三种不同价值。它可以帮助运营者查看上一次已知配置，可以保留来源和修订信息，也可以在不涉及权限的页面上维持可用性。这些价值不要求缓存继续批准动作。

权限准入回答的是另一道问题：当前治理者是否仍允许这项能力？如果远程策略可能已经撤销某项权限，那么旧副本即使格式正确、内容完整、来源真实，也无法证明撤销没有发生。把“文件还在”解释为“许可还在”，会让缓存层越过授权层。

因此，策略对象不应只有存在或不存在两个状态。它还应记录来源、修订身份、取得时间、当前新鲜性判断，以及对哪些能力仍具有准入资格。数据生命周期与权限生命周期可以引用同一份对象，却不能共享一个布尔值。

## 新鲜性属于证据准入，而不是缓存优化

所选行为合同的关键，是强制刷新会同时拒绝普通快速路径和旧数据回退。这样做不是简单地“更积极联网”，而是改变了证据门槛：只有新取得的远程策略才能满足当前动作所要求的权威条件。

这一区分防止了隐蔽降级。如果网络失败后自动使用最后一次允许结果，系统表面上保持可用，实际上把“无法确认当前权限”转换成了“继续允许”。这种转换没有新的权威来源，也没有显式风险接受，因此不是中性的容错。

旧策略仍然值得保存。它可以说明上一次系统为什么做出某个决定，也可以支持差异检查和故障诊断。但后续执行必须读取“这份证据当前是否可准入”，而不能只读取其内容。新鲜性因此属于授权证据的一部分，而不只是缓存性能元数据。

## “无法确定”应成为受治理权限状态

官方说明列出的限制范围包括非默认的模型上下文协议服务器、绕过权限的运行方式，以及若干受策略约束的插件与市场操作。这里有两个重要边界：限制只覆盖被点名的能力；证据来自产品变更说明，而不是底层实现。

一个可审计的“无法确定”状态至少要包含四项信息：哪些能力被限制，为什么无法确认当前权威，什么事件能够恢复，以及谁可以批准例外。它不能被下游解释成“没有限制”，也不能让不同能力在没有声明的情况下共享同一失败语义。

恢复也应是一项可观察事件。成功取得最新策略后，系统可以重新计算能力资格；仅仅等待一段时间、重启进程或发现旧缓存仍可解析，都不能证明权威已经更新。

## 可用性例外必须显式授权

严格要求新鲜策略会牺牲部分可用性，尤其在远程控制面故障时。某些低风险、只读、可逆能力可能适合受治理的宽限期。但宽限期必须按能力定义风险、时限、审计和撤销条件，不能由通用缓存层自动决定。

对于高影响写操作、权限绕过或插件变更，旧策略保留已经撤销权限的风险可能高于短时不可用。此时失败关闭不是“缓存失效”，而是系统诚实承认自己无法证明当前权限。

## 仍需回答的实施问题

所选来源没有披露：什么修订、账户或组织身份构成“最新”；远程响应如何认证；失败后如何重试；畸形数据如何处理；会话中途变成无法确定时，已经运行的能力如何收口。因此，产品行为合同支持限制状态，却不能证明未公开实现已经安全。

设计评审应继续追问：策略证据绑定了哪个权威身份？取得与使用之间是否会发生切换？拒绝回执能否区分旧权限、网络故障和数据错误？哪些能力允许宽限，批准者是谁？这些答案决定“最新策略”是可核查的授权条件，还是只有名称的刷新动作。
