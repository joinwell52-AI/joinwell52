# 批准一次动作，尚未说明谁有权委派

一次人工批准之后，执行器继续的是原来的动作。这是一个可以通过代码检验的具体承诺；“这次委派调用已获得正确授权”则还涉及谁发起调用、批准覆盖什么范围，以及动作是否经过相应检查。两者之间不能只用一个确认框连接。

本次研究把这条边界落到一个有限的执行结果上：在固定版本的 AgentSpec（智能体动作约束框架）局部函数中，同意会继续原动作，拒绝会跳过；空规则和未触发的规则仍保留原动作。我们的判断是，动作批准、规则覆盖与调用者权限需要分别取证。这个结果既不认证完整平台的安全性，也不构成对某个已部署产品的绕过指控。[1][2]

## 确认之后，究竟继续了什么

已读源码中的同步执行路径先调用约束检查，再进入实际动作执行。人工检查函数接收动作，询问用户并返回相应结果。本次研究分析已在固定提交上抽取并执行所选函数；这是登记基线版本，不是对当前最新代码或论文发布包的认定。[1]

内部实验依据的范围很窄：五个人工回答用例，以及六个规则分派用例。动作、规则、规则解释器和状态使用明确披露的测试替身；真实领域谓词、适配器以及 LangChain（智能体应用框架）均未运行。它检验的是分支行为，不是完整系统复现。[2]

| 输入或条件 | 内部探针观察到的结果 | 能支持的判断 |
|---|---|---|
| 回答 yes，或带空白的 y | 返回继续，保留同一个动作对象 | 本函数的同意分支没有替换动作 |
| 回答 no 或 n | 返回跳过，动作变为跳过对象 | 本函数可抑制该动作 |
| 无效回答后再回答 yes | 询问两次，随后继续原动作 | 无效输入没有直接放行 |
| 已触发规则，解释结果分别为继续、跳过、停止 | 分别保留动作、转换为跳过、转换为结束 | 分派遵循所注入的解释结果 |
| 未触发规则或空规则列表 | 保留原动作 | 是否阻止动作取决于规则覆盖与触发 |
| 规则值缺失 | 抛出规则不得为空值的异常 | 空列表与缺失规则不是同一种路径 |

表中结果均来自本次研究的内部隔离函数探针，不是第三方独立验证，也不是用户真实调用样本。解释器的继续、跳过和停止结果由替身提供，因此不能从分派正确推论实际谓词也正确。[2]

保留同一个动作对象，只能说明这次同步函数调用的返回关系。它没有测量并发修改、批准后的对象变化、异步调用或恢复执行。把“原对象继续”写成“批准内容与最终执行内容始终一致”，会超出实验。

## 检查存在，不等于规则已经覆盖

空规则与未触发规则是必要的对照。它们说明执行路径存在检查调用，并不意味着每个需要约束的动作都被某条有效规则拦住。要判断一个动作受到什么保护，仍需找到适用规则、触发条件、谓词读取的状态，以及最终执行点。这里只执行了其中很小的一段。

AgentSpec 的论文将机制描述为触发、谓词与执行约束，并讨论动作、状态和结束边界；论文记录的实现对接框架版本为 0.3.13。公开机制描述支持“应检查哪些位置”的讨论，不能自动补足未审计解释器、领域适配器或异步路径的证据。[3]

论文还报告了约束的代价与覆盖差异：其具身任务中的安全任务完成率从 58.62% 降至 54.26%；自动生成规则在八项驾驶违规中阻止五项，而手工规则在所测场景中取得完全合规。这些是作者报告的指定实验结果，未由我们重跑；它们提醒读者把规则选择视为待评估对象，而不能把“有约束机制”直接读成“所有任务都会安全完成”。[3]

## 组织关系、令牌与批准回答各管什么

Salesforce（企业软件供应商）的帮助文章描述了同组织内由父级规划者委派、跨组织的明确关系，以及网关按智能体提供控制等能力。这些是供应商的能力描述；所读材料没有给出足以验证本次委派凭据范围、令牌传播链或实际执行结果的数据。不能从组织关系推断每一次工具调用的权限已经得到验证。[4]

MCP（模型上下文协议）的已捕获授权草案处理另一层责任。授权在该草案中是可选能力；基于 HTTP（超文本传输协议）的实现若支持授权，应遵循相应流程，STDIO（标准输入输出传输）则应从环境取得凭据。对采用该授权流程的请求，资源服务器需要验证令牌面向自己的受众；安全条款还要求上游接口使用单独令牌，禁止直接透传客户端令牌。[5][6]

同一组安全指导把状态句柄归为普通工具参数：它不能用来认证调用者，应在服务器端绑定到已经验证的主体。猜中一个流程句柄，不应就能操作另一个用户的状态。这是一项规范要求，不是对任何具体服务已经正确实现的测量。[7]

这些材料可以放在一起比较责任，却不能拼成一次不存在的集成测试：组织关系说明如何建立协作；令牌受众与上游凭据限制说明资源边界；状态绑定说明谁拥有某份状态；人工回答则决定所见检查点上的动作走向。只有最后一项在本轮执行了局部分支探针。其他层面的规定或描述不能替它提供执行证据，局部探针也不能反过来验证其他层面。

由此得到的工程解释是：评审一条委派调用时，应分别追问调用主体如何确认、动作及资源范围如何限定、批准对应哪一次动作，以及所有实际执行路径是否经过适用规则。这是根据现有证据提出的检查方向，不是一个已经实现或验证的完整授权方案。

## 单用户检查可以足够，分布式证据仍待补齐

一个同步、本地、单用户的人工检查点可能完全符合其威胁模型。不能因为所读文件没有分布式批准凭据，就断言完整系统缺少这类控制；也不能把本实验未测试的路径写成漏洞。

目前仍未建立的，是子动作与发起主体、任务实例和批准实例如何绑定，长期委派中撤销权限如何生效，以及异步、工具内部和恢复路径是否经过相同约束。要回答这些问题，需要相应路径及凭据的实际证据。本轮能够成立的边界停在这里：批准确实改变了所测函数中的动作走向，而委派权限还需要自己的证明材料。
