# 字符串“假”，为什么拿到了完成进度？

把“没有找到”写成字符串，可能得到与布尔假完全不同的进度。在本次隔离探针中，同一个文档示例把字符串 `"false"` 计为“记录已读”，却把布尔值 `false`（布尔假）留在部分完成。问题落在工具结果变成证据的那一刻：**真值转换不能代替类型合同**。工具适配器作者可以据此检查，究竟哪一层承诺了字段类型，哪一层负责拒绝异常值。

## 一次转换，改变了字段的含义

MedHarnessBench（医疗智能体过程评测基准）的当前运行器文档提供了读取结果解析示例。这个例子的职责很具体：接收工具事件中的查询结果，再把它转换为可以汇总的进度。字段类型在此处是否已经可靠，决定了这一步转换的业务含义。

示例中的 `resolve_read`（读取结果解析函数）从事件取出 `found`（是否找到字段），先做 Python（本次执行所用编程语言）的真值转换，再决定是否增加已读里程碑。

代码把这个里程碑命名为 `record_read`（记录已读里程碑）。关键表达式如下，属于公开文档的原字段节选：[运行器文档](https://raw.githubusercontent.com/Tomry1114/Awesome-Agent-Harness-for-Healthcare/main/runner/README.md)。

```python
found = bool((event.get("result") or {}).get("found"))
```

这个表达式询问的是值在该语言中是否为真，并没有先询问它是不是布尔值。非空字符串即使拼写为“假”，仍会转成真；整数一也一样。只有当上游已经保证字段类型时，二者才可能在这个接口上等价。这是接口前提，不能从函数名或“解析成功”反推出来。

论文把模型提议、环境产生的效果与评估判断分开，是有意义的责任划分。但这种高层划分不能替代每个转换点的输入前提。[论文第一版第 3.2 节](https://arxiv.org/html/2610.15714v1)所定义的过程评测，也不能单凭一个辅助示例就被判定失效。

## 八组输入只回答示例层的问题

同日 Analysis（研究分析阶段）已经执行了内部实验：从已读文档用抽象语法树抽出未改动的函数，输入八组人工构造结果。没有导入上游运行器，没有调用模型或医疗环境。下表转述该实验实际输出；右栏是我们提出的严格布尔对照策略，**不是上游实现**。

| 输入字段值 | 文档函数的输出 | 我们提出的严格布尔对照 |
|---|---|---|
| 布尔 `true`（布尔真） | 成功，增加记录已读 | 成功 |
| 布尔 `false` | 部分完成，不增加 | 部分完成 |
| `null`（空值） | 部分完成，不增加 | 类型无效 |
| 字符串 `"false"` | 成功，增加记录已读 | 类型无效 |
| 字符串 `"true"` | 成功，增加记录已读 | 类型无效 |
| 整数 `0` | 部分完成，不增加 | 类型无效 |
| 整数 `1` | 成功，增加记录已读 | 类型无效 |
| 空列表 `[]` | 部分完成，不增加 | 类型无效 |

来源：本日内部隔离实验；方法、原输入和输出见随文[实验记录](/assets/evidence/2026-11-18-sig-20261118-006/experiment-006.json)及[可复查实验程序](/assets/evidence/2026-11-18-sig-20261118-006/resolver-probe.zip)。附带程序保留同一解析函数与八组对照，供读者复查，本篇生产阶段没有重新执行实验。八个输入不是八个临床任务，也不是八次完整基准运行。

实验否定了一个很窄的假设：“这个示例只有遇到布尔真才增加进度。”它没有说明非布尔值能通过原生生产者、适配器派发和最终汇总。假如工具的序列化合同已强制布尔类型，字符串输入可能根本到不了这里；此时探针展示的是防御性边界，而不是可达故障。

## 严格裁判合同管的是另一个接口

chi-Bench（医疗任务环境评测基准）的当前裁判文档明确要求 JSON（结构化数据交换格式）布尔值；字符串形式的假不会被解释为通过。它还检查完整的裁判条目身份、证据引用和输出完整性。裁判超时、缺失或不完整会使测量无效；传输中的数值零只是占位，不能直接解释为智能体拿到零分。[裁判合同](https://raw.githubusercontent.com/actava-ai/chi-bench/main/docs/judge.md)

两份材料来自不同作者团队，但它们没有独立复现同一个系统。前者位于工具事件到进度的转换点；后者位于裁判输出到有效测量的接纳点。比较的价值在于看清责任位置，不能据此排出两个基准的可靠性高下，更不能断言后者所有工具结果都受到相同类型约束。

对于读者自己的适配器，一条可执行的检查链是：

| 环节 | 负责者与输入 | 必须留下的结果 | 停止条件 |
|---|---|---|---|
| 产生工具结果 | 工具实现提供原始字段 | 明确且版本化的字段类型约定 | 类型约定缺失，先记为未知 |
| 接纳并解析 | 适配器接收原始值 | 合法值、业务否定、无效测量分开 | 类型不符或字段缺失，按声明策略处理 |
| 增加进度 | 进度聚合器读取已接纳结果 | 能追溯到原结果的里程碑 | 不以非空、可解析或真值替代业务成功 |
| 形成评测 | 评估器接收完整证据 | 有效结果及无效原因 | 所需裁判缺失时不冒充有效失败 |

这张表是我们的检查建议，并非两套系统已统一实现的流程。以字符串假为贯穿例子：生产者若不能证明只会输出布尔值，适配器就应明确承担拒绝或标记无效的责任；聚合器随后只能消费有身份、有语义的结果。修复点在哪里，应由真实调用链决定。

## 仍缺的是原生路径证据

本篇的公开事实来自两个项目各自的文档；这些是可核验的一手定义，不是独立运行验证。内部实验只支持所抽取函数的行为。我们的解释是应在生产者与消费者之间分配类型检查责任，尚未观察到临床影响、总体成功率失真或原生路径漏洞。文档快照于 2026-11-18 的 Reading（深度阅读阶段）获取并按字节固定；可变分支没有被伪装成论文运行时的固定提交。

下一步应核对原生生产者模式，保留从字段生成、接纳、解析到最终汇总的同次调用证据，再测试错误类型是否实际可达。如果上游始终拒绝这些输入，就应把结论停在示例的健壮性边界；如果它们能进入汇总，还需要量出哪些里程碑和最终结果受到影响。**能区分布尔假与无效测量，是检查的起点；整个系统是否已经做到，仍需另一层证据。**
