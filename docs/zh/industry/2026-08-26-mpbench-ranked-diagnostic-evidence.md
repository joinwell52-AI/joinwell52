# 一次多智能体失败，可能不只有一个合理原因

一条多智能体执行轨迹可以完全确定，但对它为什么失败的解释却未必唯一。

Agent A 可能收集了薄弱证据，Agent B 可能过早接纳，Agent C 最终做出了肉眼可见的错误动作，而调度器又可能没有及时阻止。任务失败以后，这四个位置都可能具有诊断价值，但很多故障系统最后仍然要求把某一个步骤写进 `rootCause` 字段。

这个压缩动作很方便，也可能直接损失证据。

KAIST 与 Adobe Research 在 2026 年发布的论文 **Rethinking Failure Attribution in Multi-Agent Systems: A Multi-Perspective Benchmark and Evaluation**，把这个问题做成了一个正式基准 MP-Bench。它不预设一次失败轨迹只有一个唯一正确的“致错步骤”，而是让多名专家独立阅读同一轨迹，并保留他们之间的差异。

这篇论文并没有证明所有生产事故都存在多个同等正确的根因。它提供的更有边界的证据是：**把多智能体失败归因强行压缩成单标签，可能过于严格。** 对工程系统来说，这意味着“因果归因”应该被当作诊断证据，而不是和日志事实放在同一层级。

## 同一条轨迹，专家可以给出不同的合理诊断

MP-Bench 包含 **289 条失败执行日志**，覆盖 **121 种不同的多智能体配置**。论文报告其中 169 条来自人工设计的 MAgenticOne 配置，120 条来自自动生成的 CaptainAgent 配置，任务来自 GAIA 与 AssistantBench。

每条失败轨迹由三名经过筛选的专家独立标注。对轨迹中的每一步，专家都要记录三个内容：

- 这一步是否属于 failure-inducing step；
- 为什么；
- 理想情况下 Agent 应该采取什么动作。

Adobe Research 公开的数据仓库也按三名专家分别保存了这些逐步标注与解释。

真正值得注意的不是“专家存在分歧”这句泛泛而谈，而是分歧的比例。

在至少被一名专家认为是失败步骤的条目中，作者报告：只有 **16.2%** 被三名专家同时认定；**27.8%** 被两名专家认定；而 **56.1%** 只被一名专家认定。论文还报告，不同专家之间的成对分歧在部分比较中可以接近 **60%**。

这些数字属于论文作者报告的实验与数据分析结果；本次 Academic 运行没有独立复现完整数据统计。但论文和官方公开数据已经足以确认 MP-Bench 的设计目标：它有意允许多个因果解释同时存在。

这里必须区分两种完全不同的信息：

- **发生了什么**：消息、工具调用、输出、状态变化、错误；
- **为什么最终失败**：对这些事实所做的因果解释。

前者往往可以重放，后者可能长期存在争议。

## 多视角不等于“大家说什么都算”

MP-Bench 并没有因为接受多个解释，就把所有解释放到同一优先级。

它把专家标注转换成 **共识率排序**。三个人都认定为失败步骤的位置，高于只有一人认定的位置。随后，基准用 nDCG 去评价模型给出的排序，而不是要求模型必须命中唯一一个 oracle step。

这个设计实际上拆开了两个经常被单标签系统混为一谈的问题：

1. **哪些因果假设仍然合理？**
2. **哪些假设应该优先调查？**

所以，多个解释并不妨碍形成一个有序的排障队列。

论文对 LLM 的实验也沿用了这个思路。作者会多次采样模型的故障归因，再把结果聚合成排序。论文报告，完全确定性的解码通常不如引入一定随机性，但温度继续升高并不会单调提升效果；作者还报告，多种模型家族组合在其测试设置下取得了较强结果。

这些结果有价值，但不能越过证据边界：**模型多样性不是独立的因果证据。** 三个模型可能因为共享同一条轨迹、同一种提示方式，甚至共享同一个错误前提而同时得出相同结论。多样性适合帮助生成诊断假设，却不能自动给假设盖上“已验证”的章。

这里还有一个值得保留的原始表格细节。论文正文把增加采样次数描述成“持续提升”，但 Table 4 并非完全如此：GPT-5.1 在自动生成 MAS 轨迹上的 nDCG@5，从 `N=3` 时的 **0.7819** 变成 `N=10` 时的 **0.7769**。整体趋势仍然可以讨论，但不应被改写成无例外定律。

## 一个可靠的诊断 Runtime，至少要保存四种不同对象

下面的四层模型是 Research Center 基于 MP-Bench 形成的工程解释，**不是论文作者提出的正式协议**。

![诊断证据包络：轨迹事实支持多个因果假设，经过共识与显著性排序后，才形成一个受治理的修复决定。](/assets/figures/academic-mpbench-diagnostic-evidence-envelope.svg)

### 1. Trace Facts：轨迹事实

最底层应该是不可变的执行证据：Agent 消息、工具输入输出、外部回执、状态转换、策略判断、时间戳与错误。

这一层只回答 **发生了什么**，不要急着回答 **为什么整个任务失败**。

如果某个工具返回 HTTP 403，这是事实；“访问限制就是整个任务的根因”，已经属于解释。

只要事实层可以重放，后续不同诊断者就能基于同一个底座重新判断。否则，每出现一个新解释，系统都可能顺手改写历史。

### 2. Failure Hypotheses：失败假设

不要再让一个新的诊断覆盖旧的 `rootCause` 字符串，而是把每个因果解释做成独立记录。

一个有用的失败假设至少应包含：

- 涉及的步骤、Agent 或系统边界；
- 解释理由；
- 产生这个判断的视角或诊断方法；
- 支持它的轨迹证据；
- 反证；
- evidence identity；
- 当前支持度或置信状态；
- 与其他假设是兼容还是互斥。

这样，分歧本身就变得可检查。后续如果有确定性规则、新的外部证据或人工审阅，可以强化某个假设，却不需要删除其他历史解释。

### 3. Consensus / Salience：共识与显著性

接下来才是排序。

共识当然有价值。三名独立专家同时指出同一个步骤，与一个单独的推测不是一回事；同时，严重性也很重要。一个置信度不高但涉及授权越界的假设，可能比一个置信度极高的样式错误更值得优先处理。

但是必须把 **共识** 和 **独立性** 分开记录。

同一个模型跑三次，是三个视角，不是三个独立事实源；三个 Agent 如果都引用同一份虚假材料，也可以形成百分之百一致的错误结论。

因此，一个受治理的 Runtime 至少应该维护两个维度：

- **视角收敛度**：有多少诊断路径支持这个假设；
- **证据独立性**：这些路径是否真的来自不同证据家族。

MP-Bench 直接给了前一个维度的启发；后一个维度则是为了避免把“大家都这么说”误写成“已经验证”。

### 4. Repair Decision：修复决定

真正运行系统最后还是要执行一个动作。

很多系统正是在这里错误地把诊断变成单一答案：“既然我们只能做一个修复，那就一定只有一个根因。”其实没有这个逻辑关系。

**修复决定可以是单一的，而因果诊断仍然可以是多个。**

系统完全可以因为两个高显著性假设都能被一个低风险、可回滚的补丁覆盖，就先选择这个补丁，并记录为什么授权、完成后要收集什么新证据。

如果修复成功，它会成为新的证据，却并不能自动证明最初的某一个假设就是唯一原因。

## 允许多个诊断，反而可以让执行更严格

假设一次研究 Agent 的失败存在三个解释：

- 搜索 Agent 选了低质量来源；
- 分析 Agent 把来源结论夸大；
- 发布门禁没有拦住这个夸大。

如果系统只有一个根因字段，就必须三选一。

如果系统保存的是一个诊断证据集合，就可以先保留三个假设，然后做出一个明确的风险决定：优先加强发布证据门禁。原因不是“已经证明发布门禁就是根因”，而是这个修复成本低、可回滚，并且无论上游究竟是哪一种错误，它都能阻止最危险的最终结果。

这不是犹豫，而是把 **因果信念** 和 **风险控制** 分开。

多智能体系统尤其需要这种分离，因为错误会传播。肉眼可见的错误通常发生在下游，而最早的弱状态可能出现在上游；更复杂的是，那个上游错误原本可能还可以被后续 Agent 修复。

所以，“是谁造成的”和“应该在哪里介入”，是相关问题，却不是同一个问题。

## MP-Bench 能支持什么，不能支持什么

这篇论文及公开仓库可以直接支持几个事实：

- 同一条 MAS 失败轨迹上，经过筛选的专家可能对致错步骤产生大量分歧；
- 基于共识率的排序可以保留多视角，同时优先处理高共识位置；
- 在论文自己的评测协议里，测试过的 LLM 可以形成有用的多视角故障排序；
- 随机采样与跨模型多样性会影响基准表现。

它**不能**直接证明：

- 所有真实事故都有多个同等有效的根因；
- 专家共识等于因果真相；
- 多模型组合在生产系统里总是最优诊断器；
- LLM 合并与 LLM Judge 是中性的测量工具；
- 这些结果已经适用于软件工程、科研 Agent 或企业数字员工；
- 已经解决了生产 Runtime 的 crash-safe、exactly-once 等执行语义。

MP-Bench 本身也采用质量优先而不是规模优先的路线。作者明确把领域覆盖和 MAS 框架多样性列为限制。arXiv 页面显示论文仍处于 under review。本次运行找到了论文和第一方公开仓库，但没有识别到完整复现其主要实验结论的独立第三方证据。

另外，Adobe Research 的官方数据仓库明确使用非商业研究许可证。代码和数据“公开可见”不能被自动理解成允许商业产品直接使用。

## 一条最重要的工程规则：不要让解释覆盖事实

因此，一个可靠的故障记录不应该只剩下：

```text
rootCause = "Agent C, step 17"
```

更合理的结构是：

```text
trace_facts        = immutable
failure_hypotheses = append-only, provenance-aware
consensus          = ranked, not truth-equivalent
repair_decision    = explicit, bounded, verifiable
```

这个结构故意制造了一种不对称：**事实越来越难被改写，假设则应该随新证据持续修正。**

对多智能体可靠性来说，这种方向更合理。系统应该只有在证据增加时才提高确定性，而不是因为数据库 schema 强迫它只能填一个值。

## 还没有解决的问题

MP-Bench 已经把归因歧义变成可测量对象，但生产系统真正困难的问题还在后面。

当多个诊断 Agent 共用一个模型家族时，怎么识别“相关共识”？什么样的证据足以把一个 plausible hypothesis 提升成 operationally decisive？能不能先用确定性的依赖图排除不可能的因果假设，再调用 LLM？修复后的新证据应该怎样更新因果信念，同时又不改写历史记录？

更重要的是，下一步真正需要的基准不是只看“诊断排序与专家是否相似”，而应该测量：**保留多视角以后，真实修复质量有没有提高。**

在这之前，可以先采用一个更谨慎、也更实用的结论：**一次失败不要求只有一个因果故事。先保存证据，再选择修复。**
