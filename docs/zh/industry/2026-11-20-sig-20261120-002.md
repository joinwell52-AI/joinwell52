# 待审批请求恢复了，通知配置也跟着回来了吗？

一项等待人工审批的任务恢复后，请求编号还在，是否就能继续通知审核人？这不是一次已发生的故障，而是集成验收中应主动设置的检查场景：有的接口会重新发出待处理请求，有的恢复调用却要求重新提供通知地址。本文的判断是，请求恢复、响应关联和通知配置必须分别验收。平台工程师可以带走一张责任表，查清“恢复成功”究竟覆盖了哪一段。

## 两份文档，划出了不同的恢复边界

Microsoft Agent Framework（微软智能体框架）的[人工参与文档](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)说明：外部响应通过请求标识关联，交给发出请求的执行器处理。其示例把请求标识作为响应映射的键。检查点会保存待处理请求；恢复时，这些请求会再次成为请求事件，也可以在同一次恢复调用中提交响应。

这回答了“从哪里继续等待、把回答交给谁”。[检查点文档](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)进一步说明，它保存执行器状态、下一步待处理消息、请求与响应及共享状态。内存存储不提供跨重启持久性；文件或数据库存储承担不同的持久化用途。重新构建的工作流还必须保持拓扑和执行器身份，自定义执行器需要负责保存与恢复自己的状态。这里的拓扑是执行节点及其连接关系，不是部署网络图。

这些都是官方文档规定的合同，尚不是本次实测的部署行为。特别是，能找到原请求，不等于已经核实回答者仍有权批准它。

CrewAI（智能体协作框架）的[人工参与指南](https://docs.crewai.com/en/learn/human-in-the-loop)讨论了另一条路径：企业版通过网络回调发送执行标识、任务标识和任务输出，暂停等待人工输入；调用方提交反馈与是否批准的字段来恢复执行。指南明确要求，恢复调用再次传入启动时使用的任务、步骤和整体执行通知地址，这些设置不会自动沿用。

因此，保留执行标识和任务标识，不能替调用方补齐通知配置。这一要求针对指南中的企业版网络回调方式，不能外推到本地人工反馈装饰器，也不能据此声称企业版“没有保存任何状态”。

两份文档并不矛盾，也不构成可靠性排名。微软说明的是待处理请求如何恢复和重新进入外部交互；另一份指南强调继续通知所需的调用配置。它们使一个通常被笼统称作“人工参与”的功能，显露出不同的责任边界。

## 七组局部检查，实际检查到了什么

同日分析阶段执行了两类内部检查。第一类抽取微软文档中的事件收集函数，用合成异步事件替代真实框架事件流；函数保持原样，人工输入仍保留原示例的省略号占位值。第二类依据另一份指南明确列出的要求，检查恢复载荷有没有漏掉通知字段。后者是分析者编写的合同检查器，没有向企业服务发请求。

| 检查输入 | 实际结果 | 结论到哪里为止 |
| --- | --- | --- |
| 没有请求事件 | 不返回响应映射 | 仅覆盖空输入分支 |
| 两个不同请求标识 | 保留两个映射条目 | 示例能区分这两个键 |
| 同一请求标识重复出现 | 只留下一个映射条目 | 键相同会合并，不是防重放证明 |
| 同一标识、不同内容 | 仍只留下一个映射条目 | 示例映射不负责验证内容是否冲突 |
| 指南中的完整恢复载荷 | 未缺通知字段 | 只检查字段存在 |
| 保留执行与任务标识，删掉全部通知地址 | 缺三个通知字段 | 对象标识不能补回通知配置 |
| 仅删掉步骤通知地址 | 缺一个通知字段 | 检查器能定位这一处遗漏 |

完整输入、输出、环境、源码片段与局限保存在[局部检查证据](/assets/evidence/2026-11-20-sig-20261120-002/probe-evidence.json)。这些数字是四组收集函数检查和三组载荷检查的计数；其中两组重复标识用例的实际输入相同，因此七组不代表七个不同分支，更不能相加成为七项真实重启测试。所有执行结果都来自内部检查，独立厂商文档并没有使它们变成第三方复现。

一个三秒例子可以解释映射的边界：同一标识先带“偏低”的提示，后带“偏高”的提示，字典仍然只有一个位置。这个结果不意味着框架真的产生了碰撞，也不意味着批准被覆盖；收集函数中的人工回答还只是占位值。它只提示集成方：请求发生标识、内容版本与外部回答之间的关系，不能由一个字典赋值替你判断。

## 用一条等待中的任务分配验收责任

下面是建议的集成验收表，不是声称两款产品都已实现的统一协议。贯穿例子是一项输出等待人工审阅、暂停后重新恢复的任务。先明确恢复的输入与负责人，再要求各段交出自己的可核对输出。

| 环节与输入 | 建议责任主体 | 应保留的输出 | 单独检查的条件 |
| --- | --- | --- | --- |
| 暂停时的任务状态 | 应用与持久化组件 | 可定位的检查点及待处理请求 | 是否使用跨重启存储、自定义状态是否完整 |
| 检查点进入恢复过程 | 工作流构建与恢复入口 | 兼容身份和拓扑下重新出现的请求 | 结构或身份不兼容时如何处理 |
| 请求事件交给外部集成 | 事件接入方 | 请求发生标识与待审内容的关联 | 再次发出是否代表同一次请求，内容变化如何辨认 |
| 恢复调用继续通知 | 调用方与通知集成 | 必需通知设置及实际发送、接收记录 | 地址是否按合同重传，接收是否真正发生 |
| 回答进入任务继续执行 | 响应路由与应用授权层 | 回答归属、当前审批权及对应动作 | 过期、重复、改派或动作变化如何处理 |

这张表把“保存了什么”和“由谁继续做什么”放在同一条验收链上。请求记录能告诉恢复入口继续等哪个回答；通知配置告诉集成往哪里发；送达记录才回答外部是否收到。最后一行又是独立的权限问题。不能因为前几行有了记录，就把最后一行勾成通过。

对使用指南所述企业版回调方式的应用，一个可执行的下一步是：在固定部署版本中建立条件一致、分别暂停的任务实例，保留各自执行与任务标识，一个使用完整配置恢复，另一个使用遗漏配置恢复，记录服务返回、实际发送与接收情况。对使用微软框架的应用，则在固定软件包版本与持久化存储上重启进程，核对重新发出的请求与外部接入记录。两条测试各自回答集成问题，不应把它们混成一场产品竞赛。本文没有执行这些测试。

## 显式重传配置，也可能是合理设计

重复发出同一个待处理请求，可能正是让外部接入方重建等待状态的正确做法。同一请求标识合并为一个映射条目，也可能符合预期。它本身既不证明重复通知造成了副作用，也不证明副作用已被消除。

同样，恢复时显式提供通知地址，可能使调用方能调整接收目的地。这里不能把设计动机当作厂商已经确认的事实；但它足以成为另一种合理解释，阻止我们把“需要重传配置”直接写成产品缺陷。

不适用的场景也应说清：没有跨进程恢复、没有外部通知的本地同步审阅，不需要照搬整张表。相反，一旦要声称“重启后必达”或“旧批准不能重放”，就需要真实部署、重复响应与权限变化的实验。指南中对审核人分配、权限、升级和服务时限管理的描述仍是厂商陈述，本次没有检查其实现，不能用来填补这些空白。

## 下一次验收，要看到哪条外部记录

现有证据足以要求集成验收分别列出恢复、关联和通知配置；尚不足以宣布任何一款产品恢复后可靠送达或审批安全。下一次最有价值的记录，是一次真实重启前后的同一请求、实际接收回执以及响应处理结果。若审核人被改派或待批动作已改变，还应检查旧回答如何处置。只有把这些记录接起来，才有材料回答“恢复后仍是谁在批准哪一次动作”，而不仅是“任务编号还在不在”。
