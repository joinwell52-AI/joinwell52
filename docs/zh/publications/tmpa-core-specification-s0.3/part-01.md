# TMPA Core Specification

## 文本化多智能体流程架构——Core 对象、Reader 语义与一致性

> **规范版本：** Draft S0.3  
> **来源基线：** `TMPA-Paper-v1.md`, Draft V1.0-R24  
> **状态：** 抽取的规范草稿  
> **抽取日期：** 2026-07-31  
> **权威性：** 在本规范独立冻结为 TMPA Core V1.0 前，TMPA 综合母版仍为权威来源。

# 1. 状态、范围与一致性边界

本文档从包含架构、实现和案例研究的综合来源中抽取供应商中立的 TMPA Core。它定义规范治理对象模型、单写者与生命周期语义、来源聚合、确定性治理重建、信任假设、规范要求以及 C01–C14 一致性行为。

TMPA Core 治理流程—责任证据。它不规定模型 Runtime、调度器、存储引擎、消息传输、数据库、文件系统布局、身份提供方、密钥管理系统或企业控制平面。Profile 可以绑定这些机制，但它必须保留 Core 语义，并标明每一项附加假设或保证。

本草稿区分三类文本：规范要求（第 9、10 节）；解释规范条款所必需的架构定义（第 2–5 节）；说明性的抽取与可追踪说明（第 11 节和附录 A）。

除非命名 Profile 另行加入，否则以下能力不属于 TMPA Core：经过认证的企业身份、凭证签发、递归委托、运行时准入控制、受保护或防篡改存储、分布式共识、语义真实性验证、拜占庭韧性、法律认证和司法辖区特定合规。

符合规范的实现可以使用文件、数据库行、对象存储对象或事件作为来源工件。实现不得仅因为存储 Markdown、生成日志或实现工作流状态机就声称符合 TMPA。一致性是行为性质，取决于可观察的对象、生命周期、重建、冲突、恢复和测试要求。

# 2. 术语与表示阶段

| 术语 | 固定含义 |
|---|---|
| 受治理工作项 | 其责任和生命周期受到治理的任务、请求、决策或流程主题 |
| 主载体 | 锚定一项工作 ID 和最低治理上下文的稳定治理对象 |
| 治理对象 | 由一个创建者、以一个责任角色、在一条写者流中编写的规范语义单元 |
| 文本消息 | 治理对象传递工作、证据、复核或决策语义时承担的通信功能 |
| 状态载体 | 对象、迁移记录或 Profile 定义位置对状态证据作出贡献的持久化功能 |
| 来源工件 | 证据的一种物理表示或观测 |
| 来源候选 | 提交给聚合阶段的已发现来源工件，包括格式错误或冲突观测 |
| 规范候选集合 | 聚合返回的、保留来源、已解析、已索引且完成确定性规范化的集合 |
| 写者流 | 一个可归属写者发布的局部有序治理对象序列 |
| 来源聚合器 | 发现、保留、解析、索引与规范化来源候选，但不决定治理真值的阶段 |
| 治理 Reader | 把固定 Profile 应用于规范候选集合的确定性阶段 |
| 治理图与问题集合 | 重建得到的偏序流程视图和规范未解决条件输出 |

同一个规范治理对象可以由不同物理 Profile 实现。两个来源工件若声明相同对象 ID，却包含不同规范内容，则构成必须保留和评估的冲突候选。

# 3. Core 架构模型

TMPA 定义治理语义，而不是 Runtime 组件。其架构规定哪些治理事实必须被表示、责任与生命周期如何表达，以及如何把独立证据重建为权威视图。

## 3.1 治理对象

治理对象是 TMPA 中最小的、能够独立归属责任的语义单元。每个治理对象包含或标识稳定对象 ID、文档类型、一个创建者身份、一个责任角色、流 ID 与序号、创建时间、生命周期 Profile 与声明状态、类型化引用、规范文本内容和完整性证据。

已发布治理对象不可变。更正不会删除或重写原对象，而是创建新对象，以取代、拒绝、限定或解决先前对象。同一 ID 对应不同规范内容构成冲突，而不是更新。

## 3.2 文档类型

每个实现 Profile 发布有限文档类型注册表。每条注册项定义类型名称与版本、治理责任、允许创建者角色、必填字段、允许引用关系、适用生命周期 Profile 与验证规则。

## 3.3 角色与权限模型

TMPA 角色是在明确范围内具有治理权限的权威主体，而不只是 Prompt 标签。对象中的 `role` 字段声明创建者以何种权威行动，但该字段不会自行创造权限。Reader 必须根据有效角色分配和适用策略验证该声明。

## 3.4 生命周期模型

生命周期 Profile 包含有限状态集合 `S`、初始状态 `s0`、终止状态集合 `F`、动作集合 `A`、迁移关系 `T`、授权函数和验证函数。只有来源状态匹配、迁移合法、角色授权、前置条件满足且证据验证通过时，迁移才被接受。非法或未经授权的迁移不会改变权威生命周期状态，并必须保持可观察。

## 3.5 文本消息、单写者流与异步并行

对于每个受治理工作项 `t`，Profile 定义一个稳定主载体 `c_t`。接受、执行报告、复核、决策、更正和恢复记录都是引用 `c_t` 的独立对象。

令 `A` 为责任写者集合。每个已发布对象恰好有一个写者，每个写者发布一条可独立归属的串行流：

`S_a = ⟨o_{a,1}, o_{a,2}, ..., o_{a,n}⟩`

流内序列是权威局部顺序。多条流不必同步推进；没有显式跨流依赖的对象保持并发且不可比较。

> 一项任务有一个主载体。每个已发布对象由一个写者拥有。每个写者内部保持串行。多条流异步推进，形成并行协作。

## 3.6 读端聚合与治理重建

来源聚合器构建保留来源的规范候选集合 `C_τ = A(O_τ)`，不决定哪项声明为真，不静默修复冲突，不虚构缺失证据，也不把到达顺序转换为治理顺序。

治理 Reader 在固定 Profile `P` 下计算：

`R_P(C_τ) = (G_τ, I_τ)`

其中 `G_τ` 是偏序流程与治理图，`I_τ` 是规范问题集合。对同一来源集合的任意排列 `π`：

`R_P(A(π(O))) = R_P(A(O))`

重建主体或子图首先获得三值治理判断，再映射为运行视图：`valid` 通常映射 authoritative；证据缺失或依赖不完整导致 `undetermined/partial`；有效证据冲突导致 `undetermined/disputed`；完整性、身份、重复 ID 或禁止环问题可导致 quarantined。

TMPA 要求冲突保留与扩展时证据保留。确定性拓扑序列化不得在不可比较节点之间创造治理顺序。

## 3.7 完整性与签名证据

TMPA 区分归属、完整性与认证完整性。角色标签不是密码学签名；Digest 可以检测修改但不能证明创建者；有效签名证明来源与完整性，但不证明内容为真。

# 4. 规范对象、编码与重建

## 4.1 规范对象 Schema

TMPA Core V1.0 的完整 JSON Schema 定义稳定 ID、类型、流、创建者、角色、时间、生命周期、引用、内容、完整性和扩展字段。Schema 有效是权威接受的必要条件，但不是充分条件；Reader 仍必须评估 ID 唯一性、类型规则、流顺序、权限、生命周期合法性、引用、Digest 与签名策略。

## 4.2 规范文本编码 Profile

仅选择 JSON、YAML 或 Markdown 不能定义规范文本表示。版本化规范化 Profile 至少定义字符编码与 Unicode 规范化、换行、字段与集合排序、空白与转义、数值与时间表示、缺失/null/空值差异、正文处理、附件 Hash、扩展字段处理、Schema/Profile 版本绑定，以及自引用完整性字段的排除或规范化。
