# Agent 有工具权限，为什么还要为每一次执行重新核对？从 GitHub MCP 到任务证据链

我们给任务加了一道安全检查，本意很简单：如果一项工作还没有准备好，就别急着交给 Agent 开工。

**CodeFlowMu** 是我们在开发的一个本地运行的多 Agent 协作系统。

检查上线后，几张旧任务单却同时停住了。没有异常堆栈，没有模型胡说八道，也没有人把项目路径填错。它们只是被系统判定为“不该继续”。这类故障最难受，因为表面上看，安全措施正在正常工作。

排查后才发现，系统把一句“最好补一份验收说明”读成了“没有这份说明就禁止开工”。前者是给项目负责人的提醒；后者是运行时替负责人作出的决定。两句话只差一步，造成的结果却完全不同：一条建议把本来合法的历史任务卡死了。

这件事改变了我们对“工具权限”的理解。DEV Agent 会用 Git、会跑测试，当然不等于它可以不受约束地操作任意项目；但反过来，给它多加一道检查，也不等于系统就有资格把所有不完美的信息升级成禁令。

## 一道看似正确的门，为什么把人挡在外面

这次修复的目标，是让派工前能核对任务是否具备继续条件。问题不在“检查任务条件”本身，而在条件的性质。

有些条件是硬的。例如根任务已经关闭、目标不在当前项目范围内、需要人工批准的高风险操作尚未获准。对这些情况，运行时应该明确拒绝当前动作。

另一些信息只是提醒：计划还不够完整、某项验收建议值得补充、负责人应该再看一眼。它们能帮助 PM 做判断，却不该让系统自动停工。

旧任务里恰好混有第二类信息。门禁把它们全部当成第一类，于是“提示”变成了“禁止”。这不是模型的理解错误，而是我们把规则写错了。

> 安全门禁的职责是拦住没有资格发生的动作，不是把所有尚不理想的情况都判成不能发生。

## 不是一次全绿就算修好

第一组定向测试很快通过：派工与可完成性相关的 87 项检查全部通过。但这只说明我们问过的那 87 个问题有了答案，不能说明整条系统链已经恢复。

接下来发生的事情更有价值：

| 检查发生的顺序 | 结果 | 这一步真正确认了什么 |
| --- | ---: | --- |
| 定向派工检查 | 87 / 87 通过 | 目标门禁的已覆盖路径可用，尚不能代表全链路 |
| 首轮 Runtime 全量回归 | 失败 | advisory 仍被错误提升为硬门禁 |
| 修正后 Runtime 全量 | 1702 / 1702 通过 | 该回归集不再复现这类误拦 |
| 首轮 Shell 全量回归 | 失败 | 测试仍保留 3 条旧页面状态语义 |
| 修正后 Shell 全量 | 936 / 936 通过 | 测试断言已与新规则一致 |
| 首轮受控现场重启 | 失败 | API 与前端之间存在缺失的兼容字段 |
| 第二次受控重启 | 通过 | 前端展示与后端规范状态对齐 |

这不是一串用来装点文章的数字。它展示的是一次规则修复必须走过的三种检验：代码里的逻辑、测试对规则的理解、以及实际运行进程给页面的数据。第一层通过，后两层仍然可以错。

特别是最后一项。API 已经有了规范化状态，却没有输出页面仍在读取的兼容字段。页面因此把“我看不懂”显示成“任务冲突”。如果只停在 1702/1702，我们会把一个仍会误导使用者的问题当成已经解决。

## GitHub MCP 给了一个相似但更窄的答案

前半段的教训是：不要把建议当禁令。这个问题解决后，还有另一个更窄、但同样重要的问题：即使工具名字没变，系统是否也该根据这一次调用的参数，重新决定边界？

在这次修复之后，我们看到 [GitHub MCP Server 的 PR #3128](https://github.com/github/github-mcp-server/pull/3128) 已合并。它处理的是 OAuth，不是本地任务调度；它启发的正是后一件事——同一项工具能力，面对不同参数时，所需许可可能不同。

它举的例子是文件写入。普通仓库文件与工作流文件都由“写文件”工具处理，但改工作流文件会额外要求 `workflow` scope。工具名字没有变化，系统却在实际调用时检查目标，再决定需要什么授权。

CodeFlowMu 这次并没有实现 GitHub 的 OAuth 挑战机制，也不能把 GitHub 的设计当作我们的功能背书。我们得到的是一条更贴近任务协作的经验：派工时不能只问“这个角色原则上能做什么”，还要问“这张任务单、这个目标、这个版本，是否允许现在做”。

## 从误拦规则，再往前走一步

本文已经证实的，是“建议不能被误读成禁令”。如果要把这条原则延伸到生产环境中每一次会产生副作用的操作，还需要另一层更完整的执行回执：不只看规则文字，还记录这一次动作面向谁、作用到哪里、依据什么批准、结果怎样返回。下面五个问题是下一轮工程研究的设计目标，不是对 V1.9.6 已有能力的宣称。

如果 DEV 要把代码推送出去，静态能力表只能回答第一层问题：它有没有 Git 工具？真正开始执行前，系统至少还要能回答：

- 这次推送属于哪张任务单，还是 Agent 顺手做的？
- 它面对的是不是这张任务单绑定的项目和分支？
- 任务的当前版本有没有变，之前的批准是否已经过期？
- 这是一条明确的硬约束，还是一条应该交给 PM 判断的提醒？
- 同一次请求因网络重试到达时，会不会又产生一次副作用？

前面三项是在收紧行动范围；第四项避免运行时越权下结论；最后一项避免“重试”变成第二次操作。它们合起来，才接近一次可追溯的执行回执：谁在什么任务里，对什么目标做了什么，为什么允许，以及结果如何。

当前 V1.9.6 的证据并不证明这套回执已覆盖每一种工具调用。它只证明这一次派工门禁曾经误拦，并被用全量回归、Shell 回归和受控现场检查纠正。把任务、目标摘要、版本、重试去重和到期条件统一记录到每次副作用之前，仍是下一步工程工作。

## 结尾：先问“它凭什么拦住我”

对 Agent 加安全门禁时，最值得问的不是“规则够不够多”，而是：**这条规则凭什么有权阻止这一次动作？**

若它能指向关闭的任务、越界的目标、缺失的正式批准或明确依赖，拒绝有依据；若它只能说“计划看上去还不够好”，它应当提醒负责人，而不是让系统自行停工。

这次误拦没有证明 CodeFlowMu 已经解决了所有调用授权问题。但它把一件常被忽视的事变成了可验证的工程规则：能力是工具给的，克制是架构给的。

系统当然应该阻止越界、无权和危险的动作；可当它只看到“计划还不够理想”时，更可靠的做法不是替人关门，而是明确说出自己缺少什么判断依据，把决定交还给负责人。一条真正可靠的门禁，必须说清自己为什么在这一次把门关上，也必须知道什么时候不该替人把门关上。
