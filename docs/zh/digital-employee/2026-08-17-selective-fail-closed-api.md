# 前向兼容 API 也需要有选择地失败关闭

允许未知字段，通常是 API 前向兼容的实用选择：新客户端增加字段时，旧服务端不必立刻失败。但同一规则遇到已经退役的权限字段时，可能产生相反效果。服务端虽然成功解析了请求，调用者以为自己提交的授权约束却已被静默丢弃。

2026-08-17 的 Research Object 检查了一项已合并的 Codex App-server 变更。实现会在宽松反序列化之前，针对 `thread/start`、`thread/resume`、`thread/fork` 与 `turn/start` 四个方法显式拒绝已移除的 `permissionProfile`，并提示调用方改用命名 `permissions`。与此同时，无关未知字段仍被接受，有效的新权限表示仍能工作，重复提交旧字段也不会破坏连接。

这组一手代码与回归测试支持一个窄而重要的判断：**结构上的前向兼容，与授权语义上的兼容，不是同一个决定。**

## 同一个未知字段规则，可能产生两种相反风险

“所有未知字段都拒绝”可以让 Schema 更严格，却会让无害扩展难以上线；“所有未知字段都忽略”保留了扩展空间，却可能抹掉调用者认为仍然有效的安全意图。问题不在于宽松或严格哪个永远正确，而在于字段被忽略后，系统含义是否发生了实质变化。

对低风险展示元数据，静默忽略可能完全合理。对权限、执行环境或外部效果约束，旧字段的消失可能让请求从“按调用者指定边界执行”变成“按服务端默认边界执行”。即使服务端返回成功，兼容也只发生在语法层；调用者和服务端对实际授权状态的理解已经分叉。

因此，字段退役需要增加一个语义风险分类。一般未知字段继续走宽松路径；那些静默丢失会改变授权或执行预期的已知退役字段，则进入显式例外登记。

## 定向拒绝保留了一般兼容规则

所选实现没有把整个协议改成严格 Schema，也没有让一次无效请求演变成连接级失败。它在宽松解码前识别一个已知旧字段，只拒绝当前请求，并在错误中指出替代表示。

这条边界带来三项可操作价值。第一，调用者收到明确失败，而不是在错误安全假设下继续工作。第二，新旧表示之间的迁移入口可见，运维团队能够把失败关联到陈旧客户端。第三，无关扩展仍可前向兼容，安全例外不会扩大成“拒绝所有未来字段”。

兼容翻译仍可能是另一种选择，但前提是新旧字段的语义等价可以被证明。若旧字段只是名称变化，受控迁移层可能比立即拒绝更友好；若新表示改变了授权模型，静默翻译同样可能掩盖风险。失败关闭并非字段退役的默认答案，而是语义等价无法安全维持时的例外机制。

## 退役登记应描述语义，而不只是版本

一个可执行的退役登记至少应回答：哪些方法曾接受该字段；静默丢失会改变什么授权或执行预期；受支持的替代表示是什么；从哪个版本开始拒绝；客户端如何识别和修复；失败如何进入遥测而不记录敏感请求内容。

Resume、Fork 与 Turn 边界值得单独审查。持久任务可能把旧表示跨时间保存下来，客户端升级并不意味着所有已存状态已经迁移。若成功响应还能暴露实际采用的 Policy/Profile 版本，恢复任务就更容易证明自己究竟在什么授权表示下继续运行。这是架构建议，不是所选实现已经提供的能力。

## 证据没有证明端到端授权安全

当前证据只覆盖一个已合并实现、四个方法及其测试。它没有认证调用者或审批者，没有证明策略来源，也没有证明所有权限承载路径均采用同一检查。公开仓库中的维护者代码属于公开一手事实，但不是独立安全评估。

严格版本化协议也可能避免逐字段例外，前提是客户端与服务端能够同步升级。对低风险字段，静默忽略仍可能正确。这里支持的不是“安全字段永远拒绝”这样的宽泛口号，而是一条更窄的治理规则：当结构宽松会静默改变安全语义时，应把该退役字段从一般未知字段路径中单独识别出来。

仍待回答的问题是：什么证据足以把一个字段分类为“具有安全意义”；如何为陈旧客户端设置迁移期限；如何记录失败频率而不泄露内容；恢复任务能否核验实际生效的策略表示。前向兼容可以保持开放，但开放不应以悄悄丢失授权含义为代价。
