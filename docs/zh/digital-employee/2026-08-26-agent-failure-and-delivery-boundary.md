# 失败不能被绿勾覆盖：从 CrewAI 看 Agent 团队怎样保留技术失败与业务结论的边界

一条任务显示“完成”，可同一份最终报告刚刚又被提交了一遍。这个绿勾到底代表什么？是第二次完成？是第一次记录丢了？还是用户只是重复按了提交？

**CodeFlowMu** 是我们在开发的一个本地运行的多 Agent 协作系统。

文中把问题单称为 ISSUE，把“当前正在处理”称为 open（开放），把过去但仍保留的记录称为 history（历史）。这些名字不重要，重要的是它们不能被一枚绿勾混成同一件事。

如果系统答不出来，绿勾就不可信。更糟的是，有些系统会用一个漂亮的当前状态把问题藏起来：被打回的报告不见了、已替换的版本看不见了、六条历史 ISSUE 被删掉，或者为了不显得难看，连仍未解决的问题也一并关掉。

CodeFlowMu 的两次修复正好围绕这个问题展开。它们没有让页面“更绿”，而是先回答：什么是当前结论，什么是历史证据，什么只是同一事实的重复提交。

## 一份报告重复交回来，算几次完成？

最初，根任务的最终报告识别依赖隐藏字段或正文猜测。异步交接后再提交同一份报告，可能得到 HTTP 409（请求冲突）；而在更复杂的情况下，系统也可能把它当成另一份需要处理的新结论。

这两种结果都不理想。报错会把一次普通重试伪装成失败；再造一份结论则会让账本出现两个“完成”。

修复后，提交动作必须明确指出“哪张任务单的哪份报告”：`submit_task_review(task_id, report_id)`。如果同一份报告已经进入正确位置，再次提交只返回 `ok/no_change`——人话就是：我收到过了，账本不需要再添一笔。

而当 ADMIN 打回一份报告时，系统也不删除它。旧报告保留为被拒绝的历史提交，页面不再把它冒充为当前主报告。因为“被拒绝过”不是页面应该擦掉的污点，而是后来判断为什么重试、为什么改动的证据。

| 这次要防什么 | 系统怎样处理 | 为什么这样更可信 |
| --- | --- | --- |
| 同一份报告重复提交 | 返回 `ok/no_change` | 重试不制造第二个完成事实 |
| 最终报告被打回 | 保留为历史 | 当前页面不抹掉曾经发生的拒绝 |
| 异步交接后的状态变化 | 先完成正式状态移动，再处理重复提交 | 不让时序差异变成业务冲突 |

这部分的定向验证包括 Runtime 86 / 86、Panel 31 / 31，以及一次根任务重复提交 1 / 1。它们只能说明指定路径已被检查，不能说明每一种报告异常都已覆盖；但至少把“重复提交怎么办”从模型猜测变成了明确规则。

## 55/57：两条没有通过的检查在提醒什么

更难的问题出现在报告和 ISSUE 的页面收口。我们希望页面只显示当前应该让人行动的信息，同时保留历史。首轮定向检查是 55 / 57，不是通过。

失败原因很具体：两份已经被替换或判为无效的最终报告，被“主报告”规则抢到了当前位置。若只看页面上是否有一份主报告，这个错误几乎看不见；可它会让读者以为被替换的记录仍是现在应当相信的版本。

修复的关键不是再加一个颜色，而是调整记录优先级：当前报告必须从任务的现有状态推导，不能让一份历史记录因为名字更像“final”就抢占位置。改完后，同一集合达到 57 / 57；新增的语义检查 14 / 14，通过报告、ISSUE、Panel 与移动端的集成检查为 221 / 221。

这一串数字最重要的不是大，而是顺序：先有 55 / 57 的反证，才有 57 / 57 的修复。没有前者，后者只是一次漂亮的自报通过。

## 让历史留下来，但不要让它霸占今天

现场快照给出了一个比“全部通过”更有用的画面：报告页有 1 份当前主报告、4 份子报告、0 份被误当当前的 record，以及 12 份历史记录；ISSUE 里，6 条同根因旧记录仍被保留为 resolved（已解决），但 ISSUE-007 仍是 open（开放），菜单角标为 1。

| 页面上的数字 | 它表示什么 | 它不表示什么 |
| ---: | --- | --- |
| 1 主报告 + 4 子报告 | 当前任务链里可见的当前报告结构 | 只有这 5 次工作曾发生 |
| 12 条历史 | 仍可追溯、但不该冒充当前的记录 | 12 次失败或 12 个当前风险 |
| 6 条已解决 ISSUE | 同一根因的旧问题已结案，文件仍保留 | 可以删除原始问题 |
| 1 条开放 ISSUE、角标 1 | 仍有一个独立问题等待处理 | 系统已没有任何风险 |

这才是一枚绿勾应该有的边界：它可以告诉读者“现在这一步已经完成”，却不能替读者宣布“过去没有失败”“没有被打回”“没有其他问题仍在开放”。

## CrewAI 的提醒：别让机器内部的动作冒充用户做的事

[CrewAI #7079](https://github.com/crewAIInc/crewAI/pull/7079) 处理的是另一个场景：记忆检索、路由等框架内部 Flow，不应被当成调用者发起的业务动作。它解决的不是 CodeFlowMu 的报告投影，却和我们面对的是同一类错误——系统不能只看一个事件的表面名字，就替它决定应该进入哪一本账。

CrewAI 把内部 Flow 与用户真正发起的执行分开；CodeFlowMu 则把当前报告、历史报告、已解决 ISSUE 与仍开放 ISSUE 分开。两者都在防止一件事：一条记录被放错位置之后，看起来可能仍然“正常”，但团队据此作出的判断已经不可靠。

## 结尾：先问绿勾覆盖了什么

下次在 Agent 团队的页面上看到“完成”，不妨先问四句：这份报告绑定的是哪张任务？重复提交会怎样？被打回的版本还能找到吗？角标统计的是今天的待办，还是所有历史？

一枚绿勾不是审计结论，只是当前状态的一小块投影。可信的系统不是从不出现失败，而是失败、重试、替换和仍未解决的问题都各有位置，谁也不能被一个更漂亮的状态悄悄覆盖。
