# 目标已经换了，旧证据还能记功吗？

补丁已经部署，验证材料却来自部署前。这类错位不是日志真假问题：日志可能完全真实，只是没有检查现在的目标。研究者记录过这样的修复案例。我们据此检查一个更小、可以实际运行的问题：目标轮换后，旧证明还能否继续记功？实验揭示了两道具体检查，也给出了不能把记功通过当成修复完成的反例。读者可以据此拆开自己的验收记录。[来源：作者案例](https://arxiv.org/html/2610.19005v2#S5.SS3)

## 先分清作者案例和本次问题

CyberArena（攻防代理评测研究）的作者报告，在审计的 466 局游戏中，23% 出现未验证修复、21% 出现局部补丁、8% 出现过度阻断；类别可以重叠。这些分母是“包含某种模式的游戏”，不能改写成每次修复的失败概率。作者还记录过阻断合法业务的补丁。本文没有复现这些游戏或重新审计这些比例。[来源：第 5.3 节与表 3、4](https://arxiv.org/html/2610.19005v2#S5.SS3)

Octagon（提供目标管理与记功机制的攻防引擎）让我们检查更窄的问题：证明是否仍属于当前目标。它的内存目标存储会轮换目标、移除旧证明，并在记功时检查观察对象和当前轮次。公开代码是作者方一手材料；它不是独立第三方复现。[来源：固定版本目标存储](https://github.com/cyber-arena-ai/octagon/blob/3bb9eb1bef72a454ee455ad3cc321933133cd3eb/flag/store.py)

## 轮换前后，证明怎样失效

本次内部实验于 2026 年 10 月 20 日在 Windows（操作系统）11 与 Python（编程语言）3.13.13 下完成。分析阶段从固定提交提取原可执行函数体并使用真实上游类型，运行两组共 17 项受控检查：8 项覆盖证明提交与目标轮换，9 项覆盖写入标记和记功。生产阶段仅复核已绑定哈希的结果，没有重跑实验。受控输入是机制探针，不是模型生成的轨迹。

以下是记录中的有区分力的结果，而非成功率统计。返回值分别表示接受、重复、轮次过期和未知证明。

| 受控操作 | 实际观察 |
| --- | --- |
| 提交当前证明，再重复提交 | 先接受，后判为重复 |
| 使用错误轮次提交；轮换后再提交旧证明 | 前者判为轮次过期，后者判为未知 |
| 同一读取者提交新轮次的新证明 | 接受 |
| 查询旧轮次与当前轮次的目标 | 分别为 0 个、1 个 |
| 删除目标存储后再提交其旧证明 | 判为未知 |
| 同轮次重复签发写入标记；换轮次再签发 | 同轮次保持同一标记，换轮次得到新标记 |
| 把完整性令牌当作可提交证明 | 判为未知 |
| 观察写入标记后轮换，再为旧观察记功 | 判为轮次过期 |
| 为当前对象记功，再重复记功 | 先接受，后判为重复 |
| 轮换时复用旧目标身份 | 拒绝；当前记录保持不变 |

来源：本次内部实验的两组逐项结果，合计 17 项检查符合预期；原始记录尚未公开，访问受限。该表合并了成对操作以方便阅读，不代表 17 个独立部署或 17 次攻防。对应实现的整组目标替换会清理旧证明；写入记功还要求观察到的对象仍是当前存活记录。轮次匹配与对象身份检查承担不同责任。[来源：同一固定版本的轮换与记功函数](https://github.com/cyber-arena-ai/octagon/blob/3bb9eb1bef72a454ee455ad3cc321933133cd3eb/flag/store.py)

## 最容易越过的是调用者责任

还有一项关键探针：不执行远端观察，直接以当前对象调用记功接口，仍得到接受。接口名 `credit_claim`（为已观察的写入声明记功）对应的调用合同，把“确实观察到写入标记”留给调用者；函数本身检查的是当前对象与轮次。这个探针故意不满足调用者前置条件，暴露的是责任分配，不能据此声称真实生产路径存在可达的绕过漏洞。

因此，记录“记功被接受”可以支持内存中的记功状态发生了变化，却不能独自支持“远端确实写入”。进一步推到“部署的是预期补丁”或“合法用户仍能使用”还跨越了更多边界。这里的建议是分开保存观察、目标版本、部署归属和业务检查结果；本文没有实现新的回执系统。

这个区分也能帮助阅读其他恢复研究。ARIA（面向代理运行修复的研究）的附录描述重建上下文后的继续执行，其代码还区分补丁独有成功与材料实际落地。这与当前部署目标的证明新鲜度回答不同问题，不能合并成一个恢复成功率，也不能据此排名两个系统。[来源：重建继续执行附录](https://arxiv.org/html/2610.20780v1#A2)、[修复记录准入实现](https://github.com/LabRAI/ARIA/blob/ce68c040cca0796b37fa8ae46e2a87a073f64001/src/repair/v5_records.py)

## 还缺部署后的那一段证据

本次没有运行容器、远端标记植入、健康探针、补丁部署、正常业务回归或并发压力测试。串行地把观察放在轮换之前，能检查这一种交错，不能覆盖所有竞态；从原文件提取函数体也没有检验包导入和集成。对不轮换目标的静态任务，这种轮次规则未必是主要问题。

下一步值得验证的是一条贯穿链：观察者取得目标证据，记功层核对当前身份，部署层绑定实际补丁版本，业务测试层检查部署后的正常路径。每层都需要自己的结果和失败条件。现有实验只执行了其中的内存机制；远端观察怎样独立复核、部署指纹怎样绑定、业务回归由谁承担，仍是开放问题。
