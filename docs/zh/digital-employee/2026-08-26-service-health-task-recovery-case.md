# 服务在线，任务为什么仍交不出来？从 OpenHands 到一次真实的 Agent 团队恢复案例

两个 Agent 的任务停住了。控制台还在线，于是最自然的冲动是：再唤醒一次。

**CodeFlowMu** 是我们在开发的一个本地运行的多 Agent 协作系统。

这次不能这么做。任务还没有从“待领取”正确迁入“执行中”；如果直接重跑，下一位 Agent 可能拿到一份不完整的上下文，继续往下游写报告、开测试，最后得到一串看似正常的完成状态。真正的问题不是“怎么把 Agent 叫醒”，而是：谁有权修复这条路，修完后又凭什么确认可以重新派工？

这是 CodeFlowMu 在 2026 年 8 月 25 日保留下来的真实恢复案例。它最终没有被写成“PM 修好了一切”，因为记录里还留下了一个不该被绿色终态遮住的因果缺口。

## PM 拿到的不是万能修复权限

ADMIN 发出的正式指令，只允许 PM 做四件事：修复“任务还没从待领取迁入执行中就被唤醒”的链路；增加回归与证据验证；恢复或重派两项卡住的任务；在开发角色（DEV）和运维角色（OPS）交回真实终态报告前，不解锁测试角色（QA）。

这份授权的重要性在于它同时写清了不能做什么。PM 可以修技术路径、组织恢复、补测试；它不能绕过现有治理与证据要求，不能替业务角色宣布交付合格，也不能把一句“应该没问题”写成任务完成。

换句话说，轨道机的角色不是替团队工作，而是在团队已经被授权恢复时，帮它把“能否继续”变成可检查的条件。

## 恢复是怎样发生的

下表只保留理解这次恢复所需的几个节点。时间在这里不是装饰，它用来回答一个更严肃的问题：下游究竟是在什么证据之后被释放的？

| 北京时间 | 发生的事 | 说明 |
| --- | --- | --- |
| 14:35:22 | ADMIN 发出受限恢复授权 | PM 的修复权限有来源和范围 |
| 14:35:29 | 指令投递给 PM，续跑上下文创建成功 | PM 可以开始此次恢复 |
| 14:43:54 | OPS 任务恢复派工 | 第一项卡住工作重新进入处理 |
| 14:47:32 | DEV 任务恢复派工 | 第二项卡住工作重新进入处理 |
| 14:48:25 | QA 从待领取进入执行中 | 测试角色已被释放，尚不代表验收完成 |
| 14:48:42 | OPS 交回终态报告 | 第一份上游证据到达 |
| 14:49:37 | DEV 交回终态报告 | 第二份上游证据到达 |
| 15:30:36 | 修复提交完成 | 问题被转成可审查的代码变更 |

故事到这里并不圆满。QA 在 14:48:25 被释放，早于 OPS 和 DEV 两份终态报告。可正式授权要求，二者回执齐备前不解锁 QA。

这不允许我们仅凭时间戳断言“门禁已被绕过”：写入时间、事件时间和时钟来源仍需补证。但它同样不允许我们拿最终的三个 `done` 说“顺序已被证明正确”。现有记录只能支持一个诚实结论：**QA 被释放时依赖条件的因果依据没有被记录得足够清楚。**

这个缺口比一次漂亮的恢复更有价值。它指出下一步不该再加一盏健康绿灯，而应让每一次下游释放引用其已满足的上游事件和版本，而不是只留下几个物理时间。

## 修复后，系统具体多查了什么

后续修复没有让轨道机决定“任务是否业务成功”。它只把重新唤醒前的技术条件收紧：

- 任务必须先进入明确可执行的状态；
- 启动会话前，要核对本次执行轮次、执行权有效期和负责 Agent 是否仍匹配；
- 前置核对失败时，不启动会话，并把本次执行权结束掉；
- PM 的主动恢复申请按故障与动作摘要去重，避免同一故障反复触发恢复。

复验也分组保存，而不是给出一个笼统的“全绿”：任务状态检查 16 / 16、派工检查 46 / 46、文件状态回退 4 / 4、PM 路由 7 / 7、恢复技能路由 5 / 5，共 78 项断言通过，TypeScript 类型检查无错误。

它们说明这次修复的指定路径可被重放；不说明所有卡住任务都能自动恢复，更不说明当天 QA 的因果顺序已经自动补齐。

## OpenHands 让这个问题更容易看见

在整理这条记录时，我们读到 [Aaron Abu Usama 提交的 OpenHands PR #4548](https://github.com/OpenHands/software-agent-sdk/pull/4548)：健康接口仍返回 200，浏览器工具会话却卡住 8 小时 21 分。它的修复会取消剩余任务，并把关闭等待限制在默认 10 秒；维护者也明确说明这是尽力而为的保护，不保证所有资源已清完。

它不是 CodeFlowMu 的根因，也不能替我们的修复背书。但两起事故问的是同一句话：一个“在线”信号究竟说明什么？

OpenHands 将答案落在会话关闭与执行活性上；CodeFlowMu 的这次案例把它延伸到任务协作：服务能回答、会话仍在推进、任务合法可派工、交付可被验收，是四件不同的事。前一项成立，不能替后三项签字。

## 结尾：别把“还能回答”当成“可以继续干活”

恢复现场最容易犯的错，是把“服务还在”当成“团队可以继续”。这次案例给出的顺序恰好相反：先确认谁有权修、修复范围是什么、任务是否真正进入可执行状态，再谈重新唤醒；最后还要把下游释放与上游证据连起来。

真正可靠的恢复，不是让更多 Agent 立刻开始做事，而是让每一次继续都能回答：我为什么现在可以继续？
