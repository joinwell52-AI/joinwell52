# 服务在线，任务为什么仍交不出来？从 OpenHands 到一次真实的 Agent 团队恢复案例

一个浏览器工具会话的关闭流程卡住了 8 小时 21 分：`/health` 仍返回 200，元数据仍可读取；但会话已无法继续关闭或推进。继续把“服务在线”理解为“任务会继续交付”，会让调度器向一个无法推进的执行器继续派活。

这不是假设出来的紧张感。[OpenHands software-agent-sdk PR #4548](https://github.com/OpenHands/software-agent-sdk/pull/4548) 报告过一次浏览器工具会话关闭卡住 8 小时 21 分的生产故障：`/health` 与元数据仍返回 200，但会话事件请求已经无法打开。它只证明一个很小、却很关键的切片：**服务健康不等于会话活性。** 本文把这个切片与 CodeFlowMu 一次真实的“唤醒先于生命周期迁移”恢复记录放在一起，给出四项恢复检查：看服务、看活性、看任务状态、最后才看是否可验收。

读完后，你可以用这四项检查判断：面对一条“在线但不交付”的 Agent 任务，应该停止派工、恢复会话，还是把决定交回负责人。

## 一盏绿灯，回答不了四个问题

| 要核对的事实 | 它真正回答什么 | 常见误判 |
| --- | --- | --- |
| 服务健康 | 进程或 API 是否响应？ | 200 就等于工作完成 |
| 会话/作业活性 | 心跳、进度年龄、调用时限和取消结果是否正常？ | 有会话就等于在工作 |
| 任务生命周期 | 任务是否唯一、状态合法且允许派工？ | 页面显示进行中就能唤醒执行者 |
| 正式验收 | 执行报告和审查是否满足签发条件？ | 恢复成功就等于交付通过 |

四项不能互相代替。服务健康是入口检查；会话活性回答“现在还有没有在推进”；生命周期回答“是否允许继续动作”；验收才回答“这份结果能不能交付”。轨道机在这里是服务 Agent 团队的技术边界：它检查前置条件、停止不安全派工、留下诊断与恢复路径；它不替业务负责人宣布任务已经完成。

## 外部事故只照亮“活性”这一格

PR #4548 由 AaronAbuUsama 提交、neubig 于 2026-08-25 合并。它把 `AsyncExecutor.close()` 改为先取消剩余任务、最多等待 10 秒；超时后显式警告并放弃守护线程。讨论还说明，随后合并的单会话生命周期锁会把卡住关闭的影响限制在单个会话。

这些都是该 PR 所描述的修复范围。它并不证明任务状态迁移正确、报告已经齐全，或所有 OpenHands 故障都已消除；更不能证明 CodeFlowMu 有同一根因。把它放进本文，只是为了提醒：健康检查通过时，仍须单独询问“这条具体会话和作业还在推进吗？”

## 一次恢复，怎样逐项走过四个问题

CodeFlowMu 的受控私有证据包保存了 2026-08-25 的一次恢复。问题不是 OpenHands 的会话关闭故障，而是“在完成必要生命周期迁移前就唤醒执行者”的本地链路问题。有效治理指令授权 PM 只做四类动作：修复迁移、唤醒与执行报告门禁；增加回归和证据验证；恢复或重派两项卡住的下游任务；在 DEV、OPS 的真实终态回执出现前不解锁 QA。

把这条授权放回四项检查，读者就能看见它不是内部流水账：

| 恢复检查 | 本案已记录的做法 | 仍未被本案证明 |
| --- | --- | --- |
| 服务健康 | 本案没有把健康响应当作恢复或验收证据 | 当时所有组件的完整健康诊断 |
| 会话/作业活性 | 将“卡住”作为恢复或重派对象，而非直接写成业务失败 | 每一个会话的完整心跳和取消链 |
| 任务生命周期 | 先修复迁移与唤醒门禁，再允许后续派工 | 任意状态缺陷都已被消除 |
| 正式验收 | QA 解锁被合同化地依赖 DEV、OPS 终态回执 | 仅凭现有字段就能证明回执先后关系 |

案例保留了修复提交、脱敏重放夹具与回归结果：案例回归 3/3、既有治理路由回归 5/5、TypeScript 检查通过。这些第一方材料支持的结论很有限：该恢复链被记录，并在受测夹具中重放。它们不是“所有故障都能自愈”的证明，也不是独立验证。

## 设计反思：有状态，不等于有因果

本案留下的最重要发现不是全绿，而是一个应被修复的审计缺口。案例摘录里，QA 的 `released_at` 早于两份上游执行报告的 `submitted_at`；现有夹具只断言终态存在，并不证明它们的因果顺序。

这不能直接定性为门禁绕过：可能是时钟不同步，可能是写入时刻与逻辑事件时刻不同，也可能是摘录没有呈现完整字段语义。但它足以否定另一种过强表述——不能仅凭这些物理时间戳宣称“已经证明 QA 在上游回执之后才释放”。

下一步应让因果本身可检查：每次解锁引用满足它的前置报告或审查事件，并携带单调逻辑序号或版本前置条件。物理时间戳继续服务排障，却不再单独承担跨进程、跨设备的因果裁决。

## 我们的判断：轨道机负责恢复边界，不替团队交付

OpenHands 的事故把“健康”与“活性”拆开；我们的恢复案例再把活性、生命周期和验收拆开。我们的判断是，轨道机最有价值的角色不是替 Agent 团队决定项目是否完成，而是在故障时停止错误派工、保存诊断、限制恢复授权，并把下一步业务选择交还给 PM、ADMIN 或正式审查者。2026-08-25 的治理指令、修复与回归材料说明这套受限恢复曾被真实执行；QA 时间字段的因果缺口也说明，恢复记录仍需要逻辑事件关联，不能用一片“绿色”遮住尚未证明的顺序。

## 恢复前的六项检查

1. 任务在规范化路径上是否唯一，且处于允许执行的状态？
2. 当前执行轮次和有时限的执行权是否仍归属正确 Agent，过期或冲突是否已结算？
3. 会话、子进程和长作业的心跳、进度年龄与取消结果是什么？
4. 执行报告是否绑定正确的任务和版本，而非旧执行残留？
5. 每一项解锁是否引用了满足它的前置事件和逻辑序号，而非只比较物理时间戳？
6. 恢复授权是否只覆盖当前技术动作，并把后续业务放行保留给有权角色？

这不是再造一套重型控制系统，而是避免“在线但不可交付”时继续制造错误动作与错误证据的最低条件。

OpenHands 的案例也带来一个可讨论的后续问题：除进程级健康检查外，readiness（就绪性）是否应包含有界执行器年龄、卡住会话的执行权等生命周期进度信号？本文不替该项目回答，只把它作为恢复设计的检查方向。
