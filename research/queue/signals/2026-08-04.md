## Normalized candidates and decisions

### Q-20260804-11 — Condition-aware long-running Digital Employee monitoring

```yaml
candidate:
  id: Q-20260804-11
  normalized_question: How should a Digital Employee runtime represent waiting, external state change, condition evaluation, no-operation success, notification, and consequential action without wasteful polling or false completion?
  primary_object: official_research_article_open_source_benchmark_and_technical_report
  priority: P1
  status: Selected
  reason: The source package exposes a bounded runtime and evaluation problem directly relevant to condition-watch automations, Research Runtime Scheduler, CodeFlowMu operation nodes, completion verification, and cost-aware execution.
  next_action: Invoke Skill 03 — Deep Reading on the SentinelBench technical report, repository, lifecycle, active/passive and absolute/relative task taxonomy, no-op cases, evaluation database, and wait_for versus sleep baselines.
  publication_authorized: false
```

SentinelBench provides an official article, open-source benchmark, and technical report. The benchmark includes time-evolving environments, a four-state evaluation lifecycle, no-operation tasks, objective database evaluation, and explicit comparison of fixed sleeping with condition-aware waiting. Reported pass-rate and cost results remain source claims until Reading and Evidence & Citation validation.

### Q-W003-03 — Human authority lifecycle node

S-20260804-01 and S-20260804-04 add two different authority surfaces:

- Workspace Agents separate draft editing, publishing, schedule/API activation, role-based access, connection identity, write approvals, and connector action constraints.
- GitHub Actions may hold a potentially malicious workflow until a collaborator with write access approves it through an authenticated web session.

These signals strengthen the distinction between configuration authority, execution authority, write approval, authenticated release, and security enforcement. The object remains `Selected / P0`; Queue Stage does not advance it to Reading.

### Q-W003-02 and Q-W003-04 — Completion verification and comparative experiment

S-20260804-03 adds a primary research methodology for auditing benchmark tasks and validators. The OpenAI audit distinguishes failures caused by the system under test from failures caused by broken tasks, underspecified prompts, overly strict tests, low-coverage tests, and misleading instructions. It also uses agent-assisted investigation plus independent human review.

This evidence is registered for later Reading and Analysis. `Q-W003-02` remains `Selected / P0` because its ownership dependency is unresolved. `Q-W003-04` remains `Queue / P1` because its experiment contract depends on Q-W003-01 through Q-W003-03.

### Q-W003-08 — Full Digital Employee Studio

S-20260804-01 and S-20260804-02 add current product evidence for:

- reusable agent definitions;
- draft versus published versions;
- schedule and API-triggered execution;
- role and connection identity;
- job-bounded knowledge and system access;
- policy, approved actions, escalation, simulation, graders, post-launch signals, and controlled rollout.

The evidence is architecture-relevant but insufficient to promote the broad Studio object. Workspace Agent documentation describes a product surface, while Presence is a limited-availability managed product and does not expose enough independent evaluation detail. `Q-W003-08` remains `Queue / P3`.

### Q-W003-07 — Unrestricted computer-use runtime

S-20260804-06 adds direct evidence that evaluation infrastructure itself can become a consequential attack surface when agent capabilities, privileges, and containment are misconfigured. The signal does not justify unrestricted operation. It strengthens the existing requirement for a bounded application case, isolated credentials, explicit permissions, deterministic validation, and recovery controls. The object remains `Queue / P2`.
