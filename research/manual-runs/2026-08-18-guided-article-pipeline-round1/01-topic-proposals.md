# 第 1 门：三个栏目候选题

当前只选择题目和纲要；尚未写正文、制作图片或发布。

## A｜理论与治理深度

### 多 Agent 协作为什么需要一份所有人都能读懂的工作账本？

1. 一个任务分散在四个对话里时，人为什么很难回答“现在发生了什么”。
2. 共同工作账本必须记录的四类事实：任务、当前状态、执行回执和审查判断。
3. 文件、位置和事件怎样分别承载内容、当前状态与历史。
4. TASK、REPORT、ISSUE、REVIEW 怎样让协作行为具有明确身份。
5. 人、Agent 和界面为什么可以读取同一份事实。
6. 一次规格遗漏、实现错误、审查驳回和返工如何被完整保留。
7. 怎样判断自己的 Agent 系统是否已有一份合格的工作账本。

**文章结果：**一张工作账本结构图、一份最小字段清单和一套系统审查问题。

## B｜开源实现与协议工程

### 从 TASK 到 REVIEW：用文件状态机实现一条可检查的 Agent 协作链

1. 为什么聊天记录和内存变量不足以充当可检查的任务状态。
2. TASK、REPORT、ISSUE、REVIEW 的文件身份和职责。
3. inbox、active、review、done、archive 的合法迁移。
4. 每次迁移怎样追加时间、来源、去向、执行者和工具。
5. 生命周期 review 与治理 REVIEW 为什么必须区分。
6. 创建、认领、提交、驳回、完成和归档怎样用测试验证。
7. 输出最小实现、状态图、示例文件和自动化测试清单。

**文章结果：**一份能运行的最小状态机、一张状态图、四类文件示例和对应测试。

## C｜数字员工与场景落地

### 一人怎样带一支 AI 开发团队：从需求拆解到测试验收的完整工作流

1. 同时打开四个 Agent 窗口，为什么不等于拥有一支团队。
2. PM、DEV、OPS、QA 分别负责什么，不应互相代替什么。
3. PM 怎样把需求变成带范围、依赖和验收条件的正式任务。
4. DEV、OPS、QA 怎样围绕同一任务分别实现、运行和验证。
5. REPORT、REVIEW 和 EVAL 怎样检查“已经完成”的声明。
6. 真实返工案例：第一版为什么被驳回，下一张任务怎样变清楚。
7. PC、PWA 和磁盘工件怎样让一个人掌握团队状态。
8. 输出四角色责任表、任务模板、操作步骤和验收清单。

**文章结果：**一份可照做的一人 AI 开发团队运行手册和完整任务时间线。
