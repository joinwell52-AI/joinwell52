# 三篇 Article Brief

## 一｜多 Agent 治理为什么可以从文件开始？“万物皆文件”的工程价值

- 目标读者：正在把单 Agent 扩展为多人/多 Agent 协作系统的技术负责人。
- 痛点：状态散在对话、内存和日志里，人无法快速回答“谁在做什么、依据是什么、为什么返工”。
- 核心问题：文件何时是治理起点，而不是落后的临时方案？
- 唯一主张：文件的核心价值不是替代所有中间件，而是用最低门槛建立人和 Agent 可共同读取、检查、复制与恢复的工作账本。
- 原创价值：把 Unix 的统一接口、黑板模型的共享工作面和 FCoP 的文件/路径/事件三分法连接起来，同时明确文件并发和持久性边界。
- 文章类型：思想型 + 决策型。
- 章节逻辑：失控场景 → Unix/黑板启发 → 三层工作账本 → FCoP 案例 → 适用边界 → 最小字段与审查问题。
- 证据身份：Unix 原始论文、AI Magazine、Anthropic、FCoP 规范/ADR、dogfood。
- 边界：不写“最优解”“零通信”“无需中间件”；不讨论我们没有实现的 Redis/MQ 方案细节。
- 读后行动：为现有 Agent 系统建立最小工作账本，并用七个问题审查它。
- 与系列区别：解释“为什么从文件开始”，不展开状态机代码，也不写 Cursor 操作步骤。
- Brief 结论：PASS。

## 二｜文件、路径与事件：FCoP 协作状态机如何实现和测试

- 目标读者：实现本地 Agent runtime、MCP server 或协议工具的开源开发者。
- 痛点：聊天状态和内存枚举难以检查；直接写目标文件会暴露半写内容；状态与审查判断容易混淆。
- 核心问题：怎样把 FCoP 规范落成一条可验证的文件状态机？
- 唯一主张：实现 FCoP 的关键不是“监听目录”，而是同时守住文件身份、路径状态、事件证据和写入原子性四份契约。
- 原创价值：用最小算法、迁移表、测试断言和本轮 22 项测试结果将规范变成实现工件。
- 文章类型：机制型 + 实操型。
- 章节逻辑：为什么内存状态不够 → 四份契约 → 状态表 → 写入/迁移算法 → review 双义消歧 → 测试分层 → 平台边界。
- 证据身份：FCoP 规范/发布说明/代码/测试，POSIX 标准与 rationale。
- 示例需求：文件 front matter、伪代码、状态图（下一阶段再做正式图）。
- 边界：原子 rename 仅在明确文件系统语义下讨论；不声称锁、租约、无死锁、exactly-once。
- 读后行动：实现最小 lifecycle governor，并复用测试清单验证自己的适配器。
- 与系列区别：只讲协议机制和测试，不论证总体治理哲学，不写团队运营手册。
- Brief 结论：PASS。

## 三｜在 Cursor 里带一支 AI 开发团队：从需求拆解到测试验收

- 目标读者：希望用 Cursor 和本地工具完成真实代码交付的独立开发者、技术负责人。
- 痛点：多开 Agent 窗口制造并行错觉，却没有责任边界、共同状态、验收和返工机制。
- 核心问题：怎样把多个 Cursor Agent 组织成一条可验收的交付链？
- 唯一主张：本文不重复提出新的团队治理理论，而是把站内既有“声明者—验证者—接受者分离”结论投影成 Cursor 中可执行的交付步骤。
- 原创价值：把 Cursor 原生计划/工具/review/checkpoint 与 CodeFlowMu/FCoP 的 PM/DEV/OPS/QA、独立 EVAL 和工件层组合成一份可照做手册。
- 文章类型：教程型 + 场景型。
- 章节逻辑：失败场景 → 何时需要团队 → 四执行角色 + EVAL → 需求卡 → 派工/执行 → QA REPORT → PM 接收/返工 → EVAL 旁路 → 人工批准 → 一日运行表。
- 证据身份：Cursor 官方文档、Anthropic、CodeFlowMu-open、FCoP、dogfood。
- 示例需求：需求卡、TASK/REPORT/REVIEW 模板、角色责任表和验收清单。
- 边界：CodeFlowMu-open 当前只陈述公开版能力；checkpoint 不是 Git；小任务无需强行多 Agent。
- 读后行动：用一项真实小功能跑通一次需求—实现—测试—验收闭环。
- 与系列区别：专注既有治理结论在 Cursor 中的操作与交付结果，不解释 Unix 哲学，不展开状态机内部代码。
- Brief 结论：PASS。
