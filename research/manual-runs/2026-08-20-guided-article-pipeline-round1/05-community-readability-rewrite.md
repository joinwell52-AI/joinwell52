# 2026-08-22 三篇文章社区可读性重构记录

状态：`Revised / Independent Review PASS`

## 修改原因

三篇文章的代码、测试与事实边界已经通过独立复核，但不同 IT 子领域的专业读者仍需要跨过过高的术语门槛。用户要求提高跨专业可理解性，并在中文正文首次出现专业英文词时给出准确中文解释；科普化不等于删除技术细节或面向零基础读者。

## 通用修改原则

1. 第一屏先建立事故、核心判断和读者所得，不用测试数字打断叙事。
2. 每篇只使用一套稳定隐喻，隐喻用于建立心智，不替代技术事实。
3. 先解释工程作用，再出现英文术语、类名、字段名和错误码。
4. 中文采用“英文词（中文解释）”完成首次术语注册；英文稿使用自然英文，不机械加入中文括注。
5. 建议中的签名、租约、统一元数据注入、沙箱等能力必须按当前代码核验；未实现部分继续标为目标设计。
6. 版本不符、证据缺失和归属冲突使用中性工程裁决，不在没有证据时定性为欺诈。
7. 保留代码、测试、错误边界和一手来源；白话入口只负责帮助相邻专业读者建立正确心智。

## 三篇具体变化

### 技能与工具权限

- 增加办公室发布场景，将操作手册、执行工具、角色门禁、操作工作单与单次批准明确分开。
- 增加四层职责表，并明确 Tool（工具）不是权限，也不天然安全。
- 首次解释 Skill、Tool、Role Capability、Operation Policy、Approval、MCP、HTTP、RBAC 与 ABAC。

### 项目安全换根

- 增加“整支施工队换工地”的统一场景。
- 将七个项目根消费者改写为技术组件、白话角色和失败结果对照表。
- 用“先停旧影响、锁定新地址、统一发图、验证同根”概括主流程。
- 首次解释 Runtime、MCP Server、Watcher、`cwd`、FCoP、Symlink、Immutable Context、`EBUSY` 与 `EPERM`。

### 报告归属

- 增加“谁干的、拿什么证明、对谁负责”归因三问。
- 增加任务派发到独立接受的端到端责任链。
- 增加归因否决清单，并明确否决表示过期、冲突或证据不足，不自动意味着恶意欺诈。
- 保留当前三字段硬门与 44 项测试的真实边界；统一 Runtime 元数据注入和全工具证据采集仍标为目标合同。
