# 社区技术文章写作规则｜2026-08-19 三篇返工提炼

适用范围：Research Center 面向公开社区的技术文章。本文档记录本轮三篇文章为什么返工，以及后续写作必须遵守的表达门禁。它不修改 TMPA、FCoP、CodeFlowMu 的规范或工程合同。

## 一、为什么返工

第一轮正文的主要问题不是事实错误，而是**把内部架构说明书的写法带进了社区文章**：

- 技术判断严密，但第一屏不能让普通开发者迅速看懂文章价值；
- 英文缩写、规范编号和代码内部名先于现实问题出现；
- 自有项目名称缺少铺垫，读者容易误以为在读内部周报；
- 真实实验细节没有先升华为通用工程教训；
- “读取到文件末尾”“手机审批”“故障恢复”等能力边界容易被一句强表达推过证据范围。

因此，公开文章必须同时通过两种审查：**事实是否准确**，以及**普通技术读者是否愿意继续读**。前者通过不代表后者自动通过。

## 二、强制写作规则

### R1｜第一屏必须完成“10 秒价值说明”

文章前 200 字内回答：

1. 读者正在遭遇什么具体损失？
2. 本文给出的唯一核心判断是什么？
3. 读完能带走什么做法或工件？

禁止用项目背景、规范编号、版本说明或术语定义开篇。

### R2｜先写车祸现场，再写规则

抽象规则出现前，至少给出一个具体失败场景，并写清可观察后果。

- 弱写法：“重复事件可能影响幂等性。”
- 强写法：“文件通知来了两次，系统启动两个 Agent，同时修改同一份代码。”

场景必须是证据支持的风险或明确标注的故障注入目标，不能用“99% 都会失败”等无来源数字制造危机。

### R3｜中文叙事优先，稳定字段后置

正文主干先使用读者能直接理解的中文：

- Work Package → 独立施工单 / 任务包
- Gate → 人工审批卡点 / 红灯
- DAG → 先后依赖图
- Requirement Ledger → 需求台账
- Digest / SHA → 防伪指纹 / 校验码
- Stale → 旧批条作废
- EOF → 文件最后一行 / 读取范围末尾
- Attempt → 执行轮次 / 第几次尝试
- Lease → 锁定期 / 有时限的执行权
- Idempotency Key → 防重复流水号
- Fail-closed → 信息不确定时默认不放行
- Canonical object → 唯一权威记录

英文原字段只有在读者需要对照代码或规范时才出现，统一放在后置术语表、代码块或来源说明中。

### R4｜内部规范编号不得充当论点

禁止用“C03、C06、C14”作为公开文章的章节骨架。正文先给出放之四海而皆准的工程铁律，再在括号、脚注或来源中标注自有规范条款。

读者应先学会方法，再知道我们的规范怎样实现或验证它。

### R5｜自有项目必须先解释角色，再出现名称

首次出现 TMPA、FCoP、CodeFlowMu 时必须用一句大白话说明：

- TMPA：治理架构与研究基础；
- FCoP：协作文件和状态历史的通用规范，像图纸/公文标准；
- CodeFlowMu：运行 Agent、派工、检查和提供控制面的工程系统，像施工调度系统。

名称不得在开头突兀出现，也不得把 FCoP 写成调度器、模型运行时或手机产品。

### R6｜内部开发日志要升华成通用原则

错误码、内部类名、测试文件名和提交细节只在以下情况进入正文：

1. 它们是读者复现实验所必需；
2. 它们直接改变工程判断。

否则应留在证据记录，把正文改写成通用教训。例如：

- 开发日志：“实现返回新错误码，测试仍期待旧错误码。”
- 社区文章：“权限重构后，后端实现、用户提示和回归测试必须同时更新，否则控制面会展示不存在的能力。”

### R7｜事实、推断、建议必须使用不同语气

- **事实：**“本轮 9 项原子写入测试执行并通过。”
- **推断：**“这说明当前实现覆盖了有限重试分支。”
- **建议：**“还应补充突然断电和目录持久性测试。”

不得把“应当怎样设计”写成“当前系统已经具备”。不得把静态代码对照写成已经执行的测试结果。

### R8｜读取范围不等于理解证明

文件行数、校验码和读取到末尾只能证明读取记录覆盖了全文，不能证明模型理解、记住或正确使用了每条要求。

公开表述必须同时给出后续检查：需求台账、原文位置、覆盖矩阵与独立验收。

### R9｜界面入口不等于权限与执行成功

手机或电脑上的“批准”按钮只是一条请求入口。服务端仍须检查对象、当前版本、角色、理由和防重复流水号。

批准表示允许尝试下一步，不表示工作已经完成；请求超时应显示“结果未知”，不能由客户端猜成功。

### R10｜每个抽象机制必须配一个三秒例子

至少使用一种：

- 错误做法 / 正确做法对比；
- 故障前 / 故障后对比；
- 一条具体任务从输入到验收的贯穿例子；
- 可直接复制的清单、表格或最小伪指令。

例子不能冒充仓库现成 API；示意必须明确标注为示意。

### R11｜项目证据服务于通用结论，不主导叙事

正文顺序固定为：

```text
现实问题 → 通用判断 → 机制解释 → 自有规范/代码/实验验证 → 适用边界 → 可执行清单
```

禁止使用：

```text
项目名 → 版本号 → 内部类名 → 规范编号 → 读者最后才知道为什么重要
```

### R12｜社区表达与证据门禁必须同时达标

正文进入配图前必须同时满足：

- 社区技术文章独立评分至少 8.5/10；
- 内容评分至少 77/90；
- 证据至少 20/25；
- 10 秒价值、现实场景、术语解释、专有名词铺垫、通用行动清单全部通过。

技术严密但表达劝退，不能用高证据分抵消；语言流畅但事实越界，也不能进入配图。

### R13｜方法论文章必须画出端到端责任链

只解释单个机制，读者仍可能不知道整套方法如何落地。方法论文章必须明确列出每个阶段的输入、责任主体、输出和阻断条件，并用一个贯穿例子把“原始要求 → 任务 → 测试 → 证据 → 验收”串起来。

流程图只能表达已核验的现有步骤；建议中的理想流程、未来能力或伪接口必须标成示意，不能因为图画得完整就写成已经实现。

### R14｜协议能力与产品实现必须逐项分账

当文章同时介绍协议、运行时和产品时，必须单列职责矩阵，回答每一层“负责什么”和“不负责什么”。

- 协议工件不能被写成运行时调度能力；
- 项目内的规划结构不能被写成协议新增标准；
- 界面入口不能被写成服务端权限；
- 自动校验不能被写成人工授权；
- 执行报告不能被写成最终验收。

若建议稿中的名称、文件格式、API 或自动化步骤与当前规范和代码不一致，以可定位的规范、代码和测试为准，并在正文中删除或降级为目标设计。

### R15｜理论、协议、实现与验证不得互相代证

当文章同时引用理论模型、协议规范、产品实现和测试结果时，必须写清四层关系：

1. 理论层定义哪些可观察治理语义；
2. 协议层怎样把语义投影为具体工件与状态；
3. 实现层增加了哪些调度、会话、权限和恢复责任；
4. 验证层究竟执行了哪些测试，哪些仍是建议清单。

理论条款不能证明某个产品已经实现；协议符合不能证明运行时可靠；测试清单不能冒充测试结果；作者运行不能冒充独立验证。建议中的理论解释若与现行规范冲突，必须按规范收紧，而不是为了叙事完整保留强结论。

## 三、本轮三篇具体修改

### 文章一｜长需求变施工图

- 标题从“可执行任务图”改成“能落地的施工图”。
- 增加 10 秒看懂与漏读、混淆、多人抢写三个现实后果。
- 将 Requirement Ledger、WP、Gate、DAG、Digest、Stale、EOF 全部退出叙事主干。
- 用需求台账、独立施工单、先后依赖图、人工红灯、防伪指纹和旧批条作废贯穿全文。
- 将 FCoP / CodeFlowMu 后置为“图纸规范 / 工地调度系统”。
- 收紧“读完”与“手机已接入规划审批”的证据边界。
- 增加来源锁定、需求台账、工作包、校验审批、派工验收五步责任链，逐步写清输入、责任和输出。
- 明确需求台账、工作包和规划审批属于 CodeFlowMu 规划层，不是 FCoP 核心协议的新工件；FCoP 正式协作工件仍为 TASK、REPORT、ISSUE、REVIEW。
- 删除建议稿中未经实现核验的 `ledger.yaml`、自动派完全部工作包和模型品牌路由等表述；规划批准只开放匹配版本的 `WP-00`。

### 文章二｜运行时故障测试

- 开头改成半截文件、重复派单、测试未执行三种事故。
- 将规范编号改成六条通用防御铁律。
- 将 Attempt、Lease、Canonical ID 等改成执行轮次、锁定期和任务身份证。
- 把原子写入、重复/漏通知、派发崩溃、测试误报组织成四类故障。
- 保留 9/9、5/5、两个未执行和一个真实失败的证据纪律。
- 当前未覆盖的崩溃窗口明确写成补测目标，不冒充已验证能力。
- 标题改为直接面向读者风险的“全绿演示 / 故障注入 / Agent 调度系统”，删除未解释的“文件式运行时”。
- 增加 TMPA → FCoP → CodeFlowMu → 验证四层关系，说明身份、生命周期与验收分离、对象不可变、冲突保留和确定性恢复五个治理支点。
- 明确 TMPA 不要求生命周期有向无环，摘要不是不可伪造身份，CodeFlowMu 不是完全无状态；TMPA C01–C14 与本文 12 项故障清单不是同一测试套件。

### 文章三｜电脑执行与手机控制

- 第一屏改成“电脑干活、手机观察与决策”的一句话边界。
- 删除正文中的内部错误码对照，将其升华为权限实现、用户提示、回归测试三处必须一致。
- 增加危险审批 / 正确审批三秒对比。
- 将 Idempotency Key、Fail-closed、Canonical 等改成防重复流水号、默认不放行、唯一权威记录。
- 明确缓存旧页面可以读，旧版本决定不能执行。
- 保留局域网 5/5 的有限证据，不外推到公网、加密传输或端到端安全。
- 审批决定单明确标成目标协议示意，不冒充现成 API；绑定凭据说明区分长期哈希记录与 10 分钟进程内完成结果缓存。
- 弱网界面同时展示服务端观测时间与“距最后心跳 X 分钟”；服务端负责过期裁决，不能依赖手机墙上时钟。
- 设备吊销区分“已有代码路径”与“已通过安全测试”：当前实现可单独吊销或保留一台可信设备，但缓存、在途请求、重启和多端并发仍需故障验证。
- 10 分钟是绑定结果重放资格窗口；完成记录在后续访问时惰性清理，不得写成定时器准点删除。
- TMPA 的稳定主载体不得解释成“电脑硬盘是法定主体”；本地 PC 权威执行面是 CodeFlowMu 的部署选择。
- 任务 REVIEW 与高风险 Operation Approval 必须分开，手机入口不能把两者合成一个万能审批文件。

## 四、后续执行检查表

每篇正文提交独立编辑前，作者必须回答：

- 第一屏是否不看项目背景也能理解？
- 是否存在一个具体事故或损失？
- 英文缩写是否能删、能翻译、能后置？
- 自有项目是否先解释角色再出现名称？
- 代码内部细节是否已经升华为通用工程原则？
- 当前事实与目标设计是否分开？
- 是否有一个三秒例子和一个可直接使用的清单？
- 来源能否支持每个数字、能力和限制？
- 读者能否在读完后立刻改变一项工程做法？
