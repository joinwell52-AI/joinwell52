## 二、阻断项

### B1｜Article 3 英文把 10 分钟重放资格写成原 token 驻留上限

位置：`02-article-3-local-runtime-mobile-control.en.md` 第 56 行。

当前句子：

> `an in-process completion record temporarily retains the original session token for ten minutes`

当前固定提交的 `mobileBindStore.ts` 确实定义 `replayTtlMs = 10 * 60 * 1000`，但没有定时器或周期清扫。`completed` Map 只会在后续 `tryConfirm(bindId, token)` 再访问该 `bindId`、发现超时后才删除；若没有后续访问，原 token 可以继续驻留内存，直到再次访问或进程退出。

所以 10 分钟只证明“同一绑定请求仍可取回第一次结果的资格窗口”，不能证明“原 token 最长只保留十分钟”。中文已写准，英文尚未同步，形成证据边界分叉。

最小修正方向：明确 `The replay eligibility window is ten minutes`，并补一句记录是 later access 时 lazy removal，而非 timer-based deletion；不能把 plaintext residency 上限写成已证明的十分钟。

### B2｜Article 3 英文末段把目标审批协议重新写成当前 CodeFlowMu 行为

位置：同一英文稿第 153 行；同类语气也出现在第 89 行图注。

当前末段写成：

> `When a user taps Approve ... CodeFlowMu rechecks ... current revision, and prior use of the request key.`

前文第 73 行已经正确声明这是 `a safer target protocol` 和 `an architectural example`，不是当前公开 API；但第 153 行位于新的职责总结段，以现在时重新陈述后，普通读者会把它理解成已实现行为。

当前手机审批路由 `/approvals/:filename/*` 的请求体主要接收 `reason`/decision。治理审批路径在服务端为每次调用新建 `actionId` 并把它当作 `idempotencyKey`；它没有按正文示意接收客户端提供的“所见版本 + 防重复流水号”，也不能据此证明弱网重试会返回第一次结果。Operation Approval 的摘要绑定和一次性高风险尝试边界真实存在，但不能替代通用手机决定协议尚未具备的客户端幂等合同。

最小修正方向：第 153 行改为 `In the target design described here, the phone should send... and CodeFlowMu should recheck...`；第 89 行图注同步注明 `The target boundary requires...`。如果坚持写成当前能力，则必须补直接实现与运行测试证据，而不是引用目标设计。
