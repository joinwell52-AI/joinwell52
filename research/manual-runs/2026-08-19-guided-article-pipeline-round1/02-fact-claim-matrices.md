# 2026-08-19｜三篇文章事实—主张矩阵

标签：**事实**=来源直接支持；**推断**=Research Center 对多项事实的解释；**建议**=可执行工程做法，不伪装成已验证结果。

## T1｜两万字需求，怎样拆成 AI 团队能落地的施工图？

| ID | 类型 | 正文主张 | 证据 | 可支持范围 | 反证、边界或未决问题 |
|---|---|---|---|---|---|
| T1-F1 | 事实 | TMPA 把文本作为持久消息与状态载体，并要求稳定主载体、单对象单写者与确定性重建 | O1、O2 | 支持把计划当治理工件而非聊天摘要 | 不规定长任务规划的唯一算法 |
| T1-F2 | 事实 | Core 要求来源、身份、引用、依赖、无环、权限、生命周期、恢复和历史可由确定性 Reader 检查 | O2 C01–C14 | 支持计划需要机器可检的图与证据合同 | Schema valid 仍不代表事实真或商业判断正确 |
| T1-F3 | 事实 | CodeFlowMu 当前长任务合同要求完整读到 EOF、记录 digest/行数、建立 Requirement Ledger、覆盖 REQ→WP/Gate/Test/Evidence，并计算 DAG 与预算 | C1、C2 | 支持“编译链”作为本项目实现方法 | 不是行业标准；当前专项测试未在此环境完成重跑 |

| T1-F5 | 事实 | E2EDevBench 在 50 个 PyPI 项目上报告长链路软件开发仍有大量未实现需求；对抽样未实现项的分析中，规划是主要根因类别之一 | E1 | 支持“计划质量是实质风险” | 数据集、模型与工作流有限；不能推出本方法会达到某一提升幅度 |

## T2｜怎样测试一个文件式多 Agent 运行时？从状态铁律到故障注入

| ID | 类型 | 正文主张 | 证据 | 可支持范围 | 反证、边界或未决问题 |
|---|---|---|---|---|---|
| T2-F1 | 事实 | FCoP 定义文件工件、路径状态与事件历史；CodeFlowMu 才负责 Watcher、派发、模型会话和恢复 | O4、O5、C4 | 支持协议测试与 Runtime 测试分层 | 不能把 FCoP 描述成调度器 |
| T2-F2 | 事实 | Core C01–C14 给出身份、来源、权限、生命周期、冲突、恢复与历史等治理不变量；把这些基线与 CodeFlowMu 的观察、依赖、派发、会话和 lease 职责组合后，才能形成本文的 Runtime 测试坐标 | O2、C4 | 支持测试按不变量而非页面动作组织，并区分 Core 基线与产品职责 | “会话绑定派发意图”“忙 Agent 阻塞”等是 CodeFlowMu/本文层，不是 Core 单独规定；Core 也不等于完整性能/安全测试标准 |
| T2-F3 | 事实 | 当前原子写入专项测试 9/9 通过 | C3、C8 R1 | 仅支持当前提交、当前环境、该测试文件覆盖的分支 | 工作树非 clean；不证明掉电后目录项持久性、跨挂载点 rename、网络文件系统或 exactly-once |
| T2-F4 | 事实 | POSIX rename 提供有条件的原子名称替换语义 | E3 | 支持将 rename 作为提交点设计的一部分 | 不能写成“天然无死锁/并发安全”；Windows 与不同文件系统语义需单独验证 |
| T2-F5 | 事实 | FoundationDB 公布以确定性模拟、故障注入和可复现 seed 测试分布式系统的方法 | E4 | 支持故障注入和可重放测试方法的独立合理性 | 不能借其结果为本运行时背书 |
| T2-F6 | 事实 | 本轮两个专项入口因依赖缺失，领域测试体为 0 executed；PWA 边界测试 1 executed / 1 failed，首先暴露错误码契约漂移 | C4、C7、C8 R2/R3/R5 | 支持 PASS/FAIL/NOT RUN 必须分开，测试本身也是合同漂移探针 | PWA 失败尚不能定性为实现 bug；steps 差异为静态对照且未执行到第二断言；需维护者裁决新契约 |
| T2-I1 | 推断 | 运行时可靠性应围绕“不变量 × 故障点 × 可观察裁决”设计测试 | T2-F1–F6 | 本文的统一测试框架 | 不能替代压力、性能、长稳、渗透或生产故障演练 |
| T2-R1 | 建议 | 建立 12 个最小场景：身份冲突、双位置、半写入、rename 错误、重复事件、周期对账、忙 Agent、依赖阻塞、派发两阶段崩溃、报告重放、冲突历史、NOT RUN 处置 | O2、C3–C4、E3–E4 | 可作为工程起步清单 | 场景数量是本文建议，不是官方规范数字 |

## T3｜本地运行与手机控制面的双端设计

| ID | 类型 | 正文主张 | 证据 | 可支持范围 | 反证、边界或未决问题 |
|---|---|---|---|---|---|
| T3-F1 | 事实 | CodeFlowMu Open 是本地应用，公开产品线含 PC Panel、Mobile PWA、FCoP 工件和人工审批；当前 Agent 入口只对接 Cursor SDK | O1、C6、项目 README | 支持本文场景与产品边界 | 不支持把 roadmap 或私有能力写成当前公开能力 |
| T3-F2 | 事实 | Core 要求一个稳定主载体、事实与接受分离、角色权限和可重建历史 | O1、O2 | 支持手机控制面不应成为第二套事实源 | Core 不规定 PWA、Gateway 或具体 token 方案 |
| T3-F3 | 事实 | 当前绑定实现使用短期 token、TTL、pending 单次消费，并为同一 bind_id/token 的完成结果保留 10 分钟幂等重放窗口；长期设备记录只存会话 token 哈希，但进程内 completed map 在窗口内暂存首次原 token 以返回同一结果 | C6 | 支持描述当前有限机制及处理双请求的合同 | 代码审阅不是安全认证；不能概括成全系统只存摘要，短期原凭据重放需纳入威胁模型、日志脱敏与部署审计 |
| T3-F4 | 事实 | 当前 LAN 专项测试 5/5 通过 | C5、C8 R4 | 支持地址选择的有限实现事实 | 工作树非 clean；不等于移动端完整 E2E，也不覆盖公网、NAT、TLS、弱网和网关故障 |
| T3-F5 | 事实 | 当前 Open Edition 的 PWA 发布接口为只读，发布权限外置；对应测试 1 executed / 1 failed，首先暴露旧/新错误码漂移 | C7、C8 R5 | 支持不能让手机/开源壳层越过发布权限；也支持契约漂移必须可见 | 未决：新错误码是否已成为正式合同；steps 差异为静态对照，运行在错误码断言处已停止 |
| T3-F6 | 事实 | Web App Manifest 提供可安装外壳；Service Worker 负责事件/缓存但可被浏览器终止 | E5、E6 | 支持 PWA 适合作为控制面而非长任务执行面 | 不否定云端远程 Runtime；只是说明不能把 Service Worker 当可靠后台进程 |
| T3-F7 | 事实 | Local-first 研究强调本地数据所有权、离线可用与跨设备同步的价值 | E7 | 支持本地为权威数据面这一设计方向 | 不能证明我们的同步和冲突解决已达到论文愿景 |
| T3-I1 | 推断 | “执行面在 PC、控制面在手机”能减少双写和弱网下的事实分叉 | T3-F1–F7 | 本文原创系统判断 | 替代方案：真正云端 Runtime 可让手机直接操作云任务；适用于另一故障与信任模型 |
| T3-R1 | 建议 | 移动端只开放读取、带理由的批准/驳回、暂停/恢复请求等少数动作；每个写操作都需幂等键、当前版本和服务端裁决 | O2、C6 | 可形成权限与验收清单 | 具体动作集需按产品威胁模型缩减；不能仅依赖 Prompt 约束 |

## 统一禁写清单

- 不写“FCoP 会调度 Agent、启动模型、提供 PWA 或实现全局编排”。
- 不写“原子 rename 天然无死锁、天然并发安全或提供 exactly-once”。
- 不写“14/14 PASS 证明当前 HEAD、任意部署或第三方采用成功”。
- 不把当前依赖缺失写成产品 FAIL，也不把 PWA 错误码漂移掩盖为 PASS。
- 不把项目愿景、建议清单或 Research Center 推断写成已验证事实。
