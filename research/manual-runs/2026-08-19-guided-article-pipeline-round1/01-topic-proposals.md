今天三篇围绕同一个母主题展开：**CodeFlowMu 是工程轨道机，FCoP 是轨道上的协作协议。** 三篇分别回答工作怎样进入轨道、轨道怎样经受故障、人在离开电脑后怎样继续掌握轨道，题意和读者行动互不重复。

## 1｜两万字需求，怎样变成 Agent 团队能执行的任务图？

**写给谁：**要把长任务书、跨模块改造或长期研发计划交给 Agent 团队的技术负责人、架构师和 PM。

**文章要得到的结果：**不是再写一篇“先计划再编码”，而是交付一套能直接使用的长任务书编译方法。读者最终会拿到 Requirement Ledger 样例、REQ→WP→Gate→Test→Evidence 映射、WP/DAG 模板和开工前门禁清单。

**核心判断：**长任务规划不是摘要写作，而是一条受治理的编译链：完整摄入、需求台账、现场事实冻结、工作包 DAG、确定性校验，再由人只开放第一个执行边界。

**大纲：**

1. 一份两万字任务书为什么不能直接等同于一份可执行计划。
2. 第一件事不是摘要：从首字节读到 EOF，并冻结版本、SHA、行数和引用集合。
3. 把自然语言拆成 Requirement Ledger：必须、目标、现状、估算、假设和权限边界。
4. 先找冲突再排期：哪些矛盾可以规范化，哪些必须停下来让人决定。
5. 从 REQ 编译到 WP：需求、工作包、依赖、角色、Gate、测试、证据与恢复如何一一映射。
6. DAG、关键路径和预算怎样从工作包自底向上计算，而不是先拍一个总工期。
7. 为什么通过校验仍不能自动开工：正文摘要、验证摘要、修订号和人工决定必须一致。
8. CodeFlowMu 与 FCoP 的分工：协议保存协作事实，工程轨道负责规划、派发与门禁。
9. 可直接复制的 Requirement Ledger、WP 模板和开工前检查表。

**与近期文章的区别：**8 月 17 日的文章讨论“计划为何必须可审查”；本篇只讲超长任务书怎样被编译成任务图，以及怎样防止旧计划、旧批准和新正文错配。

## 2｜怎样测试一个文件式多 Agent 运行时？从状态不变量到故障注入

**写给谁：**正在开发 Agent Runtime、任务调度器、MCP 宿主或本地多 Agent 工具链的工程师。

**文章要得到的结果：**读者不只看到测试代码，而会得到协议层与 Runtime 层的不变量表、一个最小故障注入夹具、12 个必测场景，以及判断测试是否只覆盖 happy path 的审查清单。

**核心判断：**可靠性测试不能围绕页面动作组织，而要围绕不变量组织：一个任务身份、一个当前权威位置、有限次写入重试、幂等观察、受依赖约束的派发，以及可追踪的失败结果。

**大纲：**

1. 为什么跑通一次 TASK→REPORT 不能证明运行时可靠。
2. 先画边界：FCoP 规定协作语义，CodeFlowMu 宿主负责 Watcher、派发、会话、依赖和恢复。
3. 六个核心不变量：身份唯一、当前位置唯一、历史只增、派发可归因、依赖先满足、失败可重建。
4. 存储故障注入：临时文件、rename、fsync、Windows EPERM/ENOENT 和有限重试分别测什么。
5. 事件故障注入：重复 Watcher 事件与周期对账同时发生时，为什么不能重复派发或重复写历史。
6. 调度故障注入：未知来源、同一 Agent 忙碌、显式唤醒和业务依赖阻塞。
7. 崩溃与重放：写入成功但会话未启动、会话启动但回执未落盘时如何判断下一步。
8. 怎样建立测试金字塔：纯函数、存储契约、Runtime 集成、真实进程与 Windows 回归。
9. 12 个必测场景和一个可复现的故障注入夹具。

**与近期文章的区别：**昨日的 FCoP 状态机篇验证协议迁移与原子提交；本篇研究宿主 Runtime 在重复事件、依赖、会话、平台错误和崩溃交错下怎样测试。

## 3｜人离开电脑后，怎样继续掌握 AI 团队？本地运行与手机控制面的双端设计

**写给谁：**在本机运行长期 Agent 任务、但需要从手机查看进度和处理关键决定的独立开发者与小团队负责人。

**文章要得到的结果：**读者会得到一张本机执行面—手机控制面架构图、PWA 最小页面清单、设备绑定与权限边界表，以及弱网、重连、审批和隐私验收清单。

**核心判断：**移动端不应成为第二个 Runtime。本机拥有执行和持久事实，PWA 通过受绑定的控制面读取同一任务、报告和审批记录，只把少数人类动作代理回正式服务。

**大纲：**

1. 一个日常场景：Agent 在家中电脑上跑长任务，人已经离开电脑。
2. 先分清两层：本机 Runtime 拥有执行和持久事实，手机只提供观察与少量决策入口。
3. PWA 最少需要看什么：团队状态、任务线、报告、审批、动态、聊天和设备状态。
4. 为什么手机不能复制一份任务数据库：列表、详情、父子任务和报告必须来自同一事实源。
5. 设备怎样绑定：一次性入口、会话令牌、设备启停和最后在线时间。
6. 手机审批怎样不越权：必须说明理由、保持幂等，批准只表示允许尝试而不是执行成功。
7. LAN 与 Gateway 的两条路径：可达性、重连、状态展示和 Open Edition 的发布禁区。
8. 弱网、缓存和版本更新：什么时候展示旧数据，什么时候必须失败关闭。
9. 隐私与公开截图：二维码、绑定链接、令牌、聊天正文和真实任务数据为什么不能入库。
10. 可直接使用的双端架构表、绑定流程和 15 项验收清单。

**与近期文章的区别：**昨日的 Cursor 团队篇讲一项需求如何交付；本篇只研究人在离开 PC 后怎样通过受约束 PWA 继续观察和作出少量决定，重点是双端事实一致、绑定与权限。
