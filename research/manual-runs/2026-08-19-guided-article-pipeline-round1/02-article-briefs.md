## Brief 1｜两万字需求，怎样拆成 AI 团队能落地的施工图？

- **目标读者：**承担跨模块改造、长期研发计划或复杂任务书的技术负责人、架构师、PM。
- **读者痛点：**原始要求很长；摘要会漏掉硬要求；计划看似完整却无法逐项验收；批准后正文一改，旧批准仍被误用。
- **核心问题：**怎样把长篇自然语言需求编译成可追溯、可验证、可暂停并只开放第一个执行边界的任务图？
- **唯一主张：**长任务规划不是让 AI 写摘要，而是把原文编译成可追溯的需求台账、独立施工单、先后依赖图、测试证据和绑定当前版本的人类批准。
- **原创价值：**把 TMPA 的稳定载体、确定性 Reader、冲突保留与 CodeFlowMu 的长任务合同连接成一条可操作编译链。
- **文章类型：**机制型 + 实操型。
- **论证节点：**10 秒说明收益；真实车祸现场；完整读取与防伪指纹；需求台账六类条目；冲突分层；要求到施工单的映射；先后依赖与预算；检查和批准分离；FCoP/CodeFlowMu 的“图纸规范/调度系统”分工；中文术语表与最小清单。
- **证据身份：**O1/O2/O3 是已发布自有研究；C1/C2 是当前实现；E1/E2 是独立对照。
- **示例需求：**“为本地 Agent 团队增加手机审批，同时不得改变发布权限”贯穿全文，演示 REQ、WP、Gate、Test、Evidence。
- **图示需求（写作通过后再做）：**一张“需求文档→Ledger→任务图→Gate→WP-00”编译管线；一张小型 REQ/WP DAG。
- **边界：**小改动可直接执行；完整规划增加成本；规划质量仍受源要求质量、现场事实与模型能力限制。
- **读后行动：**复制 Ledger、WP 和 Planning Gate 检查表，把一份真实长任务书跑完一次。
- **与系列其他文章区别：**本文解决“工作怎样进入轨道”；不讨论运行时故障注入或手机控制面架构。
- **判定：**PASS。

## Brief 2｜别被“全绿演示”骗了：怎样用故障注入，测出一个真正靠谱的 AI Agent 调度系统？

- **目标读者：**Agent Runtime、调度器、MCP 宿主和本地多 Agent 工具链开发者。
- **读者痛点：**TASK→REPORT 跑通一次就被当作可靠；协议行为与 Runtime 行为混测；重复事件、崩溃与平台错误没有可重放夹具；依赖缺失也被误报为 PASS/FAIL。
- **核心问题：**怎样把基于文件协作的 Agent 调度系统从一条演示路径，转化为可重复的治理断言与故障注入测试？
- **唯一主张：**测试单位不是页面上的成功动作，而是“一条不能破坏的铁律 × 一个故障插入位置 × 一个可以检查的最终结果”；TMPA 提供治理语义，FCoP 将其投影为协作工件，CodeFlowMu 承担观察、派发、会话和恢复，三层必须分别验证。
- **原创价值：**讲清 TMPA、FCoP 与 CodeFlowMu 的实现关系，严格区分 TMPA C01–C14 一致性测试与本文 12 项运行故障清单，并使用本轮真实的 PASS/NOT RUN/合同漂移结果说明判定纪律。
- **文章类型：**硬核工程 + 测试方法。
- **论证节点：**半截文件、重复派单、测试未执行三个事故；六条防御铁律；TMPA 的身份、生命周期/验收分离、对象不可变、冲突保留和确定性恢复五个治理支点；FCoP 文件投影；CodeFlowMu 运行责任；磁盘提交、重复/漏通知、派发崩溃、测试误报四类故障；12 场景；当前重跑实录与限制。
- **证据身份：**O2/O4/O5 为规范；C3–C7 为代码与现行实验；E3/E4 为独立规范/工程对照。
- **代码需求：**给出 TypeScript 伪夹具接口 `inject(point, failure)`、可复现 seed、断言当前权威位置与事件历史；代码明确是示意而非仓库现成 API。
- **图示需求：**一张“协议层/Runtime 层 × 故障注入点”图；可选一张两阶段派发崩溃矩阵。
- **边界：**TMPA C01–C14 与本文 12 项不是同一测试套件；12 项是待执行的工程清单，不代表已经全部通过，也不替代性能、压力、长稳、安全或跨文件系统验证。
- **读后行动：**先写不变量表，再为每个不变量至少放入一个失败点和一个可观察裁决。
- **与系列其他文章区别：**本文解决“轨道怎样在故障下被证明”；不再重复 FCoP 生命周期基础教程。
- **判定：**返工稿待重新独立复核；旧版 PASS 不沿用。

## Brief 3｜人离开电脑后，怎样继续掌握 AI 团队？本地运行与手机控制面的双端设计

- **目标读者：**让 Agent 在本机长期运行、同时希望从手机观察进度和处理少量关键决定的独立开发者与小团队负责人。
- **读者痛点：**手机端复制任务库后产生双写；PWA 被误当作第二 Runtime；弱网展示旧状态却允许新审批；绑定链接和 token 容易泄露；开放版边界被宣传文案越过。
- **核心问题：**怎样在不复制执行权和事实源的前提下，让手机安全地观察并控制本机 Agent 团队？
- **唯一主张：**PC 是执行与持久事实的数据面；PWA 是受绑定、版本化、可撤销的控制面；每个移动写动作必须回到同一服务端事实和权限裁决。
- **原创价值：**把 TMPA 的稳定主载体/权限分离与 CodeFlowMu 的移动绑定、LAN/Gateway 实现连接起来，同时用现行测试漂移展示“边界必须能被测试”。
- **文章类型：**架构型 + 场景实操。
- **论证节点：**10 秒说明“电脑干活、手机控制”；地铁离桌与双写事故；同一事实源；短期绑定、有限重复请求与设备吊销；危险审批/正确审批三秒对比；局域网/中转路线；权限实现、用户提示、回归测试三处对齐；弱网、缓存、服务端时间与心跳间隔；TMPA/FCoP/CodeFlowMu/PWA 四层关系；任务 REVIEW 与高风险 Operation Approval 分离；双端验收清单。
- **证据身份：**O1/O2/O3 为研究与边界；C5–C7 为当前实现与测试；E5–E7 为 Web/PWA 与 local-first 独立资料。
- **示例场景：**PC 上 QA 提交失败报告，手机收到摘要；管理员查看同一任务 revision，填写理由后请求返工；服务端确认版本未变才写决定。
- **图示需求：**一张中心化双平面图（PC Runtime/事实在左，绑定 Gateway 在中，手机控制面在右）；一张移动写操作的版本化握手图。
- **边界：**不声称完整安全审计；当前 LAN 测试只覆盖地址选择，不证明公网、TLS 或端到端安全；10 分钟是绑定结果重放资格窗口，完成记录在后续访问时惰性清理；设备吊销已有代码路径但未由本轮完整安全测试证明；抗时钟漂移 UI 是下一轮验收目标；云端 Runtime 是不同有效方案。
- **读后行动：**按双端清单审查现有 PWA，删除第二事实源和无理由/无版本写操作，并补测时钟漂移、设备吊销与在途请求。
- **与系列其他文章区别：**本文解决“人离桌后怎样掌握轨道”；不讨论需求编译或 Runtime 测试体系全貌。
- **判定：**返工稿待用户确认与重新独立复核；旧版 PASS 不沿用。
