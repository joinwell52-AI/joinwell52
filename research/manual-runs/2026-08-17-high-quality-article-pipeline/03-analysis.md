# 分析：为什么评测分数需要两条执行链

## 可争论判断

一个 Agent 评测只有在 **Agent 运行链** 与 **evaluator 运行链** 都可检查时，才有资格进入发布准入。分数只是两条链的末端产物，不是证据链本身。

这不是四篇论文共同提出的标准，而是 Research Center 对独立证据的综合：

1. AgentLens 说明输出通过会掩盖 lucky pass，所以需要运行轨迹。
2. UnderSpecBench 说明“完成”会掩盖目标错误和过度影响，所以需要场景边界与副作用 Oracle。
3. EvalAgent 说明 evaluator 代码本身会无法执行或产生空洞结果，所以需要保存并测试 evaluator。
4. ScientistOne 说明分数、代码、文字结论和引用会彼此错位，所以需要 claim-to-artifact 绑定和后验审计。
5. OpenAI 的最新基准审计说明问题还可能位于任务、测试和参考解（gold patch），而不只在 Agent 输出。

## 两条执行链

### 链 A：Agent 运行链

`场景与边界 → 环境与版本 → Agent/模型身份 → 动作与工具调用 → 外部副作用 → 最终输出`

它回答：Agent 在什么条件下做了什么，是否改对对象，是否越过范围，最终结果如何产生。

### 链 B：Evaluator 运行链

`评测计划 → 测试数据/fixture → trace 或结果输入 → Oracle/rubric → evaluator 代码与依赖 → evaluator 运行 → 分数与判定 → 报告主张`

它回答：是谁、用什么规则、在什么版本上把运行解释成这个分数；评测是否真的执行，是否读取了正确对象，是否产生非空洞结果，报告是否忠实于代码和工件。

两条链共享 `scenario_id`、`run_id`、`artifact_hash` 和版本身份。任何一条链断开，分数都只能是一个待调查信号。

## 八类最小审阅面

| 工件 | 必须回答的问题 | 缺失时的典型误判 |
|---|---|---|
| 场景合同 | 成功、目标、禁止动作、容许替代和风险等级是什么？ | 改错对象或扩大范围仍记为成功 |
| 环境身份 | 代码、模型、harness、工具、数据和外部服务版本是什么？ | 分数无法比较或重跑 |
| trace 与副作用 | 实际发生了哪些动作和状态变化？ | lucky pass、盲重试与越界不可见 |
| Oracle / rubric | 哪些事实由确定性检查，哪些由语义判断？ | 把不完整测试当完整真相 |
| evaluator 与依赖 | 评分代码是否可执行，读取什么 schema？ | 计划—代码偏移、依赖漂移或空洞指标 |
| 原始结果 | 每个场景的输出、错误、退出状态和分项判定是什么？ | 只剩聚合分，无法定位失败 |
| claim links | 报告中的数字和结论指向哪个工件？ | 分数真实但叙述错误 |
| meta-evaluation 与局限 | evaluator 如何被测试，已知假阳性/假阴性和适用边界是什么？ | 把评测器的盲点当成 Agent 能力 |

这八类是最小“审阅面”，不是保证可靠的魔法清单。低风险、无副作用的任务可压缩实现；高风险、不可逆任务应增加人工裁决、权限与外部状态审计。

## 替代解释与反例

1. **“最终测试都通过了，为什么还看过程？”** 对纯函数、完备测试和无副作用环境，过程信号价值可能很低。但现实 Agent 常调用外部工具、修改共享状态，测试也不完备；应按风险决定是否检查过程，而不是一律保存全部思维文本。
2. **“过程评分会不会惩罚探索？”** 会。多次试验不必然不可靠，PTA 或固定权重也可能偏向常见路径。因此过程分只能触发审查，不能自动否决正确的新路径。
3. **“确定性 Oracle 最可信，是否应全部确定化？”** 不可能。副作用和数值可确定检查，语义质量往往需要 rubric、人审或 LLM judge。关键是把判断类型和不确定性显式标注。
4. **“完整包太贵。”** 成本是真实边界。可采用风险分层：本地低风险回归保存 manifest、结果和失败日志；共享状态或发布操作增加完整 trace、副作用和人工签字。
5. **“固定 seed 就可复现。”** 只能提高可比性。模型服务、并发、时间、网络和外部 API 仍会变化；应区分 `rerunnable`、`replayable` 和 `bitwise reproducible`。

## 工程准入建议

建议按以下顺序失败关闭：

1. 校验 manifest、版本、哈希与必需工件。
2. 在隔离环境执行 evaluator fixture，验证正常、异常和空输入都产生预期结果。
3. 重跑 evaluator，确认退出状态、分项结果和聚合逻辑非空洞。
4. 检查目标、禁止副作用和实际状态变化。
5. 将 pass/fail 与过程诊断并列展示，不用单一加权分覆盖。
6. 验证每个发布主张都有工件链接，并显式记录部分支持或未支持。
7. 对高风险或 evaluator 不确定案例升级人工审阅。

## 适用边界

- 本文不提出新的统计 benchmark，也不声称八类工件已经被实验验证为最优集合。
- 本文不要求保存模型的隐藏推理；需要的是可观察动作、工具输入输出、状态变化和必要决策记录。
- 本文不把过程质量当功能正确性的替代品。
- 本文不把 LLM judge 当确定性 Oracle。
- 本文不声称完整包能消除数据污染、未知攻击、测试缺口或审阅者错误。

## 待验证问题

1. 不同风险等级下，哪些工件的边际价值最高？
2. evaluator fixture 能否测量和持续监控假阳性/假阴性？
3. 如何在隐私与可审计性之间保存最小充分 trace？
4. claim-to-artifact schema 能否跨编码、运维、研究和客服 Agent 通用？
5. 谁来独立验证 evaluator，如何防止 evaluator 与被测 Agent 共享同一盲点？
