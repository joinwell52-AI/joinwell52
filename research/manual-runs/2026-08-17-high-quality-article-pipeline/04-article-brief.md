# Article Brief：一个分数之外的 Agent 评测包

## Brief 决定

状态：**PASS**
文章类型：机制驱动的工程分析（mechanism-led engineering analysis）
主题 ID：`TP-20260817-04`

## 标题方向

- 中文工作标题：**Agent 评测不能只交一个分数：把运行与评分变成可执行证据包**
- 英文工作标题：**An Agent Evaluation Should Ship More Than a Score**
- 英文副题方向：**Turn Runs and Graders into an Executable Evidence Package**

标题避免内部编号、日报/周报标签和论文名拼接；中文强调工程动作，英文以同一事实边界自然成文，不做字面对译。

## 读者

第一读者是正在把 Agent 接入 CI、发布门禁或高风险操作流程的平台工程师与评测负责人。第二读者是需要依据评测结果签字放行、但无法逐条重放 Agent 运行的技术负责人。

读者已经知道 benchmark、trace、grader 等基本概念，但可能仍把 eval 交付理解为一个 dashboard 分数或一份汇总报告。

## 具体问题

同一个 Agent 运行可能出现三种“表面通过”：最终测试通过但过程靠盲重试；任务完成但改错对象或扩大影响范围；分数可复验但报告描述了代码没有实现的方法。与此同时，evaluator 本身也可能没跑起来、读取错输入或产出空洞指标。

**可争论问题**：当评测结果要作为发布准入证据时，一个可执行评测包必须交付什么，才能区分可靠运行与碰巧通过？

## 核心命题

单一分数没有足够的证据密度承担发布准入。评测只有在两条执行链都可检查时才具备审阅价值：

1. Agent 运行链：场景、环境、动作、工具调用、副作用与结果。
2. Evaluator 运行链：评测计划、输入、Oracle/rubric、评分代码与依赖、执行状态、分项结果与报告主张。

Research Center 的综合建议是把两条链封装成八类可重跑、可审阅、可追溯的工件。这个包不会保证 Agent 可靠，但能把“为什么得到这个分数”变成可质疑、可定位的工程对象。

## 原创价值

文章不再重复“完成需要独立验收”，而是提供三个新的组合：

1. **两条执行链**：把 evaluator 的执行可靠性提升到与被测 Agent 同等地位。
2. **八类工件合同**：把四组独立研究中分散的失败面归纳成一个可落地的目录与 CI 审阅面。
3. **分层准入**：把确定性 Oracle、过程诊断、语义 rubric 和人工裁决分开，避免用一个总分掩盖判断类型。

这些是跨来源综合与工程建议，不伪装成某篇论文已经验证的标准。

## 论证节点

1. **具体开场**：用“假设发布面板显示 0.82 和 PASS”作为说明性示例，再追问 evaluator 是否运行、是否读对 trace、是否检查目标与副作用。
2. **先拆分失败面**：输出正确、过程可靠、动作边界正确、evaluator 可执行、报告忠实是五个不同问题。
3. **证据链一**：EvalAgent 的 Eval@1 表明 evaluator 自己是会失败的软件。
4. **证据链二**：AgentLens 的 lucky pass 说明结果通过不代表过程稳定。
5. **证据链三**：UnderSpecBench 说明任务完成不代表目标和范围正确。
6. **证据链四**：ScientistOne 与 OpenAI 审计说明分数、方法、引用、任务和测试都需要单独核对。
7. **机制综合**：两条执行链与八类工件。
8. **工程落地**：目录示例、CI 失败顺序、风险分层与审阅清单。
9. **反例与边界**：过程评分可能惩罚探索；Oracle 可能过窄；完整 trace 有成本和隐私风险；可重跑不等于位级复现。
10. **待验证问题**：工件的边际价值、evaluator 假阳性/假阴性、隐私最小化、跨域 claim schema 与独立验证责任。

## 事实口径

- 所有数字绑定具体样本、分母、模型/harness 或领域。
- `Eval@1` 不写成正确率。
- `10.7%` 不写成行业 lucky-pass 比例。
- `55.8%–67.8%` 始终注明 acted-run 分母，不写成全部运行比例或生产事故率。
- ScientistOne 数字不写成通用研究 Agent 结论。
- “两条链”和“八类工件”均标注为本文综合框架。

## 预期读者行动

读者应能在一次迭代内完成四件事：

1. 为现有 eval 目录增加 manifest 与稳定 ID。
2. 把 evaluator 和依赖纳入版本控制，并建立正常/异常/空输入 fixture。
3. 将最终分数拆成结果、过程、边界与报告对齐四类判定。
4. 在 CI 中拒绝缺工件、evaluator 未运行、结果空洞、越界或无证据链接的评测。

## 风险与应对

| 风险 | 应对 |
|---|---|
| 与既有“可验证完成”文章相似 | 全文围绕 evaluator 软件工件，不复述 claimant/verifier/acceptor 角色合同 |
| 论文均为 2026 年新作、尚无广泛复现 | 写清样本和局限，用来源收敛而非单篇论文作普遍证明 |
| 八类工件看似新标准 | 明确为 Research Center 工程综合，不声称已被实验验证为最优 |
| 正文变成清单堆砌 | 先用五类失败建立机制，再用表和目录把机制落地 |
| trace 泄露隐私或隐藏推理 | 只要求可观察动作、工具 I/O 和状态变化；提出脱敏、最小化与访问控制 |
| 过程评分替代正确性 | 明确只作补充诊断，并保留人工升级 |
