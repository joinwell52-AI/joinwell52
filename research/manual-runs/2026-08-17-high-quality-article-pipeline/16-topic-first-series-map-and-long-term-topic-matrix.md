# Topic-first 系列地图与长期选题库

记录日期：2026-08-18  
适用范围：本次一次性实时运行的后续选题组织，以及 Research Center 后续人工选题参考  
边界：本文件不修改 Daily Research Runtime、Scheduler、核心 schema、skill 或 prompt。

## 编辑策略修正

用户确认下列 8 个方向都具有长期研究价值。它们不再被视为一轮运行中相互竞争、必须大量淘汰的题目，而是 Research Center 的连续研究版图。

硬门槛只回答两个问题：

1. 这个方向是否已经具备**本轮写作条件**；
2. 如果具备，应当收窄成哪个可争论、可取证、可行动的单篇问题。

证据不足、与近 30 天内容靠得太近、缺少成熟案例或可复现实验时，状态使用 `Backlog`、`Needs Research` 或 `Hold`，不等于否定其长期价值。每次实时运行只选择当下最成熟、最值得现在写、且不与近期内容重复的 1–3 题；允许 0 题，不用产量换质量。

## 正式生产顺序

1. **选题**：从长期 Topic Matrix、站点定位、目标读者和已有栏目出发，先回答写给谁、解决什么真实问题、独特角度是什么、读完能做什么、为什么现在值得写。
2. **定向多源资料搜集**：仅围绕初选题搜集一手资料与相互独立的可靠来源，验证选题能否成立。
3. **选题硬门槛**：用证据强度、30 天去重、读者价值、可争论性、可行动性和时效性作 `Go / Merge / Hold / No Selection`。
4. **深读与事实矩阵**：记录事实、原文位置、支持与不支持范围、冲突、推断和未决问题；论文/PDF 完整阅读方法、结果与局限。
5. **Article Brief**：固定包含目标读者、痛点、核心问题、唯一主张、证据需求、章节逻辑、示例/代码/图示需求、边界、读后行动和与系列其他文章的区别。
6. **写作**：采用“具体问题/场景开场 → 核心判断 → 机制拆解 → 证据或示例 → 实践步骤 → 边界/反例 → 结论与下一步”的骨架，中英文分别自然成文。
7. **独立编辑复核**：fresh-context 编辑给出 `PASS / NEEDS REVISION / REJECT`；作者自评不能替代独立复核。
8. **解释性配图**：只为内容复核通过的文章制作，图必须映射核心机制并完成视觉 QA。
9. **发布**：只发布最终 PASS 的 Research Center 文章，完成构建、链接、布局、双语和公开页面验证。

## 系列地图

### 轨道 A：架构与治理哲学

服务技术负责人、架构师。递进关系是：**协调基础设施如何选 → 多主体组织如何管 → 概率系统如何被确定性边界约束**。

### 轨道 B：开源工程与协议实现

服务开源开发者与工具链工程师。递进关系是：**工具如何互联 → 运行时如何调度与可观测 → 工具库如何从代码走向可持续生态**。

### 轨道 C：落地场景与真实踩坑

服务技术管理者与业务架构师。递进关系是：**数字员工为什么在真实业务流中卡住 → 多模型运行成本如何计量、解释和治理**。

系列槽位是导航，不是配额。每篇必须有独立问题、独立承诺、独立证据和独立读者行动；不得把一个长稿机械拆段。完成单篇后检查术语统一、前后依赖、重复解释、交叉链接和推荐阅读顺序。系列索引不能代替文章质量。

## 长期 Topic Matrix

### A1. 轻量文件系统与 MQ/Redis 在多 Agent 协同中的取舍

- **目标受众**：正在选择多 Agent 协调基础设施的架构师与平台负责人。
- **真实问题/损失**：团队可能为低规模任务过早引入重型中间件，也可能把文件式协调用于超出一致性边界的场景，造成重复执行、状态漂移或恢复困难。
- **核心问题**：在什么规模、故障模型、一致性与跨机要求下，文件系统状态机是更简单的治理方案；什么时候必须升级到数据库、队列或工作流引擎？
- **可争论的唯一判断**：协调方案应由故障模型和可检查性要求决定，而不是由“轻量”或“企业级”标签决定；文件式状态机只在边界被明确验证时成立。
- **证据需求与当前强度**：需要文件系统原子操作语义、网络文件系统限制、队列/Redis/工作流引擎的一手文档，以及真实并发和故障注入实验。当前有本地实现与规范锚点，但独立对照实验不足，强度为**中低**。
- **文章类型**：思想型 + 机制型。
- **读后行动**：用一张采用/不采用决策表和最小故障验证清单评估自身场景。
- **重叠**：与 A2 的治理对象不同，与 C1 的上线故障有交叉但不以业务接管为中心；近 30 天需进一步检索文件协调相关文章。
- **为什么现在**：Agent 团队开始从单进程脚本走向长生命周期协作，协调基础设施选择开始影响恢复和审计成本。
- **状态**：`Needs Research`。保留题意，待独立对照来源与故障实验成熟后进入 Brief。

### A2. 从单 Agent 到“数字科室”的权限、生命周期、仲裁、熔断与降级

- **目标受众**：负责多 Agent 组织设计的技术负责人、企业架构师与治理负责人。
- **真实问题/损失**：单 Agent 的权限与失败边界被直接复制到多主体系统后，容易出现职责重叠、无人负责、越权调用和失败扩散。
- **核心问题**：把 Agent 组织成“数字科室”时，哪些控制面必须在扩大自治前建立？
- **可争论的唯一判断**：多 Agent 扩容首先是组织控制面问题，只有权限、生命周期、仲裁、熔断和降级形成可执行合同后，并行主体数量才有意义。
- **证据需求与当前强度**：需要多 Agent 权限模型、长运行任务治理、故障隔离和人工接管的一手资料与事故/实验案例。当前概念材料较多，能证明因果和收益的案例不足，强度为**中低**。
- **文章类型**：思想型 + 案例型。
- **读后行动**：为现有 Agent 团队绘制职责—权限—失败域矩阵，并定义升级与降级触发条件。
- **重叠**：与 A3 的确定性边界相邻，但本题聚焦组织治理；与 C1 相邻，但本题关注控制面设计而非接管业务流的具体阻碍。
- **为什么现在**：多 Agent 产品正从演示走向持续运行，治理缺口开始比单次模型能力更决定可用性。
- **状态**：`Backlog`。需先积累可核验的权限与故障隔离案例。

### A3. 确定性工程如何约束概率模型：Prompt、Schema、拦截器与治理层边界

- **目标受众**：Agent 平台架构师、可靠性工程师与评测负责人。
- **真实问题/损失**：团队常把 Prompt 当作权限、安全和数据完整性的替代品，导致软约束被误当成系统保证。
- **核心问题**：哪些行为可留给模型推理，哪些必须由 schema、校验器、拦截器、权限和治理层确定性执行？
- **可争论的唯一判断**：Prompt 适合表达意图和启发式偏好，不适合承担不可绕过的系统不变量；关键不变量必须下沉到可测试的确定性边界。
- **证据需求与当前强度**：需要结构化输出/工具调用规范、安全拦截器、权限边界、失败案例和可复现评测。当前一手规范较强，但需要避免与站内既有“执行环境/完成核验”文章重复，强度为**中高**。
- **文章类型**：思想型 + 机制型。
- **读后行动**：把现有 Agent 合同拆成“模型建议、程序校验、权限阻断、人工批准”四层，并为每个不变量指定测试。
- **重叠**：与近期配置优先级、执行权限和完成核验主题较近；必须收窄到“不可绕过不变量”的新证据对象和具体工件。
- **为什么现在**：结构化输出、工具调用和策略层能力快速成熟，团队有条件把软 Prompt 约束迁移为可执行边界。
- **状态**：`Hold`。长期价值高，但先等待与近 30 天文章拉开问题、证据和读者行动。

### B1. MCP 与 Cursor/本地开发环境的标准协作工具链

- **目标受众**：构建本地 AI 开发工具链的开源开发者、IDE 集成与平台工程师。
- **真实问题/损失**：工具接入依赖私有脚本、环境差异和隐式权限，导致同一 Agent 在不同开发环境中不可复现、不可迁移。
- **核心问题**：怎样把 MCP、编辑器、本地进程、凭据与项目上下文组合成可移植、可审查的最小工具链？
- **可争论的唯一判断**：协议兼容只解决“能连上”，可复现协作还需要明确的能力声明、权限边界、环境所有权和失败诊断合同。
- **证据需求与当前强度**：需要 MCP 正式规范、Cursor/本地环境官方文档、至少两个真实实现和从零复现实验。当前规范来源可得，但跨环境复现实验尚未固化，强度为**中**。
- **文章类型**：教程型 + 机制型。
- **读后行动**：按最小参考工程完成一次可复现接入，并用权限、环境、错误路径清单验收。
- **重叠**：与 B2 的运行时调度不同，本题只讨论工具接入边界；需避免退化成单产品配置说明。
- **为什么现在**：MCP 生态快速扩张，互操作承诺与真实工程可移植性之间的差距值得被具体测量。
- **状态**：`Needs Research`。先建立跨两个环境的可运行参考工件。

### B2. 开源多 Agent 运行时：调度、模型适配与跨端/PWA 监控

- **目标受众**：多 Agent 运行时、模型网关和可观测平台开发者。
- **真实问题/损失**：调度、模型适配和监控被拼成多个孤立组件，任务状态在服务端与跨端界面之间不一致，故障后难以判断应恢复、重试还是人工接管。
- **核心问题**：一个可运维的开源多 Agent 运行时，最小控制面和观测面应包含什么？
- **可争论的唯一判断**：跨端监控不是附属 UI；只有当调度状态、模型适配决策和恢复动作共享同一可验证状态模型时，PWA/前端观测才具有运维价值。
- **证据需求与当前强度**：需要真实代码、状态模型、调度测试、模型故障与网络中断注入、恢复记录和跨端一致性验证。当前缺少足够公开、可复现的端到端实验，强度为**低到中**。
- **文章类型**：机制型 + 案例型。
- **读后行动**：用最小控制面清单审查自有运行时，并执行三类故障注入。
- **重叠**：与 A2 的治理控制面相邻，但本题必须落实到代码与测试；与 C1 的业务阻碍不同，本题聚焦开源运行时内部机制。
- **为什么现在**：长运行 Agent 与多模型适配让“能看到聊天记录”不再等同于可运维。
- **状态**：`Needs Research`。没有真实代码和恢复数据前不进入 Brief。

### B3. 0 到 1 开源 Agent 工具库：发版、解耦、文档与跨生态集成

- **目标受众**：准备维护 Agent 开源项目的库作者与开发者关系工程师。
- **真实问题/损失**：很多工具库停在“代码可用”，却因版本合同、依赖耦合、文档缺口和生态适配不足而无法被稳定采用。
- **核心问题**：一个 Agent 工具库从仓库走向可持续公共依赖，需要哪些不可省略的发布与兼容工件？
- **可争论的唯一判断**：开源落地的最小单位不是一次发包，而是可验证的版本合同、低耦合核心、可运行文档和跨生态兼容矩阵。
- **证据需求与当前强度**：需要真实发版记录、包注册表状态、语义版本/供应链规范、安装遥测或用户 issue，以及至少一次跨生态集成。当前通用规范丰富，但独立新闻性与成熟案例不足，强度为**中低**。
- **文章类型**：教程型 + 案例型。
- **读后行动**：生成首发前清单、兼容矩阵和可运行示例，并对失败安装路径做验证。
- **重叠**：与 B1 的工具接入不同，本题覆盖整个开源生命周期；需避免写成 README 或发布公告。
- **为什么现在**：Agent 工具数量增加后，维护质量和生态兼容性比“又一个包”更稀缺。
- **状态**：`Backlog`。等待一个具备完整版本、issue 和跨生态证据的代表案例。

### C1. 数字员工接管业务流的关键阻碍：上下文漂移、速率限制、并发冲突与文件锁

- **目标受众**：准备让 Agent 接管真实流程的技术管理者、业务架构师与运维负责人。
- **真实问题/损失**：演示中能完成的任务，在长链路、多人并发、限流和外部系统抖动下出现丢状态、重复动作、等待失控或错误接管。
- **核心问题**：数字员工从“会做一次”到“可靠接班”，最先暴露的工程阻碍是什么，如何按损失与可恢复性排序？
- **可争论的唯一判断**：上线门槛不是平均成功率，而是团队能否识别并控制状态漂移、资源限额、并发所有权和恢复路径这四类系统性风险。
- **证据需求与当前强度**：需要真实故障/事故、限流与并发规范、长运行任务数据和复现脚本；不能用单个仓库 issue 泛化。当前论坛需求强，但独立量化案例仍需汇集，强度为**中**。
- **文章类型**：方案型 + 案例型。
- **读后行动**：执行上线前故障表和影子运行清单，为每种失败指定所有者、重试上限与人工接管条件。
- **重叠**：与 A2 的组织治理、B2 的运行时恢复相邻；本题以业务损失、上线决策和跨系统责任为中心。
- **为什么现在**：越来越多团队尝试把 Agent 从辅助工具推到业务流程执行者，长链路失败开始成为真实运营成本。
- **状态**：`Needs Research`。下一轮优先补充两类独立事故/实验与可量化损失。

### C2. 多模型混合编排与 API 成本治理

- **目标受众**：负责多模型路由、预算与采购解释的技术管理者、FinOps 与平台工程团队。
- **真实问题/损失**：团队把 token、估算成本、账单金额和内部分摊混成一个数字，模型路由看似省钱却无法解释最终费用或质量损失。
- **核心问题**：多模型编排中，怎样把使用量、模型选择、供应商定价、平台加价/补贴、账单与质量结果连接成可审计的决策链？
- **可争论的唯一判断**：成本治理必须先建立可解释的计量语义和证据链，再谈自动路由；token 统计不能充当账单，也不能单独证明某个路由策略更经济。
- **证据需求与当前强度**：当前已有 Cursor 官方计费资料、GitHub 计费实现、FOCUS 开放规范、OpenAI 价格/使用数据和论坛真实问题，强度为**高**；但“混合编排最优策略”仍缺少跨任务质量—成本实验。
- **文章类型**：生活化解释型 + 机制型。
- **读后行动**：建立 usage → estimate → billed → invoiced → adjusted 词典与 reconciliation 表，再决定路由优化指标。
- **重叠**：本轮《Token 不是账单》已经覆盖计量语义基础；未来若继续该方向，必须聚焦多模型编排的质量—成本实验，不得换标题重复基础文章。
- **为什么现在**：模型与套餐价格快速变化，平台账单和 API 使用数据并存，错误分母会直接误导路由与预算决策。
- **状态**：`Selected / Published foundation`。本轮先完成计量基础篇；“混合编排策略”子题转为 `Needs Research`。

## 本轮为什么先做两题

1. **《Token 不是账单》**：论坛中“为什么用量和账单对不上”具有直接、生活化的真实需求；官方计费资料、开源实现和独立开放规范形成了相互独立的证据链；能交付术语表和核对步骤。本题是 C2 的基础篇，不声称解决所有多模型路由优化问题。
2. **《别让 Agent 立刻写代码——也别盲信它的计划》**：工程读者需要的不是“先计划”口号，而是可审查计划合同；两项独立研究给出不同层面的数据和轨迹证据；能交付计划—执行—验证清单，且与近 30 天文章在问题、证据对象和读者行动上实质不同。
3. **第三篇 No Selection**：不是其他长期方向没有价值，而是本轮没有第三题同时达到独立证据、30 天新颖性、明确行动和 85/100 门槛。其余方向按上表进入长期库继续积累。

## Gemini 对话可借鉴与不可借鉴的边界

- **可借鉴**：先建立母主题和目标读者，再画系列地图；逐篇通过 Brief；完成后做系列一致性与导航检查。
- **不可作为证据**：Gemini 对话和其中生成的草稿只是未核验灵感池，不能支撑任何事实性陈述，也不能替代多源搜集、事实矩阵或独立复核。
- **不采用其具体题目配额**：本矩阵保留的是用户确认的 8 个长期方向，不把对话中的四篇 FCoP 草稿强塞进当前文章池。

## 状态使用约定

- `Selected`：当前轮次已满足硬门槛，可进入深读或后续阶段。
- `Needs Research`：题意保留，尚需特定来源、实验或案例。
- `Backlog`：长期有效，但当前时效性、材料成熟度或优先级不足。
- `Hold`：近期重叠或边界尚未拉开，等待窗口或重新收窄。
- `No Selection`：仅表示本轮不选，不等于永久淘汰长期方向。
