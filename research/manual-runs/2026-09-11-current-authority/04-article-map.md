# 两篇文章的论证地图

## 1. 结果已经有了，为什么 Agent 还会漏交？

开头矛盾：Runner 已给出 done，但缺失工具调用的结果仍没进下一次模型输入。读者先理解“做出结果”和“交给下一步”的区别。

机制链：混合同轮调用 → 本地产生错误 → 等待另一调用的批准 → 状态保存 → 恢复时误分类 → 输出丢失。主证据是本机执行的十个上游回归与单函数消融；历史由 PR 提供，原因由原 helper/tracker 提供。自有观察与上游历史分开。

边界：测到 ScriptedModel 输入，不是云端消费确认。外部比较只用 Paperclip 事务之外的交付问题，明确层级不同。读者行动是检查 call/result 配对与暂停前后输入，不能仅看最终文案。题图选“被漏交的结果文件补回对应调用位置”，文中图精确呈现修复/消融的交付差异。

## 2. 昨天能用的模型，今天为什么不能直接恢复？

开头来自保存偏好的日常直觉，再呈现目录变化。主线是八组输入的差别，不把“全拒绝”当成保守的唯一答案。

机制链：旧偏好 → 当前目录 → 明确否定则阻止写入；目录未知则保留兼容路径；恢复与交互修改用同一守卫但错误呈现不同。原函数前后对照、setModel 调用记录和 skipped 状态组成证据。

外部比较：MCP 卡片发现与动态能力分离；点出发现能力、账号资格、实际采用是不同问题。读者行动是为恢复入口写三态合同。题图为当前模型目录保留可用条目、旧偏好退出选中位置；文中图以三种证据状态解释拒绝与兼容。

## 不强行成篇的第三条线

Superset 的本地验签检查支持一份清晰研究结论，但没有实测移动端与 Vercel 生命周期。先保留开发评审和跟踪条件，不以九项密码函数断言扩写“云端工作站完整评测”。
