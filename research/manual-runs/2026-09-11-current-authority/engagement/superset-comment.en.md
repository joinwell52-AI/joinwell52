@saddlepaddle Your separation of workspace access from sandbox wake/readiness inspired a small local experiment on the access-token boundary. Using the original signing/verifying functions at `4ec6c8e`, ephemeral Ed25519 keys, and a controlled clock, we observed rejection for a different workspace, expiry, a wrong key, and a tampered audience; a second verification for the same workspace/key within the lifetime still passed.

That last check was only another verifier call, not a sandbox restart: we did not exercise the cloud, HTTP middleware, or process lifecycle. It helped us distinguish a valid workspace credential from evidence that a particular execution instance is ready. For a follow-up stop/reopen experiment, should we expect an unexpired token to remain valid across the new process while readiness is established separately, or is there a lifecycle boundary elsewhere that should invalidate it? We are asking about the intended continuity contract, not treating the absence of a process-generation input as a defect.
