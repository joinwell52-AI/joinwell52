## 1. 写了“始终审批”，AI 为什么还是执行了？

- 骨架：外部问题 → 输入反例 → 修复边界 → 回调追问。
- 对象：OpenAI Agents Python Realtime 工具审批。来源 DeepanshuPal，PR #5029。
- 开场：人看见字符串 always 以为更严格，程序却忽略非法类型。
- 核心：声明的意思与运行时可接受的类型是两回事。配置错误应在工具执行前可见。
- 机制：needs_approval 输入 → 单一审批方法 → 真实工具调用入口 → 本地记录动作。
- 证据：完整候选源码入口；只替换前身单一方法的消融；10 输入各两模式；31 项原审批测试。无生产事故频率数据，不补造。
- 反例：返回 None 的回调仍被转成 False；不能宣称修复保证所有错误配置都安全。
- 读者行动：检查拒绝、允许、等待和非法输入四条路径，专业追问回调返回类型的约束位置。
- 项目关系：我们开发协作系统所以关注授权边界；不宣称 CodeFlowMu 使用该路径或存在该问题。

## 2. AI 报错了，为什么数据库反而多写了一条？

- 骨架：实验反常数字 → CrewAI 嵌套重试 → Orca 对未知的保留 → 工程取舍。
- 开场：一次尝试、已提交后抛错，SQLite 得到两行。
- 来源：Ritiky23 / CrewAI #7458；brennanb2025 / Orca #20723。
- 核心：报错与未发生效果不能互相替代。减少重复调用与提供业务幂等是不同能力。
- 证据：原四个 ToolUsage 方法，周边依赖替身，真实 SQLite 提交；16 条观察。Orca 完整两个生产模块及真实导入，20 条合成输入观察；没有真实重发。
- 反例：CrewAI 候选三次尝试仍三行；Orca 未知可能阻塞后续操作，不能证明自动恢复可用性。
- 图：提交与响应之间的断点；候选 6→3 不是 6→1。
- 读者行动：超时后询问已有结果；专业追问稳定业务身份和持久回执；普通读者反馈重复提交经历。

## 3. 只是按了暂停，任务为什么被判出故障？

- 骨架：暂停/故障两个用户预期 → 原因被压成布尔值 → 时间变化反例 → 取舍。
- 来源：MrBlackTongue / Paperclip #13443。上游批量事故仅属作者报告。
- 核心：阻止启动的具体原因必须随这次观察传递，不能由稍后的状态反推。
- 证据：原 getInvocationBlock、预算阻塞分支和候选暂停预检；脚本化行与升级记录器；7 场景×两版本。不是 PostgreSQL 集成或完整恢复复现。
- 反例：读取阻塞后立即恢复，仍应保留当次 pause 原因；活跃公司的预算不足仍升级；预算引起的整公司暂停仍走暂停预检。
- 图：暂停发生在预检之后，原因跟随观察跨过恢复时刻。
- 读者行动：从“不能继续”追问“为什么不能”；专业追问观察绑定与下一轮恢复；普通读者反馈暂停后恢复预期。
