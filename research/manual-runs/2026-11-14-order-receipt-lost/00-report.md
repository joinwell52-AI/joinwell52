# 订单已提交但回执丢失：公开实验记录

日期：2026-11-14。实验由独立子进程和临时 SQLite 数据库组成；业务系统、订单和进程中断点均为本地研究夹具，**不是** CodeFlowMu 或第三方真实订单服务，也不是线上事故。

## 来源与研究问题

[Paperclip #21522](https://github.com/paperclipai/paperclip/pull/21522) 描述了服务端已提交修改、客户端超时后 unknown 回执长期阻挡后续动作的真实工程问题。其修复用自身服务端的最终记录结算能够证明的结果。本实验追问：如果数字员工操作的是另一个业务系统，客户端没收到回执，何时可重试，何时只能核查？

CodeFlowMu 是我们开发的本地多 Agent 协作系统，FCoP 保存正式任务和报告。本实验不把 Paperclip 的数据库方案移植到 CodeFlowMu；外部订单结果与 FCoP 工作事实的关系是待验证的问题。

## 方法

在同一操作意图下分别于三处强制退出子进程：提交前、提交后但响应前、响应后但本地回执前。恢复程序读取模拟业务系统的订单表，只有看到该操作键不存在才再次提交；看到订单已存在则直接结算。夹具使用 SQLite 唯一索引实现该操作键的原子去重。负对照取消操作键，并在响应丢失后盲重试。

执行：`python probe_order.py`。脚本只需 Python 标准库。每次在新临时目录运行，结束即删除数据库。实验脚本：[probe_order.py](probe_order.py)。

| 断点 | 子进程退出码 | 恢复前真实订单 | 客户端回执 | 恢复决定 | 恢复后订单 |
| --- | ---: | ---: | --- | --- | ---: |
| 提交前 | 72 | 0 | 无 | 权威查询确认缺失后重试 | 1 |
| 提交后、响应前 | 73 | 1 | 无 | 据业务记录结算 | 1 |
| 响应后、本地回执前 | 74 | 1 | 无 | 据业务记录结算 | 1 |

无操作键、无结果查询的盲重试对照：第一次退出 73，第二次退出 0，最终 **2 笔订单**。本例的 `0` 条客户端回执在前两种状态下完全相同，却对应不同的业务结果。

## CodeFlowMu 对照与限制

本轮只读核对 V3.0.152 源码提交 `0d2d4e742ef2f3cb48e3ce09cc47f0c03053dc5f`。`source_call_effect.py` 在原调用证据不足时保持 `unknown/auto_retry=False`，`source_task_session_recovery.py` 拒绝效果未知的显式恢复，`source_runtime.py` 对未知写效果不自动重放。18 项恢复、审批绑定与 PM 审查作用域测试通过；另 9 项调用效果测试因非管理员 Windows 进程在测试目录保护初始化处报 `SOURCE_BOOTSTRAP_ADMIN_REQUIRED`，没有执行到断言。产品源码与测试材料在本地受限工作区，公众可以独立复跑本页订单夹具和核查上游 PR，但不能仅凭本页独立复核产品内部测试。上述路径仅覆盖当前源码与有界测试，不证明任意外部业务 API 的提交结果都可自动结算，也没有确认新产品缺陷。

本实验没有运行真实网络、并发提交、真实业务服务、FCoP Core 端到端任务或双 Host。若下游既无幂等键，也无权威结果查询，实验支持的决定是**保留未知并转人工核查**，不能从本地回执缺失推出“未执行”。

## 复核清单

1. 运行脚本，确认三处退出码为 `72/73/74`，恢复前订单数为 `0/1/1`，恢复后均为 `1`。
2. 确认无操作键的盲重试对照为 `2` 笔，不把它归因于模型行为。
3. 将“客户端回执”“下游最终记录”“FCoP 正式任务事实”分别核验，不互相代证。
