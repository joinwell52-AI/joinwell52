# “运行中”是一项证据声明，不是调度事件

一个会话已经被调度，不等于执行它的进程已经存在；进程已经创建，也不等于它完成初始化、建立连接并能够接受所有工作。只要下游界面或自动化会依据状态采取行动，这些差别就不能被一个“运行中”标签抹平。

Anthropic 在 Claude Code 2.1.247 的官方发布说明中记录了一项修复：受影响的自托管运行器会话曾在 Claude Code 尚未启动时就报告“运行中”，桌面端因此可能过早提示 Claude 正在等待用户输入。这个现象把抽象的状态建模问题变成了可观察故障——控制面只有调度意图，消费者却把它理解成可执行事实。

可辩护的结论是：**对外可见的“运行中”状态，必须由足以支撑消费者所依赖语义的执行就绪证据来决定。调度、分配和工作器认领必须与就绪保持可区分；而本次披露的进程启动边界，也不能被扩大解释成完整健康证明。**

## 状态一旦触发行为，就成为接口合同

如果一个标签只供内部排队使用，把“已分配”叫作“运行中”或许只是命名选择。但当桌面端据此发出通知、监控系统计算耗时、后续智能体开始等待结果，状态就已经成为跨组件合同。它不仅描述控制面发生了什么，还承诺消费者现在可以安全推断什么。

本案例中的问题不是文字不够准确，而是证据强度与外部承诺错位。发布说明能直接支持三个事实：相关版本已经发布；此前存在进程启动前报告“运行中”的路径；修复阻止了这类报告早于进程启动。至于修复究竟等待进程创建、进程间通信、协议握手、首次心跳还是其他信号，公开材料没有说明。

因此，运行体不能用自己最容易获得的事件定义状态，而应以消费者真正依赖的最小事实定义状态。内部“已安排”可以很早出现，面向用户的“可执行”则需要更强证据。

## 把容易混淆的事实拆成证据阶梯

一条更诚实的生命周期至少应区分：

1. 已调度：任务进入计划，但尚未指定实际执行者。
2. 已认领：某个工作器取得执行机会，但执行进程未必启动。
3. 启动中：进程或执行底座正在建立，仍可能初始化失败。
4. 运行中：已经越过该消费者所要求的就绪门槛。
5. 终态：成功、失败、阻塞或跳过已有持久证据。

这不是要求所有产品采用相同名称，而是要求每个名称绑定可检查的证据。工作器认领能够证明责任归属，却不能证明进程已准备好；进程启动能够证明时间顺序，却不能证明依赖加载、认证、网络连接或特定能力已经可用。

更丰富的状态也能改善诊断。任务停在“已认领”，说明问题可能位于工作器启动；停在“启动中”，则应检查初始化或握手。如果所有阶段都投影成“运行中”，运营侧只能看到一个长时间不变的标签，既无法判断真实进度，也无法解释错误通知为什么发生。

## 从消费者承诺反推就绪门槛

就绪不是一个脱离场景的全局布尔值。命令行界面可能只需要进程能够接收输入；带工具权限的数字员工还可能要求身份、权限、依赖和通信通道全部完成初始化。不同消费者可以读取同一内部状态机的不同投影，但每个投影都应明确自己的证据门槛。

设计时可以反向提问：消费者看到“运行中”后会做什么？这个动作如果要成立，系统必须已经知道什么？哪一条可记录事件证明这些条件被满足？如果证据暂时不存在，就应保留“已认领”或“启动中”，而不是用乐观标签填补空白。

失败路径同样重要。启动超时不应短暂经过“运行中”再变成失败；重试也不应让旧工作器的状态污染新执行轮次。状态事件最好绑定执行轮次、发生时间、证据来源和负责组件，使恢复过程能够区分新的就绪事实与陈旧记录。

## 已知边界比更响亮的结论更重要

当前证据来自官方发布说明，并非独立复现，也没有公开内部源码或回归测试。它能建立的是一个有界的顺序要求：在受影响路径上，对外“运行中”不能早于 Claude Code 进程启动。

它不能证明进程启动等于完全初始化、健康、已连接或能够接受所有类型工作，也不能证明所有 Claude Code 生命周期都采用同一门槛。把这次修复写成“进程一启动就全面就绪”，会再次制造证据与语义错位。

评审任何运行状态时，最实用的问题不是“标签叫什么”，而是：**哪个消费者会据此采取什么行动，仓库中哪一条可核查证据足以为该行动负责？** 如果这两个问题没有明确答案，状态仍然只是控制面意图，不是可依赖的运行事实。

**一手证据：** [Claude Code 2.1.247 官方发布说明](https://github.com/anthropics/claude-code/releases/tag/v2.1.247)。该来源支持受影响路径上的故障描述与进程启动顺序，不构成完整就绪语义的独立验证。
