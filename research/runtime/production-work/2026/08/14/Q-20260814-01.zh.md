# 持久化不是执行许可：长期数字员工的三重边界

长期数字员工真正困难的地方，不是把任务“存下来”，而是在进程中断、预算耗尽、操作者暂停或系统重启之后，仍能回答三个彼此不同的问题：这项工作是否仍然存在？现在是否允许把它交给执行器？此前的暂停或中断是否已经被明确解除？

## 从队列持久化到执行边界

当天研究对象基于 Codex 已合并实现和回归测试。公开一手事实表明，待处理提交可以按线程持久保存，并拥有稳定的队列项身份和客户端消息身份。更关键的是，持久化记录不会因为“可见”就自动被消费：派发器先请求 Core 在空闲时启动，只有 Core 明确返回 Started 后，队列项才被删除。

这个顺序把一个常被混为一谈的问题拆开了。队列负责证明“工作存在”，Core 的 Started 负责证明“本次执行已经准入”。如果在准入之前删除记录，会产生工作丢失窗口；如果在 Started 之后删除，至少能把持久记录保留到执行权已经被接纳的时刻。

## 中断不是普通空闲

同一实现还对 Interrupted 状态做了不同处理：包括预算限制导致的中断在内，系统不会仅因为线程再次处于可派发位置就自动继续，而是保留显式 queue/start 路径，让恢复成为一个独立授权动作。这说明暂停语义属于执行策略，而不是存储语义。

因此，长期 Agent Runtime 更适合把三类事实建模为独立控制层：持久工作身份、执行准入、恢复授权。Persistence 解决“东西还在不在”；Admission 解决“现在能不能开始”；Resumption Authorization 解决“此前的暂停是否允许解除”。把三者合并，系统就可能把一次简单重启误读成继续执行的许可。

## 这并不等于 Exactly-once

现有证据仍有清晰边界。按线程的派发通过进程内 Mutex 串行化，但这并没有建立跨进程互斥、分布式租约或外部副作用 Exactly-once。即使队列项只在 Started 后删除，执行开始后的崩溃仍可能留下未知的外部效果。

这意味着多 Worker 数字员工还需要额外的 Ownership 机制，例如可持久租约与 fencing；而调用邮件、数据库、文件系统或外部 API 后的恢复，还需要独立的 Effect Evidence、Idempotency 或 Compensation。稳定队列身份只是可靠执行的一层，而不是完整事务保证。

## 工程含义

对长期运行系统而言，工作记录应独立于 Worker Session 和 UI Connection 保留稳定身份；消费动作应发生在权威准入之后，而不是因为队列中出现一条记录；Pause、Interruption、Budget Exhaustion 与 Policy Stop 应拥有明确恢复状态；一旦进入多消费者场景，本地锁必须升级为跨进程 Ownership；一旦执行可能产生外部副作用，就必须把副作用证据从会话历史中独立出来。

这些原则并不要求所有低风险单进程助手都引入复杂工作流引擎。对简单系统，即时自动 Drain 可能是合理取舍。但随着任务寿命、风险和执行范围扩大，“持久化即允许执行”的隐含假设会越来越危险。

## 局限与开放问题

本次证据只覆盖一个 Codex 的实验性按线程队列实现及其测试，并不是对数字员工调度架构的独立评估。它没有建立分布式共识、跨进程排他、优先级、截止期、依赖关系或 SLA 策略。

仍需回答的问题包括：多个 Worker 消费同一线程队列时需要怎样的 durable lease 与 fencing；哪些失败应自动继续、自动暂停或要求人工授权；以及从执行准入到持久完成之间发生崩溃时，哪些效果证据必须存续，才能避免 Retry 重复外部副作用。
