Agent Research & Competitor Intelligence · 2026-09-18 ​

Asia/Shanghai · Only meaningful technical or product developments are included.

Back to the daily archive

Daily conclusion ​

Today's strongest convergence is that “resuming the same session” is being decomposed into a much more precise execution contract: current host, current-turn environment snapshot, provider outcome, reviewer authority, credential namespace, and workspace branch each need their own proof. A long-lived Agent may preserve context, but a surviving Session does not automatically carry forward an old Host, approval, credential, or working branch.

1. Kazuhiro Sera / OpenAI Agents Python: v0.22.3 ships, and conditional approval now constrains the gap between inspected and executed arguments ​

Status: RELEASED · v0.22.3 (2026-09-18 Asia/Shanghai)

Kazuhiro Sera (seratch) published OpenAI Agents Python v0.22.3. This patch release is primarily about tightening execution semantics rather than adding a large new API surface:

  • A callable conditional-approval policy runs only when argument preparation can prove that the values inspected for approval are the same values the Python Tool will execute. Defaults, coercion, application models, custom validation, regex/plugins, or other transformations that cannot be safely compared now fall back to manual approval instead of authorizing raw arguments and executing different prepared values.
  • Server-managed resume retains locally generated tool-not-found outputs that have not yet been delivered, avoiding lost or incorrectly replayed outputs.
  • SQLite / AdvancedSQLiteSession fixes tighten concurrent startup, branch identity, and durable tool-usage history.
  • Windows-host sandbox command paths retain POSIX semantics, and early Codex event-stream closure reaps the subprocess correctly.
  • The documentation now states the Unix-local boundary explicitly: Linux adds no OS command confinement, and macOS filesystem restriction is not network isolation.

Why it matters: an approval must refer to the normalized input that will actually produce the Effect, not the earliest string seen by the UI/decorator. Resume must also distinguish produced, persisted, delivered, and consumed results.

CodeFlowMu/FCoP relevance: ADMIN/QA/EVAL approval receipts should bind the normalized Effect/Arguments plus policy revision; a transformation before execution should invalidate an approval that no longer proves the same effect.

Interaction value: very high. Suggested question: Will approval receipts eventually bind the prepared/normalized argument digest so a resumed or transformed tool call can prove it is executing exactly what was approved?

2. OpenAI Codex: a running Turn freezes its Environment Snapshot; provider-gateway credentials gain an independent OAuth lifecycle ​

Status: #46310 MERGED; #46318 MERGED

Codex #46310 makes environment selection changes effective only for the next Turn. A running Turn keeps the environment snapshot and MCP workspace roots it activated with; switching remote/local environment during that Turn is saved as a future selection and cannot redirect currently executing tools or pending setup. Manual compaction first stops the current task before adopting a new environment.

#46318 adds an OAuth credential manager for model-provider gateways: PKCE browser sign-in, loopback callback, refresh after expiry/rejection, cross-process serialization of token exchange/persistence, and a separate encrypted namespace with an independent keyring key. Refresh-token rotation is persisted even after caller cancellation, and a rotated credential whose save fails is retained as pending. Crucially, credential refresh does not imply that the failed request is safe to replay; the caller still owns that decision.

Why it matters: configuration changes and credential refresh must not silently change the identity of an in-flight effect. A Turn should own a frozen execution context; credential refresh answers what credential may be used next, not whether the previous effect may be resent.

CodeFlowMu/FCoP relevance: a useful contract is Turn/Run Generation → Environment/Host Snapshot → Credential Identity → Effect Identity → Replay Eligibility.

Interaction value: high. Suggested question: Will the active environment snapshot and provider OAuth credential generation become part of a single execution-context digest attached to tool/effect receipts?

3. Paperclip: named Agent Reviewers now have a formal, narrowly scoped, recoverable Review Handoff ​

Status: #13581 MERGED

Paperclip #13581 fixes the formal collaboration path where a native child task requests a different Agent reviewer. Previously the reviewer wake failed assignee/execution-lock checks, leaving the child in review and the parent waiting.

Reviewer admission is now bound to the exact company, issue, source run, decision, revision, addressee, and resolver policy. The reviewer receives a narrow Paperclip control surface for reading child context/history/documents and calling resolve_review; the worker remains the child assignee. Reviewer run, durable wake, and child execution lock must be claimed atomically; if another run owns the lock, the provider does not start. Only the current running reviewer session holding the current issue lock can resolve the exact assigned card; stale, reassigned, unrelated, or terminal review runs are rejected.

Accepted/rejected review outcomes enter parent continuation evidence but do not change issue ownership or grant unrelated tool authority. The change also adds durable reviewer wake/recovery handling and duplicate-wake protection, with focused live Codex and Claude handoff checks.

Why it matters: “another Agent reviews the work” is becoming a responsibility/authority object rather than a chat convention.

CodeFlowMu/FCoP relevance: this is close to an independent EVAL/QA channel: review decisions may enter the parent's evidence chain, while reviewer authority remains limited to a named review object rather than ordinary TASK mutation.

Learning: very high | Competitive risk: very high | Radar: Paperclip remains top priority.

Interaction value: very high. Suggested question: Will reviewer assignment eventually carry a durable evaluator identity/model boundary so a review receipt proves not only which agent resolved it, but which independent evaluation channel produced the decision?

4. Paperclip: real Run JWTs were captured from process argv — a high-value credential-isolation incident ​

Status: #13572 OPEN / NOT MERGED

Paperclip #13572 documents a real credential exposure. Every Agent prompt taught a curl form with Authorization: Bearer $PAPERCLIP_API_KEY directly in argv. On Linux, /proc/<pid>/cmdline and host-wide ps -ww -eo args can expose those arguments to other same-host/same-UID processes during the curl lifetime. A continuous /proc sampler captured real working-agent Run JWTs; this is not merely a theoretical issue.

The current JWT also has no early revocation path (jti=None, no denylist), so the proposed fix focuses on prevention: move the Authorization header from argv to stdin (curl -H @-), update prompt templates/adapters/skills/artifact-upload paths, and ship a RED/GREEN regression that first proves the detector can observe an argv leak and then proves the safe transport produces zero hits.

The PR is still open, and several pinned skill snapshots, scripts, workflows, and documentation examples remain explicitly out of scope, so this must not be described as fully fixed.

Why it matters: environment-variable injection is not sufficient credential isolation. The command pattern taught to the Agent can re-project the secret into argv, logs, shell history, checkpoints, or persisted sessions.

CodeFlowMu/FCoP relevance: Host admission should test not only where a secret originates but how tools/prompts transport it at effect time.

Learning: very high | Competitive risk: very high | Radar: raise Credential Projection / Host Co-tenancy weight.

Interaction value: very high. Suggested question: Would Paperclip move from denylisting unsafe examples toward an allowlisted credential-transport primitive so agents never need to construct bearer headers themselves?

5. Paperclip: durable exe.dev VMs formally separate Run lifetime from Environment lifetime ​

Status: #13575 OPEN / EXPERIMENTAL / OFF BY DEFAULT

Paperclip #13575 adds an experimental durable exe.dev environment: one environment binds one durable VM, while each Agent/Workspace Run uses a separate reusable lease. Ending or cancelling a Run does not delete the VM or its disk. Task-scoped directories persist across Turns, and the native runner uses a pinned Linux image plus a matching provider pack.

Validation is extensive: 8 leases / 64 concurrent commands, SSH loss, disk continuity, timeout, cancellation isolation, escaped descendants, private HTTP, VM reboot, plus paid browser compatibility/recovery/warm-session cases. The boundaries are equally explicit: Agents on the same VM must trust each other; directories and systemd cgroups are not a tenant security boundary; there is no autosleep/HTTP-wake guarantee; the experiment is disabled by default and is not a production rollout.

Why it matters: a Digital Employee workstation is moving from “ephemeral sandbox per task” toward “long-lived Environment + short-lived Run Lease.”

CodeFlowMu/FCoP relevance: multi-host design can make Environment Identity ≠ Run Lease ≠ Workspace Identity. Durable state may survive across runs, while execution authority is freshly claimed each time; a missing/replaced VM identity should fail closed.

Learning: very high | Competitive risk: very high | Radar: raise Paperclip multi-host / durable-workstation weight.

Interaction value: high. Suggested question: Will durable VM identity, image digest, workspace lease and provider-pack digest be bound into one run receipt so recovery can prove which long-lived environment actually executed the effect?

6. Orca: host-scoped resume, explicit provider outcome, and real 14,000-desktop fleet pressure all reinforce “Session ≠ Run ≠ Host” ​

Status: #21288 OPEN; #21278 OPEN; #21303 MERGED

Three Orca changes align strongly:

  • #21288: a provider session minted on Host A was resumed on Host B, which had never written that transcript, producing “No conversation found with session ID”. The proposal makes resume issuers check execution-host provenance; a record that positively belongs to another host is refused and preserved. Older records whose host cannot be positively disproved remain fail-open rather than inventing provenance.
  • #21278: structured-turn lifecycle {state:"completed"} previously covered both success and provider errors. The proposal adds independent outcome: success | failure | cancellation; absent outcome on old/ambiguous rows means UNKNOWN, never success. Host-observed lifecycle termination and provider verdict remain distinct facts.
  • #21303 is merged and comes from a production fleet of roughly 14,000 desktops: each host renewed a control lease every 30 seconds, creating roughly 470 independent DB writes/s and 5–12 second fleet stalls that broke mobile pairing and caused desktop reconnects. Relay cells now batch up to 200 due renewals per second and use FOR UPDATE ... SKIP LOCKED so one contended host does not block a cell.

Why it matters: provider Session ID is not Run ID or Host identity; “Turn ended” is not provider success; control-plane lease traffic is part of remote-agent correctness, not just background telemetry.

CodeFlowMu/FCoP relevance: multi-host/room design can separate Provider Session Alias → Canonical Run → Execution Host → Lifecycle → Provider Outcome, each with independent evidence.

Learning: very high | Competitive risk: medium-high | Radar: raise Orca multi-host / settlement / fleet-control weight.

Interaction value: very high. Suggested question: Do you plan to make canonical runId the common foreign key for host provenance, provider outcome, delivery settlement and replay eligibility, with provider session ids remaining aliases only?

7. OpenHands: Agent Profile tool authority starts coming from the live Server catalog instead of a hardcoded UI list ​

Status: #17516 OPEN / NOT MERGED

OpenHands #17516 moves Agent Profile tool selection away from a Canvas-maintained curated list toward a Server-authoritative catalog. With the new Software Agent SDK support, GET /api/tools/catalog provides the runnable catalog and the server materializes the effective tool set.

The UI's Standard tools section will reflect the server-resolved set, and Choose tools will select only from runnable catalog entries. A retired but previously stored tool remains visible rather than silently disappearing. The capability is gated by tool_catalog_v1; an older Server hides the picker and the client omits the tools field on save, avoiding accidental grant mutation in mixed-version deployments.

The PR currently depends on unreleased Software Agent SDK work, so the feature intentionally remains hidden until that SDK capability ships.

Why it matters: a UI must not invent Runtime capability. Tool authority should be projected from the Server/Host's current executable facts, then narrowed by the Profile.

CodeFlowMu/FCoP relevance: after Host admission, UI, Worker, PM, and EVAL should project the same Detected Capabilities → Adopted Capability Set instead of keeping separate tool lists.

Interaction value: high. Suggested question: Will the effective tool set carry a catalog revision/capability digest so a long-lived profile can detect when its stored grant references a tool whose runtime semantics changed?

8. Superset: Cloud Workspaces get dedicated working branches, and mobile-created cloud workspaces can receive image attachments inside the remote sandbox ​

Status: #7620 MERGED; #7622 MERGED

Superset #7620 fixes cloud agents working directly on the selected base branch. The control plane now carries both baseBranch and a dedicated workspace working branch named superset/<slug>-<id8>; multi-repo workspace checkouts use the same logical working branch, while PRs still target the base. The Agent no longer starts on main by default, and control-plane branch identity matches the actual box checkout.

#7622 connects mobile image attachments to cloud-workspace creation. Bytes land in cloud storage before the box exists; file IDs travel with the launch; after host-service starts, the sandbox imports those files into its local attachment store and passes in-box paths to the Agent through the same # Attached files prompt block used on other hosts. A failed attachment download does not suppress the main prompt.

Keep the validation boundary explicit: both PR descriptions noted that a complete real-box end-to-end check had not yet been performed at their early verification stage. The code is merged, but that is not evidence that every production cloud-box path has been fully exercised.

Why it matters: Superset's Cloud Workspace now carries explicit Workspace/Branch identity and mobile-to-cloud artifact transport rather than merely being a remote terminal.

CodeFlowMu/FCoP relevance: in a multi-host system, Workspace is not the Base Repository, and an uploaded Artifact should not require the destination Host to exist at the moment the human sends it.

Learning: very high | Competitive risk: very high | Radar: Superset stays on the main radar; raise Cloud Workspace identity / mobile artifact handoff weight.

Interaction value: high. Suggested question: Will workspace branch identity and attachment materialization both be included in a launch receipt so the first Agent turn can prove which base revision and exact uploaded artifacts it actually received?

Cross-project convergence ​

The common direction can be compressed to one line:

Context may be resumed; Authority must be re-proven.

OpenAI Agents binds approval more tightly to normalized inputs; Codex freezes a running Turn's Environment snapshot and separately governs provider OAuth; Paperclip separates Reviewer role, Run JWT, and durable Environment; Orca separates Provider Session, Run, Host, Lifecycle, and Outcome; OpenHands returns Tool capability to the Server as source of truth; Superset makes Cloud Workspace branch/artifact identity explicit.

For CodeFlowMu/FCoP, a stable execution chain is emerging:

Work/Run Identity → Current Task/Turn Generation → Workspace/Branch Identity → Execution Host & Capability Snapshot → Principal/Credential Projection → Reviewer/Approval Authority → Effect → Provider Outcome / Settlement → Replay Eligibility.

If any element changes, the system should not inherit old authority merely because the Session still exists.
