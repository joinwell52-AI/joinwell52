Daily conclusion ​

Two lines are accelerating at the same time: Project / Channel / Mobile are becoming formal control surfaces for long-running agents, while historical sessions, retained providers, old sandbox state, and previous approvals no longer imply current execution authority and must be re-proven near the actual effect boundary.

1. Cursor Projects: coordinator + massive subagent fan-out + month-scale context + subscriptions enter Beta ​

Status: BETA / OFFICIAL RELEASE (officially published 2026-09-10; added to the archive in this run)

Cursor officially launched Projects. A Project is designed for larger bodies of work such as features, migrations, and full applications. It preserves context over months and uses a coordinator agent that plans and delegates rather than writing code itself. The coordinator creates and manages implementation agents and can scale parallel work to large fleets of subagents.

Projects run on dedicated cloud computers, so work continues after the user's laptop closes. When local-machine testing is required, the coordinator can start a local agent. Project context is stored in files that sync across cloud and local machines, and Projects can subscribe to Slack, schedules, and PR activity so recurring or event-driven work can happen without a new prompt.

Why it matters: this is not merely another coding-agent feature. It combines a durable work object, a coordinator, parallel workers, multi-host execution, shared context, and recurring/event-driven triggers into one formal product surface.

CodeFlowMu/FCoP relevance: this strongly overlaps with CodeFlowMu's PM + multi-role/multi-agent + long-running work + cloud/local Host direction. CodeFlowMu should continue differentiating through responsibility roles, authorization boundaries, independent EVAL, recoverable facts, and FCoP protocol evidence.

Learning: very high | Competitive risk: very high | Radar: treat Cursor Projects as a top-priority external reference.

Interaction value: very high. Suggested question: When hundreds or thousands of subagents operate across cloud and local machines, how are shared-context authorship, conflict convergence, permission inheritance, and compaction provenance proven?

2. Yue Zhao / anywhere-agents v0.8.0: different models take different jobs, followed by a Windows sandbox reality check ​

Status: RELEASED v0.8.0 + POST-RELEASE FIX

Yue Zhao released anywhere-agents v0.8.0. The most relevant change is explicit model-role allocation: prun gives a larger share of parallel units to Agy/Sonnet, while Codex is reserved for the /vet gatekeeper role, partly because its current credit cost is a poor fit for bulk fan-out. Agy units support scratch or throwaway-clone execution, follow-up turns with --continue-from, and quota monitoring.

Zhao then committed a Windows-specific correction. dispatch-task-agy.py had passed --sandbox to every unit; on Windows, Agy's exebox relaunched an elevated broker, producing a UAC prompt for each shell-using unit. The dispatcher now omits that sandbox by default and makes it explicit opt-in through PRUN_AGY_SANDBOX. The documentation deliberately describes the remaining boundary as structural containment, not enforced isolation; a live probe without the flag successfully used shell, web fetch, and file writes.

Why it matters: it shows two practical engineering decisions at once. Model differences can be handled by job/cost/capability routing rather than pretending all models are interchangeable. At the same time, a sandbox claim that is operationally unusable on the real Host must be downgraded to an explicit isolation-strength fact rather than silently treated as strong isolation.

CodeFlowMu/FCoP relevance: PM/DEV/QA/EVAL model selection can be made explicit around role capability, cost, and independence. Host capability records should distinguish structural containment from a genuinely enforced sandbox.

Interaction value: very high. Suggested question: Would you record both role/model routing and current isolation strength in an auditable execution receipt so /vet can judge the environment under which a result was produced?

3. OpenAI Codex: a long-lived Thread no longer owns static Provider / Host / Sandbox authority ​

Status: MERGED / MERGED / MERGED

Three related Codex changes landed together:

  • #44944: existing app-server threads re-check current managed model_provider / model_providers requirements before turn start/steer, review, compaction, manual queue start, and active-goal updates. If requirements cannot be loaded or the retained provider no longer matches, the operation is rejected and the user is prompted to restart.
  • #44939: Windows sandbox setup now respects the actual execution host. A local TUI cannot configure a remote executor's sandbox; remote servers own their Agent permission selection, and mixed local/remote executors are surfaced explicitly.
  • #44945: Windows sandbox setup is routed through the app server and the effective sandbox mode must be verified before Agent mode is enabled. If a setup request times out or its response is lost, setup remains pending and input stays locked rather than assuming success; interrupted setup gets explicit restart semantics after reconnect.

Why it matters: the thread still exists, this provider was used last time, and the UI started setup are no longer accepted as evidence of current authority. Provider, execution host, and sandbox readiness are live admission facts.

CodeFlowMu/FCoP relevance: Host admission and recovery should bind Thread/Run Identity + Provider Identity + Execution Host Identity + Effective Sandbox Capability + Policy Revision, rather than merely restoring a session ID.

Interaction value: very high. Suggested question: Will these checks converge into one executor capability/authority digest that is revalidated before every resume, turn, and approval?

4. Paperclip: iMessage is being developed as a durable remote command and interaction channel for Digital Employees ​

Status: DRAFT / EXPERIMENTAL / live qualification incomplete

Draft PR #13299 adds experimental iMessage Photon. The goal is a stable Photon Cloud phone number per agent channel so a person can start a task, send a photo, or answer an agent's pending question from Apple Messages. DMs and explicitly enabled groups reuse the existing channel admission, identity links, task generations, publication, and interaction-continuation infrastructure.

This is more than a chat adapter. The design persists immutable text/file send identities, upload receipts, poll and option IDs, per-person drafts, and canonical interaction-continuation proofs; recovery uses a leased receiver plus checkpoints, while media handling covers HEIC/HEIF, JPEG previews, and Live Photo companion video retention.

The qualification boundary is explicit: there are no live Photon credentials/test participants yet, and real iPhone DM/group, media, poll/text continuation, restart, and ambiguous-send tests remain unrun. The PR therefore remains Draft and experimental.

Why it matters: remote Digital Employee control is moving beyond Web/PWA into normal messaging surfaces, and the correct architecture is not a simple chatbot—it preserves sender identity, task generation, continuation, and delivery facts.

Learning: very high | Competitive risk: high | Radar: keep Paperclip at the highest priority and add IM remote-control channels as a dedicated dimension.

Interaction value: very high. Suggested question: Will iMessage approvals/answers produce typed human-action receipts bound to sender identity, task generation, and the exact question/effect digest instead of merely feeding message text back to the agent?

5. Paperclip: a call-time authorization hardening attempt was deliberately closed, exposing the compatibility boundary of global fail-closed enforcement ​

Status: CLOSED / NOT MERGED / NOT DEPLOYED

PR #13297 attempted to move final authorization for approval-governed remote HTTP MCP actions to the point after all awaited preparation and immediately before the first provider operation. It used PostgreSQL time for the expiry boundary, atomically consumed request/invocation/audit disposition, and blocked credential-refresh + redispatch after an approved provider call returned HTTP 401. Its intended safety properties included no await between successful permit and HTTP write, at-most-one provider operation per approval, and uncertain rather than replay when the response outcome is lost.

The author closed the PR without merge or deployment. The focused 71-test PostgreSQL proof passed, but the provider-wide restrictions disabled or conflicted with existing legacy, Test-tab, local-stdio/built-in, and explicit-retry ask-first paths. Upstream CI had 12 server failures and all three E2E shards conflicted with the reduced contract, so the bounded rollout stop condition was used.

Why it matters: this is a valuable failure sample. Call-time authorization cannot simply be bolted in front of every provider with one global rejection rule. Each transport/execution path needs explicit single-effect, retry, statefulness, and approval semantics.

CodeFlowMu/FCoP relevance: Host/Tool authorization is better modeled as a per-effect-path contract: which paths can guarantee single dispatch, which must fail closed, and which require compensation.

Learning: very high | Competitive risk: high (architecture-complexity risk) | Radar: do not downgrade Paperclip; this is evidence that it is colliding with real production authorization boundaries.

Interaction value: high. Suggested question: Will the next version implement final permit per transport/provider capability rather than globally denying older paths that do not satisfy the single-dispatch contract?

6. Superset: Agent fleet status formally reaches the iPhone Lock Screen and Dynamic Island ​

Status: MERGED (requires a native build/TestFlight; not an OTA-only change)

PR #7452 restores and merges the iOS AgentActivity Live Activity. The Lock Screen can show up to four agent rows; Dynamic Island shows agent count and elapsed time; rows support deep links and localization.

The important product signal is not the card styling: agent-fleet state is now an operating-system-level mobile surface. The current limitations are equally important. This is a native extension that must ship in a subsequent TestFlight/preview build, and updates are currently foreground-oriented; after the app closes, the card becomes stale and Dynamic Island freezes at the last snapshot. It is therefore not yet a fully push-driven remote supervisor.

Learning: very high | Competitive risk: high | Radar: Superset is very close to the primary radar; increase the mobile-control weight again.

Interaction value: high. Suggested question: Will the next step use server push / ActivityKit remote updates to deliver typed review, permission, and failure state continuously to the Lock Screen and bind approvals to receipts?

7. Orca: DST fall-back can relaunch one Automation every scheduler tick, exposing the need for durable occurrence identity ​

Status: OPEN

PR #20179 fixes a scheduler failure in which a cron fire time inside the repeated autumn DST hour could resolve the “next occurrence” back to the same instant that just fired. The scheduler then saw nextRunAt <= now on every roughly 60-second tick and launched the agent again. In new_per_run mode, every duplicate launch also created a new worktree and consumed additional tokens.

The root cause was local wall-clock field recomposition in floorToMinute: an ambiguous minute could resolve to the earlier offset and violate the “strictly after” contract. The fix switches flooring to UTC arithmetic and adds an actual America/New_York 2026 fall-back regression: both legitimate repeated-hour occurrences fire once, while the nonexistent spring-forward minute is still skipped.

Why it matters: scheduler arithmetic errors can materialize directly as duplicate agents and worktrees, and can become duplicate external side effects if there is no independent occurrence identity.

CodeFlowMu/FCoP relevance: each scheduled occurrence should have a durable idempotency identity such as (schedule_id, intended_occurrence_instant). A scheduler regression may produce duplicate wake signals, but it should not be able to create a second business effect.

Learning: very high | Competitive risk: medium-high | Radar: raise Orca's Automation Runtime weight further.

Interaction value: very high. Suggested question: Would you persist every scheduled occurrence as a global idempotency key so DST/clock/restart errors can at worst duplicate a wake, not duplicate the business run?

Cross-project convergence ​

A clearer split is emerging:

Control surfaces can become richer, but authority must become narrower and move closer to the real effect.

Cursor Projects, Paperclip iMessage, and Superset Lock Screen expand the places from which long-running agents can be coordinated. At the same time, Codex separates Provider/Host/Sandbox authority from historical Thread state; Paperclip's failed rollout shows that final authorization must understand the concrete transport's effect contract; and Orca shows that even a Schedule needs an independent occurrence identity.

A useful CodeFlowMu/FCoP chain is:

Control Surface / Trigger → Human or System Principal → Work/Run Identity → Live Host & Capability Evidence → Call-time Authority → Effect Identity → Settlement / Replay Eligibility.

Yue Zhao's v0.8.0 adds a useful organizational conclusion: model differences do not have to be erased. Models can be treated as role resources, with fan-out vs gatekeeper duties chosen by capability, cost, and independence.
