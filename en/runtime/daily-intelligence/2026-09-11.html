Daily conclusion ​

The strongest convergence today is not another Agent feature. Static configuration, historical sessions, and previously granted approvals are increasingly treated as insufficient evidence of current authority. MCP is separating server discovery from live capability negotiation; Codex re-evaluates effective runtime context when permissions, plugin selection, or AGENTS.md change; Superset and Orca are binding execution to current workspace and provider evidence.

1. David Soria Parra / Sam Morrow · MCP Server Cards: pre-connection discovery is separated from runtime capability ​

Status: SEP text marked Final; GitHub PR #2127 remains OPEN / unmerged.

The current text of SEP-2127, authored by David Soria Parra, Sam Morrow, and Tadas Antanavicius for the Server Card Working Group, is marked Final. It defines standardized out-of-band discovery for HTTP MCP servers before a connection is opened.

A Server Card describes remote server identity, endpoints, and supported protocol versions. Domain-level discovery can use /.well-known/ai-catalog.json, and <streamable-http-url>/server-card is the recommended card location. The detailed wire format lives in the experimental-ext-server-card extension repository.

The most important boundary is deliberate: static cards do not advertise tools/resources/prompts, nor MCP capabilities/extensions, because those can vary by authenticated user, session, configuration, feature flags, and deployment state. Live protocol discovery and negotiation remain authoritative; if static metadata disagrees with live data, clients should prefer the live values.

Why it matters: Discoverable Identity ≠ Runtime Capability ≠ Current Authorization.

CodeFlowMu/FCoP relevance: a Host/Server Card can help discovery and version pinning, but admission should still require live capability probes, current identity evidence, and role-level real tests.

Interaction value: very high. Suggested question: Would a future Server Card profile expose a stable capability-manifest identity/hash without advertising user-dependent capabilities themselves, so admission can bind discovery to a later live conformance result?

2. OpenAI Codex: permission widening, plugin changes, and AGENTS.md revisions invalidate old runtime assumptions ​

Status: #44617 MERGED; #44655 MERGED; #44675 MERGED.

Three Codex changes landed in the same window:

  • #44617: an exec_command requesting with_additional_permissions can no longer reuse an earlier Guardian v2 cached approval that covered only narrower permissions. Unscored permission widening now invalidates the cached score and fails closed with scoring_failure.
  • #44655: thread-level disabled_plugin_ids now apply to plugin skills, recommendations, hooks, MCP servers, and model-visible app tools. Selection changes activate only when the next task starts, and MCP approval keys now include plugin identity.
  • #44675: long-running root threads refresh global AGENTS.md at model-request boundaries, including after tools in the same turn. New subagents inherit the parent's applied instruction snapshot, and Guardian reviewer reuse accounts for refreshed instructions.

Why it matters: approvals, plugin selection, and instruction snapshots are facts about a particular context; widening the effect scope or changing the policy/plugin identity requires renewed evaluation.

CodeFlowMu/FCoP relevance: runtime authority should bind Policy/Instruction Revision + Plugin Identity + Requested Effect Scope + Authority Epoch, with widening or policy revision forcing re-evaluation.

Interaction value: very high. Suggested question: Do you expect Guardian approval cache keys to converge on one explicit policy-context digest covering effective instructions, plugin identity and normalized permission scope?

3. Superset: Cloud Workspace moves from Blaxel to Vercel Sandbox; mobile Pages Review is now merged ​

Status: #7408 OPEN; #7367 MERGED.

Superset #7408 is a structural competitor change. After Blaxel was acquired, Superset is migrating Cloud Workspaces to Vercel Sandbox and using the migration to redefine part of the Host/Sandbox trust boundary:

  • persistent sandboxes use a four-hour session timeout extended only by opening the workspace;
  • forks come from a stopped golden snapshot;
  • organization model keys are injected at the egress firewall, while a personal provider credential suppresses the brokered key for that provider;
  • because a Vercel sandbox port is a public URL, host-service becomes the auth gate. The API signs a 10-minute Ed25519 token bound to exactly one workspace ID, while the sandbox holds only the public key;
  • addressing and waking are explicitly separate: polling does not wake a stopped workspace; opening it does. snapshot() ends the session and becomes the resume point.

The branch reports real Vercel verification: a workspace ready in about 14 seconds, a fork in about six seconds, stop/reopen with pane and scrollback returning in roughly 20–30 seconds, and 35 minutes of token refresh without 401s. The PR is still open and must not be treated as released capability.

Meanwhile #7367, previously monitored while open, is now MERGED. The mobile app can browse Agent-published Pages via signed viewUrl + WebView and perform element comments, quick feedback, threads, and pins. remove/approve are still ordinary comment text rather than fully typed intents.

Why it matters: Superset is making both Cloud Sandbox and Mobile Review first-class product surfaces: computers execute; phones review and steer; cloud hosts carry workspace-specific short-lived access credentials.

CodeFlowMu/FCoP relevance: this closely matches a local/cloud Host plus mobile approval/evidence terminal model. Address ≠ Wake, workspace-bound bearer tokens, and review-focused mobile UX are especially relevant.

Learning: very high | Competitive risk: very high | Radar: raise priority. Keep Superset as a main-radar candidate; promote if #7408 merges with production deployment/mobile E2E evidence.

Interaction value: very high. Suggested question: When a stopped Vercel workspace is reopened, will the new sandbox/process generation be explicitly bound to the previous workspace identity and current credential projection so session continuity cannot imply stale host authority?

4. Paperclip: Board API keys are becoming auditable least-privilege authority contracts ​

Status: #10972 OPEN; rebased to current master with extensive security verification, not yet merged.

Paperclip #10972 now presents a mature board-automation authorization contract:

  • a versioned scope schema with a canonical 59-permission vocabulary;
  • new board keys cannot have null scope; legacy keys are explicitly marked and temporarily preserve unrestricted behavior;
  • each request rechecks the key and owner, intersecting stored key scope with live owner authority and deriving company access from authoritative rows;
  • allow/deny audit records, audit-coupled mutations, and a self-revoke rule;
  • a checked-in inventory of board-reachable routes, with CI failing when a new/changed route lacks explicit policy metadata;
  • dedicated tests for role demotion, grant provenance, authorization order, and audit atomicity.

The PR also states an important remaining boundary: database transactions cannot roll back object-store, filesystem, process, provider, or live-publication effects, so those still require durable intent/outbox state, stable idempotency keys, retries, and compensation.

Why it matters: authority becomes Stored Scope ∩ Current Owner Authority ∩ Current Resource/Route Policy rather than “the API key is an admin token.”

CodeFlowMu/FCoP relevance: long-lived ADMIN/PM/Host credentials should be recomputed against current authority after role or organization changes, not retain their creation-time power forever.

Learning: very high | Competitive risk: very high | Radar: keep Paperclip as a first-line Runtime/control-plane competitor.

Interaction value: very high. Suggested question: Will non-database side effects eventually require an authorization receipt that binds the scoped board key, live owner authority, effect precondition and durable outbox/idempotency identity?

5. OpenAI Agents SDK Python: HITL resume must preserve undelivered Tool Output causality ​

Status: #4947 MERGED.

openai-agents-python #4947 fixes a precise recovery gap. A single model response can contain an approval-gated tool call and a call to a missing tool. The Runner locally constructs the missing-tool error output, then interrupts while waiting for approval.

Under server-managed continuation (conversation_id, previous_response_id, or auto_previous_response_id), that locally created but not yet delivered output could previously be treated as already sent, leaving the server with a function call but no corresponding output. The fix uses tool-call IDs from the latest model response as the authoritative interrupted-turn set while first recognizing server-owned items, so unsent local results are delivered and already delivered results are not duplicated. Tests cover staged approvals and require each tool output to arrive exactly once.

Why it matters: Resume must preserve the causal chain Call → Local Result → Delivered Result, not merely reconstruct a broad run state.

CodeFlowMu/FCoP relevance: WAIT/HITL/REVIEW interruptions should distinguish whether a result has been produced, persisted, and delivered. Those are separate facts.

Interaction value: high. Suggested question: Would an explicit per-tool effect/result delivery ledger make interrupted-run recovery simpler than reconstructing unsent outputs from the latest model response?

6. Orca: a restored Model choice cannot override the Provider's current live capability ​

Status: #19946 OPEN.

Orca #19946 documents a real Claude structured-session failure. Session restore can replay a model ID that was valid when saved but has since been retired; a mid-session API, including mobile agentSession.setOption, can also send an arbitrary ID. Claude Code's setModel() may accept an unlisted model, but every subsequent turn can then fail with zero tokens, leaving a session that looks alive but produces nothing.

The proposed fix checks the live session's own supportedModels() before mutating the model. A stale restored choice is skipped, leaving the provider's current model authoritative. The author also calls out the limit: provider catalog membership does not prove account/credential entitlement. If list_models is absent or empty, the current compatibility choice is permissive rather than rejecting every older CLI.

Why it matters: Persisted Configuration ≠ Current Capability.

CodeFlowMu/FCoP relevance: this directly supports a Host admission chain of version discovery → live capability collection → baseline diff → role-level real test → ADMIN adoption. Old config or prior session state is only candidate input.

Learning: very high | Competitive risk: medium-high | Radar: raise Orca's Host-capability/recovery weight.

Interaction value: high. Suggested question: Would you split provider-listed capability and credential entitlement into two explicit admission facts, so restore can fail closed only when the relevant evidence is actually available?

Cross-project convergence ​

History can be restored, identity can be discovered, and configuration can persist; current execution authority still has to be re-proven from the current context.

MCP Server Cards deliberately keep dynamic capabilities out of static discovery. Codex invalidates assumptions after permission widening, plugin selection changes, or instruction revision. Superset binds a public sandbox endpoint to a short-lived workspace credential. Paperclip intersects long-lived key scope with live owner authority. Orca rechecks a restored model against the live provider catalog. Agents SDK preserves the exact result-delivery boundary across interruptions.

A useful CodeFlowMu/FCoP chain is:

Discovery Identity → Live Capability Evidence → Principal/Scope → Policy Revision → Call-time Authority → Effect/Result Delivery → Replay Eligibility.

The crucial split is the first two terms: discovering that a Host/Server/Model exists is not proof that it is currently usable by this account, workspace, or role.
