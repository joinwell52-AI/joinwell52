AI 数字员工接班，你会通过哪份报告？ ​

设想一家企业把租金对账交给 AI 数字员工。数字员工是承担岗位职责的智慧员工。 像人接到工作一样，负责对账的 AI Agent（智能体）要理解交办、安排步骤、找证据，遇到疑点主动核实，并交代自己为什么这样算。换班时，另一个数字员工接着做，负责复核的数字员工再独立判断报告能不能通过。

这是实验情境。 实际运行中，我们用写好的测试程序代替这些 AI Agent，同样用测试身份模拟批准。整个过程没有真人换班，也没有调用大模型。真实运行的是 CodeFlowMu，我们开发的本地 AI 团队协作系统，负责管理工单、审批决定、报告和复核记录。

我们正在开发能承担这些岗位的数字员工。这笔合成账让我们在写岗位 Skill、接工具之前先看清一个问题：换班和独立复核各需要什么依据，才能让接手的 Agent 自己把工作做下去？

现在请你当复核员。两份报告都在说同一笔租金：应收 3,000 元，银行到账 2,700 元，还有一笔 300 元的暂定减免。减免申请一直没正式批下来。

早班派这张工单时，规程只认正式批准的减免。午后规程更新，允许把暂定减免也算进去。工单上留着一句话：“这一轮按派发时的规程算完。”

你拿到的报告报告怎么写
A把暂定减免算进去，差额 0 元，账已对平。
B暂定减免留在待办里，差额 300 元，等正式确认。

你会通过 A，还是 B？ 选过之后，再看复核员打开下午的新规程会判哪一份。

这张工单该通过 B。可在实验里，只按最新版复算的复核员恰好做反了：A 通过，B 被拒。

复核程序重新算了一遍，还是判反了 ​

复核程序自己从账目重算。新版允许抵扣暂定减免，所以三千减掉两千七，再减三百，结果是零。程序把报告 B 的 300 元与自己算出的 0 元比较，就判了不通过。可报告 B 用的是工单指定的原版。

问题出在谁替这张工单换了规则。早班交办时，要求晚班把三百元留作待确认。下午发布新版之后，执行程序打开最新版，复核程序也打开最新版。两道程序算式各自正确，但在这条路径里，一次规程发布就悄悄改掉了在办工单的验收条件。复核员用同一条新规则重算，反而给这次改动盖了章。这就是为什么再多找一位复核员，如果大家都只读最新版，仍然可能一致地判错。

同一个编号，会打开哪一页？ ​

我们的起点是 StaffDeck 的一处修复。StaffDeck 是 OpenBMB 开源的企业数字员工平台，可以把岗位操作规程发布给 AI Agent 使用。问题出在重启时的一段旧数据库迁移逻辑。以回归测试为例，员工原先用 sop_expense_policy 找到报销规程。迁移可能把数据库里的编号改成 skill_expense_policy，已发布的引用却还指向前一个编号。这样，规程仍保存在库里，员工顺着原编号查找时却可能看不到它。修复会保留已发布的编号，并在能确认归属且没有冲突时恢复此前被改掉的编号。

StaffDeck 的回归测试先发布一份规程，再重新打开数据库、执行初始化。测试做了两种情况：编号一直没改过，以及编号已经被旧逻辑改过。两种情况下都核对原公开编号能找回，而且员工仍能看到这份规程。这个测试保住的是 “我还找得着这份规程”。顺着它往下问：如果原编号还在，下午发布的内容却变了，晚班怎么打开早班那张工单实际该用的版本？这才是我们拿 A 和 B 做对照的原因。 StaffDeck 代码变更与回归测试

StaffDeck 的修复让我们看到，数字员工换班后，首先得拿得回岗位规程。我们顺着这个问题做了两步：先让规程编号保持不变，只在派工后更新内容，看执行和复核会不会一起用错版本。再给其中一张在办工单明确的换版批准，看接班后能不能保住已核验的流水，只重做受影响的减免判断。一轮问“有没有悄悄换规则”，另一轮问“真要换，能不能只改变获批的那部分工作”。

前六次都通过，为什么还要再跑？ ​

我们在 CodeFlowMu 里让测试程序模拟对账和复核两个岗位。每次用同一笔合成账、同一句“按派发时规程完成”。模拟接手的程序要么打开当前规程，要么沿工单找回指定版本。模拟复核的程序用自己的测试身份读回报告和工单，再分别按这两种口径复算。每次的差额和通过结果都由程序根据输入算出。

开跑前就把判据定好：原版 V1 只认已批准的减免，这张工单应保留 300 元差额。对照时固定原始账目和工单约定，只改变交接时是否发布新版，以及接手和复核时从哪里取规程。这样，结果翻转时可以回头检查是哪一条取规程的路径出了问题。

前六次让规程保持原样，两种接手读法各跑三次。此时当前版就是工单原版，六份报告都留下 300 元，两种复核也都通过。这六次给出了基线：平日规程没变化时，直接打开最新版的做法也能一路通过。 要看出两种读法的差别，得在工单已经发出、晚班尚未接手的时候改规程。

后六次就在这个时点发布新版。打开最新版的三次都交了 A，沿工单取回原版的三次都交了 B。然后把每份报告交给两种复核方式。你可以沿着图里任意一行看：待审报告没换，只换了复核依据，通过与拒绝就对调了。 对这张明确要求沿用原版的工单，只按最新版复算，三次误放 A，也三次误拒 B；按工单复核，六次判断都与交办要求相符。

每格是同一组合三次的结果。四格来自六份报告，每份报告都用两种方式复核。

任务和报告走的是正式的 FCoP 协作接口，采用工单依据的结果写成了引用对应报告的正式审查记录。换班、会计口径与两套复核方式由实验程序驱动。结果覆盖这条受控路径，真实岗位换班和企业验收仍待测量。 逐轮报告金额、两种判定和审查是否入档

工单写着旧版，旧版却找不到了 ​

最后一次故意留下工单里的旧版引用和文件指纹，也保留能打开的新版，只拿走旧版原文。接手程序能说清缺的是哪一份文件，却无从读出旧规程怎么处理暂定减免。结果是工单留在进行中，没有生成报告，也没有复核记录。这是一次缺件对照。它让前面的结论多了一个必要条件：工单引用到的那个版本，接班时得实际取回来。指纹只在拿到文件后派得上用场。

换人之后，这份工作还能接着做吗？ ​

每次换班、转派或重启，系统其实都要替下一位数字员工重新打开一张工单。能不能换人继续，取决于接手的是不是原来那项工作。 规程更新时，系统应保留两个事实：组织现在发布了什么规则，以及这张工单实际适用什么规则。前者由规程发布记录说明，后者由派工约定或有权人作出的在办任务切换决定说明。这样，换班本身就不会顺手把待批的三百元划掉。

具体落地时，工单要能找到适用的规则原文，执行报告要留下实际用了哪一版和账目依据，复核 Agent 要对照工单核验具体报告。这条记录串起来以后，复核 Agent 才有材料判断账算得对不对、用的规程是否适用。原文缺失时，接手的 Agent 要查缺的是哪份文件，并找对应负责人补证。

这次真要切版，只重做哪一步？ ​

我们又跑了一轮。这次 A、B 是两张独立工单。“早班”有两个测试账号，一个负责对账，一个负责复核。 实验脚本用对账账号核对 2,700 元的合成银行流水，按 V1 算出暂定减免可抵扣 0 元，再把两项结果保存为关联工单的记录。接着，脚本用复核账号从原始数据重新核对，并记录复核的是哪一份核验记录。两张单都停在这个进度，还没有交最终报告。

V2 发布后，实验用管理员测试身份只批准 B：保留已核验的流水，按新版重做减免判断。A 的申请仍待审批。随后我们重新打开 CodeFlowMu 的任务接口，用另外两个测试身份接手：一个运行对账程序，一个运行复核程序。它们各自从工单读回早班写下的记录。两张单都能读到 V2，只有 B 能读到对本单生效的切版决定。

这一轮的验收条件也在开跑前定好。两张单都要读回原流水核验记录，交接后重验流水都应为零。批准仍待处理的 A 继续用 V1，获批的 B 才按 V2 重算减免。验收时看文件指纹、调用次数和正式复核记录，逐项对上这个预期。

我们逐张对比了交班前后的流水核验文件，指纹完全相同。记录里，两张单交班后的流水重验次数都是零。B 只有一次减免重算和一次独立复核。最后又读回两份正式复核记录，核对它们各自引用报告和旧证据，只有 B 引用了生效的切版决定。B 的零差额这一次有据可查：工作条件确实变了，而且只重做了受影响的那一步。 两张工单的决定、原件指纹和调用次数

这是一次成对的本地对照。任务、换版决定、报告与复核走实际产品接口，两个新身份是测试身份。实验程序按决定里列出的步骤保留流水、重做减免。下一步才是验证真实 AI Agent 能否根据交接记录判断哪些旧结果仍可复用。

接班时，系统究竟该把什么交过去？ ​

StaffDeck 的修复提醒我们，规程的编号要能跨重启找回来。两轮本地实验往下追了一步：一张在办工单的交接记录，要能说明哪版规则适用、哪些结果还能用、哪些判断得重做。 第一轮只按最新版复算，放行了三份该拒的报告，也拒绝了三份该过的报告。第二轮给了一张单明确的换版决定。两张单都保住了原流水记录，只有获批那张重算减免。对数字员工系统来说，这就是可以拿来验收的区别：换了接手账号之后，结果的变化仍能追溯到具体工单上的决定。

真正让错误被发现的是数字员工自己判断、另一位数字员工独立复核。对账 Agent 接到 A 时，要主动查这张单有没有生效的换版决定，再选规程。复核 Agent 如果看到 A 报了零，就要沿工单查原版，问这 300 元为什么被抵扣，并据此给出自己的复核意见。发行新版及批准哪些工单切版，仍由组织里有权作决定的人负责。

轨道机负责把工单、轮次、获批决定和早班的工作记录交过去。工具负责返回规程原件、账目和操作回执。事实核查机制核验 Agent 声称的操作是否真实发生，例如它是否真的打开了某一版文件、是否调用了流水核验工具。即使回执证明 Agent 读过 V1，减免是否符合 V1 仍要由对账和复核 Agent 根据原件分别判断。

写一个接班的 Agent，它第一步读什么？ ​

从正式文件恢复工作。 晚班收到工单编号和这一轮的标识，先读工单、已生效的决定和已有证据。上一位 Agent 的思考或聊天可以提示去哪里查。工作走到了哪一步、哪次批准已生效、有没有正式报告，都要回到文件核对。

写这个数字员工时，要给它三样东西：

  • 工单告诉它这次做什么。 对账岗位要交一份写明差额及依据的报告。复核岗位收到具体报告的引用，要独立查证，并交复核意见。定哪一版规程适用，要看这张工单和本轮已生效的决定。
  • 岗位 Skill（工作指引）教它怎么查。 对账指引可以告诉它先查交接记录、判断哪些原件仍有效、把所用版本和证据写进报告。复核指引可以要求先读原件，再对照报告，写明哪里不一致。Agent 自己选择取证步骤，遇到缺件就主动查证。
  • MCP（模型上下文协议）提供可调用的工具。 Agent 通过工具读任务和报告、取有权访问的材料，也可以提交报告或复核意见。它从工具返回的文件和操作回执里拿到事实，再自己完成判断。

FCoP 是基于文件的协作协议。用它写出的工单（TASK）、报告（REPORT）和复核记录（REVIEW）可以按标识查回、相互引用。报告的 subject_ref 和 attempt_id 指向哪张工单、哪一轮，复核记录的 references 指向具体报告。对账 Agent 可以提交自己的结果，交付须经过另一位 Agent 独立复核。 复核 Agent 根据原件和规程判断，顺手读一遍对账 Agent 的说法还不够。报告里的“流水已核验”也要能追到流水原件和操作回执。

CodeFlowMu 在实验里负责按测试身份读写这些材料，由产品的指令服务按工单和轮次查已批准的指令。两张单都能读到 V2。A 查不到针对本轮生效的换版决定，B 能读到仅针对本单本轮的决定。实验走的是这条链：

text
执行岗位：读 TASK 和执行轮次 → 取获批决定与原证据 → 写 REPORT → 提交待审
独立复核岗位：另读工单、规程和原证据 → 验具体 REPORT → 写 REVIEW 引用该报告

换版选择和计算在这次实验中由脚本按已批准的清单执行。换成真实 AI Agent 时，FCoP 仍负责把工作事实落在文件上，CodeFlowMu 仍负责把这些事实和可用工具送到岗位。接手之后怎样查、该重做什么、报告能不能通过，由执行和复核 Agent 各自作判断。 文件写着“通过”，我们就能查到谁审了哪份报告。要判断这份报告到底对不对，还得回到它引用的规程和原件。

多一个 Agent，究竟多查到了什么？ ​

这两轮实验让我们重新看待“独立复核”。用错规程时，第二次计算可以和第一次一模一样。它们共用的是一个错误的前提。我们因此想问：怎样让复核真正增加一次查证，使团队有机会推翻第一个答案？ 同一笔账可以继续拆成三个问题。

先有答案，还是先有证据？ 真实 Agent 会不会被执行报告里的“差额 0 元”带着走？本轮只测了两种取规程的方式，答案出现的先后还需要另测。配对给两组复核 Agent 同样的工单、原件和报告，一组先看报告，另一组先查原件并留下自己的初判，再读报告。混入两类样本：算得对且用对版本，以及算得对却用错版本。事先按工单标好预期，比较漏掉错版和误拒正确报告的次数。这样才知道“先查原件”能不能改善复核。

说查过、确实查过、查明白了，是三件事。 让复核 Agent 面对两个对照样本。一份报告声称读过 V1，但在完整记录的读取工具里找不到这次调用。另一份确实有读取回执，报告却把 V1 不允许抵扣的 300 元扣了。前一项用操作记录核对声明，后一项由独立复核 Agent 找条款、解释错在哪里。两种错误分别记下来，才知道该补的是操作证据，还是岗位 Skill 里的核对方法。

什么条件变了，才值得把哪一步重做？ 续验里，批准已经写清“留流水、重做减免”。下一轮把问题留给接手 Agent 自己判断。做一组只改减免的对照，再做一组银行已撤回那笔到账的对照。给两组同样格式的工单、原件和生效决定，要求执行 Agent 说明哪些结果还能用，复核 Agent 独立检查。预期是前者保留流水核验，后者重验流水并重算差额。记录该重做却漏掉的步骤，也记录重复做了多少仍然有效的工作。

每组都固定工单样本、模型版本、岗位 Skill、可用工具和权限，先定义验收标准，再改变本组要研究的条件。FCoP 文件留下两位 Agent 各自的结论和原件引用，工具回执留下它们实际做过的事。

这些实验会影响我们怎样开发数字员工：如果先查原件能减少错版漏检，就有依据把它写进复核 Skill；如果查不到关键操作，就补工具回执；如果接手的 Agent 分不清哪些旧结果还能用，就检查交接文件有没有记录当时的规则、原件和步骤之间的关系。下一轮先验证第一项。我们要知道，多一位数字员工复核，究竟多带来哪一条能核对的依据，什么时候它会改变结果。
