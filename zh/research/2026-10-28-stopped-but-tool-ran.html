AI 已经叫停，排队的工具为什么还会启动？ ​

想象你让一个 AI 助手查资料、整理文件、再发起一次操作。中途检查发现第一步出了错，于是助手报告：“任务失败，停止执行。”

听起来很安全。但此时第二个工具可能已经开始，第三个还在队列里。错误被报告出来和之后不再发生新动作，其实是两件事。对会调用外部工具的 Agent，这个时间差比最后一句回答更重要。

本文要追问的是：一个系统声称“已停止”，究竟要拿出哪些事实，才值得我们相信？ 一句状态文本装不下排队工作、进行中的调用和已经送往外部的操作。我们先用一项可复跑实验检查其中的执行队列，再把它放回更完整的工程问题。

我们为什么追这条变化 ​

在 10 月 28 日的18 组 Agent 工程动态中，OpenAI Agents Python 的 PR #5446描述了一种具体情况：一个函数工具的失败已经被选为本次运行的错误，程序还在收拾先前完成的输出，排队的另一类工具却可能继续执行。并行输入检查拒绝时，也有相似的停止边界。

这正对应我们研究的一个问题：“停止”什么时候才真正传到执行队列？ 它可以用固定源码、同一测试、修复前后两份代码来回答，比只读 PR 描述更可靠。

把“报错”和“停手”分开测 ​

我们没有调用真实模型，也没有让工具触碰真实文件或网络。使用上游修复版的回归测试，ScriptedModel 按预设顺序发出工具请求；合成的 custom tool 和 local shell tool 只记录自己是否启动、是否收到取消。测试把“已有工具在运行、另一个在排队、函数失败被选定”的时刻控制住，再放行收尾步骤。

同一测试放在修复前的 a91f0bfe 和合并版 cd26bbbc 上运行。我们交叉了两类工具、流式与非流式、输入拒绝与否、清理期间是否再出错，共 16 种受控时序。

源码16 种时序的结果失败或通过意味着什么
修复前16/16 未通过已启动的 native 工具没有在这个时间窗收到预期取消信号。
合并版16/16 通过同样时序下，活动工具收到取消，排队的调用没有越过停止边界。

我们又在合并版运行相关的两个测试文件，共 84/84 通过。这不是“84 种真实场景都安全”，只是相关回归未出现失败。前版的 16 个用例均停在相同的取消断言，且测试进程打印了实际加载的前版源码路径；这样排除了“只是在两次运行里不小心测到同一份代码”的疑问。

再加一个反例：调用取消后，远端仍可完成 ​

上面的对照回答了“排队调用会不会启动”，还没回答“已经送出去的动作会怎样”。我们因此自行构造第二组探针：仍穿过合并版真实 Runner 和工具入口，让活动工具先把请求交给一个延迟提交的合成远端，再触发函数失败。合成远端是本进程里独立等待的任务，不是实际网络服务。

在失败被选定的瞬间，活动工具已收到取消，排队调用没有启动；但合成远端已经接收请求，尚未提交。本地运行结束后，我们再放行远端，提交照样发生。这个反例没有发现 OpenAI SDK 的新漏洞；它验证的是一个更基本的边界：本地停止状态不能替已经接收请求的外部系统回答最终结果。 探针脚本与两次状态快照

从一次取消，走向一份可核查的“停止回执” ​

修复把“选定失败”变成一个会影响其他工具的事件：活动 native 工具接收取消，队列也不再继续放出新调用。它仍会在有界时间里处理已完成工具的输出，避免简单丢失错误前已经产生的结果；真正由调用者发出的取消则优先结束。

从测试能直接确认的，是“选定失败”不再放任这组受控时序中的活动工具和排队调用继续按旧路径推进。一个更完整的停止回执还需要把三件事分开：

  1. 队列是否封口？ 停止之后，迟到的消息、重试或下一项工具调用还能否重新点火？Codex 0.165.0 的发行说明也专门修复了 interrupt 后排队 Agent 消息重新唤醒工作的情况。那是另一个上游项目的已发行变化，不是我们本轮复测结果。
  2. 活动调用停在何处？ Python 任务收到取消，不必然等于底层执行者已经结束。AG2 1.2.2 的说明明确提醒，同步工具 worker 超时后仍可能继续运行并产生副作用。我们的合成工具能观察取消信号，不能替真实 worker 作担保。
  3. 外部结果是否查清？ 合成探针已经表明，本地取消之后，先前接受的请求仍可提交。Paperclip 的接管实现把不确定 mutation 暂停，等待后续确认。这提供了处理方向；我们没有运行 Paperclip 接管实验。

这三项是从本轮两组有界探针与另外三条一手变化归纳出的工程判断，不是一个已通过真实网络端到端测试的通用协议。特别是“撤销已发生的副作用”并不由取消自动实现。PR #5446 已合并，我们没有核验某个正式发行版是否包含它。

一个可讨论的最小回执，应把“未启动的调用”“收到取消但尚未确认结束的调用”“外部结果仍不确定的调用”列成不同状态，并保留各自的时间与工具标识。这样下一位接手者才能知道：哪些事无需重做，哪些事必须先向外部系统查证。这个回执结构尚未在本轮实现或验证。

如果你正在用 Agent 执行真实任务，可以问一个具体问题：当检查失败或人按下停止时，系统能否说清哪些调用尚未启动、哪些已经启动、哪些虽被取消但外部结果仍不确定？

下一步需要把合成远端换成可独立查询的服务，并检查恢复者拿到什么记录。这次探针还没有测试恢复流程。专业读者可以讨论：不确定结果应由工具、运行时还是业务方负责核对？普通使用者遇到过“显示停止，却还有文件或远端状态变化”的情况吗？具体时间顺序会比一句“AI 没停住”更有帮助。
