界痕 BoundaryXP：让 AI 团队的任务边界看得见 ​

假设你把一项工作交给 AI：“核对这批车辆的维修记录，找出异常，交一份报告；只查资料，不改系统。”

一个能够调用工具的智能体，可能会自行拆分步骤：读取记录、比对费用、下载附件，再请另一个智能体整理报告。此时，任务中的“只查资料”就很重要。即使它发现某条数据明显有误，修正数据库也超出了这次交办的范围。

智能体的特点，是能够根据目标选择做法。许多原本由人逐步安排的事情，现在会由它继续规划和分工。因此，交代“要完成什么”还不够，还需要说明：用哪些资料、允许做哪些动作、谁有权确认、能花多少资源，以及哪些事情明确不能做。工具账号能完成某个操作，也不代表这项任务允许它这样做。

这就是任务边界：在这一次交办中，什么是必须履行的要求，什么做法可以接受，什么条件尚未满足，什么行为不能发生。任务分给多个智能体后，这些要求还要继续约束每一份子方案，并接受整体检查。

界痕 BoundaryXP 围绕这个问题提出 7+1 任务边界判定方法：先把自然语言里的要求和关系表达清楚，再用数学方法检查主任务、子任务及其组合。BXP 协议约定这些要求怎样表示、怎样保留依据和形成判定；BoundaryXP 工具把方法用于具体任务，输出可以追到原文的报告。方法论文与协议草案均已公开。

7+1，先把任务里的八个问题问清楚 ​

一份自然语言任务书，常把目标、权限、预算和验收要求写在同一段话里。7+1 给这些内容安排了清楚的位置：七类任务要求，加上一类独立保留的禁止边界。

维度要问清楚的问题
I · 输入范围可以使用哪些资料、系统和对象？范围到哪里？
O · 交付要交出什么成果，交给谁？
A · 动作必须做什么、允许做什么？针对哪个对象？
P · 责任主体与角色分工谁执行、谁复核、谁批准、谁接收？
R · 资源预算、时限、容量和数量上限是多少？
V · 版本依据依据哪份规则、制度或证据？采用哪个版本和时间基准？
C · 完成停止什么条件算完成？什么时候必须停止或上报？
B · 独立禁止边界哪些动作、对象或效果明确禁止？有哪些明确的条件和例外？

例如，在前面的车辆维修核查任务中，“这批车辆的维修记录”限定输入，“异常报告”规定交付，“核对”规定动作，“不改系统”保留为明确禁令。如果任务没有说明报告交给谁，就应把这个问题留出来，不能替发出任务的人补写一个接收者。也不能把所有空栏一律判成失败；还要看缺少的信息是否影响这次判断。

列出八栏只是开始，要求之间的关系同样重要。 两个小组说的“预算”是不是同一笔钱？“验收通过后才能发布”中的验收，指的是哪个版本？子任务中的“设备一号”，是否就是主任务里的那台设备？这些关系决定后面的计算究竟在检查什么。

遇到行业术语和企业内部称呼时，L2 行业语义库、L3 企业语义库可以帮助核对含义和身份。例如，某个简称究竟指测试环境还是生产环境，需要有依据。词库的解释和岗位名称本身都不能增加授权。八类视图与共享关系的定义及词库工具说明给出了具体约定。

从文字到数学，边界怎样算出来？ ​

可以把任务边界理解为：所有满足已明确要求的做法，组成的一个范围。 子任务可以把工作安排得更具体，但适用的上级要求仍然有效。合并子任务时，还要检查共同预算、同一设备、交接条件和先后顺序。

先看一个用于说明原理的简化预算例子。主任务给整个团队 500 元，四项计划费用分别为 180、160、120、80 元。假定它们都占用同一笔预算，四项都要发生，没有重复计费或抵扣：

180 + 160 + 120 + 80 = 540 元 ＞ 500 元，超出 40 元。

每一项单独看都不到 500 元，合起来仍然超支。这里真正需要进入计算的，除了四个数字，还有“共同占用同一笔预算”这个关系。如果漏掉最后一项，计算器会正确算出 460 元，却没有检查完整方案。

不同要求，可以采用不同的数学表达：

原文中的要求可以怎样检查
整个团队合计不超过 500 元把同一范围内的支出相加，与总上限比较。
只能读取指定的两份文件比较拟读取的文件集合与允许范围，找出多出来的对象。
复核通过后才能发布保留“复核通过”这个前置条件，检查方案是否允许绕过它。
多个工序有严格先后关系把工序和先后要求组成有向图，检查是否出现无法满足的闭环。

同样的对象、数值和规则，能够被反复核对。数学方法让已经表达清楚的要求有共同的判据，也能指出具体冲突：多读了哪个文件，超出了多少预算，哪几条顺序不能同时成立。

不过，数学检查需要先知道它在检查哪道题。自然语言中的对象、否定、条件和范围，都应保留到表示中；有歧义的地方需要澄清或保留未知。可复核的计算，加上可追溯的原文，才能让边界判断有意义。 论文和协议讨论的正是从要求表示、形式模型到计算判定的这一过程。

每个小组都能安排，合在一起为什么做不了？ ​

界痕公开的 RT044 保存案例给出了一个多任务组合问题。这是一份实验室计划约束案例：同一轮工作里，安全复核、设备开机、包装、送检各发生一次。

主任务和三个小组分别提出要求：

来源顺序要求
主任务安全复核结束后，才能开机。
测试组开机结束后，才能开始包装。
实验室组包装结束后，才能开始送检。
安全组送检结束后，才能开始这一次安全复核。

三个小组各自增加的那条顺序，分别与主任务比较，都能找到一种满足要求的安排。但三条一起加入，就形成了：

安全复核 → 开机 → 包装 → 送检 → 同一次安全复核。

这个问题可以用很简单的数学关系说明：每个事件都要先开始、后结束，上一件事结束后下一件才能开始。沿着这些严格先后关系走一圈，最终会要求**“安全复核的开始时刻，早于它自己的开始时刻”**。一个时刻不可能严格早于自身，因此不存在满足全部要求的时间安排。

原文已经限定“同一轮、同一次事件”，所以不能擅自假设“再做一次复核”或“另送一份样本”来解开这个环。需要由有权修改计划的人保留主任务要求，调整子方案中的顺序，再重新检查。

这也说明了多智能体任务为什么需要整体核验。局部可安排，只说明当时比较的那部分要求可以共同成立；它不能替代联合检查。这里应指出组合方案越界，并列出参与闭环的要求，不能把联合冲突直接归成每个小组各自单独越界。

越界、未越界、信息不全，各回答什么？ ​

边界判定关心的是方案或已给出的行为事实与任务要求的关系。界痕公开演示中的三种结果，可以这样理解：

结果与案例判断依据这项结论说明什么
越界：RT044同一轮的严格先后要求形成闭环。当前组合方案存在确定冲突，需要修改。
未越界：RT042同一设备分别占用 10—11 点、11—12 点；规则明确到点释放、允许立即接入，清场也已计入。在这些条件下，两段占用没有重叠。
信息不全：L23-050林舟和赵清都参加会议，任务却只写“由他确认”，没有唯一指代依据。最终确认人无法确定，需要补明身份。

RT042 中，两段设备占用可写成 [10:00, 11:00) 和 [11:00, 12:00)：左端包含、右端不包含。第一组在 11 点释放，第二组从 11 点开始，交集为空。这个结论依赖明确的释放与清场规则；只看到两个时间段还不够。设备案例原文与计算

L23-050 中，准备材料与请求澄清可以继续，最终确认人的身份仍需明确。现有文字不能因为某人的岗位更高，就替任务发出者选定他，也不能据此说已经有人违规完成了验收。责任人案例原文与计算

“未越界”只针对本次所检查的要求与材料。 它不等于工作已经完成、成果已经正确或业务批准已经取得。同样，存在未知信息也不必然阻止所有判断；如果已知费用已超过上限，而且其他费用只能增加、没有抵扣，剩余金额尚不明确也不能消除已经确定的超支。

方法、协议和工具，怎样相互支撑？ ​

7+1 方法把任务要求及其关系组织成可比较的表示；BXP 协议进一步约定表示、依据、计算和结果的处理方式；BoundaryXP 工具负责把具体任务送入这一过程，展示原文、分析、计算回执和未决问题。协议草案与工具实现各有版本，当前实现范围以实现状态说明为准。

公开研究材料保存了 625 组任务、3,219 个任务节点和 3,469 项查询，涉及逻辑、数量、集合身份、依赖和复合约束。625 组保存结果的最终判定均与各自的现行标注一致，保存的模型整体判断也与程序汇总一致。逐项比较时，模型判断与程序结果仍有 9 项差异，包括 6 项标签编码差异和 3 项计算判断差异；另有 3 项计算因指定输入缺失而未完成。统计口径与原始记录

这些材料的作用，是让人检查方法怎样用于具体问题，冲突怎样定位，未知信息怎样影响结论。整组一致性衡量的是这些保存记录与现行标注的对应关系，不能外推为新任务准确率。

网站 11 月 14 日的复核记录还保存了摘要与分类核对、六项选定数学见证以及一个费用案例九项计算的复算结果。这些是有范围的历史复核，没有重新运行全部模型分析。本次修订沿用这些证据，并更新了产品接入信息。

怎样看报告，怎样分析自己的任务？ ​

可以先打开中文交互演示，从 RT044 开始：点任务树里的一个节点，选中一个维度，再查看相关条款和原文。这样能看到一个结论究竟对应哪些任务要求。

分析自己的任务，可以按 MCP 中文安装指南接入 Cursor 或 Codex。截至 2026 年 11 月 16 日，公开预发行版是 0.4.0-rc.8，面向 Windows x64，提供 18 个工具、10 项资源和本地浏览器工作台。该版支持使用当前宿主的模型分析，无需另配一把模型 API 密钥；也可以选择独立 API 模式。宿主模式仍有模型参与，不能把“无需额外 API 密钥”理解成不使用模型服务。rc.8 发布说明

实际使用时，先导入完整的主任务和子任务，检查任务树，再保存并明确提交分析。报告会保留模型的解释和计算内核对受支持操作数的复核结果，二者可以分别查看。对已保存的操作数，还可以不新增模型调用地复算。打开工作台本身不会提交一次新分析。工具职责说明

目前公开内容包括文档、协议、论文、研究案例和编译安装包；计算内核的原始实现源码仍在独立私有仓库维护。使用报告时，也应保留它的判断范围：计算能够核验已经表达出来的问题，原文是否被完整、准确地理解仍需检查；修改计划、业务批准和实际执行，仍由相应的责任人或业务系统决定。

当一项任务交给一个智能体时，边界让它知道自己承担什么、可以做到哪里。交给一组智能体时，还需要把它们的安排放回同一份任务中，看共同要求是否继续成立。界痕希望把这件事做得具体：指出是哪条要求、哪几个子任务、哪一项计算出了问题，让人能够据此修改，而不只收到一句“整体看起来可行”。
