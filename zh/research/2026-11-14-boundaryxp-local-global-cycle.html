界痕 BoundaryXP：让 AI 团队的任务边界看得见 ​

假设你把一项工作交给一组 AI Agent：

核对这批车辆的维修记录，找出异常，交一份报告。只查资料，不改系统。

执行中，一位 Agent 发现某条记录明显有误，打算直接修正数据库；另一位准备把附件下载到本地，交给同伴写报告。先别急着给两件事下同一个结论：修正数据库明显违反“不改系统”；下载附件是否在允许范围内，还要看任务对资料、存放位置和使用方式的约定。

更麻烦的是：如果子任务各自添加了工作顺序，单独看都能完成，合在一起却形成闭环，冲突该归到哪个层级？是主任务没写清楚，还是子任务增加的要求在组合时相互冲突？这些问题只靠“感觉”判断，很难统一，也很难追到原文。

界痕 BoundaryXP 要做的，是让任务边界可以检查、可以讨论，也能找到判断依据。它提出 7+1 任务边界判定方法：先整理自然语言里的八类要求及其关系，再用数学方法检查主任务、子任务和组合方案。方法论文在 Zenodo 公开。

为什么说清楚目标还不够？ ​

智能体会根据目标规划步骤、调用工具，甚至继续分工。交代“要完成什么”之外，还需要说明：可以用哪些资料，允许做哪些动作，谁有权确认，能花多少资源，哪些事情明确不能做。工具账号能完成某个操作，也不代表这项任务允许它这样做。

这就是任务边界：在这一次交办中，什么必须履行，什么做法可以接受，什么条件尚未满足，什么行为不能发生。任务分给多个智能体后，这些要求仍要约束子方案，并接受整体检查。

7+1，先把任务里的八个问题问清楚 ​

一份自然语言任务书，常把目标、权限、预算和验收要求写在同一段话里。7+1 给这些内容安排了清楚的位置：七类任务要求，加上一类独立保留的禁止边界。

维度要问清楚的问题
I · 输入范围可以使用哪些资料、系统和对象？范围到哪里？
O · 交付要交出什么成果，交给谁？
A · 动作必须做什么、允许做什么？针对哪个对象？
P · 责任主体与角色分工谁执行、谁复核、谁批准、谁接收？
R · 资源预算、时限、容量和数量上限是多少？
V · 版本依据依据哪份规则、制度或证据？采用哪个版本和时间基准？
C · 完成停止什么条件算完成？什么时候必须停止或上报？
B · 独立禁止边界哪些动作、对象或效果明确禁止？有哪些明确的条件和例外？

例如，在前面的车辆维修核查任务中，“这批车辆的维修记录”限定输入，“异常报告”规定交付，“核对”规定动作，“不改系统”保留为明确禁令。如果任务没有说明报告交给谁，就应把这个问题留出来，不能替发出任务的人补写一个接收者。也不能把所有空栏一律判成失败；还要看缺少的信息是否影响这次判断。

列出八栏只是开始，要求之间的关系同样重要。 两个小组说的“预算”是不是同一笔钱？“验收通过后才能发布”中的验收，指的是哪个版本？子任务中的“设备一号”，是否就是主任务里的那台设备？这些关系决定后面的计算究竟在检查什么。

遇到行业术语和企业内部称呼时，L2 行业语义库、L3 企业语义库可以帮助核对含义和身份。例如，某个简称究竟指测试环境还是生产环境，需要有依据。词库的解释和岗位名称本身都不能增加授权。

先自己判断：每个小组都能安排，合在一起呢？ ​

界痕公开的 RT044 保存案例给出了一个多任务组合问题。这是一份实验室计划约束案例：同一轮工作里，安全复核、设备开机、包装、送检各发生一次。

主任务和三个小组分别提出要求：

来源顺序要求
主任务安全复核结束后，才能开机。
测试组开机结束后，才能开始包装。
实验室组包装结束后，才能开始送检。
安全组送检结束后，才能开始这一次安全复核。

先试着回答三个问题：每个小组新增的要求，分别与主任务放在一起时能否安排？四条要求全部合并后呢？如果出现冲突，能否直接说某一个小组单独越界？

建议先停几秒，或者在纸上沿着箭头走一圈，再继续往下看。

合并后的结果 ​

三个小组各自增加的那条顺序，分别与主任务比较，都能找到一种满足要求的安排。但三条一起加入，就形成了：

安全复核 → 开机 → 包装 → 送检 → 同一次安全复核。

这个问题可以用很简单的数学关系说明：每个事件都要先开始、后结束，上一件事结束后下一件才能开始。沿着这些严格先后关系走一圈，最终会得到一个矛盾：安全复核必须在它自己开始之前开始。因此，不存在满足全部要求的时间安排。

原文已经限定“同一轮、同一次事件”，所以不能擅自假设“再做一次复核”或“另送一份样本”来解开这个环。需要由有权修改计划的人保留主任务要求，调整子方案中的顺序，再重新检查。

这也说明了多智能体任务为什么需要整体核验。局部可安排，只说明当时比较的那部分要求可以共同成立；它不能替代联合检查。这里应指出组合方案越界，并列出参与闭环的要求，不能把联合冲突直接归成每个小组各自单独越界。你刚才对第三问的判断，能否用这四条原文逐条说明？

从文字到数学，边界怎样算出来？ ​

7+1 先保存八类要求及其共享的对象、身份、作用域和条件；在解释固定后，BXP 协议草案把边界定义为满足约束的候选方案集合：

χM(x)=Q(x)∧¬F(x)∧K(x)∧Φ(x),ΩM={x∈XΣ∣χM(x)}.

Q 是义务，F 是禁止状态，K 是完成或停止条件，Φ 包含其余约束；ΩM 中才是该固定解释下可接受的方案。边界不必逐个列出方案：计算某个方案是否属于 ΩM，或者合并要求后该集合是否变为空集，就能比较边界。

计算一：RT044 的局部与整体。 令 A 为安全复核、D 为开机、B 为包装、C 为送检；下标 s/e 分别是同一轮、同一次事件的计划开始和结束。保存的 7+1 报告将主任务与三个子任务写为：

P=(Ae≺Ds)∧⋀X∈{A,B,C,D}(Xs≺Xe)T=(De≺Bs),L=(Be≺Cs),F=(Ce≺As)

前一式是主任务；后三式依次是 TEST、LAB、SAFETY 新增的顺序。报告先计算局部和两两组合：

SAT(P)=true,SAT(P∧T)=SAT(P∧L)=SAT(P∧F)=true,SAT(P∧T∧L)=true,SAT(P∧T∧F)=true,SAT(P∧L∧F)=true.

全部合并后，严格先后关系却回到了自己的起点：

As≺Ae≺Ds≺De≺Bs≺Be≺Cs≺Ce≺As⟹As≺As（不可能）.SAT(P∧T∧L∧F)=false,ΩP∧T∧L∧F=∅.

计算结果：主任务可行，全部子顺序合并后无可行计划，组合方案越界。 保存报告的查询结果也相符：KT、KL、KF 分别未越界，联合查询 KJ 越界。SAT 表示是否存在满足全部所列约束的计划；这里计算的是任务书，不表示四个事件已经发生。

计算二：RT042 的设备占用与交接。 另一份保存的 7+1 报告按同日零时起的分钟数记录同一仪器 M 的两段计划占用：J_X=[600,660)、J_Y=[660,720)。半开区间的重叠函数代入端点后给出：

o⟺max(sX,sY)<min(eX,eY)⟺max(600,660)<min(660,720)⟺660<660=false.JX∩JY=∅,sY−eX=0.

父任务明确允许到点释放、同刻接入，清场也包含在原占用时段。报告还把文本已述的交接状态与计划区间分开求值：r 为“11:00 已释放”，b 为“无残余占用”，n 为“无第三个同时预约”；这些真值来自原文陈述。

D=r∧b=true∧true=true,N=n=true.

报告查询：K1 的计划占用判为未越界；K5、K6 的文本已述状态均为给定事实条件符合。

K1 比较的是计划；K5、K6 核对的是文本已述状态的支持条件。三个结果都不是设备已实际运行、工作已验收或获得执行授权的证明。RT042 的报告也没有数值预算，不能把一个假设的预算加法冒充它的计算。

这些结果之所以可比，是因为报告保留了同一事件、同一仪器、半开端点和来源条款。如果对象、否定或作用域仍有歧义，公式只能求出某一种解释下的结果，不能自动证明原文已经被正确、完整地理解。

越界、未越界、信息不全，各回答什么？ ​

边界判定关心的是方案或已给出的行为事实与任务要求的关系。界痕公开演示中的三种结果，可以这样理解：

结果与案例判断依据这项结论说明什么
越界：RT044同一轮的严格先后要求形成闭环。当前组合方案存在确定冲突，需要修改。
未越界：RT042同一设备分别占用 10—11 点、11—12 点；规则明确到点释放、允许立即接入，清场也已计入。在这些条件下，两段占用没有重叠。
信息不全：L23-050林舟和赵清都参加会议，任务却只写“由他确认”，没有唯一指代依据。最终确认人无法确定，需要补明身份。

上面的 RT042 代入过程给出 660 < 660 = false：两段计划占用不重叠。释放与无第三预约另由 K5、K6 依据原文状态核对，不能把这些结果扩展成现实执行回执。

L23-050 中，准备材料与请求澄清可以继续，最终确认人的身份仍需明确。现有文字不能因为某人的岗位更高，就替任务发出者选定他，也不能据此说已经有人违规完成了验收。责任人案例原文与计算

“未越界”只针对本次所检查的要求与材料。 它不等于工作已经完成、成果已经正确或业务批准已经取得。同样，存在未知信息也不必然阻止所有判断；如果已知费用已超过上限，而且其他费用只能增加、没有抵扣，剩余金额尚不明确也不能消除已经确定的超支。

方法、协议和工具，怎样相互支撑？ ​

7+1 方法把任务要求及其关系组织成可比较的表示；BXP 协议进一步约定表示、依据、计算和结果的处理方式；BoundaryXP 工具负责把具体任务送入这一过程，展示原文、分析、计算回执和未决问题。协议草案与工具实现各有版本，当前实现范围以项目的版本说明为准。

公开研究材料保存了 625 组任务、3,219 个任务节点和 3,469 项查询，涉及逻辑、数量、集合身份、依赖和复合约束。625 组保存结果的最终判定均与各自的现行标注一致，保存的模型整体判断也与程序汇总一致。逐项比较时，模型判断与程序结果仍有 9 项差异，包括 6 项标签编码差异和 3 项计算判断差异；另有 3 项计算因指定输入缺失而未完成。统计口径与原始记录

这些材料的作用，是让人检查方法怎样用于具体问题，冲突怎样定位，未知信息怎样影响结论。整组一致性衡量的是这些保存记录与现行标注的对应关系，不能外推为新任务准确率。

网站 11 月 14 日的复核记录还保存了摘要与分类核对、六项选定数学见证以及一个费用案例九项计算的复算结果。这些是有范围的历史复核，没有重新运行全部模型分析。本次修订沿用这些证据，并更新了产品接入信息。

怎样看报告，怎样分析自己的任务？ ​

可以先打开中文交互演示，从 RT044 开始：点任务树里的一个节点，选中一个维度，再查看相关条款和原文。这样能看到一个结论究竟对应哪些任务要求。

分析自己的任务，可以按 MCP 中文安装指南接入 Cursor 或 Codex；安装包见 npm 官方页面。截至 2026 年 11 月 16 日，公开预发行版为 0.4.0-rc.9，面向 Windows x64，提供 21 个 MCP 工具、17 项资源和本地浏览器工作台。新版增加了 L2 行业与 L3 企业自定义字典的格式说明、校验与导入功能，便于核对任务中的专业术语和内部称呼。该版支持使用当前宿主的模型分析，无需另配一把模型 API 密钥；也可以选择独立 API 模式。宿主模式仍有模型参与，不能把“无需额外 API 密钥”理解成不使用模型服务。

实际使用时，先导入完整的主任务和子任务，检查任务树，再保存并明确提交分析。报告会保留模型的解释和计算内核对受支持操作数的复核结果，二者可以分别查看。对已保存的操作数，还可以不新增模型调用地复算。打开工作台本身不会提交一次新分析。

目前公开内容包括文档、协议、论文、研究案例和编译安装包；计算内核的原始实现源码仍在独立私有仓库维护。使用报告时，也应保留它的判断范围：计算能够核验已经表达出来的问题，原文是否被完整、准确地理解仍需检查；修改计划、业务批准和实际执行，仍由相应的责任人或业务系统决定。

现在，轮到你来检查边界 ​

当任务交给一组智能体时，把各自的安排放回同一份任务，才能看出共同要求是否继续成立。界痕希望把这件事做得具体：指出是哪条要求、哪几个子任务、哪一项计算出了问题，让人能够据此修改，而不只收到一句“整体看起来可行”。

你可以从自己的任务开始：按 7+1 写下输入、交付、动作、责任、资源、版本依据、完成停止和禁止边界，再问一句：全部相关子任务合在一起时，有没有出现单独检查或两两比较时看不到的冲突？

还有几个问题值得继续追问：下载附件的保存位置未写清楚时，哪些判断应暂留未知？行业词库或企业词库更新后，旧报告要怎样保留当时的词义依据？组合方案确有冲突时，谁有权调整顺序，又怎样证明上级要求没有被悄悄改掉？子任务自行增加的更严格约束，什么时候会妨碍共同交付，又由谁决定否决或调整？

如果你遇到难以表达的真实约束，或对某个保存案例的判定有异议，欢迎带着有权公开的最小任务摘录、版本和具体疑问参与讨论。也可以先打开演示，在雷达图里选一条要求，沿着报告回到原文，亲自检查 RT044 的闭环。方法只有经得起使用者的核对与质疑，边界才会变得可靠。
