Agent 核心研究与竞品动态 · 2026-09-14 ​

当日结论 ​

本日最强的共振是：生产级 Agent 正把“调度前判断”进一步拆成可观测的实时资源、Workspace/Run 所有权、Transport 合同与恢复边界。 一个 Provider 还能连、一个 Session 还能续、一个 Tool 名还存在，都不再足以证明“这一轮可以安全执行”。

1. Yue Zhao（赵岳）/ anywhere-agents：并行调度开始读取“当前可用模型组额度”，而不是失败后才发现资源已经耗尽 ​

状态：MERGED（commit 050ee0b）

赵岳本人提交的 050ee0b 把 Agy 的 quota meter 真正接入 prun 调度。Agy 将 Gemini 与 Claude/GPT-OSS 分成两个独立额度组；此前 fan-out 不读取这份状态，真实 2026-09-11 七单元批次中，Claude 组的五小时桶耗尽后连续四个单元失败。

新逻辑在 dispatch 前读取 agent-quota.py 的 snapshot：使用一个组中最紧的 bucket 判断可用性；Claude/GPT 组为空而 Gemini 可用时自动换到 Gemini 默认模型；Gemini 为空则明确退出，不会未经授权反向升级到更贵/更稀缺的组。fallback 会写入 MODEL-FALLBACK 和实际 model ledger，不允许结果看起来像由原模型完成。它还处理了 snapshot TTL、reset time 已过、stale refresh、非有限数值与失败后强制刷新等细节。

为什么重要： 资源调度正在从“Provider 报错后再 fallback”转向 pre-dispatch live capacity admission。同时它保留“未知 ≠ 空”的语义，读不到 fresh snapshot 时不会把未知误判为拒绝。

与 CodeFlowMu/FCoP 的关系： 多模型团队不必强行抹平模型差异；应把 Role → Candidate Models → Live Capacity/Cost → Selected Model → Fallback Receipt 作为可审计调度链。EVAL/Gatekeeper 可以继续使用高价值模型，而规模化 Worker 根据实时资源分流。

值得互动：非常高。 技术切入：Would you persist the quota snapshot identity/age into each dispatch receipt so later evaluation can prove which live resource evidence selected the model?

2. OpenAI Codex：Agents Overview 已能直接创建并绑定新的 Managed Worktree Session ​

状态：MERGED（PR #45276）

PR #45276 已合入。Codex 的 Agents Overview 现在可以从项目默认分支创建新的 managed worktree，并立即启动一个空白 Session绑定到该 checkout；不会给新 Session 自动发送第一轮消息，也不会中断已有 Agent。

值得注意的不是快捷键本身，而是边界处理：默认分支来自缓存的 remote HEAD，必要时才回退到 main/master；保留源 checkout 的本地编辑；继承已选择的 approval reviewer；Session 启动失败时，clean 且未认领的 worktree 会清理，已经需要保留的 checkout 则把路径明确报告给用户；创建期间还会暂停冲突动作，并在 reconnect 后清掉 pending creation state。

为什么重要： Codex 的“Agent 概览”正在从 Session 列表升级成 Workspace + Session 生命周期管理面。Thread/Session 和 Worktree 开始结构化绑定，而不是由用户自己在外部 Git 命令里拼接。

与 CodeFlowMu/FCoP 的关系： 对多角色房间/Branch TASK 很有参考价值：Workspace Creation → Session Binding → Approval Context → Ownership/Cleanup 应是同一事务，但 Conversation history、Workspace identity 与授权继承仍应分别记录。

值得互动：高。 技术切入：Will managed-worktree creation eventually emit a durable lineage receipt binding source revision, new checkout identity, thread ID and inherited approval context?

3. AG2：MCP Server 的 HTTP Transport 开始成为“运营者自己的合同”，而不是悄悄继承依赖包默认值 ​

状态：DRAFT / OPEN（PR #3252）

Draft PR #3252 暴露了一个很重要的 MCP 运行边界：AG2 过去自己创建 streamable-HTTP session manager，却只允许配置 stateless 和 json_response，其余安全/生命周期行为由安装的 mcp 版本默认决定。

新 TransportConfig 提议显式拥有：MCP session idle timeout、max sessions、request body size、transport security、SSE retry interval 和 event store。它同时引入可选的 RFC 8707 token resource 校验，使一个为其他服务签发的 bearer token 不能直接用于当前 Agent Server。event store 则让断线客户端可以用 last-event id 恢复错过的事件。

作者特别指出：AG2 原先没有 DNS rebinding protection，而且运营者没有入口启用；mcp 2.2.0 又在同一个 2.x 范围内改变了 session timeout/cap 默认值，这意味着两个看似安装“同一 AG2 版本”的部署可能因为依赖小版本不同而出现不同 Runtime 行为。

为什么重要： 这是典型的 Dependency Default ≠ Product Contract。长期 Agent 的 timeout、session cap、resumability、host/origin policy 都应被产品自己固定并可审计。

与 CodeFlowMu/FCoP 的关系： Host 准入不应只测“能不能连 MCP”，还要读取/验证 Transport contract：session lifetime、body limit、origin/host policy、event replay、token audience/resource binding。

值得互动：非常高。 技术切入：Would you expose a transport-contract digest in server metadata so clients can bind resumability/security assumptions to the exact runtime configuration they connected to?

4. Paperclip：Clean-machine 安装验收已把“API key 用户”和“本地 CLI subscription 用户”拆成不同准入路径 ​

状态：MERGED（PR #13372）

PR #13372 来自一个真实 nightly release gate 失败：全新 Docker 环境在 Onboarding 的 “Connect a model” 步骤卡死。API key 已经被 Provider 实时验证为有效，但 managed adoption 仍强制要求本地 Claude CLI hello probe；干净机器没有 CLI，因此用户无法完成第一位 Agent 的 hire。

合入后的语义更精确：api_key binding 在 adoption 时再次调用 Provider live endpoint 验证，不再强制要求本地 CLI；subscription 路径仍保留严格 hello probe。Paperclip 还为 release smoke 做了本地 HTTPS provider mock，只开放 GET /v1/models，其他 endpoint 全部 404，从而可以验证“安装包在 Provider 接受 credential 时确实能完成 onboarding”，又不把真实付费凭证塞进 CI。

为什么重要： 这是安装交付成熟度的实质提升。一个真正可交付的数字员工产品不能把“Provider credential 有效”和“本机安装了对应 CLI”混成同一准入条件。

与 CodeFlowMu/FCoP 的关系： Host/Provider admission 应拆分为 Credential Validity、Required Local Runtime、Selected Execution Lane 三个事实。不同 lane 只能验证自己真正需要的依赖。

学习：非常高｜竞争风险：很高｜雷达判断：Paperclip 继续维持最高优先级，安装/首次运行成熟度上调。

值得互动：高。 技术切入：Will onboarding eventually publish the selected execution-lane identity so later runs can prove whether they were admitted through API-key direct execution or a local subscription CLI?

5. Paperclip：@mention 心跳 Run 可能把“别人的 Run”写成当前 Issue 的执行锁 ​

状态：OPEN / NOT SAFE TO MERGE YET（PR #13374）

PR #13374 记录了一个很典型的多 Agent ownership bug：Issue 分配给 Agent B，但评论里 @mention Agent A 后，A 会启动 heartbeat run，且 contextSnapshot.issueId 指向该 Issue。如果此时 B 的 assignee wake 到来，旧逻辑可能把 A 的 Run 误认成该 Issue 的 active execution lock，把 A 的 runId 写进 executionRunId，从而阻塞真正的 B，最长约 30 分钟。

候选修复的核心是：legacy run 只有在 legacyRun.agentId === issue.assigneeAgentId 时才能被收养为 execution lock，并把同一条件放进数据库 update predicate，防止并发 reassignment 绕过检查。

但当前 PR 还不能视为完成。review 已指出它附加的 10 分钟 stale-lock sweep 可能直接清锁而绕过 deferred-wake promotion，反而把后续工作永久留在 stranded 状态；同时缺少针对 ownership/race 的自动回归测试。因此只能把它当作真实事故证据和正确 ownership 方向，不能把整个 patch 当成成熟修复。

为什么重要： context points to issue 绝不等于 run owns issue。跨 Agent 的 comment/watch/mention 很容易把“观察关联”误当成“执行所有权”。

与 CodeFlowMu/FCoP 的关系： 多角色之间的 TASK/REPORT/提醒必须明确区分 Referenced Object、Responsible Role、Execution Owner、Wake Recipient。任何 lock/adoption 都必须以 Owner identity 为硬前置，而不是仅凭关联 ID。

学习：非常高｜竞争风险：高｜雷达判断：提高 Paperclip cross-agent ownership / deferred-wake recovery 的观察权重。

值得互动：非常高。 技术切入：Now that subagents are first-class in the UI, will their parentage also become a durable execution/audit identity rather than only a presentation hierarchy?

7. OpenAI Agents SDK Python：clear_session() 清掉历史后，旧 Response/Compaction Chain 仍可能“穿回来” ​

状态：OPEN（PR #5000）

PR #5000 修复 OpenAIResponsesCompactionSession.clear_session：过去虽然底层 history 已清空，_response_id 与 _last_unstored_response_id 仍保留；后续 run_compaction 可能继续把这个旧 response id 传给 responses.compact，等于在“已清 Session”之后恢复引用被删除的 conversation chain。

候选修复让 clear_session 像此前的 pop_item 一样，同时失效 _response_id、_deferred_response_id、_last_unstored_response_id，包括 failed acknowledgement path。

为什么重要： “删除历史”不能只删 visible items；所有能够把未来操作重新连接到旧世界的 continuation pointer / deferred pointer / response-chain identity 都必须一起失效。

与 CodeFlowMu/FCoP 的关系： Reset/Archive/Forget/撤销操作应该拥有明确的 generation barrier。旧 checkpoint、provider continuation、pending retry、approval reference 只要仍能跨过 barrier，就不是真正的清除。

值得互动：高。 技术切入：Would it be safer to model session clear as a monotonic generation change so every continuation pointer carries the generation it belongs to and fails structurally after reset?

跨项目共振 ​

本日可以归纳成一条很清楚的工程趋势：

长期 Agent 正从“保存状态”转向“保存带身份、时效、所有权和资源证据的状态”。

赵岳把 live quota snapshot 放到 dispatch 前；Codex 把 Worktree 与 Session 正式绑定；AG2 准备固定 MCP Transport 的安全与生命周期参数；Paperclip 把 Credential lane 与 CLI lane 分开，并暴露 cross-agent execution ownership bug；Agents SDK 则证明 reset 必须切断 continuation chain。

对 CodeFlowMu/FCoP，可以进一步固定这一链：

Work/Run Identity → Workspace Identity → Responsible Owner → Live Capability/Capacity Evidence → Transport/Provider Contract → Call-time Admission → Effect → Settlement / Generation Barrier。
