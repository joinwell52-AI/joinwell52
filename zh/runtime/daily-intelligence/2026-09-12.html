当日结论 ​

本轮最强的共振是两条线同时加速：一方面，Project / Channel / Mobile 正成为长期 Agent 的正式控制面；另一方面，历史 Session、旧 Provider、旧 Sandbox 状态和旧 Approval 都不能自动继承执行权，必须在真正执行前重新证明。

1. Cursor Projects：协调器 + 千级 Subagent + 月级上下文 + 订阅触发正式进入 Beta ​

状态：BETA / OFFICIAL RELEASE（官方 2026-09-10 发布，本轮补录）

Cursor 官方发布 Projects。Project 用来承载 feature、migration、完整应用等大型工作体，长期保留上下文，由一个 coordinator agent 规划和分派任务；协调器本身不写代码，而是创建并管理多个实现 Agent，可按工作量并行扩展到大量 subagent。

Projects 运行在独立 Cloud computer 上，用户合上笔记本后仍可继续；需要在本机测试时，协调器会启动 local agent。Project 还维护跨云端和本机同步的共享文件上下文，并支持订阅 Slack、Schedule、PR 等信号，触发无需再次提示的持续工作。

为什么重要： 这不是普通 Coding Agent 功能，而是把长期工作对象、协调器、并行 Worker、多 Host、共享上下文和定时/事件触发组合成一个正式产品形态。

与 CodeFlowMu/FCoP 的关系： 它与 CodeFlowMu 的 PM + 多角色/多 Agent + 长期工作 + Cloud/Local Host 路线高度重叠。区别在于，Cursor 当前强调 coordinator + shared context，而 CodeFlowMu 更应继续强化责任角色、授权边界、EVAL 独立性、可恢复事实和 FCoP 协议证据。

学习：非常高｜竞争风险：非常高｜雷达判断：Cursor Projects 应作为最高优先级外部参照。

值得互动：非常高。 技术切入：当同一 Project 有数百/数千 subagent 跨 cloud/local 执行时，共享上下文的写入归属、冲突收敛、权限继承和 compaction provenance 如何被证明？

2. Yue Zhao / anywhere-agents v0.8.0：用不同模型承担不同岗位，并立即修正 Windows Sandbox 现实边界 ​

状态：RELEASED v0.8.0 + POST-RELEASE FIX

Yue Zhao 发布 anywhere-agents v0.8.0。本版最值得关注的不是单一 Skill，而是明确的模型岗位分工：prun 将更大比例的并行执行单元交给 Agy/Sonnet，Codex 则保留为 /vet gatekeeper，理由之一是 bulk fan-out 的当前成本不合适。Agy 单元支持 scratch / throwaway clone、--continue-from 后续轮次以及 quota 监测；发布说明也明确记录 Codex 的 gatekeeper 位置。

发布后赵岳本人又提交 Windows 修正：此前 dispatch-task-agy.py 对每个单元传 --sandbox，Agy 的 exebox 会为每个 shell 单元触发 UAC elevation；现在默认不再请求该 sandbox，改为显式 PRUN_AGY_SANDBOX opt-in。文档同时把这种运行边界明确表述为 structural containment，而不是 enforced isolation；无 sandbox 的 live probe 中 shell、web fetch 和 file write 都可成功。

为什么重要： 这同时给出两个非常现实的工程判断：模型差异可以通过岗位/成本/能力路由处理；但“声明有 sandbox”若在真实 Host 上造成不可接受的运行副作用，就必须把隔离强度重新写成事实，而不能假装仍有强隔离。

与 CodeFlowMu/FCoP 的关系： 对 PM/DEV/QA/EVAL 的模型选择，可以考虑“角色所需能力 + 成本 + 独立性”的显式路由，而不是让所有岗位用同一种模型。同时 Host capability record 应区分 structural containment 与真正 enforced sandbox。

值得互动：非常高。 技术切入：是否考虑把 role/model routing 和当前 isolation strength 一并写入可审计的 execution receipt，让 /vet 能判断一次结果是在何种模型与隔离强度下产生的？

3. OpenAI Codex：长期 Thread 不再拥有静态 Provider/Host/Sandbox 权力 ​

状态：MERGED / MERGED / MERGED

Codex 连续合入三项高度相关的控制面修复：

  • #44944：已有 app-server thread 在 turn start/steer、review、compaction、manual queue start、active goal update 前，都重新检查当前 managed model_provider / model_providers 要求；若要求无法读取或旧 provider 已不匹配，则拒绝继续，并提示重启。
  • #44939：Windows sandbox setup 必须尊重实际 execution host；本地 TUI 不得配置 remote executor 的 sandbox，remote server 自己拥有 permission selection。混合 local/remote executor 会显式警告。
  • #44945：Windows sandbox setup 统一交由 app server；Agent mode 启用前必须验证 effective sandbox mode。若 setup 请求超时或响应丢失，状态保持 pending、输入保持锁定，而不是猜测成功；reconnect 后对中断 setup 给出 restart 语义。

为什么重要： Thread still exists、provider used last time、TUI says setup started 都不再构成当前执行授权。Provider、execution host、sandbox readiness 被重新定义为 live admission facts。

与 CodeFlowMu/FCoP 的关系： Host 接入与恢复最好绑定 Thread/Run Identity + Provider Identity + Execution Host Identity + Effective Sandbox Capability + Policy Revision，而不是只恢复 session_id。

值得互动：非常高。 技术切入：这些检查是否会最终收敛为一个 executor capability/authority digest，并在每次 resume/turn/approval 前统一验证？

4. Paperclip：iMessage 正被做成数字员工的耐久远程指令/交互通道 ​

状态：DRAFT / EXPERIMENTAL / 未完成 live qualification

Draft PR #13299 新增 experimental iMessage Photon。目标是一名 Agent 对应一个稳定的 Photon Cloud number，让真人可以从 Apple Messages 启动任务、发送照片、回答 pending question；DM 和 group 都复用既有 channel admission、identity links、task generations、publication 与 interaction continuation。

设计不仅是“接一条聊天消息”：它保存 immutable text/file send identity、upload receipt、poll/option ID、per-person draft、canonical interaction continuation proof，并用 leased receiver + checkpoint 处理恢复；媒体还覆盖 HEIC/HEIF、JPEG preview 和 Live Photo companion video。

当前边界也写得很清楚：没有 live Photon credentials / test participants，真实 iPhone DM/group、媒体、poll/text continuation、restart 与 ambiguous-send qualification 都还没跑，因此 PR 保持 Draft / experimental。

为什么重要： 数字员工远程端正在从 Web/PWA 向真正的日常 IM 入口移动，而且正确路线不是“聊天机器人”，而是把 sender identity、任务代际、继续执行和发送结果都做成耐久事实。

学习：非常高｜竞争风险：很高｜雷达判断：Paperclip 继续维持最高优先级，并新增“IM 远程控制通道”专项。

值得互动：非常高。 技术切入：iMessage 中的批准/回答是否会形成 typed human-action receipt，绑定 sender identity、task generation、question/effect digest，而不是仅把文本继续喂回 Agent？

5. Paperclip：一次 call-time authorization 强化尝试被主动关闭，暴露“全局 fail-closed”兼容性边界 ​

状态：CLOSED / NOT MERGED / NOT DEPLOYED

PR #13297 原本试图把 approval-governed remote HTTP MCP 的最终授权移动到所有异步准备完成之后、provider 第一次真实操作之前：使用 PostgreSQL time 判断过期边界，原子消费 request/invocation/audit disposition，并阻止 approved provider call 收到 HTTP 401 后做 credential-refresh + redispatch。目标安全属性包括：permit 成功后到 HTTP write 之间不再 await；一个 approval 最多产生一次 provider operation；结果丢失保持 uncertain，绝不自动 replay。

但该 PR 最终由作者关闭，没有 merge 或 deployment。原因不是核心 focused proof 不工作——71 个 PostgreSQL 定向测试通过——而是新的 provider-wide 限制会让 legacy、Test-tab、local-stdio/built-in 等现有 ask-first 路径失效；上游 CI 出现 12 个 server failure，3 个 E2E shard 也冲突，因此按 bounded rollout stop condition 停止。

为什么重要： 这是一个非常有价值的失败样本：call-time authorization 不能简单在“所有 Provider”前放一个统一拒绝器。不同 transport / provider path 的单次副作用、重试、状态性和审批语义必须先被明确建模。

与 CodeFlowMu/FCoP 的关系： Host/Tool authorization 最好采用 per-effect-path contract，明确哪些路径可做到 single-dispatch、哪些只能 fail closed、哪些需要 compensation，而不是只用一个全局 allow/deny 开关。

学习：非常高｜竞争风险：高（复杂性风险）｜雷达判断：不下调 Paperclip；反而证明其正在真实碰撞生产授权边界。

值得互动：高。 技术切入：下一版是否会按 transport/provider capability 分层实现 final permit，而不是让不满足 single-dispatch 合同的旧路径一起被全局拒绝？

6. Superset：Agent 状态正式进入 iPhone Lock Screen / Dynamic Island ​

状态：MERGED（需要下一次原生构建/TestFlight；非 OTA）

PR #7452 已恢复并合入 iOS AgentActivity Live Activity：Lock Screen 最多展示四个 Agent 行，Dynamic Island 展示 Agent 数量和 elapsed time，并提供 per-row deep links 与多语言支持。

这里最重要的产品信号不是卡片样式，而是 Agent fleet state 已经进入操作系统级移动端状态面。不过当前限制同样重要：这是 native extension，必须通过下一次 TestFlight/preview build；更新仍以 foreground 为主，App 关闭后卡片会很快 stale，Dynamic Island 也停留在离开前的 snapshot，因此它还不是完整的 push-driven 远程监工面板。

学习：非常高｜竞争风险：高｜雷达判断：Superset 已经非常接近主雷达，移动端权重继续提高。

值得互动：高。 技术切入：下一阶段是否会用 server push / ActivityKit remote update 把 review、permission、failed 等 typed state 持续送到 Lock Screen，并直接连接审批 receipt？

7. Orca：DST 回拨可让一个 Automation 每分钟重复拉起 Agent，暴露 occurrence identity 缺失风险 ​

状态：OPEN

PR #20179 修复一个非常典型的 scheduler 事故：秋季 DST fall-back 的重复小时内，cron 的“下一个 occurrence”可能算回刚刚执行过的同一个 instant，于是 scheduler 每约 60 秒重新启动一次 Agent；在 new_per_run 模式下，每次还会创建新 worktree 并继续消耗 token。

根因是 floorToMinute 用本地 wall-clock field 重组时间，歧义分钟可能解析为较早 offset，使“strictly after”合同被破坏。修复改为 UTC arithmetic，并补真实 America/New_York 2026 fall-back 回归测试：重复小时中的两个合法 occurrence 各执行一次，spring-forward 的不存在分钟仍跳过。

为什么重要： 这是自动化系统里最危险的一类错误：轨道机时间算法错误会直接物化成重复 Agent、重复 worktree，进一步可能成为重复外部副作用。

与 CodeFlowMu/FCoP 的关系： Schedule occurrence 应拥有独立、持久化的 idempotency identity，例如 (schedule_id, intended_occurrence_instant)；即使 scheduler 算法回归，也不能因为 tick 再次命中就创建第二份业务 effect。

学习：非常高｜竞争风险：中高｜雷达判断：继续提高 Orca Automation Runtime 权重。

值得互动：非常高。 技术切入：是否考虑把每个 scheduled occurrence 的 identity 持久化成全局幂等键，使 DST/时钟/重启错误最多造成重复 wake，而不能造成重复 business run？

跨项目共振 ​

本轮出现了一个更清楚的分层：

Control Surface 可以越来越丰富，但 Authority 必须越来越窄、越来越接近真实 effect。

Cursor Projects、Paperclip iMessage、Superset Lock Screen 都在扩张数字员工的控制面；与此同时，Codex 把 Provider/Host/Sandbox 从历史 Thread 中抽离出来重新验证，Paperclip 的失败 rollout 又证明 final authorization 必须理解具体 transport 的副作用合同，Orca 则证明 Schedule 本身也必须有 occurrence identity。

对 CodeFlowMu/FCoP，可以把这一链条继续固定成：

Control Surface / Trigger → Human or System Principal → Work/Run Identity → Live Host & Capability Evidence → Call-time Authority → Effect Identity → Settlement / Replay Eligibility。

另外，Yue Zhao 的 v0.8.0 给出了一个很实际的组织层启发：模型差异不必抹平，可以把模型当成岗位资源，由角色边界、成本、能力与独立性决定谁做 fan-out、谁做 gatekeeper。
