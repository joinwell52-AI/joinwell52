当日结论 ​

今天最强的共同信号是：“恢复同一会话”正在被拆成更精确的执行合同：当前 Host、当前 Turn 的环境快照、当前 Provider outcome、当前 Reviewer authority、当前 Credential namespace 与当前 Workspace branch 都需要分别证明。 长期 Agent 可以保留上下文，但不能因为 Session 仍然存在，就自动继承旧 Host、旧审批、旧 Credential 或旧工作分支的执行权。

1. Kazuhiro Sera / OpenAI Agents Python：v0.22.3 正式发布，Conditional Approval 开始对“审批时看到的参数”和“实际执行参数”做一致性约束 ​

状态：RELEASED · v0.22.3（2026-09-18 Asia/Shanghai）

Kazuhiro Sera（seratch）发布了 OpenAI Agents Python v0.22.3。这次 patch release 的核心不是新增 API，而是把一组执行边界修得更严格：

  • Conditional approval 只有在参数准备后仍能证明“审批所检查的值”与“Python Tool 实际会执行的值”一致时，才调用 callable approval policy；如果 defaults、coercion、application model、custom validation、regex/plugin 等让输入发生不可安全比较的变化，则改为人工审批，而不是用 raw arguments 做决定后执行另一组值。
  • Server-managed resume 保留本地已经产生但尚未送达的 tool-not-found output，避免恢复时漏交或错误重复。
  • SQLite / AdvancedSQLiteSession 修复并发初始化、branch identity、历史 tool usage 等持久化边界。
  • Windows host 的 sandbox command path 保持 POSIX 语义；早期关闭 Codex event stream 会正确回收 subprocess。
  • 文档明确 Unix-local 边界：Linux 不增加 OS command confinement；macOS filesystem restriction 也不等于 network isolation。

为什么重要： Approval 的对象必须是最终将产生 Effect 的那组规范化输入，而不是 UI/Decorator 最早看到的字符串。另一方面，Session resume 也必须区分“结果已产生、已持久化、已交付、已消费”。

与 CodeFlowMu/FCoP 的关系： ADMIN/QA/EVAL approval receipt 应绑定规范化 Effect/Arguments 与 policy revision；如果执行前参数经过 transform，旧 approval 不应继续有效。

值得互动：非常高。 技术切入：Will approval receipts eventually bind the prepared/normalized argument digest so a resumed or transformed tool call can prove it is executing exactly what was approved?

2. OpenAI Codex：Running Turn 冻结自己的 Environment Snapshot；Provider Gateway Credential 获得独立 OAuth 生命周期 ​

状态：#46310 MERGED；#46318 MERGED

Codex #46310 让环境选择变化只影响下一 Turn。运行中的 Turn 继续使用自己已经激活的 environment snapshot 与 MCP workspace roots；用户在这一 Turn 中切换 remote/local environment，只会保存为 future selection，不能把正在执行的 Tool 或 pending setup 半路重定向。Manual compaction 也会先停止当前 task，再采用新的 environment。

随后 #46318 为 model-provider gateway 增加完整 OAuth credential manager：PKCE browser sign-in、loopback callback、过期/拒绝后的 refresh、跨进程串行化 token exchange/persistence，以及独立 encrypted namespace + 独立 keyring key。更关键的是，refresh rotation 在 caller cancellation 后仍会完成保存；save 失败的 rotated credential 会保留为 pending。实现还明确要求：Credential refresh 以后，调用方仍必须自己判断原请求是否安全 replay。

为什么重要： 配置改变和 Credential 更新都不能偷偷改变当前 Effect 的身份。Turn 应拥有 frozen execution context；Credential refresh 只解决“下一次用什么 Credential”，不能自动授予“重发上一次 Effect”的权力。

与 CodeFlowMu/FCoP 的关系： 可以进一步固定：Turn/Run Generation → Environment/Host Snapshot → Credential Identity → Effect Identity → Replay Eligibility。

值得互动：高。 技术切入：Will the active environment snapshot and provider OAuth credential generation become part of a single execution-context digest attached to tool/effect receipts?

3. Paperclip：Named Agent Reviewer 已成为一条正式、窄授权、可恢复的 Review Handoff ​

状态：#13581 MERGED

Paperclip #13581 修复了 native child task 请求另一名 Agent reviewer 时的正式协作路径。此前 reviewer wake 会被“不是 assignee / 不持有 execution lock”拒绝，child 留在 review，parent 也一直等待。

现在 reviewer admission 会绑定精确的 company、issue、source run、decision、revision、addressee 与 resolver policy。Reviewer 只获得读取 child context / history / documents 与 resolve_review 的窄控制面；child 原 assignee 不变。Reviewer run、durable wake 与 child execution lock 必须在同一个 transaction 中 claim；存在竞争 lock 时 Provider 不启动。只有当前 Running reviewer session、当前 issue lock、精确 card/decision 才能 resolve；stale、reassigned、unrelated review 一律拒绝。

接受或拒绝的 review outcome 会作为 parent continuation evidence，但不因此改变 issue ownership，也不授予其他 Tool authority。项目还补齐 durable reviewer wake、stale-card / abandoned-run recovery 和 duplicate wake 防护，并用 Codex/Claude 做了 live review-handoff checks。

为什么重要： “Reviewer 是另一 Agent”终于不是聊天层概念，而是正式的 responsibility / authority object。

与 CodeFlowMu/FCoP 的关系： 这与独立 EVAL / QA 非常接近：Review 可以进入 parent 的证据链，但 Reviewer 的裁决权应被限定到指定 review object，不应借 review 身份获得普通 TASK mutation 权。

学习：非常高｜竞争风险：很高｜雷达判断：Paperclip 继续最高优先级。

值得互动：非常高。 技术切入：Will reviewer assignment eventually carry a durable evaluator identity/model boundary so a review receipt proves not only which agent resolved it, but which independent evaluation channel produced the decision?

4. Paperclip：真实 Run JWT 已在 /proc/<pid>/cmdline / ps 中被捕获，Credential isolation 出现高价值安全事故 ​

状态：#13572 OPEN / NOT MERGED

Paperclip #13572 记录了一个真实 credential exposure：系统在每次 Agent Prompt 中教授 curl -H "Authorization: Bearer $PAPERCLIP_API_KEY" ...。Linux 上 /proc/<pid>/cmdline 与 ps -ww -eo args 可以让同 Host、同 UID 的其他进程在 curl 存活期间读取 argv。项目用持续 /proc sampler 实际捕获到了工作中 Agent 的真实 Run JWT，这不是理论风险。

当前 Run JWT 又没有可用于提前 revoke 的 jti / denylist，因此候选修复选择 prevention：把 Authorization header 从 argv 移到 stdin（curl -H @-），同时修改 Prompt template、多个 Adapter、Skills 与 artifact-upload 路径，并加入先证明 detector 能抓到泄漏、再证明修复路径 0 hit 的 RED/GREEN 回归测试。

PR 仍未合入，而且仓库里还有若干 pinned skill snapshots、scripts、workflow/docs 示例尚未纳入本修复，所以不能写成“已经解决”。

为什么重要： Environment variable 本身不是 Credential isolation；Agent 学到的命令模式也会改变 Secret 的实际暴露面。

与 CodeFlowMu/FCoP 的关系： Host 准入除了检查“Secret 是否以 env 注入”，还应检查 Tool/Prompt 是否把 Secret 复制到 argv、日志、shell history、checkpoint 或 persisted session。

学习：非常高｜竞争风险：很高｜雷达判断：提高 Credential Projection / Host Co-tenancy 权重。

值得互动：非常高。 技术切入：Would Paperclip move from denylisting unsafe examples toward an allowlisted credential-transport primitive so agents never need to construct bearer headers themselves?

5. Paperclip：Durable exe.dev VM 把“Run 生命周期”和“Environment 生命周期”正式拆开 ​

状态：#13575 OPEN / EXPERIMENTAL / OFF BY DEFAULT

Paperclip #13575 增加实验性的 durable exe.dev environment：一个 environment 绑定一个持久 VM，而每个 Agent/Workspace Run 使用独立可复用 lease。Run 结束或取消不会删除 VM 与磁盘；Task-scoped directory 可跨 Turn 保留，native runner 通过预构建、固定 digest 的 Linux image 与 provider pack 运行。

当前验证相当深入：8 leases / 64 concurrent commands、SSH loss、disk continuity、timeout、cancellation isolation、escaped descendants、private HTTP、VM reboot 等 14 项 live stress checks；另有 27 个 paid browser cases 和多种 provider compatibility / recovery / warm-session 检查。但项目也明确写出边界：同一 VM 上的 Agents 必须互相信任，目录与 systemd cgroup 不是 tenant security boundary；没有 autosleep / HTTP wake 保证；实验默认关闭，没有 production rollout。

为什么重要： 数字员工工作站开始从“每次任务开一个临时 Sandbox”走向“长期 Environment + 短期 Run Lease”。这更接近真正长期数字员工。

与 CodeFlowMu/FCoP 的关系： 多 Host 可以借鉴 Environment Identity ≠ Run Lease ≠ Workspace Identity。持久 Host/VM 上的状态可跨 Run 保留，但每一轮 execution authority 应重新 claim；缺失或被替换的 VM identity 必须 fail closed。

学习：非常高｜竞争风险：很高｜雷达判断：Paperclip 的 multi-host / durable-workstation 权重继续上调。

值得互动：高。 技术切入：Will durable VM identity, image digest, workspace lease and provider-pack digest be bound into one run receipt so recovery can prove which long-lived environment actually executed the effect?

6. Orca：Host-scoped Resume、显式 Provider Outcome 与 14,000 Desktop Fleet 的真实控制面压力，共同指向“Session ≠ Run ≠ Host” ​

状态：#21288 OPEN；#21278 OPEN；#21303 MERGED

Orca 今天三条变化放在一起非常有价值：

  • #21288：真实问题中，一个在 Host A 创建的 provider session ID 被拿到 Host B 上执行 resume，Host B 根本没有对应 transcript，最终报 “No conversation found with session ID”。候选修复要求 resume issuer 先检查 execution-host provenance；若记录明确属于另一 Host，则拒绝 resume 并保留证据。对无法正证明 host mismatch 的旧记录仍保持 fail-open，作者没有伪造未知 provenance。
  • #21278：structured turn 的 lifecycle {state:"completed"} 过去同时覆盖成功与 Provider error。候选增加独立 outcome: success | failure | cancellation；旧记录或无法确认的情况 outcome 缺失即 UNKNOWN，绝不能解释成 success。Lifecycle 只表示 Host 看到了 Turn 结束，Provider outcome 是另一事实。
  • #21303 已合入，来自约 14,000 Desktop 的 production fleet：每台每 30 秒写一次 lease heartbeat，约 470 个独立 DB writes/s，造成 5–12 秒 fleet stall，手机 pairing 失败和 Desktop reconnect。现在 relay cell 每秒批量更新最多 200 个 lease，并用 FOR UPDATE ... SKIP LOCKED 跳过单个 contended host，避免一个锁阻塞整个 cell。

为什么重要： Session ID 不是 Run ID，也不是 Host identity；“Turn 已结束”不是 Provider 成功；fleet 心跳也不是普通后台指标，而是影响远程控制可用性的核心 Runtime contract。

与 CodeFlowMu/FCoP 的关系： 多 Host/房间线可以明确拆成 Provider Session Alias → Canonical Run → Execution Host → Lifecycle → Provider Outcome，并让每个字段有独立证据来源。

学习：非常高｜竞争风险：中高｜雷达判断：继续提高 Orca 的 multi-host / settlement / fleet-control 权重。

值得互动：非常高。 技术切入：Do you plan to make canonical runId the common foreign key for host provenance, provider outcome, delivery settlement and replay eligibility, with provider session ids remaining aliases only?

7. OpenHands：Agent Profile 的 Tool 权限开始由 Server 实时 Catalog 决定，而不是 UI 硬编码 ​

状态：#17516 OPEN / NOT MERGED

OpenHands #17516 正把 Agent Profile 的 Tool selection 从 Canvas 硬编码列表迁移到 Server-authoritative catalog。过去 UI 因为 Server 无法回答“当前可运行工具有哪些”，只能维护自己的 curated list；现在依赖新的 Software Agent SDK endpoint GET /api/tools/catalog，由 Server 提供 runnable catalog 与 materialized effective tool set。

UI 的 Standard tools 将显示 Server 实际解析后的集合，Choose tools 也只从可运行 catalog 中选择；retired 但已存储的 tool 不会静默丢掉，而会保留可见。能力通过 tool_catalog_v1 capability gate：旧 Server 不支持时，UI 隐藏 picker，而且保存时不发送 tools 字段，避免旧 Client/Server 组合误改权限。

当前 PR 仍依赖尚未发布的 software-agent-sdk PR，因此功能在 SDK 发布前有意保持隐藏。

为什么重要： UI 不能自己发明 Runtime capability。Tool 权力的事实源应是 Server/Host 当前可运行能力，再由 Profile 做授权投影。

与 CodeFlowMu/FCoP 的关系： Host 准入完成以后，UI、Worker、PM/EVAL 都应该投射同一份 Detected Capabilities → Adopted Capability Set，而不是各自维护工具列表。

值得互动：高。 技术切入：Will the effective tool set carry a catalog revision/capability digest so a long-lived profile can detect when its stored grant references a tool whose runtime semantics changed?

8. Superset：Cloud Workspace 获得独立工作分支，手机创建 Cloud Workspace 时的图片也能进入远端 Sandbox ​

状态：#7620 MERGED；#7622 MERGED

Superset #7620 修复 Cloud Workspace 直接站在 base branch 上工作的问题。现在控制面同时保存 baseBranch 与 workspace working branch，工作分支统一采用 superset/<slug>-<id8>，多 repo workspace 的各 checkout 使用同一个逻辑工作分支；PR target 仍指向 base。这样 Agent 不再默认直接在 main 上工作，Control Plane 记录的 branch 也和 Box 真实 checkout 对齐。

随后 #7622 打通了手机创建 Cloud Workspace 时的图片附件：图片先进入 Cloud storage，file IDs 随 launch 进入 Sandbox；host-service 启动后再下载并 materialize 到本地 attachment store，最后通过和其他 Host 相同的 # Attached files prompt block 交给 Agent。失败下载不会阻止主 Prompt 启动。

需要保留边界：两个 PR 的描述都明确说，在提交/早期验证阶段尚未完成真实 Box 的完整 E2E；代码已合入，但不能把“所有 production cloud box 场景已验证”当成事实。

为什么重要： Superset 的 Cloud Workspace 正在形成独立 Workspace Identity、Branch Identity 和跨手机/Cloud 的 Artifact transport，而不只是“远端开一个终端”。

与 CodeFlowMu/FCoP 的关系： 多 Host 设计中可以借鉴：Workspace 不是 Base Repository；上传的 Artifact 也不应依赖目标 Host 在用户点击发送时已经存在。

学习：非常高｜竞争风险：非常高｜雷达判断：Superset 继续主雷达；提高 Cloud Workspace identity / mobile artifact handoff 权重。

值得互动：高。 技术切入：Will workspace branch identity and attachment materialization both be included in a launch receipt so the first Agent turn can prove which base revision and exact uploaded artifacts it actually received?

跨项目共振 ​

今天可以把共同方向压缩成一条：

恢复的是 Context；重新证明的才是 Authority。

OpenAI Agents 把 approval 对象收紧到规范化输入；Codex 把 running Turn 的 Environment snapshot 冻结，并单独治理 Provider OAuth；Paperclip 把 Reviewer role、Run JWT 与 Durable Environment 拆成不同边界；Orca 把 Provider Session、Run、Host、Lifecycle 与 Outcome 拆开；OpenHands 让 Tool capability 回归 Server 事实源；Superset 让 Cloud Workspace 的 Branch / Artifact 进入明确的启动合同。

对 CodeFlowMu/FCoP，一个越来越稳的执行链是：

Work/Run Identity → Current Task/Turn Generation → Workspace/Branch Identity → Execution Host & Capability Snapshot → Principal/Credential Projection → Reviewer/Approval Authority → Effect → Provider Outcome / Settlement → Replay Eligibility。

这里任何一项发生变化，都不能仅凭“还是同一个 Session”自动继承旧权力。
