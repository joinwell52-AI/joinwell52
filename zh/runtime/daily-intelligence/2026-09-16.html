Agent 核心研究与竞品动态 · 2026-09-16 ​

当日结论 ​

今天最强的共同信号是：长期 Agent 的“当前执行上下文”正在变成需要独立证明的对象。 模型额度、执行 Host、Sandbox、插件权限、Guardrail 结论、凭证、Workspace 位置、移动端请求代际，都不能因为 Session 仍在或历史记录仍在，就被默认为仍然有效。

1. Yue Zhao（赵岳）/ anywhere-agents：从“额度耗尽再失败”推进到实时配额均衡；完成的 Review 遇到晚到 503 也不再被简单丢弃 ​

状态：COMMITTED TO MAIN / COMMITTED TO MAIN

赵岳本人在 anywhere-agents 连续提交两项很有价值的运行治理修改。

第一项是 91c64c1。9 月 15 日一次 198-unit prun 在 63 分钟内消耗了 Agy Gemini 五小时额度 77 个百分点，而 Agy 的第二组额度——claude-sonnet-4-6、claude-opus-4-6-thinking、gpt-oss-120b-medium——完全没有使用。现在，未显式指定模型的 unit 会在 dispatch 前读取两个 quota group 的 snapshot，并在另一组至少多 15 个百分点、且关键窗口信息完整时，路由到额度更宽裕的一组；每个 unit 独立决定，因此同一批次可以随着实时额度变化切换组。系统同时留下 MODEL-BALANCE 和实际执行模型记录；如果用户显式指定了模型，则不进行这种自动均衡。

第二项是 a566f92。9 月 15 日四次 /vet Agy Review 都已经在最终 result event 中产生了完整 Review，但随后服务端返回 UNAVAILABLE 503，旧 dispatcher 因 terminal status 不是 SUCCESS 而把四份 Review 全部丢弃。现在，只有同时具备当前 round marker、独立 Verification status 和 commit verdict 的结果才允许作为 recovery candidate 发布；同时写入 backend-failure，Health Check 8 必须警告，Coordinator 仍需检查是否存在 placeholder、叙述残片或截断 findings，不能静默接受。

为什么重要： 这两项实际上把 Agent Runtime 的两个常见二态判断拆开了：quota available / unavailable 变成带时效的实时资源证据；process SUCCESS / ERROR 也不再直接等于 work complete / incomplete。一个完整工作成果可以存在于晚到的基础设施错误之前，但它必须保留异常证据并重新验证。

与 CodeFlowMu/FCoP 的关系： 模型应作为岗位资源动态调度，但调度应留下当时的 quota snapshot、实际模型与 fallback/balance 原因；同时应明确区分 Provider Terminal Status → Work Artifact → Verification Verdict，不能由任一层直接替代最终裁决。

值得互动：非常高。 技术切入：是否考虑把 quota snapshot 的时间/来源、实际模型、backend terminal status、recovery warning 与最终 verifier verdict 统一写进 dispatch receipt？

2. OpenAI Codex：Thread/Turn 正开始绑定执行 Host、Sandbox Policy、插件权力和恢复证据，而不是只保存 Conversation ​

状态：MERGED TO MAIN

Codex 今天连续合入一组相互呼应的运行时修改：

  • #45813 把 Windows Sandbox policy 和每个 Thread 的 executor-host classification带进 TUI。Host 根据 app-server 上报环境区分 local / remote / mixed / unknown，并在 start、resume、fork、replay 中持续保留；Sandbox setup 也要同时服从配置与 managed requirements。
  • #45812 为 Responses 请求加入 workspace routing。HTTP/WebSocket 的 backend origin、account routing、credential revision 都进入连接身份；routing request 禁止 redirect，credential refresh 后重新建立请求上下文，setup/routing 过程中账号变化会直接拒绝。
  • #45807 让 managed daemon recovery snapshot 不再只保存 Thread ID，还保存正在运行且未取消的 Turn ID、output schema、service tier、cyber access program 等 turn-specific options。
  • #45806 明确只有 root thread 可以请求安装 Plugin；Subagent 在解析参数或触发安装交互之前就会被拒绝。
  • #45789 / #45782 在 model switch、compaction、restart 的 checkpoint migration 中保留 Guardian 的用户限制和已验证答案；reviewer/checkpoint 不兼容时继续采用 legacy evidence，而不是把不兼容 checkpoint 当成新授权事实。

为什么重要： 这几项合起来说明，长期 Thread 的连续性正在被拆成 Conversation Identity、Turn Identity、Executor Host、Sandbox Policy、Plugin Authority、Authorization Evidence 和 Recovery Generation。仅仅“Thread 还能 Resume”已经不足以证明当前执行上下文与旧上下文等价。

与 CodeFlowMu/FCoP 的关系： 多 Host/独立房间/模型切换后，恢复最好绑定一份明确的 execution-context digest，而不是从 UI Session 推断权力连续性。PM/DEV/QA/EVAL 的正式边界也应避免让内部 Subagent获得安装、扩权或修改 Host 能力的权力。

值得互动：非常高。 技术切入：这些 per-thread/per-turn facts 是否会最终收敛成统一 execution-context digest，把 Host/Sandbox、Plugin authority、policy evidence 和 recovery generation 一起绑定？

3. OpenAI Agents JS：Guardrail、Tool Set 和 MCP Credential 都开始要求“当前上下文重新成立” ​

状态：MERGED TO MAIN

今天 openai-agents-js 连续合入几项治理相关修复：

  • #1938：如果 output guardrail batch 自身出错，即使没有任何 guardrail 正式返回 tripwire，最终 assistant output 也被视为未验证，不会写入 Session history，也不会在后续 replay 中重新进入模型上下文。原始用户输入可以保留；transaction-aware Session 还能保留已经确定的 Tool pair。
  • #1937：Computer safety-check 的拒绝应当阻止对应动作，但不再因此粗暴终止整个 Run。
  • #1931：Realtime Agent 转到显式 tool-less Agent 时，空 Tool 列表现在具有真实语义，旧 Agent 的 Tool 不再因继承逻辑残留。
  • #1933：MCP credentials 在进入 AI SDK/browser UI 输出边界前做脱敏。
  • #1932：即使 Tool discovery 来自缓存，当前 MCP tool filter 仍必须重新作用，不能因为历史已经发现过就继续暴露。

为什么重要： guardrail 未完成、当前 Agent 无 Tool、当前 filter 已变化 都不应该被旧 Session 状态覆盖。历史存在只能证明过去发生过，不能证明当前仍有展示、调用或继承资格。

与 CodeFlowMu/FCoP 的关系： EVAL/审核结果如果未完成或执行器异常，应保留“不确定/未验证”而不是把模型最终文本写进正式事实链；Role/Agent 切换时，Tool capability 和 credential projection 也应按当前角色重新计算。

值得互动：高。 技术切入：是否会把 effective tool set、credential projection 和 guardrail completion identity 写入 Session generation，从而让 resume/replay 无法继承旧 capability？

4. Paperclip：一边补齐 Sandbox 产物的耐久交付，一边发现 ACPX Session 正把 Run Credential 明文写盘 ​

状态：#13493 MERGED；#13498 OPEN

Paperclip #13493 已合入。此前 legacy sandbox bridge 会拒绝 attachment listing，queue bridge 又只能正确承载 JSON/UTF-8，导致 PNG/PDF 等二进制产物无法可靠发布；native runner 也需要统一的 durable file registration。现在 legacy/native 两条路径都能完成 attachment listing/upload/download、work-product registration 与 response binding；queue envelope 支持受边界限制的 base64 body，同时保留 multipart header、stable retry identity 和 uncertain-write 语义。真实 Daytona 验证覆盖 PNG/PDF、Unicode 文件名、duplicate registration、授权控制，以及 Sandbox 删除后仍能 byte-for-byte 下载。Task UI 也会把新产物显示到 Artifacts。

但同日的安全 PR #13498 暴露出更值得关注的问题：ACPX Session Store 会把完整 session_options.env 写进 <stateDir>/sessions/*.json，其中包含当前 Run 绑定的 API key/token；单机安装中多个 Seat 使用同一 OS Account，因此文件权限并不能隔离不同 Seat。Codex 路径还可能通过 $CODEX_HOME/shell_snapshots/*.sh 再复制一次环境变量。候选修复在 save() 前剥离 launch env，并在 load() 时从当前 Run重新注入；同时关闭受管 Codex Home 的 shell snapshot。Focused 195 tests 已通过，但 PR 仍为 OPEN，不能当成已发布修复。

为什么重要： Session persistence 应保存“如何继续 Conversation”，不应该顺便冻结一份旧 Credential。Workspace/Session 可以长期存在，凭证则必须属于当前 Run/Principal，并在恢复时重新投射。

与 CodeFlowMu/FCoP 的关系： 多角色/多 Host 设计应坚持 Session State ≠ Credential State。数字员工的长期档案、房间和任务可以耐久，但 Secret 只能通过当前授权主体和当前执行代际动态注入；落盘 Session Record 里不应出现可复用 Secret。

学习：非常高｜竞争风险：非常高｜雷达判断：Paperclip 继续保持最高优先级；新增“Session-at-rest secret exposure / durable artifact delivery”专项维度。

值得互动：非常高。 技术切入：Paperclip 是否会把“Session 可持久字段”做成显式 allowlist contract，并让 credential reinjection 绑定 Run principal / authority epoch，而不是继续依赖对象字段清洗？

5. Paperclip：Recovery 的 blocked 终态开始被要求同时拥有可执行的“解除阻塞责任人” ​

状态：OPEN

PR #13494 来自一个真实恢复缺陷：四条 recovery escalation 路径可以把 Issue 设置为 blocked，却既没有 blockedByIssueIds，也没有 unblockDescriptor。结果这个 Issue 看起来是正式 Blocked，但既不出现在任何责任人的可执行队列，也没有任何 wake 路径，实际上变成“永久隐形卡死”。

候选修复要求：如果没有一等 blocker relation，就在同一次状态写入中设置 board-owned unblockDescriptor；不能把 assignee Agent 再设为解除责任人，因为进入该路径的原因往往正是 assignee 已无可调用执行路径。Provider quota wait 或本来已有 blocker relation 的情况则不额外制造 descriptor。项目同时明确：这次只修“生成孤儿 Blocked”的路径，还没有完成全局 blocked && no blocker && no unblock owner invariant detector。

为什么重要： Blocked 不能只是颜色和状态码。一个真正的非终态阻塞必须回答：谁负责解除、什么条件解除、解除后谁被唤醒。 否则轨道机只是把工作从“运行问题”变成“永远没人处理的状态”。

与 CodeFlowMu/FCoP 的关系： 这与 QA 催办、“等待 QA 回执”清理和一键解除卡死直接相关。以后可把 Blocked 合同固定成：Block Cause + Unblock Owner + Unblock Condition + Wake Target，缺任一项就不能把 TASK 物化成可恢复的 Blocked。

学习：非常高｜竞争风险：高｜雷达判断：维持 Paperclip 一线，并提高 Recovery ownership 权重。

值得互动：高。 技术切入：是否会增加 board-level invariant，让任何 blocked Issue 在提交时就必须证明 blocker relation 或 typed unblock owner，而不是等 Recovery 再修？

6. Superset：Cloud Workspace 正从“一个可选地点”升级为 CLI/MCP/SDK 的一级位置语义，但对非 Cloud 账户保持保守回退 ​

状态：MERGED TO MAIN；Cloud 能力仍受账户/Feature Gate 约束

Superset #7564 已合入。对于具备 Cloud Workspace 能力的账户，Workspace list/get/open/update/delete、terminal 操作与 agent create 在未指定位置时开始以 Cloud 为默认；需要本机或其他 Host 时明确写 --local / --host。对没有 Cloud 能力的账户、离线场景或旧 API 无法回答 capability query 的情况，则保守维持原本的本机行为，不会因为版本漂移误启一个计费 Sandbox。

这次变化不仅是 CLI 参数：MCP 把 cloud-specific workspace tools 折叠回统一 workspace tools；SDK 被收敛为 cloud workspace/terminal/agent 控制面；Cloud Workspace 从 Environment 取得 Repository 集合。另一方面，正在运行的 Cloud Workspace 不再每次读取就 Wake：客户端先复用 0600 权限的本地 ticket，再尝试基于已保存地址 mint 不唤醒的 ticket，只有 sandbox 确认 stopped/unreachable 才真正 Wake；一个可能已经抵达 Host 的 mutation 不会因为 wake/reconnect 自动重试。

为什么重要： Superset 正把 Workspace Location 做成一级产品抽象：Cloud / Local / Named Host 是同一套 Workspace API 的不同执行位置。同时它也意识到“默认到 Cloud”可能造成真实付费副作用，所以 capability query 不确定时选择 local，而不是猜测。

与 CodeFlowMu/FCoP 的关系： CodeFlowMu 多 Host 后也适合把 Workspace Identity 与 Execution Location 分离；默认路由必须是可证明的 capability/授权决定，而且“查询地址”与“Wake 机器”应是两个不同 Effect。

学习：非常高｜竞争风险：非常高｜雷达判断：Superset 已是主雷达；新增“Workspace Location semantics / no-wake access / billed-default guard”专项维度。

值得互动：非常高。 技术切入：Workspace location/default-route 是否会成为 durable scope，绑定账户 capability revision 与 Host identity，从而避免同一 CLI/MCP 命令在账户/计划变化后静默换执行地点？

7. Orca：移动端 RPC 开始用 Generation Lease 统一管理 Cache、In-flight Request 与旧结果发布资格 ​

状态：OPEN

PR #20914 是 Orca Mobile RPC foundation 的 Step 5。新的 GenerationScopedRequestOwner 把原先散落在 hook 中的 generation ref、cache、in-flight map 与 stale-response 判断集中到一个 owner 对象：read/load 必须携带 authority epoch、workspace identity 和 params 构成的 scope；owner 看到新的 scope 会先 retire 旧状态；只有 owner 自己签发的 module-private lease 才能 commit(value)，generation 已移动时 commit 会被拒绝。

它还特别处理了 A→B→A：即使 scope 最后看起来回到同一值，reset() 仍会推进 generation，因此第一次 A 的迟到响应不能在第二次 A 中重新获得发布资格。显式测试覆盖 reset、blur、cutover、reconnect-mid-request 与 stale in-flight cleanup。项目也明确承认 mobile 目前还没有真实的 negotiated capability epoch，因此没有为了满足新抽象而伪造字段，只保留已有 host/workspace identity latch。

为什么重要： 这是典型的“同样的参数再次出现，不等于还是同一代授权”。旧 Request 的结果可以晚到，但不能因为 key 又一样了就重新取得 UI/业务发布权。

与 CodeFlowMu/FCoP 的关系： 多 Host、Room、Resume、Page/状态面板都可以采用相同原则：Generation 是授权边界，不是缓存优化。一次 Reset/Rebind/Host 切换后，旧请求即使成功返回也只能保留为历史证据，不能覆盖新一代事实。

学习：非常高｜竞争风险：中高｜雷达判断：继续提高 Orca 的 Mobile RPC / authority-generation 权重。

值得互动：非常高。 技术切入：Generation lease 是否最终会扩展成跨 RPC、terminal、notification 和 recovery 的统一 authority epoch，而不是只停留在移动端 request cache？

跨项目共振 ​

今天可以把跨项目方向收敛成一句话：

持久化的是事实链，不是旧权限；恢复的是上下文，不是旧执行权。

几个独立项目正在从不同角度证明同一件事：赵岳把实时 quota snapshot 变成 dispatch 前证据；Codex 把 Host/Sandbox/Plugin/Evidence 放进 Thread/Turn 恢复；Agents JS 要求当前 Guardrail/Tool Filter 重新成立；Paperclip 一边让 Artifact 跨 Sandbox 消亡继续存在，一边把 Credential 从 Session record 中剥离；Superset 把 Workspace Location 做成显式执行语义；Orca 则直接用 Generation Lease 拒绝旧请求在新代际发布结果。

对 CodeFlowMu/FCoP，可以继续收敛为：

Work/Run Identity → Current Generation → Principal/Credential Projection → Workspace/Host Identity → Live Capability/Capacity Evidence → Call-time Authority → Effect/Artifact → Verification/Settlement

其中 Generation 应成为真正的恢复和权限屏障：Session、缓存、Provider conversation、历史 result 都可以跨代际保留证据，但不能自动跨代际获得 Authority。
