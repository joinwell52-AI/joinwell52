2026-11-17 Agent 核心研究与竞品动态 ​

今天最值得深入研究的是三件事：Agent 消息不能冒充人的授权；Stop/超时返回不能冒充副作用已停止；子任务有输出不能冒充父任务已经收到并验收。 Orca、Codex、OpenHands、Paperclip、ADK 等提供了具体修复或开放反例。AAE 的 A2A 扩展讨论则提供请求绑定与“获准但执行失败/被拒且未执行”的协议对照，仍属开放提案。

本轮 44项事实观察 → 6组研究分析。实际执行起点为 2026-11-17 10:48:23 Asia/Shanghai（02:48:23 UTC）；Registry 从最新 main 读取，47位研究者。上次成功记录为 2026-11-16T010724Z；没有伪造11月15日等漏跑日期的日报。当前重点新增窗口接上轮各来源成功基线，历史未完成分页继续保留缺口。事件发生时间以下均用 UTC，发布日期与合入日期分开。

“已合入”只证明上游主干状态；除明确给出 Release 或官方可用公告外，不代表已打包、部署或默认开启。测试数字均为注明的上游证据，本轮没有新增本地实验、安装体验、文章或开发评审派工。CodeFlowMu/FCoP 关联均是研究判断与待验证候选。

研究分析 ​

A1 优先研究：消息来源不能升级为执行授权 ​

依据：O1、O2、O3、O4、O5、O10、O14、O18、O19、O38、O39、O44。

已有证据支持：Orca、OpenHands、Agents SDK 和 GitHub MCP 分别处理了 Agent 来信、系统 goal、人的决定、精确请求接受的来源差异；Codex 又加入证据截面。企业治理不只是工具 allow/deny，还要知道谁说了什么、批准的究竟是哪一个动作。Orca 仓库永久信任则是另一种取舍，不能与动作级授权等同。待验证推断：CodeFlowMu 的岗位委派、任务留言、人工批准若在适配时都变成普通 user 文本，可能丢掉 authority 边界；本轮未确认本地存在此缺陷。实验候选 P0：同一测试上传动作分别由员工来信、系统提醒、人的明确批准触发，再加入过期批准、参数被替换和批准后撤权。验收看被阻止的副作用、拒绝原因和实际批准绑定，不能只看审查模型说“安全”。FCoP 可比较发送者/委派/证据的表达；身份认证、当前权限和调用拦截属于 Runtime/适配层职责。代价是稳定身份、请求摘要与授权版本的管理，并可能增加人工等待。互动议题：跨 Agent 引用一段真实人的旧授权，如何避免在新请求中被重用？

A2 优先研究：停止、超时、接管和结算必须分开验证 ​

依据：O5、O6、O8、O9、O13、O22、O23、O24、O25、O29、O31、O33、O40。

已有证据支持：CrewAI 的按时 TimeoutError 不会杀掉已运行线程；Paperclip 则区分请求停止、交接、证明未启动、结算；Paradev 以 session 代际阻止旧停止事件覆盖新实例。这些事实支持“调用者返回”和“执行已停止”需要分开核实，不证明所有框架都存在同一故障。实验候选 P0：测试员工执行一个带唯一 ID 的可计数本地动作，在准备前、交接后、动作完成但回执未落盘、控制器重启、旧终态晚到五处中断；另做超时后转交备用员工。记录重复副作用数、无归属进程、未结算回执、恢复时延和是否需人工判断。目标阈值需实验前定义，不能预报通过。FCoP 可对比任务/事件/结果与证据引用的契约；lease、owner generation、重试策略和进程终止放在 Runtime。代价是故障注入与不确定状态保留，不能靠把所有失败自动重试来省略。互动议题：已交给外部工具但没有可判定结果时，何种证据足够恢复而不重复执行？

A3 审计要能解释缺失、删改、聚合与历史窗口 ​

依据：O1、O7、O11、O12、O15、O32、O34、O35、O36、O37、O41、O42。

已有证据支持：审计不是“存了日志”就结束。OpenHands 用追加更正保留原记录，Langfuse 聚合仍保留对象集合和稳定 ID，Phoenix 同时暴露漏发与不该导出的遥测风险；Kyvvu 则公开有限历史窗口。待验证推断：若数字员工仪表盘只呈现最终摘要，失败成本、历史策略边界和证据缺口可能被掩盖，但本轮无本地故障证据。实验候选 P1：在离线轨迹中插入一条坏 span、一次脱敏编辑、跨窗口 secret-read、1,000对象批量动作、失败模型用量与并行 worker 文件写入；核验原记录可追溯、更正可解释、对象集合完整、丢失有计数。auditable 0.5 可作分阶段方法分类与对照工具候选，不能把 PRE/LIVE/POST 分数混成一个安全承诺。FCoP 比较证据引用与更正语义；数据采集、存储、导出权限和保留策略归 Runtime/运维。代价是存储、索引、隐私与可查询性的权衡。互动议题：聚合审计如何证明没有漏掉对象，而不把敏感值再次写进审计？

A4 优先研究：协作完成需要结果被交付并消费 ​

依据：O6、O9、O13、O14、O16、O25、O30、O33、O44。

已有证据支持：ADK 的事件流有 child output 不代表父上下文拿到了结果；Paperclip 合并 wake 后要保留子任务完成原因；Codex 明确 accepted 不等于 wake。可比较的对象是消息接受、执行启动、工件产生、交接、父任务消费、独立验收等不同阶段。实验候选 P0：用“采购研究→方案汇总→独立复核”的三岗位流程，主动打乱消息与工件次序、重复通知、暂停父任务、让子任务先完成再恢复；核验每份结果进入正确版本的父上下文、最终报告没有漏项，审阅员工能独立拒绝不完整交付。FCoP 在此可和 A2A 的 task/artifact/授权结果、AAE 的 request_digest 作语义对照；MCP 的工具调用就绪与技能目录属于互补接入层，不把它们都叫同层竞品。AAE 跨实现数字仍是参与者主张，须独立重算并区分离线判定与线上互通。代价是消息/工件版本及消费状态维护；当前尚未证明需要修改 FCoP 内核。互动议题：父任务取消后晚到的子工件，应入历史、触发重开，还是进入独立验收队列？

A5 持续履职员工需要受控技能供应链与可升级运行环境 ​

依据：O3、O8、O16、O17、O18、O19、O20、O23、O27、O28、O29、O38、O43。

已有证据支持：公共目录开关、组织来源限制、可执行脚本权限、不可变工具盘、OAuth 注册恢复和新旧状态兼容分别解决不同环节。OpenHands 默认公共来源仍开启，Copilot 的 plugin-only 还需市场限制，Orca 仓库信任涵盖未来版本，这些默认值必须写进体验方案。待验证推断：岗位/SOP 即使固定，实际 CLI、hook 或 connector 升级也会改变员工行为；需要版本与生效身份一起记录。体验候选：固定版本的 Paperclip/Orca/Paradev 作升级、重启和权限恢复对照；云盘路径依赖 Vercel，不适合作为零依赖本地交付方案直接移植。FCoP 比较工件与版本声明，安装、依赖、沙箱、凭证轮换及回滚属于 Runtime/产品交付层。代价包括旧版本兼容、缓存盘成本、操作系统权限差异和更新失败降级。互动议题：自动化信任从“已批准字节”迁移到“未来仓库内容”时，组织如何识别并撤回授权？

A6 竞品与开源应用：优先体验恢复和真实交付，不按功能数量排位 ​

依据：O2、O3、O21、O22、O23、O24、O25、O26、O27、O28、O29、O30、O40。

已有证据支持：Paperclip 持续补任务/唤醒/停止结算，Orca 补消息来源与跨端可观测，Orkas 正式发行面向内容、商务文档的工作流，Paradev 补云环境分发与生命周期。它们分别覆盖公司任务协作、通用员工工作台、内容交付和编码环境；不能由几项 PR 推定整个企业治理已成熟。体验顺序：第一，Paperclip（MIT）验证一个父任务带多岗位、停止/恢复和独立验收；第二，Orca（MIT）验证 Agent 来信、真实人工批准、手机接管与仓库信任；第三，Orkas（MIT 源码与打包商业能力分开）验证一份可编辑文档/媒体成果跨重启恢复。Paradev（MIT）作为云分发/升级机制资料与后续体验候选。均需安装、模型/服务凭证与运行成本；本轮没有安装或付费体验。雷达判断：四者都值得继续高优先跟踪，风险分别在恢复治理、授权来源/跨端控制、业务交付广度、云运维效率；不改 Registry、不调整既定雷达圈层。
