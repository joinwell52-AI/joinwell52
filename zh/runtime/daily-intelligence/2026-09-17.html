当日结论 ​

今天最强的共同信号是：“用户想要什么”必须被翻译成真正生效的 Runtime 合同，而且这个合同必须进入连接、缓存、重试、恢复和 Credential 的身份边界。 UI 显示只读、Manual、已审批、已撤销或“重试同一个操作”，如果底层连接/Provider/配置源没有携带同一份约束，最终都可能变成另一种真实效果。

1. Yue Zhao（赵岳）/ anywhere-agents：无变化写入正在反过来销毁恢复证据 ​

状态：MERGED（commit ce6457a）

赵岳本人修复了一个来自真实多 consumer 环境的问题：bootstrap 每次 session start 都执行，一次 27-consumer 循环会在一个下午跑 27 次。即使 settings.json 内容完全没有变化，旧实现仍重新发布并先备份旧文件。2026-09-15 的实测里，27 个 consumers 共留下 198 份备份，而且每份都与 live settings.json 字节完全一致，有限的 backup history 反而被 no-op churn 填满，把真正有恢复价值的历史挤掉。

修复后，merge 在锁内比较即将发布的 canonical bytes 与当前文件；完全相同就既不写也不备份。首次安装、真实变化或不同字节形态仍正常发布并保留恢复副本。相关 Bash/Windows bootstrap 与 release smoke 也同步调整；四轮 /vet 中发现并修复了 BOM、并发覆盖和“无法写 probe 时误判成功”等问题。

为什么重要： Recovery evidence 不是越多越好。重复的“无变化事实”如果和真实变更共用同一个有界历史，会主动降低恢复能力。

与 CodeFlowMu/FCoP 的关系： 配置、规则、Host profile、授权事实的持久化应遵循 semantic/no-op dedupe + real-change retention。轨道机不应因为“每次启动都跑一次”就制造新的业务事实或挤掉真正的历史。

值得互动：高。 技术切入：是否会进一步把 backup retention 从“文件副本数”升级为“distinct content/revision generations”，让恢复历史按真实状态变化而不是启动次数计数？

原始来源：anywhere-agents commit ce6457a

2. OpenAI Codex：MCP 的“只读”开始成为连接身份，而不是模型提示 ​

状态：MERGED（PR #46042）

Codex 已合入 read-only MCP policy。启用后，tools/list 和 tools/call 都会带 openai/readOnly=true，并覆盖调用方试图传入的 false；更关键的是，read-only policy 被纳入 MCP connection identity。只读连接不会复用 unrestricted connection，也不会读取或污染共享 Apps / persistent tool catalog cache，因为一个已经缓存的可写工具目录本身就可能绕过只读 discovery。

测试还覆盖 legacy/modern protocol、session recovery、unrestricted connection isolation 和 shared Apps catalog isolation。

为什么重要： Capability filtering 如果只发生在 Tool 列表展示阶段，而 connection/cache 仍与 unrestricted session 共用，权限边界只是 UI 幻觉。

与 CodeFlowMu/FCoP 的关系： MCP/Host 连接池和 Tool catalog 必须按 Authority Scope 分区。ReadOnly / Write / Approval-required 应成为连接与缓存身份的一部分，而不能只写进 Prompt。

值得互动：非常高。 技术切入：是否会把 normalized MCP effect scope / read-only policy 进一步写入 connection/tool-call receipt，使 resume 或 cache reuse 能证明当时真正生效的 Authority Scope？

原始来源：openai/codex PR #46042

3. Paperclip：人在 Agent 运行中点“批准/回答”，现在先形成耐久事实，再决定何时交付 ​

状态：MERGED（PR #13539）

Paperclip 已把运行中的 confirmation、checkbox confirmation 和 question answer 投射到现有 message queue。用户点击后，系统立即持久化 immutable typed response，保留精确的 approval revision 和选择答案；但这不再隐式 steer 当前 Agent。默认是在 active run 结束后按队列继续，用户也可以明确选择 Steer（兼容 native turn）或 Interrupt（需要 fresh session）。如果 Provider 正阻塞在原始 question request 上，回答仍可直接解除那个请求。

Acknowledgement 会消费 receipt，因此重试不会重复交付；process stop、environment cleanup、ownership 和 recovery gate 仍继续适用。该 PR 最终 CI 全绿并已合入。

为什么重要： Human decision 的“发生时间”和“Agent 消费时间”是两件事。批准事实需要先独立持久化，不能把 UI 点击直接等同于修改一个正在执行的 Turn。

与 CodeFlowMu/FCoP 的关系： ADMIN/EVAL/QA 的审批、回复、纠偏应被建模为 Decision Receipt → Delivery/Continuation Policy。这样长时间运行、排队、重启或切换 Provider 时，审批不会因为 Turn 消失而丢失，也不会被错误送给后来的另一代工作。

学习：非常高｜竞争风险：非常高｜雷达判断：Paperclip 继续最高优先级。

值得互动：非常高。 技术切入：typed interaction receipt 是否会进一步绑定 target run / task revision / effect generation，防止一个延迟批准在后续新计划上重新获得 Authority？

原始来源：Paperclip PR #13539

4. Paperclip：Recovery 终于暴露了“错误码不是失败原因”；Credential revoke 也必须改权威源而不是删投影 ​

状态：OPEN / NOT MERGED（PR #13549、#13529）

PR #13549 记录了一个很强的生产证据：某一日 320 个 terminal runs 因 subscription/session limit 失败，全部被 ACP engine 折叠成 errorCode=acpx_turn_failed；其中 186 个带 retryOfRunId，但 0 个被识别成 quota retry。原因是 Recovery classifier 只扫描少数 error code，Provider 明明已经给出 “session limit / resets at …”，系统却把它当普通 continuation failure，继续在同一个已耗尽窗口里启动新 Run。候选修复只在 acpx_turn_failed 文本确实含 quota 语义时进入 quota wait，并使用 Provider 给出的 reset time；当前仍未合入。

另一个 OPEN PR #13529 处理 credential revoke。company_secret_bindings 只是从 Agent adapterConfig 派生出来的 projection；直接删除 binding row 看起来成功，但下一次 config write 会把它重新生成，而且 Secret 仍可能进入 Runtime。候选实现因此从权威 adapterConfig 删除 secret ref，走 versioned config revision，再让 binding projection 收敛，并写 secret_access_events outcome=revoked。

为什么重要： 两个问题其实是同一类：派生字段/错误码不能替代产生它的语义事实源。 acpx_turn_failed 只是阶段结果，不是失败原因；binding row 只是投影，不是 credential authority。

与 CodeFlowMu/FCoP 的关系： Recovery 应依赖 typed cause，而不是把 transport/error code 当业务裁决；授权撤销必须改变 source of authority，再让 UI/投影/缓存收敛。

学习：非常高｜竞争风险：高｜雷达判断：继续提高 Paperclip Recovery Cause 与 Credential Revocation 权重。

值得互动：高。 技术切入：能否把 provider failure cause 与 config/secret authority generation 都升级成稳定 typed facts，避免 Recovery 和 revoke 继续从 text/derived rows 反推权力？

原始来源：Paperclip PR #13549 · Paperclip PR #13529

5. Superset：Slack 正从“发消息入口”升级成带真人 Credential 的远程 Agent 操作面 ​

状态：#7585 MERGED；#7589 OPEN / NOT MERGED

Superset 已合入 #7585：Slack Agent 可以使用当前 linked user 自己连接的 Linear/GitHub plugins。Credential 在 API server 每次调用时解密，通过 credential proxy 使用，不交给模型；当前只暴露 curated allowlist（11 个 Linear、12 个 GitHub 工具），允许读取、创建 Issue/评论/开 PR 等受限动作，禁止 delete、merge 和 bulk writes，而且 allowlist 同时在 discovery 与 execution 两层 enforcement。Plugin list/call 受 Run deadline/AbortSignal 限制；没有连接时会给 Connect 按钮。PR 明确说明未用真实已连接 Linear/GitHub 账号做 live QA，因此这里报告的是已合入实现，不是“所有远程 Provider 已做生产 E2E”。

后续 #7589 仍 OPEN：Slack 里启动的 Agent 第一轮结束后，计划在原 Thread 回一条完成消息，并保存 slack_agent_launches，通过 QStash 30 秒→5 分钟轮询 Host，最多 24 小时；completed_at 条件更新用于 at-most-once completion post。PermissionRequest 已被识别为 waiting，但这项还没合入。

为什么重要： Slack 已经从 Trigger 入口向 Remote Command + Per-human Plugin Effect + Long-running Completion Callback 演化。

与 CodeFlowMu/FCoP 的关系： IM/手机远控不应只是聊天。真正的数字员工远程端需要绑定 Human Principal → Run → Tool Credential Scope → Effect Receipt → Completion/Approval Notification。

学习：非常高｜竞争风险：非常高｜雷达判断：Superset 已在主雷达，继续提高 IM Remote / Human Credential / Completion Callback 权重。

值得互动：非常高。 技术切入：Slack instruction principal 与 per-user plugin credential projection 是否会绑定到每个真实 Tool effect receipt，尤其同一个 Thread 被不同真人接手时？

原始来源：Superset PR #7585 · Superset PR #7589

6. Orca：一次手机点击如果响应丢失，不能再因此启动第二个 Agent ​

状态：OPEN / NOT MERGED（PR #21106）

Orca 发现 agent.launch 不能安全重试：existing-workspace launch 完全没有幂等；create-worktree 只有 60 秒内存缓存，而且不按 caller 分区、进程重启即消失。手机在 lost reply 后正常 retry，就可能为一次点击创建两个 Agent / Workspace。

候选方案引入可选 operationId，由 Host 对解析后的 intent 计算 fingerprint；admission 发生在读取可变 live precondition 之前。核心是 durable atomic claim：pending → unknown 用条件状态转换抢执行权，只有一个 winner 真正调用 launch。成功结果完整持久化；unknown 是终态，不自动重执行、不 fallback、不重造 ID。跨 Host restart 的 replay 返回记录过的原结果。

还有一个很成熟的兼容性设计：新能力通过 Host 广播 agent.launch.replay.v1。因为旧 Host 会静默丢掉未知 operationId 字段并照常启动，Client 只有确认 Host 宣告该 capability 后，才可以认为 retry 安全。

为什么重要： “我发送了 operationId”不等于“对方真的理解幂等合同”。幂等本身也是需要协商的 capability。

与 CodeFlowMu/FCoP 的关系： Schedule、手机、IM、PWA、Host API 的 mutation 都应使用 Effect Operation Identity + Host Capability Proof。Unknown outcome 必须保留 Unknown，不能把响应丢失解释成失败然后重做。

学习：非常高｜竞争风险：中高｜雷达判断：继续提高 Orca Mobile / Idempotency / Effect Identity 权重。

值得互动：非常高。 技术切入：operationId 是否会进一步统一成为 schedule/mobile/remote launch 的 durable effect identity，并把 caller principal 从当前 bearer-token fallback 中独立出来？

原始来源：Orca PR #21106

7. Orca：UI 显示“Manual”却可能让 Codex 完全不审批——Intent 与 Provider-effective Policy 再次分裂 ​

状态：OPEN / NOT MERGED（PR #20977）

Orca 的 Agent Permissions toggle 原本把权限选择作为 CLI flag 传给 Codex app-server；但 app-server 实际从 typed thread/start / thread/resume 字段读取 policy。结果是：用户 UI 选择 Manual，若 ~/.codex/config.toml 恰好配置 approval_policy="never"，新 Codex chat 仍可能完全 bypass approvals，Settings 画面却继续显示 Manual。

候选修复让 Manual 显式发送 approvalPolicy=on-request 与 sandbox=workspace-write，Yolo 则发送 never / danger-full-access；每次 structured-session acquisition 都从当前 Settings 重新派生，不把 posture 永久锁进旧 Session record。作者已在 Codex 0.153.4 上测得 typed thread params 会成为 effective policy；PR 仍未合入。

为什么重要： UI / Config / Provider 三层里，只有 Provider 真正执行的 policy 才是最后事实。一个“权限设置”如果没有被翻译到 Provider 正确的协议字段，就是假的控制面。

与 CodeFlowMu/FCoP 的关系： Host 准入不只要测试 Tool 能不能用，还要测试 Permission Projection 是否真的被 Host/Provider 接受并生效。页面显示的 active binding / permission 不能自己成为事实源。

学习：非常高｜竞争风险：中高｜雷达判断：继续提高 Orca Host compatibility / permission projection 权重。

值得互动：非常高。 技术切入：能否把 provider 回读的 effective approval/sandbox policy 写入 Run receipt，让 UI 显示的是“已验证生效的 posture”而不是仅仅用户意图？

原始来源：Orca PR #20977

跨项目共振 ​

本日可以归纳为一条非常明确的原则：

Control Intent 只有进入权威执行边界并被验证生效，才成为 Authority。

对 CodeFlowMu/FCoP，可以继续收敛为：

Human/Control Intent → Authority Source & Revision → Connection / Provider Effective Policy → Operation Identity → Effect → Durable Settlement / Replay Eligibility。

其中今天尤其值得固定三条工程规则：

  1. 只读/权限范围必须进入连接与缓存身份，不能只过滤 UI 或 Prompt。
  2. 撤销必须修改权威源，删除派生投影不算 revoke。
  3. 重试安全本身需要 capability negotiation；Client 发了 idempotency key，但旧 Host 不理解时，仍然不能重试。
