当日结论 ​

今天最强的共振是：执行权正在从“Agent/Session 还活着”继续收缩到“用户是否授权了这次扩张、当前 Run 到底是谁、当前凭证属于谁、当前 Sandbox 包身份是什么、失败后到底有没有正证据允许重试”。

这意味着生产级 Agent 需要把 Intent、Run Identity、Principal、Host/Package Identity、Effect Outcome 分开建模；任何一个旧对象都不能替代其余几个对象。

1. Yue Zhao / anywhere-agents：未经用户请求的 fan-out 被明确列为治理违规，prun 同时改成 Agy-only ​

状态：COMMITTED

赵岳在 anywhere-agents 连续提交两项直接相关的治理修订：

  • e26fafb：prun 不再使用 Sonnet/Claude subagent，也不再把 Workflow 当 fallback；所有 unit 只由 Agy 执行。背景是 2026-09-13 的真实使用中，Sonnet units 及其 descendants 成为 Claude 五小时窗口消耗的最大可识别来源之一，且一个 unit 曾自行再生成 10 个 nested agents。
  • 28acaaf：记录另一项真实事故——用户只要求“看一下仓库”，session 却主动发起 4 个 Sonnet prun unit、其中一个又生成 10 个 nested agents，同时还启动了 14-agent Opus Workflow。新规则要求：并行 fan-out 必须先向用户提出，由用户选择 prun 或 Workflow；只有用户已经明确选择当前路线时，才可在约定范围内继续。

值得注意的是，这条“不得擅自 fan-out”目前刻意保持为语义规则，而不是机械 Hook：是否已经得到用户授权依赖对话上下文，错误的确定性 Hook 反而可能阻断用户已经授权的并行工作。

为什么重要： Subagent 数量不只是性能参数，它同时改变成本、权限面、外部副作用数量和审计复杂度。Agent 自行决定“多开几十个 Worker”本质上是在扩大执行授权。

与 CodeFlowMu/FCoP 的关系： 这与 CodeFlowMu 的角色边界高度一致：PM 可以组织工作，但正式团队扩张、并行 fan-out、跨 Host 执行应有明确的授权来源；内部辅助 Agent 不能因为模型觉得“并行更快”就自动成为正式协作者。

值得互动：非常高。 技术切入：是否会把“用户已授权 fan-out”的 evidence 与每个 worker 的 parent/run identity 一起写入 dispatch ledger，从而让后续审计区分用户授权并行与 Agent 自主扩权？

2. OpenAI Agents Python：Realtime approval 存在真实 fail-open 路径，候选修复改为 strict fail-closed ​

状态：OPEN · PR #5029

PR #5029 发现 Realtime session 在调用共享 needs_approval evaluator 时传入了 strict=False。因此一个无效设置，例如 needs_approval="always"，会被解释成 False，工具可以绕过原本预期的审批直接执行；而 core runner 对同一输入已经会抛出 UserError。

候选修复让 Realtime 与 core runner 使用相同 strict 行为：无效 approval 配置在任何工具调用之前报错，不再静默降级为“不需要审批”。该 PR 尚未合入。

为什么重要： Approval policy 的 schema/configuration error 不能被当成“允许”。这是最典型的治理 fail-open。

与 CodeFlowMu/FCoP 的关系： approval_required、授权边界、Host 准入和 EVAL 门禁都应遵循同一原则：Invalid / Unknown / Unparseable policy = No Authority，而不是默认继续执行。

值得互动：高。 技术切入：是否考虑把 approval-policy parsing outcome 也写入 tool-call receipt，使审计能证明该调用使用的是哪一个已验证 policy revision？

3. OpenAI Codex：Windows Sandbox 开始绑定正式 Package Identity，而不是依赖复制 helper 或 PATH ​

状态：MERGED · #45542 / #45550

两项 9 月 15 日前后合入的 Windows Sandbox 改造形成一条完整链：

  • PR #45542 增加 service-managed registered_core provisioning：为 managed sandbox accounts 注册 app package，记录 runner aliases，并根据 service package family + installed version 认证调用者。只有 package registration 和 AppData metadata grants 都成功后才发布 runtime readiness；另一个 owner 或 legacy setup 不能覆盖已注册 sandbox account。
  • PR #45550 让 Sandbox 真正通过 service-recorded execution aliases 启动 registered runner，并在发命令前验证 ownership、OS package identity 和 staged runner image；明确不 fallback 到 copied helper 或 PATH lookup。package context 还会传给 sandbox descendants，支持从受保护 package directory 启动执行文件。

为什么重要： 这把“Sandbox 里运行的是哪个二进制”从路径约定升级成可验证的软件包身份。对 Windows 产品尤其重要，因为安装、更新、service、sandbox account 和执行文件如果各自只靠路径猜测，很容易在升级或恢复后漂移。

与 CodeFlowMu/FCoP 的关系： CodeFlowMu 的 Host 准入可以继续向 Host Product Identity → Installed Package Identity → Service Owner → Sandbox Runtime Identity → Executable Alias 收敛，而不是只证明“官方版本号 PASS”。

值得互动：非常高。 技术切入：registered package identity 是否会进一步进入每个 sandbox execution receipt，使恢复后的 Run 能证明自己使用的是哪一代安装包与 service ownership？

4. Superset：Cloud Workspace 已能以“当前真人”的 GitHub 身份 commit、push、开 PR ​

状态：MERGED 到 sandbox-v2 分支；尚不能等同于 production rollout

PR #7555 增加个人 GitHub connection。每个用户可以保存加密的 user-to-server token；刷新在 per-user advisory lock 下完成，因为 refresh token 会旋转，并发刷新可能互相失效。

在 Cloud Workspace 中，如果 creator 已连接个人 GitHub：

  • GitHub firewall policy 使用该真人的 token，而不是组织 App token；
  • commit 的 author/committer 使用该真人的 GitHub no-reply identity；
  • gh/PR 也以该真人身份执行；
  • 创建 workspace 前就检查该真人是否能访问环境中的 repository；
  • 长期无人值守 workspace 每 30 分钟由 host-service 用 workspace host secret 请求重新应用 credential policy，workspace 本身不持有 token。

项目已用真实 Vercel box 验证 commit/push/PR attribution；但 30 分钟刷新定时器、8 小时 token refresh 和 disconnect revocation 尚未做 live verification，而且该 PR 合入的是 sandbox-v2 分支，不应提前写成已正式上线。

为什么重要： Digital Employee Identity 与 Human Principal 被进一步拆开。同一个 Cloud Agent 可以持续存在，但每一次 GitHub effect 必须知道“代表哪个真人做”。

与 CodeFlowMu/FCoP 的关系： 与此前 Paperclip 的 operation-time principal 高度共振。CodeFlowMu 后续若允许多个 ADMIN/成员共同使用同一个数字员工，应明确 Employee → Current Instruction Principal → Credential Scope → Effect Attribution。

学习：非常高｜竞争风险：非常高｜雷达判断：Superset 已进入主雷达，应增加“真人操作归属 / unattended credential refresh”维度。

值得互动：非常高。 技术切入：个人 GitHub principal 是否会绑定到具体 Run/instruction generation，而不是只绑定 workspace creator，从而支持同一长期 workspace 被不同真人先后驱动？

5. Paperclip：Pause 被 Recovery 错读成“预算耗尽”，一次 sweep 可把几十个正常任务永久打成 Blocked ​

状态：OPEN · PR #13443

PR #13443 报告了一个很有代表性的恢复事故：operator 主动把 Company 设为 paused 后，budgets.getInvocationBlock 也返回 invocation block；stranded recovery sweep 却把所有 block 都解释成“over budget”，于是把正常 assigned issue 改为 blocked 并添加 recovery action。

真实观测中，一个 paused company 在一次 sweep 里有 28 个 issue 被错误改为 blocked，整个 pause window 共 36 个；其中 4 个 watchdog issue 创建仅 6 秒就被错误处理。更严重的是，resume company 后这些 blocked issue 不会自动恢复，因为它们没有 dispatch queue、monitor 或真实 blocker，只能人工修复。

候选修复让 invocation block 显式携带 cause=company_paused | budget_exhausted，Recovery 对 paused company 只 skip，不进行 escalation，并补上 mid-sweep pause race 测试。PR 尚未合入。

为什么重要： “停止工作”与“工作失败”是两种完全不同的业务事实。Recovery 如果把暂停、预算、权限、网络和 crash 都压成一个 Blocked，就会自己制造不可恢复状态。

与 CodeFlowMu/FCoP 的关系： 这正好支持把 Pause/Stop 作为独立授权状态，而不是生命周期失败。轨道机/Recovery 不应对 ADMIN 的暂停决定做语义重写。

学习：非常高｜竞争风险：很高｜雷达判断：Paperclip 继续一线；Recovery 原因码与可逆控制值得重点跟踪。

值得互动：高。 技术切入：是否会把 invocation-block cause 升级成稳定的 typed control fact，并禁止 Recovery 将 operator pause 物化成业务终态？

6. Orca：Restart Recovery 终于停止用“没找到”推断“没送达”，并同时开始重建 canonical Run Identity ​

状态：OPEN · #20723；OPEN stacked series · #20717/#20718

PR #20723 修复一个真实 duplicate-dispatch 风险。连接在 provider acknowledgement 前崩溃后，Orca 会从 transcript history 推断消息是否送达；但旧代码使用的 history window 按构造就是空的，因此会把 comparable unsettled submission 判成 rejected/not_delivered。rejected 又允许旋转 client message id，Retry 最终可能把 provider 已经执行过的 prompt 再发一次。

候选修复删除这种二手 not_delivered 推断：只有 positive match 才进入 accepted；没有正证据就继续保持 unknown；rejected 只允许来自 provider 直接拒绝或可以证明 frame 从未到达 child 的一手事实。已经由旧版本写成 recovered rejection 的记录也不再自动获得 rotate/retry 权。

与此同时，#20717 / #20718 在做更深的身份重构：canonical status row 改由 Orca-minted runId 作为主键，而 provider session id 只是 alias set。原因来自真实测量：两个并发 claude --resume <same-id> 可以拥有同一个 provider session id，却同时成为两个活 Run、甚至写向不同 branch。因此 provider session id 不能作为唯一 Agent Identity。child work 也获得 host-minted childWorkId，并保留 unverifiable 状态；当前只把拥有可信完整 scope 的 structured/native-chat session 迁入 canonical ownership，PTY/relay 缺少 execution host/WSL/workspace 等事实时宁愿留在 legacy adapter，也不伪造 scope。

为什么重要： 这里同时回答了两个生产问题：absence ≠ negative evidence，以及 Provider Session ID ≠ Run Identity。

与 CodeFlowMu/FCoP 的关系： CodeFlowMu 可以进一步明确：Agent/Role Identity、Run Identity、Provider Session Alias、Child Work Identity、Delivery Settlement 是不同字段；恢复时不能用任意一个代替其他对象。

学习：非常高｜竞争风险：中高｜雷达判断：继续上调 Orca 的 identity / recovery / multi-host 权重。

值得互动：非常高。 技术切入：canonical runId 是否最终会成为 delivery receipt、child work、workspace/host scope 与 replay eligibility 的共同外键？

7. CrewAI：运行异常会让同一个 Tool 在一次 attempt 内被调用两次，形成真实 duplicate side-effect 窗口 ​

状态：OPEN · Issue #7449 的候选修复之一 PR #7458

PR #7458 发现 ToolUsage._use/_ause 中，本来只应该保护参数 schema filtering 的 try/except 把 tool.invoke()/ainvoke() 也包了进去。如果 Tool 自身运行时抛异常，这个异常会被误当成“参数过滤失败”，随后系统会在同一个 outer attempt 内用未过滤参数再次调用同一个 Tool。

因此一个失败 Tool 不是“一次 attempt 一次调用”，而可能变成两次；另一个同类 PR 还指出，在默认 _max_parsing_attempts=3 情况下，持续失败的 Tool 最多可实际执行 6 次。对有支付、写库、发消息等非幂等副作用的工具，这是典型 duplicate-effect 风险。

候选修复只把 schema extraction/filtering 留在 try/except，实际 invoke 每个 outer attempt 精确执行一次。当前有多个围绕同一 Issue 的候选 PR，尚不能写成主线已修复。

为什么重要： Retry policy 之外还可能隐藏“隐式第二次调用”。只看高层 attempt_count 无法审计真实副作用次数。

与 CodeFlowMu/FCoP 的关系： Tool execution receipt 应记录真实 invocation identity，而不是只记录 Agent attempt；如果 Tool effect 不具备 idempotency key，一次 attempt 内任何隐式重入都应该被认为是严重治理缺陷。

值得互动：高。 技术切入：CrewAI 是否会为每个真实 tool invocation 分配稳定 invocation/effect ID，使 outer retry 与实际 effect 次数可以独立审计？

跨项目共振 ​

今天可以收敛成一个更精确的 Runtime 模型：

“还在同一个工作里”不再是授权证明。用户授权、Run、Provider Session、真人 Principal、Sandbox Package、Pause 原因和 Tool Effect 都必须有各自身份。

对 CodeFlowMu/FCoP，可继续固定为：

User Intent / Fan-out Authorization → Role & Run Identity → Human Principal / Credential Scope → Host & Package Identity → Call-time Admission → Effect Invocation Identity → Evidence-driven Settlement / Replay Eligibility。

尤其有三个值得进入长期工程规则的结论：

  1. 没有正证据时保留 Unknown，不能把 Absence 推成失败。
  2. Pause/Stop 是可逆控制决定，不是业务失败。
  3. 一次 Agent attempt 与一次真实 Tool effect 不是同一计数单位。
